# start-design の評価

## 目的

`/forge:start-design` と、それが従う設計手法（`design_method.md`）が、要件から正しい設計を作れるかを確かめる。

確かめるのは、次の 3 点である。

- **要件だけで上流の設計ができるか**（start-design Phase 2）: 既存の実装・設計パターンを見ずに、要件定義書とプロジェクトのルールだけから上流の設計（Step 0〜4）を作れるか
- **既存との照合と再設計が正しく働くか**（Phase 3）: 上流の設計の観点から既存を読み、修正せずに使えるものを見つけ、直さないと使えないものに引きずられないか。設計が既存の仕様を変える・重なる場合を見つけられるか
- **詳細設計で既存を手段として使えるか**（Phase 4）: 照合で見つけた、修正せずに使える既存の実装を、詳細設計（Step 5）の手段として使えるか
- **整合性の確認が終わるか**（Phase 5）: 追跡表とチェック項目を、正しい設計で満たせるか

## 方式

1. ケース（`cases/<ID>/`）の `case.md` を、評価を行う Agent に渡す
2. Agent は、start-design の Phase 1〜5 と `design_method.md` に従って設計し、設計書を書く
3. 設計書を、ケースの外の `expected.md` の観点と照らす

ケースの Markdown だけがテストである。実行を補助するスクリプトは置かない（道具がテストの対象になるため）。

## start-design 本体を動かさない理由

start-design は、`.doc_structure.yaml` による出力先の解決や、`/forge:query-db-specs` による検索など、実際のプロジェクトを前提にした仕組みの上で動く。ケースの中の架空のプロジェクトに対して、本体をそのまま動かすことはできない。

そのため、Agent には「start-design の手順に従い、検索の代わりにケースの文書を読む」形で実行させる。確かめられるのは手法と流れの正しさであり、検索・出力先の解決・採番・レビュー・commit といった仕組みは対象外である。

## 自己完結

ケースは、リポジトリの変化に左右されない。要件定義書・既存の仕様・既存のコードを、ケースの中に固定して入れ、製品名は `Foo` `Bar` `Hoge` のプレースホルダで書く。

## ケース

1 ケースが 1 ディレクトリ（`cases/<ID>/`）である。

| ファイル               | 内容                                         | 読んでよい時点      |
| ---------------------- | -------------------------------------------- | ------------------- |
| `case.md`              | ケースの説明と、読む文書の一覧               | 最初から            |
| `docs/requirements.md` | 設計の入力にする要件定義書                   | 最初から            |
| `docs/rules.md`        | プロジェクトのルール（無いケースもある）     | 最初から            |
| `existing/specs/`      | 既存の要件定義書・設計書（無いケースもある） | Phase 3（照合）から |
| `existing/code/`       | 既存のコード（無いケースもある）             | Phase 3（照合）から |

期待（答え）は、ケースの外の `expected.md` に、ケース ID との表で置く。Agent はリポジトリを自由に読めるため、答えをケースの中に書くと見つかってしまう。

| ケース | 確かめること                                                     |
| ------ | ---------------------------------------------------------------- |
| D01    | 既存が無い機能を、要件だけで設計できるか                         |
| D02    | 修正せずに使える既存の部品を、設計の後の照合で見つけて使うか     |
| D03    | 直さないと使えない既存の実装に、設計が引きずられないか           |
| D04    | 要件は純粋な追加だが、設計が既存の設計書を変える場合を見つけるか |
| D05    | 既存の要件定義書まで変える必要がある場合に、設計を止めるか       |
| D06    | 常時成り立つ制約の要件を扱い、整合性の確認を終えられるか         |

## 実行の手順

ケースごとに、汎用の Agent を 1 つ起動し、次を指示する。

- `plugins/forge/skills/start-design/SKILL.md` の Phase 1〜5 と、`plugins/forge/docs/design_method.md` に従って設計する。Phase 1 の検索の代わりに、ケースの `docs/` を読む。Phase 3 の検索の代わりに、ケースの `existing/` を読む
- `existing/` は、Phase 3 になるまで読まない
- 人の承認を待つ箇所では、提示する内容を設計書に書いたうえで、承認を得たものとして先へ進む
- `ai_tests/forge/start-design/expected.md` は読まない
- 設計書は、リポジトリの外の一時的な場所（例: `.claude/.temp/`）に書く。リポジトリのファイルは変更しない
- 手法について迷った点・矛盾した点は、ファイルに書かず、最終応答の本文で返す

実行後に、Agent の動作記録で、Phase 3 より前に `existing/` を読んでいないか、`expected.md` を読んでいないかを確かめる。読んでいれば、そのケースの結果は無効である。

## 結果の読み方

- 設計はケースごとに形が変わる。期待は「設計書がこうなっていること」という観点で書いてあり、観点を満たしているかで判定する
- 観点を満たしていても、理由（なぜそうしたか）を読む
- Agent は AI で、結果が毎回同じとは限らない。揺れを見るには、同じケースを繰り返す
- start-design・`design_method.md`・関連する規範（`additive_development_spec.md` など）を変えたときは、評価を再実行する

## CI に入れない理由

結果が揺れ、実行に費用がかかるため。CI のゲート（`tests/` の単体テスト）の対象に含めず、評価は手動で実行する。
