# ADR ライターの評価

## 目的

ADR ライター（`adr-writer` Agent）が、渡された決定を、ADR に採用すべきかどうかを、正しく判断できるかを確かめる。

ADR に値するのは、「優れた方式がありそうなのに採らなかった」決定である。書くべきでないものを書かず、書くべきものを書き、情報が足りなければ補わず「不足」と返すことが、期待する動作である。

## 方式

1. ケース（`cases/<ID>/`）の、決定・文脈・代替案と、読ませる文書を、ADR ライターへ渡す
2. 返った判定（作成・棄却・不足）を、ケースの「期待」と比べる
3. 判定が一致しても、理由が期待と合っているかを読んで確かめる

ケースの Markdown だけがテストである。実行を補助するスクリプトは置かない（道具がテストの対象になるため）。

## 自己完結

ケースは、リポジトリの変化に左右されない。読ませる文書を、ケースの中に固定して入れ、製品名・文書名は、架空の名前にする。リポジトリの文書が変わっても、ケースの意味は変わらない。

## ケース

1 ケースが 1 ディレクトリ（`cases/<ID>/`）である。

| ファイル  | 内容                                                       | ADR ライターへ |
| --------- | ---------------------------------------------------------- | -------------- |
| `case.md` | 決定・文脈・代替案                                         | 渡す           |
| `docs/`   | 読ませる文書（改変前）                                     | 渡す           |
| `after/`  | 決定が文書を変えるときの、改変後の文書。変えないときは無い | 渡す           |

期待（答え）は、ケースの外の `expected.md` に、ケース ID との表で置く。ADR ライターは、リポジトリを自由に読めるため、答えを `case.md` に書くと、決定の文を探したときに見つかってしまう。`expected.md` には、決定の文を含めない。

### 種類

| ケース   | 内容                                                                     |
| -------- | ------------------------------------------------------------------------ |
| R01〜R15 | 過去の実在の決定の型を持つもの。実在の名前は、架空の名前に置き換えてある |
| F01〜F15 | 架空のもの。製品名は `Foo` `Bar` `Hoge` のプレースホルダで書く           |

### 期待の類型

| 期待                                   | 意味                                                                     | ケース             |
| -------------------------------------- | ------------------------------------------------------------------------ | ------------------ |
| 作成                                   | 優れた別案があり、採らなかった理由が前提とともにあり、文書から分からない | R11〜R15、F01〜F04 |
| 不足                                   | 棄却理由が依拠する前提が分からない。補えば作り話になる                   | F05〜F07           |
| 棄却: 決定に至っていない               | 提案・検討中・承認待ち                                                   | R01〜R03、F12、F13 |
| 棄却: 作業の経緯                       | 一度きりの作業・文書整理の記録                                           | R04〜R07、F14、F15 |
| 棄却: 誰が見ても正しい、規範から分かる | 選択肢が無い、読ませる文書にすでに定めがある                             | R08、R09           |
| 棄却: 規範本文の写し                   | 命名・書式・手順そのもの                                                 | R10、F10、F11      |
| 棄却: 一般論                           | 誰でも同じ結論になる                                                     | F08、F09           |

## 実行の手順

ケースごとに、`/forge:write-adr`（類型は `judgement`）へ、`case.md` の決定・文脈・代替案を渡し、`docs/` と `after/` の文書を関連文書として渡す。

- 作成のときは、ADR ファイルが書かれる。「作成された ADR の点検」に従って点検したあと、削除する
- 棄却・不足のときは、理由が返る。期待（`expected.md`）の類型と合っているかを確かめる
- 実行後に、ADR ライターの動作記録で、`ai_tests/` や `expected.md` を読んでいないかを確かめる。読んでいれば、そのケースの結果は無効である

## 結果の読み方

- 判定の一致は、理由の一致を意味しない。理由も読む
- ADR ライターは AI で、判定が毎回同じとは限らない。ぶれを見るには、同じケースを繰り返す
- ADR ライターは、渡した文書のほかに、リポジトリの規範も読む。ケースの内容が、リポジトリの規範や文書にたまたま書かれていると、棄却されうる。「作成」の期待が棄却になったときは、そのことを確かめる
- 規範（`adr_principles_spec.md`）を変えたときは、評価を再実行する。規範の変更で結果が変わるのは、正しい動作である
- R06 と R07 は、期待（棄却）と ADR ライターの結果（作成）が食い違う、判定が難しいケースである。不具合ではなく、既知の食い違いとして扱う。全ケースで期待と一致させることは、ベストエフォートとする

## 作成された ADR の点検

ADR ライターは、判定のほかに、ADR を書く（構築する）。判定が期待と一致しても、書かれた ADR が規範どおりとは限らない。「作成」になったケースは、書かれた ADR を、ケースの入力と規範（`adr_principles_spec.md`、`adr_format.md`）に照らして点検する。

| 点検項目                                             | 方法                                                                                   |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 形式（節の構成、番号、4 つの小節）                   | 機械的に確認できる（`tests/common/test_adr_reference_integrity.py` の検査と同じ）      |
| 入力にない事実を、補っていないか                     | 入力（決定・文脈・代替案・読ませた文書）と ADR を見比べる                              |
| 経緯・日付・実装状況・作業の記録が、混ざっていないか | 同上。入力にあった作業の記録（手順の実行、ディレクトリの削除など）が、除かれていること |
| 規範や仕様の本文を、写していないか                   | 読ませた文書と見比べる                                                                 |
| 失効マーカーや、誤っていた理由を、残していないか     | 文字列の検査と、読解                                                                   |
| 棄却した代替案に、理由と、理由が依拠する前提があるか | 読解                                                                                   |
| 入力の、規範に反する指示を、採っていないか           | 入力に規範に反する記述（失効マーカーを付ける、など）があるケースで、採っていないこと   |

## 構築の質の不具合と対策（経過）

点検で、入力にない事実を補う不具合が見つかった（30 件中の作成ケースで、複数件が該当）。主な発生箇所は「影響」の小節で、決定の仕組みから論理的に類推できることを、入力が述べていない達成済みの効果として言い切る形だった。

対策として、`adr_principles_spec.md`・`adr_format.md`・`adr-writer.md` に、根拠の無い事実・理由・帰結を書かないこと、「影響」は類推でなく入力から導ける範囲に限ることを明記した。1 ケースを 5 回繰り返す検証を 3 段階行い、補いの件数は 2〜3 件 → 3 件 → 1 件（5 回中）と減少したが、完全には無くならなかった。残る形は、入力が述べる 1 つの効果の根拠を、別の効果の裏付けとして使い回すという、より狭い抜け道である。

対策は有効だが、5 回程度の検証では「0 件」を示せない。再発を監視し、同種の抜け道が見つかれば、同じ要領で規範を狭める。

## CI に入れない理由

判定が揺れ、実行に費用がかかるため。CI のゲート（`tests/` の単体テスト）の対象に含めず、評価は手動で実行する。
