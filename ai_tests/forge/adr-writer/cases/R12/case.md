# R12 ルートを 2 択にし、判定軸を「TASK 化できるか」にする

- 決定: ルートは「ワンショット実装（`hoge-build`）」と「要件定義から開始（`piyo-spec`）」の 2 つに限る。段取りモード提案と `piyo-design` エントリは廃止する。判定軸は、やるべきことを「対象・変更内容・完了の確認方法」が埋まる TASK として列挙できるかどうかである。影響範囲が不明なら深掘りを必須とし、その結果 TASK が増えても列挙できるならワンショット実装とする。列挙できない項目（要件が定まらない・妥当な解が複数あり選択基準が要件に依存する・影響範囲が閉じない）が残るなら要件定義から開始する。変更量・修正規模は判定に使わない（この点は旧設計と同じ）。Foo の差分開発規範による feature 要否判定は `hoge-check` から外し、`piyo-spec` 以降の工程に委ねる。
- 文脈: Bar のチケット起点開発フローは、次の形で運用されていた。`hoge-check` は「変更の検証・追跡に必要な開発文書の種別」を判定軸とし、ワンショット実装 / 仕様駆動（`piyo-spec` または `piyo-design`）/ 段取りモード提案の 3 ルートへ振り分ける。運用で次の問題が顕在化した。段取りモードのルートは文書の調査結果に依存し、判定が安定しない。「対話でしか決着しない決め事が残るか」という判定は調査の深さで結論が変わり、同じチケットでも実行ごとに結果が揺れた。`piyo-design` エントリは要件定義書の実在を前提とし、仕様駆動の連続フロー（要件 → 設計 → 計画）の途中から入る判定が機能しなかった。計画は要件定義書・設計書を必要とするため、実務上は要件定義から入る以外の選択肢が成立しなかった。
- 代替案: (1) 3 ルート（段取りモード提案を含む）を維持する: 段取りモードの判定は「対話でしか決着しない決め事が残るか」を調査結果から推定するもので、調査の深さに結論が依存し安定しない。前提: `hoge-check` の調査は有限の時間で打ち切られる。決め事が残るなら、それは要件定義で合意すべき論点として `piyo-spec` に渡せば足りるため棄却。(2) `piyo-design` エントリを残す: 設計から入るには有効な要件定義書の実在が前提だが、実務上その前提が満たされるチケットはほぼ無く、判定の分岐が空振りしていた。前提: Foo の仕様駆動は要件 → 設計 → 計画の連続フローで、途中から入る自動繰り上がりを持たない。前提が変われば再検討してよいため棄却。
