# R03 起床経路の複線化（Bar サーバ経路の追加）

- 決定: 本案は採用されなかった。以下は提案として記録したものであり、一度も有効な決定になっていない。push 型起床を、単一実装から複数経路を選択できる構造に改め、Bar 向けに Bar サーバ経路を追加する。Piyo 経路は削除せず維持する。これは既存設計の撤回ではなく、その上への追加である。起床の入口を経路の選択点とし、既存の契約（best-effort であること、構造化された結果を返すこと、起床の失敗が待機の正しさを壊さないこと）は一切変更しない。新経路はこの契約をそのまま満たす。選択順序は「Bar サーバが利用可能なら優先、次に Piyo、いずれも不可なら従来どおり見送り」とする。Bar サーバを優先する理由は、端末の入力欄を書き換えないため下書き破壊・作業割り込みのリスクが無く、Piyo の入力注入を nudge 用途に限定していた理由がそのまま解消されるためである。Bar サーバ経路は Bar 専用とし、エージェント非依存の汎用性は Piyo 経路が引き続き担う。端末を Bar サーバに接続させるため、Bar 起動をラップする中継ラッパを導入する。WebSocket クライアントは Python 標準ライブラリで自前実装する。Bar サーバの常駐モードには依存しない。設定不備と「無効化」を同じ挙動にしない。ラッパやブリッジが壊れている場合は警告を出し、沈黙して素通りさせない。Hoge メッセージ基盤の要件・設計・実装を変更しない。起床は Hoge メッセージ基盤のスコープ外であり、本決定は応用側で完結する。
- 文脈: Hoge メッセージ基盤の新着検知は pull 型である。Bar 側・Foo 側いずれの停止フックも、相手自身のターンが終わったときにしか発火しない。往復のために常駐させた専用 Bar セッションでは、人間が操作しない限りターンが終了する契機が発生しない。この状態では依頼が配信されないまま滞留し、所見の受領・修正・再依頼の往復は、依頼を送るたびに相手がターンを終えることで初めて成立するため、この滞留は往復そのものを止める。以前の設計書に記録された実測値がこの帰結を示している。待機が約 7 時間に達した事例、往復 2 ラウンド目以降の恒常的な停止、1 レビューで 4 回の手動起床を要した事例であり、いずれもエラーにならず静かに止まるため人間が気づくまで検知されない。その設計書はこの限界に対し push 型起床を導入した。当時 Qux ツールの Bar サーバブリッジ方式を認識したうえで、「実運用環境（Piyo 端末多重化ツール）が既に提供する同等の機能で軽量に実現する」として Piyo を選んでおり、当時の判断としては妥当である。問題は、その経路が 1 つしか無いことにある。Piyo が無い環境では起床が `skipped` となり、push 起床という手段が丸ごと失われる。実測（Bar CLI 0.146.0）で確認した事実は次のとおり。Bar CLI 自身が Bar サーバのサブコマンドを持ち、listen オプション（標準入出力が既定 / ソケット / `ws://IP:PORT` / 無効）で JSON-RPC の口を開ける。プロトコル定義を CLI 自身から生成できる。端末は remote オプションで既存の Bar サーバに接続するが、起動後に接続する経路は無い。常駐モードは公式インストーラ版の単独インストールを要求し、パッケージマネージャ版では起動できない。中継サブコマンドは生バイト中継であり WebSocket アダプタではない。ソケット方式のトランスポートは素の改行区切り JSON-RPC を拒否し、実体は WebSocket-over-UDS であるためクライアント側に RFC 6455 の実装が要る。得るものは、Piyo 非導入環境でも push 起床が成立すること、入力欄を書き換えないため Piyo 経路の安全ゲートが不要になること、プロトコル定義を Bar 自身から生成できることである。失うものは、Bar の起動をラッパ経由にする必要があり利用者の PATH またはシェル関数への介入を伴うこと、Bar サーバが実験的と明記されたインターフェースで追随コストを負うこと、WebSocket クライアントの自前実装を保守対象として抱えること、Bar サーバ経路は Bar 専用であること、ラッパを経由せずに起動された Bar には効かないことである。また、端末が remote オプションで Bar サーバに接続し読み込み済みスレッド一覧に現れること、remote オプションがソケット方式を受けるか `ws://` 限定かは未検証のまま残った（端末の対話起動を人手で行わないと確認できない）。
- 代替案: (1) 起床を Hoge メッセージ基盤の要件として持たせる: Hoge メッセージ基盤の要件が「push 型通知の実装」を v1 のスコープ外として明示し棄却理由も記録している。Hoge メッセージ基盤は「相手がターンを終えたら配信する」ところまでを引き受け、相手にターンを終えさせることは引き受けないため、往復の即時性を必要とする応用側が持つのが正しく棄却。(2) Piyo 経路を Bar サーバ経路で置き換える: Piyo 経路は端末入力欄への注入であり相手のエージェント種別を問わない。Bar 以外が相手のときの唯一の push 手段であるため、Bar 専用の Bar サーバ経路で置き換えると汎用性を失うため棄却。(3) Qux ツールを外部依存として採用する: Hoge メッセージ基盤の「外部ツール非依存」要件が Qux 等の外部ツールを実行時依存として導入することを禁じている。加えて下流ユーザーに Qux 本体と別のランタイムの導入を要求することになり、配布方針とも衝突するため棄却。(4) 汎用ツール呼び出し規格のサーバへ寄せる: 常駐セッションが不要になり起床問題自体は消えるが、レスポンスのトークン上限と、バックグラウンド化できないことによる長時間レビューのタイムアウトという未検証リスクを抱える。また Foo 側のこの規格のサーバはツール群を公開するのみでモデルの推論を呼べず、双方向性が非対称になるため棄却。(5) Bar サーバの常駐モードを利用する: 公式インストーラ版の単独インストールを要求し、パッケージマネージャ等の他のインストール方法を排除し、配布物が利用者のインストール手段を縛ることになるため棄却。(6) 中継サブコマンドに WebSocket を肩代わりさせる: 中継サブコマンドは生バイトを中継するのみでハンドシェイクを行わないことを実測で確認したため棄却。
