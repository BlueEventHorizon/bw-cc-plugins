# R13 索引サーバの error 判別を識別子契約に依拠し、最小要求版を 1.2.1 とする

- 決定: 判別は `error.data.code` の識別子にのみ依拠する。対象は `ENTRY_ABSENT`（索引を作成してよい）と `ENTRY_ARCHIVED`（作成せず復活を案内する）の 2 値で、メッセージ文言・数値 code では分岐しない。Foo-index サーバは 1.2.1 以上を要求し、1.2.0 以下に向けた文言一致のフォールバック経路を持たない。識別子を読み取れない error は、従来どおり障害として扱い、未整備側へ倒して索引作成を試みることはしない。決め手は、識別子だけが Foo-index サーバ側の公開契約であり、それ以外はいつ変わっても Hoge に通知されない値だという点である。契約でない値に依拠した分岐は、壊れたことが検出できない形で壊れる。
- 文脈: Hoge は文書検索の backend として Foo-index サーバを使う。このとき次の 2 つを取り違えてはならない。ENTRY / series が未整備（索引を作成してから検索する）と、ENTRY が退避状態（索引を作成してはならず、復活操作を案内する）である。前者を後者と誤れば案内が出ず、後者を前者と誤れば退避状態の ENTRY へ同期を試みる。したがって両者を判別する手段が要る。Foo-index サーバ 1.2.0 に対する実測では、ENTRY 不在は JSON-RPC error ではなく `tools/call` result の `isError: true` + `content[].text` の日本語文言として返り、構造化された識別子を持たなかった。この時点の設計書は「実測して得た error の識別可能な要素を判別根拠として確定する」としており、実質的にメッセージ文言への依拠を前提にしていた。退避状態は `archive_index` が既存 ENTRY を壊すため未実測のまま残っていた。Foo-index サーバ側へ照会した結果、次が判明した。当該文言は公開契約として規定されていなかった。要件・設計のいずれにも error code の設計は無く、実装は平文の文字列整形だった。サーバ側で識別子が新設され、1.2.1 でリリースされた。JSON-RPC error を返す形に変わり、ENTRY 不在と退避状態は JSON-RPC error として届く。識別子は `error.data.code`（正本）と `message` 先頭の両方に載る。値は公開契約として固定され、数値 code は補助と位置づけられた。サーバ側から「文言には依拠しないこと」が明示された。つまり「文言を実測して判別根拠に固定する」という当初方針は、契約でないものへ依拠する設計だった。文言が変われば Hoge は例外を出さずに静かに誤判定する。得るものは、判別根拠が公開契約になり文言変更で静かに壊れなくなること、退避状態を判別するための破壊的な実測が不要になること、未整備時の索引自動作成という要件を安全に満たせることである。失うものは、Foo-index サーバ 1.2.0 以下では両者を判別できずいずれも障害として扱われ復旧が手動になること、前提条件として要求する外部依存の版が 2 つ（Bar と Foo-index サーバ）になること、識別子の網羅範囲が上記 2 種のみで判別対象を増やすにはサーバ側への依頼が要ることである。
- 代替案: (1) メッセージ文言の一致で分岐する（当初方針）: 文言は公開契約ではないとサーバ側が明言した。変更時に静かに誤判定し、テストも実運用も異常を検出できないため棄却。(2) `message` 先頭の識別子トークンで 1.2.0 以下も支援する: 接頭辞が付くのは 1.2.1 以降であり、1.2.0 以下では結局日本語文言との一致になる。後方互換を名目に、棄却したはずの文言依拠が残るため棄却。(3) 数値 code（-41001 / -41002）で分岐する: サーバ側が「判別の正本は `data.code`、数値は補助」と位置づけている。補助側に依拠すると、正本だけが保たれた変更で壊れるため棄却。(4) 退避状態を実測して文言を確定してから決める: 実測には `archive_index` の実行（破壊的操作）が要るうえ、得られるのは契約でない文言という脆い根拠。識別子契約の確定により、実測しても判断が変わらなくなったため棄却。
