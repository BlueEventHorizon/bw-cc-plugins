# hoge-check 設計（抜粋）

## 役割

チケットを受け取り、進め方を判定する。実装は行わない。

## 判定軸とルート

判定軸は「変更の検証・追跡に必要な開発文書の種別」である。次の 3 ルートへ振り分ける。

| ルート           | 条件                             | 次の工程                         |
| ---------------- | -------------------------------- | -------------------------------- |
| ワンショット実装 | 既存の仕様書で検証・追跡できる   | `hoge-build`                     |
| 仕様駆動         | 新たな要件定義書か設計書が必要   | `piyo-spec` または `piyo-design` |
| 段取りモード提案 | 対話でしか決着しない決め事が残る | 利用者へ段取りモードを提案       |

## 調査

- 仕様書・実装ルール・類似変更・既存コードを調べる。
- 調査手順は、段階別の参照文書（`phase1.md`〜`phase3.md`）に分け、`hoge-check` と `hoge-build` が共に参照する。

## 実装工程への引き継ぎ

- `hoge-build` は利用者から直接起動できず、`hoge-check` 経由でのみ起動される。
- 調査結果は、チケットのコメントに機械可読マーカー付きで書き残す。`hoge-build` はこれを読んで再調査を省く。

## チケットへの書き込み

- 判定結果（ルールと根拠）をコメントとして追記する。本文は変更しない。
