このスキルは、レビュー依頼の組み立てと、受領した所見・評価の吟味・修正・完了判定のみを行う。親が依頼している他の作業（実装等）を引き継いではならない。

> このスキル自身を `Skill ツール`で再起動しない（自己再帰禁止）。`/forge:query-db-rules` / `/forge:query-db-specs` は Skill ツールで起動する別スキルであり、依頼モードから呼んでよい。

## 概要

本体は**レビューの進行と最終決定**を担う。対象の確定・依頼の公開・reviewer と evaluator の起動・所見と評価の吟味・修正・終端の判断を行う。reviewer と evaluator には `review_id` と `round_number` だけを渡す。依頼・所見・評価は script が JSON として書き、本体は script が返したパスの JSON を直接読む。JSON を本体が組み立てない。

reviewer の実行主体（バックエンド）は reviewer そのものであり、本体と reviewer の間に別の層は無い。**バックエンド SKILL** に求めるのは、レビューを始める前の可用性検査だけである。

**所見も評価も判断の材料であり、決定ではない。** 最終決定者は本体である。どちらも誤りうるものとして扱い、`disposition` などの値にそのまま従わない（Step 7 手順 3）。

本スキルは、利用者または他スキルが Skill ツールで起動することで動く。

## コマンド構文

```
/forge:review [--diff | --branch | --files a.md,b.py,... | --dirs d1/,d2/,...] [--interactive | --auto] [--focus "<重点観点>"] [--scope "<到達目標と意図的な未実装>"] [--project-rules a.md,b.md] [--project-specs c.md] [--backend <name>]
```

| 軸             | 値                                                   | 既定値                              | 意味                                                                                                                     |
| -------------- | ---------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 対象軸         | `--diff` / `--branch` / `--files` / `--dirs`         | `--diff`                            | 未 commit 差分 / base ブランチ分岐以降の全変更 / 明示指定ファイル群 / 明示指定ディレクトリ群（配下すべて、カンマ区切り） |
| 介入軸         | `--interactive` / `--auto`                           | `--interactive`                     | 修正できる所見を全件提示して採否を得る / **確信のあるものだけ確認なしに直し、確信の無いものは提示して採否を得る**        |
| 重点観点       | `--focus "<自然文>"`                                 | 指定なし                            | 今回の依頼で特に注意を払う対象。reviewer が読む観点文書に**加えて**適用する                                              |
| 到達目標       | `--scope "<自然文・複数行可>"`                       | 指定なし                            | 今回の変更が到達すべき範囲と、意図的に含めなかった項目。**評価基準**を伝える（重点観点とは別軸）                         |
| 規範の持ち込み | `--project-rules a.md,b.md` / `--project-specs c.md` | 指定なし（Step 3 で自前に検索する） | 呼び出し元 SKILL が既に収集済みのルール・仕様パス。指定時は Step 3 の検索を行わない（同じ検索の二重実行を避ける）        |
| バックエンド軸 | `--backend <name>`                                   | 候補順による解決（Step 1.5）        | レビューの実行主体。可用性検査をどのバックエンド SKILL へ求めるか                                                        |

**位置引数（種別）は廃止した**。旧い種別（`code` / `design` / `requirement` / `plan` / `uxui`）が位置引数として渡されたら、**廃止を明示してエラー終了する**。依頼を送信しない。

- 受け付けて無視しない（指定が効かないのに効いたように見えるため）。種別から対象を推定もしない
- 伝える内容: 「種別（位置引数）は廃止されました。対象は `--diff` / `--branch` / `--files` / `--dirs` で指定してください。種別は reviewer が対象ごとに判定します」
- 廃止した理由: 依頼は対象の種別を持たない。1 つの依頼が指す対象には、ソースコードと各種の文書が混在しうるため、種別は依頼を受け取った reviewer が対象ごとに判定する

**`--dirs`（ディレクトリ指定）**: **reviewer へはディレクトリのまま渡し、配下のファイル一覧へ展開しない**（範囲指定であり、`--diff` / `--branch` と同じ扱い。Step 2 の「範囲指定を展開しない」を参照）。

**`--secrets`（独立起動）**: 上表の軸とは別に、機密情報の混入だけを対象とする独立したレビューを持つ。

```
/forge:review --secrets [--focus "<自然文>"] [--scope "<到達目標と意図的な未実装>"] [--project-rules a.md,b.md] [--project-specs c.md] [--backend <name>]
```

- **種別・対象軸と相互排他**（`--secrets --branch` 等はエラー終了する）。対象は常にリポジトリ全体であり、利用者が範囲を選ばない
- 対象を差分に絞らない理由: 過去のコミットで混入した秘密は今回の差分に現れないが、リポジトリには残っており漏洩の対象である。差分に絞った時点でこのレビューの目的を達成できない
- 介入軸は受け付けるが、**自動修正も段階的提示も行わない**（Step 6 の例外）。混入の修正は削除だけでは完了せず、該当する秘密の失効・再発行を伴うため、人間の判断が要る。採否を 1 件ずつ聞かないのは、採用の行き先が修正であり、その修正を禁じているためである
- `--focus` / `--scope` / `--project-rules` / `--project-specs` / `--backend` は併用できる（種別・対象軸を持たないだけで、その他の共通引数は他と同じに扱う）

引数解釈は AI が自然言語混在を許容して直接行う（リジッドなパーサーは使わない）。対象が不足・曖昧な場合は AskUserQuestion で補完する。

**対象軸の二重指定はエラー終了する**（`--diff` と `--files` を同時指定、`--files` と `--dirs` を同時指定等）。既定動作を推定できないため、依頼を送信せず利用者へ再入力を促して終了する。

**介入軸**: **どこまで人間へ確認するか**を決める。修正できる範囲を決める軸ではない。

| 値                                      | 動作                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------- |
| `--interactive`（既定・未指定時も同じ） | 修正できる所見を**全件**提示して採否を得る（Step 7.5 段階的提示）                       |
| `--auto`                                | **確信のある所見だけ確認なしに直す。確信の無い所見は提示して採否を得る**（Step 7.5 へ） |

**確認なしに直してよいかを決めるのは確信であって、重大度ではない**。🔴 critical でも直し方に確信が無ければ直さず、🟢 minor でも確信があれば直す。重大度は提示順の材料にとどまる。

**確信は 2 つに分かれる。対象が違うためである**。

| 記号   | 意味                                               | `--auto` での扱い  |
| ------ | -------------------------------------------------- | ------------------ |
| ✅     | 指摘は正しく、**その修正を責任を持って実行できる** | 確認なしに修正する |
| ☑️      | **指摘は正しい**と確信。ただし直し方に確信が無い   | 提示して採否を得る |
| (無印) | 指摘そのものの妥当性に確信が無い                   | 提示して採否を得る |

順序があるため 1 つの尺度で足りる。`✅` は `☑️` を含み、**指摘が正しいと確信できていないものを直すことはできない**。確信度（`☑️`）の語彙は `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` が定めるものであり、そこでの確信度は「いま述べている内容が正しいと言えるか」——**修正ではなく指摘についての確信**である。

**確信を持つのは本体である**。evaluator が評価に付ける `confidence` / `fix_confident` は、本体が確信を持つための材料であり、確信そのものではない。本体は Step 7 手順 3 の吟味を経て、自分で `✅` か否かを決める。

**`--auto` でも人間の応答を待つことがある**。確信の無い所見があれば提示するため、`--auto` は必ずしも 1 ターンで完結しない。自動で走り切ることを前提にした呼び出し元（SDD の各工程等）は、この性質を織り込む。**確信が無い箇所で止まることが `--auto` を信頼できるものにする**——そこで誤れば `--auto` は「間違えるもの」になる。

位置が確定していない所見は、介入軸にも確信にも関係なく修正できない（修正対象を特定できないため）。

**重点観点（`--focus`）**: 利用者が口頭で「特に〜を中心にレビューして」と述べた場合も、フラグを明示していないとして無視せず、その意図を重点観点として解釈する。以下の性質を持つ:

- **内蔵の観点文書を置き換えない**。reviewer が対象の種別ごとに読む観点文書によるレビューはそのまま行われ、重点観点はそこに追加される。「これだけを見る」という絞り込みではない
- **P1〜P3 の優先度体系を変えない**（`${CLAUDE_PLUGIN_ROOT}/docs/review_priorities_spec.md` §3.3「固有 perspective の追加禁止」と衝突しない）
- **severity を指定できない**。重点観点由来の所見であっても、severity は evaluator が違反している規範文書の重大度カタログから決める
- **利用者の指示をそのまま渡す**。要約・加工しない（Step 4 で受け渡しファイルに書く）

**到達目標（`--scope`）**: 今回の変更が**到達すべき範囲**と、**意図的に含めなかった項目**を伝える。段階分割された実装をレビューすると、後続タスクで実装予定の項目が欠陥として報告され、依頼側が毎回スコープを説明する往復が発生するため。以下の性質を持つ:

- **`--focus` とは別軸である**。`--focus` は「通常のレビューに加えて注意を払う対象」、`--scope` は「どの完成度を基準に評価するか」。混ぜてはならない
- **複数行を渡せる**。意図的な未実装が複数ある場合は箇条書きにする。値の内容を理由に拒まない
- **範囲外の指摘を封じるものではない**。宣言された未実装が設計書・仕様書の記述と矛盾を生んでいる場合は、reviewer も evaluator も所見・評価として扱う。スコープを伝えることと、スコープ外の指摘を封じることは別である
- **未指定は「最終形とみなす」を意味する**。範囲外項目が無い場合も、上流（`/forge:start-implement` 等）は「なし」と明示して渡す

**非対応軸の警告付き続行**: `--codex` / `--claude`、および将来 DROP されたフラグを検出した場合、「本スキルはエンジン軸を持たない（当該フラグは無視して続行する）」旨を警告したうえで、当該フラグを無視し既定動作で続行する。黙殺しない。エラー終了にしない理由: `/forge:review` を発行する既存の呼び出し元（`/forge:start-implement` の Phase 5・`/forge:start-design`・`/forge:start-plan`・`/anvil:impl-issue` 等）が `--auto` や `--codex` 付きで起動するため、エラー終了にすると旧パイプラインからの差し替えが成立しない。

**`--codex` / `--claude` を `--backend` の値として解釈してはならない**。backend 名として再解釈すると、既存の呼び出し元が意図していない実行主体を推測で選ぶことになる。バックエンドの指定は `--backend` のみで行う。

「到達目標」欄には、実際に `--scope` として渡す本文をそのまま出力する。未指定の場合は「指定なし（最終形として評価される）」と書く。単に「指定なし」とだけ書くと、情報が無いのか最終形なのかが利用者に見えないまま公開されるため。

## 依頼モード

### Step 1: 引数解釈

位置引数（種別）が渡されていないかを最初に確かめる（渡されていたらコマンド構文の規定どおり、廃止を明示してエラー終了する）。そのうえで、対象軸・介入軸・重点観点・到達目標・規範の持ち込み（`--project-rules` / `--project-specs`）・バックエンドを解釈する。対象軸二重指定なら Step を進めずエラー終了する。重点観点は `--focus` の明示指定に限らず口頭指示（「特に〜を中心に」等）からも抽出する。到達目標は `--scope` の明示指定に限らず、呼び出し元 SKILL から渡された範囲情報や口頭指示（「〜は後続タスクなので今回は見なくてよい」等）からも抽出する。**重点観点も到達目標も、利用者の指示を要約せずそのまま保持する**（要約すると担当タスク ID や分離理由が落ち、reviewer と evaluator が乖離を判断する材料を失う）。到達目標は Step 7 の吟味まで保持する（「範囲外だが設計と乖離している」型の評価を正しく扱うため）。介入軸未指定時は `--interactive` を既定値とする。確定した介入軸の値は Step 7 まで保持する。

### Step 1.1: 前回のレビューの残り

段階的提示の状態は consult が会話コンテキストにだけ持ち、永続化しない（Step 7.5）。したがって前回のレビューが残す提示の記録は無く、確認も破棄も要らない。**介入軸によらず同じである**。

**中断したレビューを続きから再開する経路は持たない [MANDATORY]**。依頼・所見・評価はレビューの終端で削除されており（Step 8）、レビューを構成する対象ファイル・観点・到達目標を引き継ぐ手段が無い。会話に前回の提示の一覧が残っていても、それが今回のレビューのものかを照合する手段が無く、続きとして扱うと次が起きる。

- 修正フェーズの allowlist は今回の起動引数から作られるのに、所見は別のレビューのものでありうる。逸脱が本物か食い違いの副作用かを判別できない
- 前回の重点観点・到達目標は失われているため、**別条件のレビューが同じレビューの続きとして扱われる**

続きが必要なら、利用者が同じ対象で新しいレビューを起動する。

### Step 1.5: バックエンドの解決

**依頼を公開する前に、どの実行主体で走るかを確定させる。** 確定した名前は公開前に出力する引数解釈結果表（前掲「引数解釈結果の定型出力」）の「バックエンド」欄に出す（実行主体が可変である以上、所見の出どころが利用者に見えている必要がある）。

#### 1.5.1 解決順と `retains_context` を得る

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/review/scripts/resolve_review_backend.py" \
  [--backend <name>] --project-root "${CLAUDE_PROJECT_DIR}"
```

exit code だけで分岐する:

| exit code | 動作                                                                                                                                                       |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0         | JSON の `mode`（`explicit` / `order`）、`order`（候補名の配列）、`retains_context`（候補名から真偽値への対応）を得て 1.5.2 へ                              |
| 20        | 設定不正、または候補に `retains_context` の宣言が無い名前がある。**既定値へ落ちず**、JSON の `message` を添えて依頼を公開せずエラー終了する（fail closed） |

`mode` は不可だったときの動作を分ける。**候補順の中身を SKILL.md 側で決めない**（既定の候補順はスクリプトが持つ。ここに名前を書くと定義点が 2 つになる）。

#### 1.5.2 候補を順に検査する

`order` の先頭から、候補ごとに次を行う:

1. backend 名 `<name>` を同名の SKILL（`forge:<name>`）へ解決する。名前と SKILL を 1 対 1 に対応させ、対応表を本体に持たせない（新しいバックエンドを足すたびに本体を編集する構造にしない）
2. 解決先が available-skills に**存在しない**場合、その候補は利用不可として扱う（理由: SKILL 不在）
3. 存在する場合、その SKILL を Skill ツールで**可用性検査**の要求として起動する。バックエンドは `available` と、不足している前提の配列（`missing`）を返す
4. `available: true` なら、その候補を採用する。**採用した候補の `retains_context` を、1.5.1 の JSON から得て、そのレビューの間保持する**。値はバックエンドごとに固定で、`resolve_review_backend.py` が持つ。名前や起動のされ方から推測しない。レビューの途中で変わる値ではなく、ラウンドごとに問い直さない

**`retains_context` が `false` のとき**、本書の流れ（毎ラウンド新しい reviewer を起動し、毎ラウンド同じ依頼を読ませる）で進む。現在 `true` を返すバックエンドは無い。**`true` が得られたら、依頼を公開せず、`true` の場合の流れが本書に定められていないことを報告して終了する**（流れを推測で補わない）。

**可用性検査の中身に立ち入らない**。cmux の有無・相手の常駐・設定の健全性といった判定はバックエンド側に閉じている。本体からこれらを直接調べない（バックエンド固有の事情を本体に持ち込まない）。本体が持つのは候補の**名前と順序**だけである。

#### 1.5.3 利用不可のときの動作

| `mode`     | 動作                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| `explicit` | **fail closed**。代替を選ばず、依頼を公開せずエラー終了する              |
| `order`    | 次の候補へ進む。**全滅したら fail closed**。各候補の不足を並べて報告する |

`explicit`（`--backend` または `.forge.yaml` の指定）で代替を選ばない理由: 利用者・プロジェクトがその実行主体を選んだ以上、満たせないなら失敗させる。代替を選ぶと「指定したのに別の主体で走った」が起きる。

**エラー報告には各候補の `missing` をそのまま並べる**。「利用できるバックエンドがありません」だけでは利用者が対処できない。どの候補で何が欠けていたか（`axis` / `detail` / `remedy`）を候補ごとに示す。

**これは自動フォールバックではない**。禁じられているのは「実行中に失敗したら別バックエンドへ暗黙に倒れる」ことである。本 Step の解決は依頼を公開する前に完了し、選ばれた結果は定型出力に出る。**reviewer または evaluator が失敗したときに代替を選ぶことはしない**（Step 7 手順 1）。

### Step 2: 対象の確定

Step 1 で解釈した対象軸から、reviewer へ渡す対象（依頼の `targets`）を確定する。

| 対象軸                           | 依頼へ渡すもの                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------- |
| `--diff`（対象軸未指定時も同じ） | 未 commit 差分であること（一覧は渡さない）                                      |
| `--branch`                       | Step 2.1 で確定した base ブランチ（対象ブランチは持たない。常に現在のブランチ） |
| `--files`                        | 指定ファイル                                                                    |
| `--dirs`                         | 指定ディレクトリ（配下へ展開しない）                                            |
| `--secrets`                      | 対象軸を持たない。Step 2.3                                                      |

`--files` と `--dirs` は、どちらも依頼の `paths` として渡す。

**`--secrets` は対象軸を持たない**。`--secrets` に対象軸が併記されていた場合はエラー終了する（どちらを優先すべきか推定できないため）。Step 2.1・2.2 は実行せず、代わりに Step 2.3 を実行する。

**範囲指定（`--diff` / `--branch` / `--dirs`）をファイル一覧へ展開しない**: 対象の確定は reviewer 自身が差分・ディレクトリから行う。forge が列挙して渡すと、列挙漏れがそのままレビュー範囲の欠落になり、欠落した事実が reviewer にも利用者にも見えない。特に削除されたファイルはワークツリーに存在せず Read できないため列挙から落ち、削除が変更の大半を占める場合はレビュー範囲が変更集合の半分以下になる。`--dirs` も同様に、依頼へはディレクトリのまま載せる。

#### 2.1 `--branch` の base ブランチ確定

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/analyze_branch_point.py" [--project-root <path>]
```

出力 JSON の `candidates` は分岐点が新しい順に並ぶ。**先頭を既定値として提示し、AskUserQuestion で利用者に確認して base を確定する**（既知ブランチ名の優先順位だけで黙って採用しない。feature から派生したブランチを誤って `develop` 起点と判定するため）。

`candidates` が空、または `target_branch` が `null`（detached HEAD）の場合は、依頼を公開せず理由を報告して終了する。

#### 2.2 対象の検証と allowlist の取得

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/resolve_targets.py" --mode <diff|branch|files|dirs> [--files a,b,...] [--dirs d1,d2,...] [--base-branch <base>] [--project-root <path>]
```

`--files` の場合は指定ファイルの実在検証に使う。`--dirs` の場合は指定ディレクトリの実在検証と、配下ファイルの列挙に使う。`status` が `error` なら依頼を公開せず理由を報告して終了する（不在ディレクトリ・配下に対象ファイルが無い場合を含む）。

**`branch` モードでは Step 2.1 で確定した base を `--base-branch` で必ず渡す**。省略するとスクリプトが `.git_information.yaml` / `develop` / `main` / `master` から自前解決するため、利用者が確認して確定した base とは別の起点で allowlist が作られる。依頼の差分範囲と allowlist の起点が食い違うと、レビュー範囲内のファイルへの修正が Step 7 で allowlist 逸脱として上がり、逸脱が本物か食い違いの副作用かを判別できなくなる。指定した base が存在しない場合、スクリプトは自前解決へ落とさず `error` を返す。

いずれの対象軸でも、返る `files` は**修正フェーズの allowlist（target_files）として保持する**。Step 7 の安全検証で使うものであり、**依頼には入れない**（reviewer へ渡すものではないため粒度保存の対象外）。

**`--dirs` で配下ファイルへ展開してよいのは allowlist に限る**: `dirs` モードが返す `files` はディレクトリ配下の展開結果だが、これは allowlist 専用であり依頼へは載せない。依頼には返る `dirs` をそのまま渡す。

#### 2.3 `--secrets` の機械スキャン [MANDATORY]

**スキャンを SKILL 側で実行しない**。`build_review_request.py` が Step 4 で `scan_secrets.py` を import して自分で実行する。SKILL がスキャンを実行して結果をファイル経由で渡す形は廃止した。

理由: 依頼本文へ載る検出値が必ず `mask()` を通ったものであることを、**構造的に**保証するため。外部ファイルを受け取る形では、渡された値がマスクを経たかどうかを形式検証でしか確認できず、形式は生成元の証明にならない（実値がたまたまマスク形式に一致すれば通る。`${CLAUDE_PLUGIN_ROOT}/docs/sensitive_information_spec.md` §5.3）。

したがってこの Step で実行するコマンドは無い。**スキャン結果を会話へ貼り付けたり、内容を要約して依頼本文へ書き写したりもしない**（経由地点を増やすことが露出経路を増やすことになる）。

スキャンが失敗した場合は Step 4 の `build_review_request.py` が非ゼロ終了する。その場合は依頼を送信せず理由を報告して終了する（fail closed）。スキャンできなかったまま「AI が目を通したから大丈夫」とするのは、二段構えの片方を黙って落とすことになる。

検出 0 件でも依頼は送信する。機械検出が拾えない混入の捜索はレビュアーの担当であり、0 件はレビュー不要を意味しない。

`--secrets` では修正フェーズの allowlist（target_files）を持たない。混入箇所は検出結果が指すファイルであり、事前に確定できないため。Step 7 の安全検証は、この事情に合わせて後述のとおり扱う。

### Step 3: 関連ルール・仕様の収集

対象に関連するプロジェクトルール・仕様を以下の別スキル呼び出しで収集し、返却されたパス一覧（プロジェクトルート相対）をまとめる。検索の依頼文には対象（ファイル・ディレクトリ・差分の概要）を書く。**対象の種別で絞らない**。どの種別が対象に含まれるかは reviewer が判定するので、依頼を組み立てる時点では確定しない。全種別分を問い合わせて渡し、reviewer が該当するものを使う。

- Skill ツールで `/forge:query-db-rules` を起動する → 依頼の `references` へ
- Skill ツールで `/forge:query-db-specs` を起動する → 依頼の `references` へ

**`--project-rules` / `--project-specs` が渡された場合は、当該軸のクエリを行わずその値をそのまま使う**。Skill ツールで本スキルを起動する上流の SKILL（`/forge:start-implement` の Phase 3 等）が同じ検索を既に実行しているため、ここでやり直すと同一タスクに対して同じ検索が 2 回走る。片方だけが渡された場合は、渡されなかった軸のみクエリする。

> 渡された一覧が不足していても、forge 内蔵の観点文書は reviewer が静的に名指しされた場所から読むため、レビューが規範なしになるわけではない。内蔵の規範が薄い code / uxui については、reviewer が「対応する規約が見当たらない」事実を所見として報告するため、不足が所見として表に出る。

forge 内蔵の観点文書（criteria / principles / format）はクエリしない。**どの観点文書を読むかは reviewer の定義に静的に書かれている**ため、SKILL 側で組み立てる必要がない。

### Step 4: 依頼の公開

**重点観点と到達目標があれば、受け渡しファイルを Write ツールで書く**。内容は Step 1 で保持した利用者の指示そのままである（改行・引用符・バッククォート・非 ASCII を含んでよい。要約・加工しない）。

- 重点観点: `${CLAUDE_PROJECT_DIR}/.claude/.temp/review_focus.txt`
- 到達目標: `${CLAUDE_PROJECT_DIR}/.claude/.temp/review_scope.txt`

指定が無い項目のファイルは書かない（書かなければ依頼はそのキーを持たず、reviewer は通常のレビューだけを行う／対象を最終形とみなす）。

次に、依頼を script に組み立てさせて公開する。**AI が JSON を組み立てない**。値を渡すだけである。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/publish_request.py" "${CLAUDE_PROJECT_DIR}" --paths {target_path} --base-branch {base_branch} --diff --references {reference_path} --focus-file {focus_file} --scope-file {scope_file}
```

| オプション                      | 渡すもの                                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| `--paths {target_path}`         | `--files` / `--dirs` のとき。Step 2.2 が返した `files` または `dirs`。複数あれば続けて並べる |
| `--base-branch {base_branch}`   | `--branch` のとき。Step 2.1 で確定した base                                                  |
| `--diff`                        | `--diff` のとき。値を取らない                                                                |
| `--references {reference_path}` | Step 3 で得たパス（複数あれば続けて並べる）。無ければ付けない                                |
| `--focus-file {focus_file}`     | 重点観点を書いたファイル。無ければ付けない                                                   |
| `--scope-file {scope_file}`     | 到達目標を書いたファイル。無ければ付けない                                                   |

`--paths` / `--base-branch` / `--diff` は 1 つ以上を渡す（通常は 1 つである）。上のコマンドは、すべてのオプションを並べた形の見本である。実際には対象軸と指定に応じたものだけを付ける。

**パスは絶対パスで渡す**。script は絶対パス以外を受け付けない。利用者の指定と検索結果のパスはプロジェクトルートからの相対パスで得られるので、本体が `${CLAUDE_PROJECT_DIR}/` を前置して絶対パスにしてから渡す。

成功すると標準出力に `{"review_id": …, "round_number": 1}` が返る。**`review_id` は以後のすべての工程で参照するためコンテキストに保持する**。`round_number` は script が返した値をそのまま運び、自分で数えない。受け渡しファイルは script が成功時に削除する。

exit code が 1 のときは標準出力の `errors` を報告して終了する（何も公開されていない。受け渡しファイルは削除されないので、直して再実行できる）。

依頼は**レビューの間変えない**。前ラウンドで何をしたかを依頼に持たせない（reviewer は毎ラウンド新しく起動され、前ラウンドを覚えていない。修正後の対象を読み直せば足りる）。

### Step 5: reviewer を起動する

Agent ツールでカスタム Agent `forge:reviewer` を起動する。**prompt に渡すのは `review_id` と `round_number` だけ**である。依頼の中身・対象・前ラウンドの所見への対応は渡さない。reviewer は 2 値から依頼のパスを得て、そのファイルを直接読む。

```text
review_id: {review_id}
round_number: {round_number}
```

- reviewer は毎ラウンド新しく起動する。前ラウンドの Agent を再開しない
- 最終応答（background で動いたときは完了通知）を受け取るまで、結果に依存する処理へ進まない。`ScheduleWakeup` で待たない。ターンを終えて完了通知を待つ
- reviewer の最終応答は、終えたことと、止まったときの理由だけである。**応答から所見や成否を読み取らない**。成否は script が判定する（Step 7 手順 1）
- reviewer の起動に失敗したときは、Step 8 を終端経路 `failure` で通す（別の実行主体へ暗黙に倒さない）

### Step 6: evaluator を起動する

**`--secrets` の例外 [MANDATORY]**: 混入の所見は自動修正しない。**介入軸が何であっても** evaluator を起動せず `confirmed_fix` を空として扱い（Step 7 と Step 7.5 を実行せず）**Step 8 へ進む**（終端経路 `halted_with_open_findings`。Step 7 を通らないため、ここで経路を確定させる）。`--interactive` でも段階的提示を行わない——採否を聞いても採用の行き先が修正であり、その修正が禁じられているためである。理由は 2 つある:

- **削除だけでは修正が完了しない**。commit 済みの秘密は履歴・fork・CI ログに残るため、該当する秘密の失効・再発行を伴う。失効は AI が実施できず、実施したかを検証もできない
- **修正を急ぐと痕跡が消える**。該当行を機械的に消すと、人間が影響範囲（いつから・どこに露出していたか）を調査する起点を失う

要約報告には所見ごとに「該当箇所」「必要な失効対象」「人間が実施すべきこと」を列挙する。**検出値そのものは報告に書かない**。

`--secrets` 以外では、Agent ツールでカスタム Agent `forge:evaluator` を起動する。**prompt に渡すのは `review_id` と `round_number` だけ**である（Step 5 と同じ形）。依頼も所見も渡さない。evaluator は 2 値から依頼と所見のパスを得て、直接読む。

- evaluator も毎ラウンド新しく起動する。reviewer の完了を待ってから起動する
- reviewer が正常に終えていなくても起動する。そのときは evaluator が評価に入れず、失敗は Step 7 手順 1 が検出する（本体が成否を判断しない）
- 完了の待ち方は Step 5 と同じである
- evaluator の起動に失敗したときは、Step 8 を終端経路 `failure` で通す

### Step 7: 所見と評価の吟味と修正

1. **所見と評価を読み出す**: 次の 2 つを実行する。どちらも、読み出してよい状態か（正常に書き終えられたか）を script が判定し、そうでなければパスを返さずに失敗する。**読んだ内容から成否を判断しない**。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/body_resolve_findings.py" "${CLAUDE_PROJECT_DIR}" {review_id} {round_number}
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/body_resolve_evaluations.py" "${CLAUDE_PROJECT_DIR}" {review_id} {round_number}
   ```

   exit code が 0 なら標準出力の `{"path": …}` が絶対パスである。そのファイルを Read で直接読む。パスを自分で組み立てない。

   **どちらかが失敗したら、レビューをそこで止める**。次のラウンドへは進まず、修正もせず、Step 8 を終端経路 `failure` で通す。失敗した側の `errors`（自然文）をそのまま利用者へ伝える。

   | 失敗した側 | 伝え方                                                                                                                                                         |
   | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | 所見       | reviewer の失敗として伝える。`errors` にエラー値（`target_unreadable` は「対象が読めない」＝指定の誤り）、または書き出されなかった旨が入る。その結果は使わない |
   | 評価       | evaluator の失敗として伝える。そのラウンドの所見は評価を経ていないので、**severity を持たない未評価の所見**として報告に載せ、未評価であることを明示する        |

   所見のJSONと評価のJSONの各項目の意味は次のとおりである（意味は定義が持つ。JSON に説明は添えられていない）。

   所見（`findings` の配列。0 件のこともある）:

   | 項目         | 意味                                                                                                                                  |
   | ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
   | `finding_id` | 所見を指す番号。レビューの中で一意で、ラウンドをまたいで連番。前ラウンドと同じ形の所見にも新しい番号が振られる                        |
   | `location`   | 所見が指す位置の配列（絶対パス）。`ファイルパス:行` か `ファイルパス:開始行-終了行`。特定できないときは `位置未確定` だけを要素とする |
   | `body`       | 所見の本文。reviewer の主張であり、成立が確かめられたものではない。severity は持たない（severity は評価が持つ）                       |

   評価（`evaluations` の配列。0 件のこともある）:

   | 項目            | 意味                                                                                                                                                                                           |
   | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `finding_ids`   | この評価が扱う所見の番号（1 個以上）。**評価と所見は 1 対 1 ではない**。複数の所見を束ねる評価、同じ所見を引く複数の評価がある。そのラウンドの所見に無い番号は、evaluator が新規に指摘したもの |
   | `disposition`   | 所見の当否の判定（下表）                                                                                                                                                                       |
   | `severity`      | `critical` / `major` / `minor`。違反している規範文書の重大度カタログから転記されたもの。提示順の材料                                                                                           |
   | `reason`        | 判定の根拠。evaluator が確定させた問題の定義を先に述べ、続けて根拠を述べる                                                                                                                     |
   | `confidence`    | 指摘そのものが正しいかの確信度。`confirmed` / `inferred` / `unverified`。`valid` のときだけ持つ                                                                                                |
   | `fix_confident` | その修正を責任を持って実行できるか。`confidence` が `confirmed` でなければ真にならない。`valid` のときだけ持つ                                                                                 |
   | `location`      | 新規に指摘した番号を含む評価だけが持つ位置の配列。reviewer の所見だけを引く評価は持たない（位置は所見が持つ）                                                                                  |

   `confidence` / `fix_confident` が無いときは低い側（`unverified` / 偽）として扱う。付け忘れが確信度を高く見せないためである。

   | `disposition`      | 意味                                                     | 対応表への記載                                                                  |
   | ------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
   | `invalid`          | 不要な指摘                                               | 「対応しない（理由: `reason`）」                                                |
   | `misunderstanding` | 対象・前提の理解に誤りがある指摘                         | ドロップするか、修正報告の中で確認・訂正を求める（`reason` を理由欄に転記する） |
   | `out_of_scope`     | 到達目標の範囲外の「実装漏れ」として報告している指摘     | 「対応しない（理由: 到達目標で範囲外と宣言した項目。担当は `<タスクID>`）」     |
   | `flawed_premise`   | 指摘が依拠する規範文書の側に欠陥がある                   | 常に提示する（手順 3）。修正対象は今回のレビュー対象の外にある                  |
   | `valid`            | 妥当な指摘（範囲外でも設計書・仕様書との乖離指摘を含む） | 手順 3 以降で吟味して振り分ける                                                 |

   `confidence` / `fix_confident` の意味は次の通り（**対象が違う**——一方は指摘そのもの、もう一方は対策である。混ぜると「指摘は正しいが直し方が分からない」を表せなくなる）。

   | 判断                          | 問い                                   | 値                                        |
   | ----------------------------- | -------------------------------------- | ----------------------------------------- |
   | 確信度（`confidence`）        | **指摘は正しいか**                     | `confirmed` ☑️ / `inferred` / `unverified` |
   | 修正の可否（`fix_confident`） | **その修正を責任を持って実行できるか** | 真 / 偽                                   |

   確信度の語彙は `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` に従う（「いま述べている内容が正しいと言えるか」であり、修正の話ではない）。

2. **対応を要する件数を得る**: 次を実行する。件数を数えるのは決定論的な処理であり、AI が JSON を読んで数えない。script は行き先を決めない。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/count_actionable.py" "${CLAUDE_PROJECT_DIR}" {review_id} {round_number}
   ```

   標準出力の `{"actionable": n}` は、`disposition` が `valid` または `flawed_premise` の評価の件数である（evaluator の新規指摘を含む）。**終端を判断する材料であって、判断そのものではない**（手順 4）。exit code が 1 のときは手順 1 の失敗と同じに扱う。

3. **吟味して振り分ける [CRITICAL]**: 所見と評価を受け取った時点で、それが**本当に正しいかを自分で理解し、調査し、考える**。対象と規範に照らして内容を吟味し、誤りがあれば、その誤りを理解したうえで、正しい対応を行う。

   - **`disposition`・`confidence`・`fix_confident` などの値にそのまま従って、修正・ドロップ・終端を決めない**。理解も調査もしないまま行った修正は信用できない。評価の `reason` が述べる問題を、評価が指す箇所（評価が引く所見の `location`。新規指摘なら評価自身の `location`）と規範を読んで確かめる
   - 評価が束ねた複数の所見は、共通の原因が本当に成立するかを確かめる。成立しなければ、評価の束ね方に従わず所見ごとに扱う
   - 退けられた評価（`invalid` / `misunderstanding` / `out_of_scope`）も、退け方が妥当かを内容で確かめる。誤って退けられていれば、対応を要するものとして扱い、その判断と理由を報告に残す
   - **`flawed_premise` は、`confidence` / `fix_confident` の値に関わらず自動修正の対象にしない。常に提示する**（`--auto` でも同じ。修正対象が今回のレビュー対象の外にあるため、採否を得る）
   - **提示の単位は評価 1 件**である。束ねた評価は 1 回だけ示し、影響する所見を列挙する（20 件の所見を 1 つの原因で束ねた評価を所見ごとに提示すると、同じ根拠を 20 回見せて 20 回採否を問うことになる）。新規指摘は、評価が持つ `location` と `reason` をそのまま位置と根拠として扱う。reviewer 由来の所見を模したレコードを作らない。どの評価がどの所見に当たるかは `finding_ids` が持っているので、評価を入口にして所見の結果から引く
   - 評価と所見のどちらの内容も、**位置は書いた時点のもの**である。修正を適用する時点で有効である保証はない。対象を読み直して位置を確定してから適用する。行番号は「どこの話か」を伝えるためのものであり、修正箇所を機械的に決める座標ではない

   `valid` と判断した評価のうち、範囲外であることを前提に設計書・仕様書の記述と現状の乖離を指摘しており、今回のスコープ内で対処できないものは、Step 8 の未対応所見（`halted_with_open_findings`）として残し、要約報告に明記する。

   `valid` と判断した評価の修正は、鵜呑みにせず**影響範囲・代替案・よりよい修正方法を検討したうえで**実施内容を決定する（提案をそのまま採用すると、別の観点からの反証で撤回に至ることがある）。**実施する修正は当該評価が指摘した内容に限定し、関連する体裁修正・リファクタリングを合わせて行わない**（評価が指摘していない箇所まで直すと、再レビューで「何が今回の修正か」が判別できなくなり往復が収束しない）。

   **位置が確定している評価かを確かめる**（介入軸によらず行う）。所見の位置の振り分けは決定論的な処理なので、AI が JSON を読んで行わず、次の script に任せる。手順 1 で `body_resolve_findings` が返した `path` を渡す。所見の本文は自由記述なので、JSON を引数へ埋め込まない。

   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/split_by_location.py" --findings-file {findings_path}
   ```

   標準出力の `unlocated` が、位置が確定していない所見（`位置未確定` だけを要素とする所見）である。引く所見がすべて `unlocated` にあり、評価自身も確定した位置の `location` を持たない評価は、修正対象を特定できない（評価が `location` を持つのは evaluator の新規指摘を含むときで、その位置が修正対象になる）。対応表には「対応しない（理由: 位置が確定していないため修正対象を特定できません。人間の確認が必要です）」と記載する。exit code が 1 のときは手順 1 の失敗と同じに扱う。**これは位置の有無を見るだけの確認であり、修正できるか・修正してよいかの判断ではない。** 修正できるか・確認なしに直してよいかは、本体が吟味して決める。

   吟味の結果を、位置が確定している評価について次の 3 群へ分ける。

   | 行き先           | 条件                                                                                                                            |
   | ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
   | `confirmed_fix`  | 吟味の結果 `valid` と判断し、**`--auto` で本体自身が `✅` と確信した**もの（`flawed_premise` は含まない）                       |
   | 提示（Step 7.5） | 吟味の結果 `valid` と判断したが `--interactive`、または `✅` でないもの。`flawed_premise` は常にここ                            |
   | ドロップ         | 吟味の結果 `invalid` / `misunderstanding` / `out_of_scope` と判断したもの。対応表に理由（評価の `reason` を確かめた結果）を記載 |

   **提示へ回る評価が 1 件でもあれば Step 7.5 へ進む**。`--auto` でも同じである。確信の無い修正を確認なしに適用すると、`--auto` が「間違えるもの」になる。

4. **終端を判断する**: 手順 2 の件数を材料に、終端に達したかを判断する。終端は `retains_context` によらず共通である。

   - **対応を要するものが尽きた**: 件数が 0 で、手順 3 で退けられた評価の退け方が妥当と確かめられたときは、**確認を要さず** Step 8 へ進む（終端経路 `approved`）。対応を要するものが無いことが、これ以上のラウンドが要らないことを意味する
   - **対応できるものが無い**: 件数が 0 でなくても、`confirmed_fix` が空で提示へ回る評価も無い場合（＝すべてドロップ・位置未確定のいずれか）は、手順 5・6 を実行せず、利用者へ AskUserQuestion で確認する。対応を要するものが残っているので、**終えるかを決めるのは利用者である**——本体が単独で打ち切らない。終えると決まれば Step 8 へ進む（終端経路 `halted_with_open_findings`）。終えないと決まったときは利用者の指示に従う。対応しなかった所見を残したまま再レビューすると reviewer が同じ所見を指摘し続け往復し続けるため、本体は自ら次のラウンドへ進まない
   - **残りが軽微**: 対応を要するものが残っていても、軽微で対応の必要が無いと本体が判断したときは、利用者へ AskUserQuestion で確認する。**判断するのは本体だが、終えるかを決めるのは利用者である**——本体が単独で打ち切らない。終えると決まれば Step 8 へ進む（終端経路 `halted_with_open_findings`）
   - 上のいずれにも当たらなければ手順 5 へ進む

5. **修正の実施（本スキルを実行している主体が直接修正 + 安全検証）**: 本スキルを実行している主体が直接、`confirmed_fix` の評価の修正を実施する（評価は evaluator が行うが、修正の実施は分離しない）。全件をまとめて修正してから検証するのではなく、評価単位で「適用 → 検証 → 判断 → 次へ」を逐次繰り返す:

   1. **baseline 取得（ループ開始前に1回）**:
      ```bash
      python3 "${CLAUDE_SKILL_DIR}/scripts/capture_syntax_baseline.py" --files-json '<target_files の JSON 配列>'
      ```
   2. `confirmed_fix` の評価を1件ずつ、以下を繰り返す:
      1. その評価の修正のみを実施する（他の `confirmed_fix` の編集は同時に行わない）
      2. この評価のために実際に Edit したファイルパスを自己申告する
      3. 検出専用の安全検証を実行する（**ファイルは一切書き換えない**）:
         ```bash
         python3 "${CLAUDE_SKILL_DIR}/scripts/verify_fix_safety.py" \
           --allowed-files-json '<target_files>' \
           --modified-files-json '<この評価で自己申告したファイル群>' \
           --baseline-json '<baseline>'
         ```
      4. 結果を自分で判断する（スクリプトは自動でロールバックしない）:
         - `allowlist_violations` / `syntax_errors` が事故的な逸脱・意図しない構文破壊と判断した場合 → 自分で元に戻し、この評価を「対応しない（理由: 修正後の安全検証で問題を検出したため取り消し）」として記録する
         - `allowlist_violations`（target_files 外の関連ファイル修正）をレビュー基準に照らして正当な波及修正と判断した場合 → 変更を維持し、その理由を修正報告に明記する（沈黙したスコープ拡大を許さない）
         - `status: "ok"` の場合 → 「対応した」として記録し、次の評価へ進む
   3. **ラウンド終了時の独立検証**: 上記ループの `--modified-files-json` は評価ごとの自己申告に基づく。申告漏れが起きると、そのファイルは allowlist・構文検証のいずれも通過しないまま見過ごされうる。すべての `confirmed_fix` 処理後、自己申告に依存しない形でこのラウンド全体の変更集合を独立に確認する。ファイルパスの抽出は行/矢印単位の手動パースでは行わない（`git status --porcelain` は空白・改行・非 ASCII を含むパスを quote し、rename/copy は `->` を含む1行で表現するため、手動パースでは実パスを取り違える）:
      ```bash
      python3 "${CLAUDE_SKILL_DIR}/scripts/collect_modified_files.py"
      ```
      出力の `files` 配列を、`target_files ∪ (このラウンドで正当な波及修正として維持したファイル)` を allowlist として `verify_fix_safety.py` に渡す。`allowlist_violations` が検出された場合、それはどの評価の自己申告にも含まれていなかった変更である。意図した変更であれば理由を修正報告に明記し、意図しない変更であれば元に戻す。この独立検証は「ラウンド終了時点で allowlist 外の変更が実際に存在するか」の粗い最終確認である。

6. **次のラウンドへ進む**: 手順 5 を終えたら（`confirmed_fix` が空で、Step 7.5 の採用で修正が決まった場合も同じ）、次のラウンドの置き場を作る。

   **次のラウンド番号が 5 以上になる場合、`advance_round.py` を呼ばず、戻らず一旦停止する**（4 ラウンドを超えても所見が解消しないのは、多くの場合、最初の対応自体の方向が誤っている兆候である）:

   1. 今回のタスクの**本質・責務・範囲**を見直す
   2. 見直して対応に問題が無いと判断できた場合、対象の設計書・要件定義書側の誤りを疑う
   3. 誤りを疑った場合、**その場で書き換えず**、修正案を添えて利用者に確認する。続けるか終えるかは利用者の回答に従う（終えるなら Step 8、終端経路 `halted_with_open_findings`）

   次のラウンド番号が 4 以下のときは、次を実行する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/advance_round.py" "${CLAUDE_PROJECT_DIR}" {review_id} {round_number}
   ```

   標準出力の `{"round_number": n}` が次のラウンド番号である。自分で数えない。exit code が 1 のときは手順 1 の失敗と同じに扱う。**依頼は変えない**。Step 5 へ戻り、新しい reviewer を起動する（`review_id` は同一、`round_number` は返された値）。**reviewer または evaluator を起動して完了を待つ状態でターンを終えてはならない**——往復の終端に到達するまで本体のループを抜けない。

> **この禁止の射程**: 禁じているのは「reviewer または evaluator を起動した状態でターンを終え、完了を引き取る主体を失うこと」である。Step 7.5 の段階的提示は**次のラウンドを起動する前**に行うため、未回収の起動が存在せず、この禁止に当たらない。人間の応答を待つためにターンを終えてよい。

### Step 7.5: 段階的提示

手順 3 で提示へ回した評価について、consult へ対話進行を**委譲する**。consult は継承型 SKILL であり、review 本体を実行しているのと同じ会話が consult の振る舞いへ切り替わるだけである。**本体が既に吟味した内容（重大度・位置・評価の根拠・`confidence`・`fix_confident`）と、consult による対話進行の結果（採否・理由）は、構造化データとして受け渡す必要がない**——同一コンテキストにあるためである。consult は提示の状態を記録・表示機構（agenda）へ記録せず、会話コンテキストにだけ持つ（暫定措置）。

対象は介入軸で変わる。

| 介入軸          | 提示する評価                                         |
| --------------- | ---------------------------------------------------- |
| `--interactive` | 修正できる評価すべて                                 |
| `--auto`        | `✅` でない評価と `flawed_premise` だけ（`☑️`・無印） |

`--auto` で提示へ回る評価が 1 件も無ければ、本 Step を実行せず手順 5 へ進む。

**consult へ渡すのは提示へ回るすべての評価に加え、`✅` として自動修正する評価・位置未確定の評価・ドロップした評価も含める**。採否を聞くかどうかと、consult の一覧に載せるかどうかは別の問いである。除外すると、利用者は**何が変更されるかを見ないまま変更が適用される**。

**`✅` の評価はまとめて直す申し出を出すよう consult へ伝える**。`✅` は「指摘が正しく、修正も責任を持って実行できる」ことを意味し、この条件は介入軸と独立に成立する。まとめて確認してよい候補であることを伝え、利用者が承諾したらその件数を `confirmed_fix` へ積み、残りを 1 件ずつ進める（`flawed_premise` は含めない）。

提示の作法・一覧の構造・状態の持ち方は consult 側が持つ。本 SKILL.md はそれを重複して規定しない。

対話進行の結果として、次を得る。

| 得るもの       | 内容                                     |
| -------------- | ---------------------------------------- |
| 評価ごとの採否 | 採用する / 採用しない / 保留する、と理由 |
| 決着状況       | 全件決着したか、中断したか、未判断の件数 |

「採用する」と決まった評価を `confirmed_fix` として積む（7.5.2）。

#### 7.5.1 中断

利用者が「残りは全部あとで」「ここで終える」と示したら、その時点で確定する。**未判断のまま残った件数を明示する。** 未判断を「対応不要」へ畳み込まない。

**中断の行き先は Step 8 であり、終端経路は `halted_with_open_findings` である**。それまでに「採用する」と決まった評価の修正は実施する（採用の帰結であるため）が、そのあと次ラウンドへは進まず Step 8 へ抜ける。**`confirmed_fix` が空でなくても同じであり、その件数は行き先を変えない**——利用者が止めたのに新しいラウンドが走るのは、中断の指示に反する。終端経路を `interrupted` にしないのは、それが**レビューそのものを終える判断**（中止の指示・再開の辞退）を指す値だからで、取り違えると未対応所見の一覧が要約報告から落ちる。**段階的提示の中断は `interrupted` の契機ではない**——`interrupted` が指すのはレビューそのものを終える判断であり、中断は所見を残したままレビューが完了する経路である。

#### 7.5.2 判断の反映

「採用する」と決まった評価が `confirmed_fix` である。手順 3 の吟味は済んでいるが、**実施内容（影響範囲・代替案）は採用が決まってから詰める**。

次ラウンドへ進む場合、以降は Step 7 手順 5・6 と同じである（修正の実施 → 安全検証 → 次のラウンド）。最終報告の対応表には「採用しない」と決まった評価も理由付きで載せる。

**利用者が中断した場合は次ラウンドへ進まない**。採用が決まった評価の修正（手順 5）までは実施するが、そのあとは Step 8 へ抜ける（7.5.1）。`confirmed_fix` の件数は行き先を変えない。

`confirmed_fix` が空の場合（全件が採用しない、または 1 件も判断しないまま中断した場合）、Step 7 手順 4 と同じく **Step 8 へ進む**（終端経路 `halted_with_open_findings`）。

### Step 8: 終端処理 [MANDATORY]

**レビューを終える経路はすべてこの Step を通す**。終端経路は 4 つあり、**この Step へ到達した時点で終端である**。

| 終端経路                    | 契機                                                                                                                           | 到達元                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| `approved`                  | 対応を要するものが尽きた（件数が 0 で、退けた評価の退け方も妥当と確かめた）                                                    | Step 7 手順 4                             |
| `halted_with_open_findings` | 対応できるものが無く、または残りが軽微で、利用者が終えると決めた、段階的提示の中断、往復の一旦停止での終了、または `--secrets` | Step 6 / Step 7 手順 4・6 / 7.5.1 / 7.5.2 |
| `failure`                   | reviewer または evaluator の起動に失敗した、または所見・評価を読み出せなかった（reviewer / evaluator の失敗）                  | Step 5 / Step 6 / Step 7 手順 1           |
| `interrupted`               | 利用者が**レビューそのものを終える**と判断した（中止の指示）                                                                   | 利用者                                    |

`interrupted` は本体由来の値である。段階的提示の中断はこれに当たらず `halted_with_open_findings` である（7.5.1）。

**終端かどうかをここで判定し直さない**。判定は到達元が既に済ませている。ここで件数などから再計算すると判定点が 2 つになり、必ず食い違う——「今回実施する修正の件数」から終端かどうかを計算し直す形では、**利用者が段階的提示を中断したのに次のラウンドが走る**。次ラウンドへ戻る経路は Step 7 手順 6 だけが持ち、この Step を経由しない。

終端経路に応じた要約報告を出力する。

| 終端経路                    | 報告                                                                                                                                                                                                                             |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `approved`                  | 指摘の件数 / 対応した修正の概要 / 不採用とした所見とその理由                                                                                                                                                                     |
| `halted_with_open_findings` | 下記「未対応所見を残した完了」                                                                                                                                                                                                   |
| `failure`                   | レビューが成立しなかったこと・失敗した側（reviewer / evaluator）と script が返した `errors`・利用者が取りうる次の手（指定の誤りなら指定の直し、実行主体の選び直し等）。evaluator の失敗では未評価の所見（severity なし）を載せる |
| `interrupted`               | 中止した時点のラウンド数・実施済みの修正・未対応のまま残る所見                                                                                                                                                                   |

**位置未確定として修正しなかった所見は、どの終端経路でも要約報告に載せる**。位置未確定の所見はここでしか利用者に届かない。`approved` で終わった場合も省略しない。ラウンドごとに、対応しなかった所見（位置未確定・ドロップ・不採用・取り消し）を会話コンテキストに積んでおき、報告に使う。

**報告を出力してから、保持物を削除する**。`review_id` が採られている（Step 4 を終えている）場合は、経路を問わず次を実行する。削除すると依頼・所見・評価の JSON は読めなくなるので、報告に載せる内容は削除前に読み終えて報告に書き出しておく。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/review/delete_review.py" "${CLAUDE_PROJECT_DIR}" {review_id}
```

置き場が無いときも成功する。exit code が 1 のときは、削除できなかった旨と `errors` を利用者へ伝える（保持物が残っている）。

> **なぜ単一の出口を通すのか**: 削除の発行漏れは、その場では何も起きず、`.temp/review/` に依頼・所見・評価が残り続けることで初めて現れる。露見が遅れる失敗であるため、経路ごとに散文で削除を指示する形を採らない。**この Step が単一の出口である**。

#### 未対応所見を残した完了（`halted_with_open_findings`）

Step 6 の `--secrets` 例外・Step 7 手順 4・手順 6・7.5.1・7.5.2 のいずれかから到達する。**対応を要する評価がなお残っている**ため、承認による完了とは異なる完了状態として扱う。要約報告には以下を明記し、承認された場合と混同しない形で人間の判断を仰ぐ:

- **対応を要する評価がなお残っていること**（承認ではない旨を冒頭で明示する）
- **修正しなかった所見全ての一覧と理由**（位置未確定のみでは不十分。以下すべてを含める）:
  - 位置未確定による対象外（全件。severity によらず対象外であり、人間の確認が必要である旨を添える）
  - 手順 3 の吟味でドロップした評価とその具体的根拠
  - **利用者が「採用しない」と決めた評価とその理由**（`--interactive` のみ。consult が会話に持つ一覧から取る。全件不採用なら次ラウンドへ進まないため、ここで落とすと報告のどこにも残らない）
  - 手順 5 の安全検証で問題を検出し取り消した評価とその内容（allowlist 逸脱・構文エラーの別）
- 現在の介入軸と、その軸で対象外になった所見に対して人間が取りうる手（軸を変えて再実行する / 直接内容を確認する）
- **`--interactive` で中断した場合は、未判断の件数を示す**。未判断を「対応不要」へ畳み込まない。提示の状態は永続化されないので、表示物の参照は載せない。続きは、利用者が同じ対象で新しいレビューを起動して追う

## エラーフロー一覧

| 異常系                                                            | 挙動                                                                                      |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 位置引数（種別）が渡された                                        | 廃止を明示して依頼を公開せずエラー終了（受け付けて無視しない）                            |
| 未知の backend 名（解決先 SKILL が存在しない）                    | 明示指定なら依頼を公開せずエラー終了（fail closed）。候補順なら次候補へ進む               |
| `.forge.yaml` の `review` セクションが不正                        | 依頼を公開せずエラー終了（fail closed）。既定の候補順へ落ちない                           |
| 候補に `retains_context` の宣言が無い名前がある                   | 依頼を公開せずエラー終了（fail closed）。値を補わない                                     |
| `retains_context` が `true`                                       | 依頼を公開せず、その場合の流れが定められていないことを報告して終了                        |
| 全候補が利用不可（可用性検査が通らない）                          | 依頼を公開せずエラー終了。**候補ごとの不足（`missing`）を並べて報告する**                 |
| 対象 0 件 / 指定ファイル不在                                      | 依頼を公開せず報告して終了                                                                |
| 指定ディレクトリ不在 / 配下に対象ファイルが無い                   | 依頼を公開せず報告して終了                                                                |
| `--files` と `--dirs` の同時指定                                  | 依頼を公開せずエラー終了（対象軸の二重指定。どちらを依頼へ載せるか推定しない）            |
| `--secrets` に種別・対象軸を併記                                  | 依頼を送信せずエラー終了（どちらを優先すべきか推定できない）                              |
| スキャン失敗（Step 4 が非ゼロ終了）                               | 依頼を送信せず報告して終了（fail closed）。二段構えの片方を落としたまま進めない           |
| 依頼の公開に失敗（`publish_request.py` が exit 1）                | `errors` を報告して終了（何も公開されない）                                               |
| reviewer / evaluator の起動に失敗、または所見・評価を読み出せない | Step 8 を終端経路 `failure` で通し、`errors` を利用者へ報告。別の実行主体へ暗黙に倒さない |

| 次のラウンド番号が 5 以上になる                                   | 戻らず一旦停止し、本質・責務・範囲の見直しと利用者への確認を行う（Step 7 手順 6）         |

## 対象外（v1 スコープ外）

- **所見の修正を専用 Agent へ委譲しない**: 評価は `forge:evaluator` に委譲する（Step 6）が、修正の実施は本スキルを実行している主体が直接行う。allowlist 検証・構文検証（検出のみ、ロールバックの判断は実行主体が行う）は Step 7 に導入済み
- **reviewer と evaluator の内部**（依頼を読む・所見と評価を書く・採番・封緘）: script と各 Agent の定義が持つ。本体は関与しない

> **段階的提示は consult へ委譲する**（Step 7.5）。consult は review と同じ会話が振る舞いを切り替える継承型 SKILL であり、別セッション・別プロセスの起動ではない。

> **状態の持ち方**: 依頼・所見・評価は script が `.temp/review/<review_id>/` に JSON として置き、本体は書かない。`--interactive` の段階的提示だけは人間の応答を挟むため設計上ターンをまたぐ。その分の状態は consult が会話コンテキストに持つ（永続化しない）。
