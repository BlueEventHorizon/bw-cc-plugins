このスキルは、レビュー依頼の組み立てと、受領した所見の評価・修正・完了判定のみを行う。親が依頼している他の作業（実装等）を引き継いではならない。

> このスキル自身を `Skill ツール`で再起動しない（自己再帰禁止）。`/forge:query-db-rules` / `/forge:query-db-specs` は Skill ツールで起動する別スキルであり、依頼モードから呼んでよい。

## 概要

本体は**レビュー実行主体に依存しない**。対象の解決・依頼本文の組み立て・所見の評価と修正・完了判定を担い、レビュアーとの往復（前提検査・送信・待機・応答の判定と所見配列化・セッション復旧・ワイヤプロトコル）は**バックエンド SKILL** へ委譲する。

| モード         | 起動契機                                                             |
| -------------- | -------------------------------------------------------------------- |
| **依頼モード** | 利用者・他スキルによる `/forge:review <種別> ...` の起動             |
| **再開モード** | 往復上限到達の通知を受けた利用者が状況確認・再開を明示指示したターン |

バックエンドが Stop フック等の非同期契機で応答を受け取る場合、その受信はバックエンド SKILL 側で成立し、判定と所見配列を得た時点で本体の「Step 6: 判定による分岐」へ合流する。

## コマンド構文

```
/forge:review <種別> [--diff | --branch | --files a.md,b.py,... | --dirs d1/,d2/,...] [--interactive | --auto] [--focus "<重点観点>"] [--scope "<到達目標と意図的な未実装>"] [--project-rules a.md,b.md] [--project-specs c.md] [--backend <name>]
```

| 軸               | 値                                                   | 既定値                              | 意味                                                                                                                     |
| ---------------- | ---------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 種別（位置引数） | `code` / `design` / `requirement` / `plan` / `uxui`  | （`--files` / `--dirs` 時のみ必須） | 依頼テンプレートの選択に使う（Step 2）。`--diff` / `--branch` では無視する                                               |
| 対象軸           | `--diff` / `--branch` / `--files` / `--dirs`         | `--diff`                            | 未 commit 差分 / base ブランチ分岐以降の全変更 / 明示指定ファイル群 / 明示指定ディレクトリ群（配下すべて、カンマ区切り） |
| 介入軸           | `--interactive` / `--auto`                           | `--interactive`                     | 修正できる所見を全件提示して採否を得る / **確信のあるものだけ確認なしに直し、確信の無いものは提示して採否を得る**        |
| 重点観点         | `--focus "<自然文>"`                                 | 指定なし                            | 今回の依頼で特に注意を払う対象。テンプレートが名指しする観点文書に**加えて**適用する                                     |
| 到達目標         | `--scope "<自然文・複数行可>"`                       | 指定なし                            | 今回の変更が到達すべき範囲と、意図的に含めなかった項目。**評価基準**を伝える（重点観点とは別軸）                         |
| 規範の持ち込み   | `--project-rules a.md,b.md` / `--project-specs c.md` | 指定なし（Step 3 で自前に検索する） | 呼び出し元 SKILL が既に収集済みのルール・仕様パス。指定時は Step 3 の検索を行わない（同じ検索の二重実行を避ける）        |
| バックエンド軸   | `--backend <name>`                                   | 候補順による解決（Step 1.5）        | レビューの実行主体。往復をどのバックエンド SKILL へ委譲するか                                                            |

**`--dirs`（ディレクトリ指定）**: 種別は `--files` と同様に必須である（テンプレートの選択に使うため。ディレクトリ名から種別を推定しない——推定を誤ると、なぜその criteria が適用されたのかが利用者に見えなくなる）。種別が無い・曖昧な場合は AskUserQuestion で補完する。**レビュアーへはディレクトリのまま渡し、配下のファイル一覧へ展開しない**（範囲指定であり、`--diff` / `--branch` と同じ扱い。Step 2 の [MANDATORY] 参照）。

**`--secrets`（独立起動）**: 上表の軸とは別に、機密情報の混入だけを対象とする独立したレビューを持つ。

```
/forge:review --secrets [--focus "<自然文>"] [--scope "<到達目標と意図的な未実装>"] [--project-rules a.md,b.md] [--project-specs c.md] [--backend <name>]
```

- **種別・対象軸と相互排他**（`--secrets --branch` 等はエラー終了する）。対象は常にリポジトリ全体であり、利用者が範囲を選ばない
- 対象を差分に絞らない理由: 過去のコミットで混入した秘密は今回の差分に現れないが、リポジトリには残っており漏洩の対象である。差分に絞った時点でこのレビューの目的を達成できない
- 介入軸は受け付けるが、**自動修正も段階的提示も行わない**（Step 7 手順 1 の例外）。混入の修正は削除だけでは完了せず、該当する秘密の失効・再発行を伴うため、人間の判断が要る。採否を 1 件ずつ聞かないのは、採用の行き先が修正であり、その修正を禁じているためである
- `--focus` / `--scope` / `--project-rules` / `--project-specs` / `--backend` は併用できる（種別・対象軸を持たないだけで、その他の共通引数は他パターンと同じに扱う）

引数解釈は AI が自然言語混在を許容して直接行う（リジッドなパーサーは使わない。`docs/rules/implementation_guidelines.md`）。種別・対象が不足・曖昧な場合は AskUserQuestion で補完する。

**対象軸の二重指定はエラー終了する**（`--diff` と `--files` を同時指定、`--files` と `--dirs` を同時指定等）。既定動作を推定できないため、依頼を送信せず利用者へ再入力を促して終了する。

**介入軸**: **どこまで人間へ確認するか**を決める。修正できる範囲を決める軸ではない。

| 値                                      | 動作                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------- |
| `--interactive`（既定・未指定時も同じ） | 修正できる所見を**全件**提示して採否を得る（Step 7.5 段階的提示）                       |
| `--auto`                                | **確信のある所見だけ確認なしに直す。確信の無い所見は提示して採否を得る**（Step 7.5 へ） |

**確認なしに直してよいかを決めるのは確信であって、重大度ではない [MANDATORY]**。🔴 critical でも直し方に確信が無ければ直さず、🟢 minor でも確信があれば直す。重大度は提示順の材料にとどまる。

**確信は 2 つに分かれる。対象が違うためである** [MANDATORY]。

| 記号   | 意味                                               | `--auto` での扱い  |
| ------ | -------------------------------------------------- | ------------------ |
| ✅     | 指摘は正しく、**その修正を責任を持って実行できる** | 確認なしに修正する |
| ☑️      | **指摘は正しい**と確信。ただし直し方に確信が無い   | 提示して採否を得る |
| (無印) | 指摘そのものの妥当性に確信が無い                   | 提示して採否を得る |

順序があるため 1 つの尺度で足りる。`✅` は `☑️` を含み、**指摘が正しいと確信できていないものを直すことはできない**。確信度（`☑️`）の語彙は `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` が定めるものであり、そこでの確信度は「いま述べている内容が正しいと言えるか」——**修正ではなく指摘についての確信**である。

**`--auto` でも人間の応答を待つことがある [MANDATORY]**。確信の無い所見があれば提示するため、`--auto` は必ずしも 1 ターンで完結しない。自動で走り切ることを前提にした呼び出し元（SDD の各工程等）は、この性質を織り込む。**確信が無い箇所で止まることが `--auto` を信頼できるものにする**——そこで誤れば `--auto` は「間違えるもの」になる。

位置が確定していない所見は、介入軸にも確信にも関係なく修正できない（修正対象を特定できないため）。

**重点観点（`--focus`）**: 利用者が口頭で「特に〜を中心にレビューして」と述べた場合も、フラグを明示していないとして無視せず、その意図を重点観点として解釈する。以下の性質を持つ:

- **内蔵の観点文書を置き換えない**。テンプレートが名指しする criteria・規範文書によるレビューはそのまま行われ、重点観点はそこに追加される。「これだけを見る」という絞り込みではない
- **P1〜P3 の優先度体系を変えない**（`${CLAUDE_PLUGIN_ROOT}/docs/review_priorities_spec.md` §3.3「固有 perspective の追加禁止」と衝突しない）
- **severity を指定できない**。重点観点由来の所見であっても、severity は委譲先 principles の重大度カタログから決まる
- **単一行に要約して渡す**。複数行の自由文はプロトコル注入（見出し行・完了宣言行の偽装）の経路になるため `build_review_request.py` が拒否する

**到達目標（`--scope`）**: 今回の変更が**到達すべき範囲**と、**意図的に含めなかった項目**を伝える。段階分割された実装をレビューすると、後続タスクで実装予定の項目が欠陥として報告され、依頼側が毎回スコープを説明する往復が発生するため。以下の性質を持つ:

- **`--focus` とは別軸である**。`--focus` は「通常のレビューに加えて注意を払う対象」、`--scope` は「どの完成度を基準に評価するか」。混ぜてはならない
- **複数行を渡せる**。意図的な未実装が複数ある場合は箇条書きにする。ただし見出し行（`#`〜`######`）・コードフェンス行・共通契約行（`REVIEW_RESULT:`）で始まる行は `build_review_request.py` が拒否する（本文の構造・返信形式契約の偽装を防ぐため）
- **範囲外の指摘を封じるものではない**。テンプレートは「宣言された未実装が設計書・仕様書の記述と矛盾を生んでいる場合は所見として報告せよ」を併記している。スコープを伝えることと、スコープ外の指摘を封じることは別である
- **未指定は「最終形とみなす」を意味する**。テンプレートがそう定義している。範囲外項目が無い場合も、上流（`/forge:start-implement` 等）は「なし」と明示して渡す

**非対応軸の警告付き続行**: `--codex` / `--claude`、および将来 DROP されたフラグを検出した場合、「本スキルはエンジン軸を持たない（当該フラグは無視して続行する）」旨を警告したうえで、当該フラグを無視し既定動作で続行する。黙殺しない。エラー終了にしない理由: `/forge:review` を発行する既存の呼び出し元（`/forge:start-implement` の Phase 5・`/forge:start-design`・`/forge:start-plan`・`/anvil:impl-issue` 等）が `--auto` や `--codex` 付きで起動するため、エラー終了にすると旧パイプラインからの差し替えが成立しない。

**`--codex` / `--claude` を `--backend` の値として解釈してはならない [MANDATORY]**。backend 名として再解釈すると、既存の呼び出し元が意図していない実行主体を推測で選ぶことになる。バックエンドの指定は `--backend` のみで行う。

### 引数解釈結果の定型出力 [MANDATORY]

依頼モードは送信前に必ず以下の定型表を出力する。「無視したフラグ」欄は無視したフラグが無い場合も省略せず「なし」と明示する（自由記述の注意書きに置き換えない）。

```
### 引数解釈結果

| 項目           | 値                               |
| -------------- | -------------------------------- |
| パターン       | <diff|branch|code|design|secrets|...> |
| 対象軸         | <diff|branch|files|dirs|なし（リポジトリ全体）> |
| 対象           | <ファイル一覧、ディレクトリ一覧、または「範囲指定のため渡さない」> |
| base / target  | <branch パターン時のみ>          |
| 介入軸         | <interactive|auto> |
| 重点観点       | <渡す1行、または「指定なし」>    |
| 到達目標       | <渡す本文、または「指定なし（最終形として評価される）」> |
| 規範の出所     | <「呼び出し元から受領」または「Step 3 で検索」（軸ごと）> |
```

「重点観点」欄には、実際に `--focus` へ渡す 1 行をそのまま出力する。「バックエンド」欄を省略しない [MANDATORY]——実行主体が可変である以上、所見の出どころが利用者に見えている必要がある。

「到達目標」欄には、実際に `--scope` へ渡す本文をそのまま出力する。未指定の場合は「指定なし（最終形として評価される）」と書く。単に「指定なし」とだけ書くと、情報が無いのか最終形なのかが利用者に見えないまま送信されるため。

## 依頼モード

### Step 1: 引数解釈

種別・対象軸・介入軸・重点観点・到達目標・規範の持ち込み（`--project-rules` / `--project-specs`）・バックエンドを解釈する。対象軸二重指定なら Step を進めずエラー終了する。重点観点は `--focus` の明示指定に限らず口頭指示（「特に〜を中心に」等）からも抽出し、単一行へ要約して保持する（Step 7 の所見評価まで保持する）。到達目標は `--scope` の明示指定に限らず、呼び出し元 SKILL から渡された範囲情報や口頭指示（「〜は後続タスクなので今回は見なくてよい」等）からも抽出する。**利用者の指示を要約せずそのまま保持する**（要約すると担当タスク ID や分離理由が落ち、レビュアーが乖離を指摘する判断材料を失う）。到達目標も Step 7 の所見評価まで保持する（「範囲外だが設計と乖離している」型の所見を正しく扱うため）。介入軸未指定時は `--interactive` を既定値とする。確定した介入軸の値は Step 7 まで保持する。

### Step 1.1: 前回の仕分けファイルを片付ける [MANDATORY]

`.claude/.temp/review/triage.md` があるか確認する。**介入軸によらず行う**（`--auto` で起動しても、前回の `--interactive` が中断したまま残っていることがある）。

```bash
ls ".claude/.temp/review/triage.md" 2>/dev/null
```

無ければ何もせず Step 1.5 へ進む。あれば内容を Read して、**未判断の件数と、どの `review_id` のものか**（見出しとアジェンダ表から読む）を示したうえで、`AskUserQuestion` で確認する。

| 選択                       | 動作                                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **削除して新しく始める**   | ファイルを削除し、Step 1.5 へ進む                                                                                                                                                              |
| **続きから進める**（既定） | ファイルを残したまま **Step 1.5 と Step 2 だけを実行し、Step 3〜6 を飛ばして 7.5.3 から続ける**。所見と判断はファイルにあり、対象・バックエンドは今回の起動引数と Step 2 / Step 1.5 で確定する |

**この確認が中断からの再開の入口である。** 段階的提示を中断すると、ファイルは未判断の行を持ったまま残る。次にレビューを起動したとき、ここで「続きから」を選べば再開できる。**探す仕組みは要らない——ファイルは常に 1 つで、置き場も名前も固定だからである。**

**「続きから」は依頼を送らない経路である [MANDATORY]**。再開とは中断した提示の続きであって、新しいレビューではない。依頼を送ると新しい所見の集合が返るが、この経路は 7.5.1（所見をファイルへ入れる工程）を通らないため、返った所見はどこにも記録されず捨てられる。加えて Step 4 は毎回新しい `review_id` を生成するため、7.5.1 以降で既存ファイルの値と食い違い、`update_triage.py` がエラーで止まる。**この経路では `review_id` は既存ファイルのものを使い続ける**——そのファイルはそのレビューの記録だからである。

Step 1.5 と Step 2 だけを実行するのは、いずれも再開後に必要になるためである。Step 1.5 のバックエンドと `retains_context` は修正後に次ラウンドを送る段（Step 7 手順 4・5）で要り、Step 2 の allowlist（target_files）は修正の安全検証（Step 7 手順 3）で要る。規範の収集（Step 3）と依頼の組み立て（Step 4）は、次ラウンドを送ると決まった時点で Step 7 手順 4 が行う。**そのとき `review_id` は既存ファイルの値を `--review-id` で渡す**——識別するのはレビューであってラウンドではない。

**この確認を飛ばしても、所見が混ざることはない**。`update_triage.py` は既存ファイルの `review_id` が今回のものと食い違えばエラーで止まる。**規約だけに頼らず、構造でも止めている**——ファイル名はどのレビューのものかを持たないため、照合が無ければ前セッションの残りに今回の所見が追記され、`review_id` だけが黙って置き換わる。

### Step 1.5: バックエンドの解決 [MANDATORY]

**依頼を 1 通も送る前に、どの実行主体で走るかを確定させる。** 確定した名前は送信前に出力する引数解釈結果表（前掲「引数解釈結果の定型出力」）の「バックエンド」欄に出す（実行主体が可変である以上、所見の出どころが利用者に見えている必要がある）。

#### 1.5.1 解決順を決める

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/review/scripts/resolve_review_backend.py" \
  [--backend <name>] --project-root "$(git rev-parse --show-toplevel)"
```

exit code だけで分岐する:

| exit code | 動作                                                                                                |
| --------- | --------------------------------------------------------------------------------------------------- |
| 0         | JSON の `mode`（`explicit` / `order`）と `order`（候補名の配列）を得て 1.5.2 へ                     |
| 20        | 設定不正。**既定値へ落ちず**、JSON の `message` を添えて依頼を送信せずエラー終了する（fail closed） |

`mode` は不可だったときの動作を分ける。**候補順の中身を SKILL.md 側で決めない**（既定の候補順はスクリプトが持つ。ここに名前を書くと定義点が 2 つになる）。

#### 1.5.2 候補を順に検査する

`order` の先頭から、候補ごとに次を行う:

1. backend 名 `<name>` を同名の SKILL（`forge:<name>`）へ解決する。名前と SKILL を 1 対 1 に対応させ、対応表を本体に持たせない（新しいバックエンドを足すたびに本体を編集する構造にしない）
2. 解決先が available-skills に**存在しない**場合、その候補は利用不可として扱う（理由: SKILL 不在）
3. 存在する場合、その SKILL を**可用性検査**の要求で起動する。バックエンドは `available`、不足している前提の配列（`missing`）、および往復の文脈を保持するかの申告（`retains_context`）を返す
4. `available: true` なら、その候補を採用して Step 2 へ進む。**`retains_context` を Step 7 手順 4 まで保持する [MANDATORY]**——2 ラウンド目以降の依頼本文の構成を決める唯一の材料であり、ここでしか得られない

**可用性検査の中身に立ち入らない [MANDATORY]**。cmux の有無・相手の常駐・設定の健全性といった判定はバックエンド側に閉じている。本体からこれらを直接調べない（FNC-1318「バックエンド固有の事情を本体に持ち込まない」）。本体が持つのは候補の**名前と順序**だけである。

#### 1.5.3 利用不可のときの動作

| `mode`     | 動作                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| `explicit` | **fail closed**。代替を選ばず、依頼を送信せずエラー終了する              |
| `order`    | 次の候補へ進む。**全滅したら fail closed**。各候補の不足を並べて報告する |

`explicit`（`--backend` または `.forge.yaml` の指定）で代替を選ばない理由: 利用者・プロジェクトがその実行主体を選んだ以上、満たせないなら失敗させる。代替を選ぶと「指定したのに別の主体で走った」が起きる。

**エラー報告には各候補の `missing` をそのまま並べる [MANDATORY]**。「利用できるバックエンドがありません」だけでは利用者が対処できない。どの候補で何が欠けていたか（`axis` / `detail` / `remedy`）を候補ごとに示す。

**これは自動フォールバックではない**。禁じられているのは「実行中に失敗したら別バックエンドへ暗黙に倒れる」ことである。本 Step の解決は依頼を 1 通も送る前に完了し、選ばれた結果は定型出力に出る。**ラウンド実行が `failure` になったときに代替を選ぶことはしない**（Step 6）。

### Step 2: パターンの確定

Step 1 で解釈した種別・対象軸から**レビューのパターン**を確定する。パターンは依頼本文のテンプレートと 1 対 1 に対応する。

| 起動                                             | パターン      |
| ------------------------------------------------ | ------------- |
| `--diff`（対象軸未指定時も同じ）                 | `diff`        |
| `--branch`                                       | `branch`      |
| `--files` または `--dirs` かつ種別 `code`        | `code`        |
| `--files` または `--dirs` かつ種別 `requirement` | `requirement` |
| `--files` または `--dirs` かつ種別 `design`      | `design`      |
| `--files` または `--dirs` かつ種別 `plan`        | `plan`        |
| `--files` または `--dirs` かつ種別 `uxui`        | `uxui`        |
| `--secrets`                                      | `secrets`     |

`--files` と `--dirs` は同じテンプレートを使う（対象軸ごとにテンプレートを増やさない）。テンプレートの対象欄は指定粒度をそのまま載せる形になっており、渡す値がファイル一覧かディレクトリ一覧かだけが変わる。

**`secrets` は対象軸を持たない**。`--secrets` に種別・対象軸が併記されていた場合はエラー終了する（どちらを優先すべきか推定できないため）。Step 2.1・2.2 は実行せず、代わりに Step 2.3 を実行する。

**`--branch` は種別指定を無視する**（ブランチ差分にはコード・文書・設定が混在するため種別軸に載らない）。上表に無い組み合わせは AskUserQuestion でどのパターンとして扱うかを確認する。

**範囲指定（`diff` / `branch` / `--dirs`）をファイル一覧へ展開しない [MANDATORY]**: 対象の確定はレビュアー自身が差分・ディレクトリから行う。forge が列挙して渡すと、列挙漏れがそのままレビュー範囲の欠落になり、欠落した事実がレビュアーにも利用者にも見えない。特に削除されたファイルはワークツリーに存在せず Read できないため列挙から落ち、削除が変更の大半を占める場合はレビュー範囲が変更集合の半分以下になる。`--dirs` も同様に、依頼本文へはディレクトリのまま載せる（`--files-json` ではなく `--dirs-json` を使う）。

#### 2.1 `--branch` の base ブランチ確定

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/analyze_branch_point.py" [--project-root <path>]
```

出力 JSON の `candidates` は分岐点が新しい順に並ぶ。**先頭を既定値として提示し、AskUserQuestion で利用者に確認して base を確定する**（既知ブランチ名の優先順位だけで黙って採用しない。feature から派生したブランチを誤って `develop` 起点と判定するため）。`target_branch` をそのまま target として使う。

`candidates` が空、または `target_branch` が `null`（detached HEAD）の場合は、依頼を送信せず理由を報告して終了する。

#### 2.2 対象の検証と allowlist の取得

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/resolve_targets.py" --mode <diff|branch|files|dirs> [--files a,b,...] [--dirs d1,d2,...] [--base-branch <base>] [--project-root <path>]
```

`--files` の場合は指定ファイルの実在検証に使う。`--dirs` の場合は指定ディレクトリの実在検証と、配下ファイルの列挙に使う。`status` が `error` なら依頼を送信せず理由を報告して終了する（不在ディレクトリ・配下に対象ファイルが無い場合を含む）。

**`branch` モードでは Step 2.1 で確定した base を `--base-branch` で必ず渡す [MANDATORY]**。省略するとスクリプトが `.git_information.yaml` / `develop` / `main` / `master` から自前解決するため、利用者が確認して確定した base とは別の起点で allowlist が作られる。依頼本文の差分範囲と allowlist の起点が食い違うと、レビュー範囲内のファイルへの修正が Step 7 で allowlist 逸脱として上がり、逸脱が本物か食い違いの副作用かを判別できなくなる。指定した base が存在しない場合、スクリプトは自前解決へ落とさず `error` を返す。

いずれのパターンでも、返る `files` は**修正フェーズの allowlist（target_files）として保持する**。Step 7 の安全検証で使うものであり、**依頼本文には入れない**（レビュアーへ渡すものではないため粒度保存の対象外）。

**`--dirs` で配下ファイルへ展開してよいのは allowlist に限る [MANDATORY]**: `dirs` モードが返す `files` はディレクトリ配下の展開結果だが、これは allowlist 専用であり依頼本文へは載せない。依頼本文には返る `dirs` をそのまま `--dirs-json` で渡す。allowlist はレビュアーへ渡すものではないため粒度保存の制約を受けない一方、依頼本文は受けるという非対称がここにある。

#### 2.3 `--secrets` の機械スキャン

**スキャンを SKILL 側で実行しない [MANDATORY]**。`build_review_request.py` が Step 4 で `scan_secrets.py` を import して自分で実行する。SKILL がスキャンを実行して結果をファイル経由で渡す形は廃止した。

理由: 依頼本文へ載る検出値が必ず `mask()` を通ったものであることを、**構造的に**保証するため。外部ファイルを受け取る形では、渡された値がマスクを経たかどうかを形式検証でしか確認できず、形式は生成元の証明にならない（実値がたまたまマスク形式に一致すれば通る。`${CLAUDE_PLUGIN_ROOT}/docs/sensitive_information_spec.md` §5.3）。

したがってこの Step で実行するコマンドは無い。**スキャン結果を会話へ貼り付けたり、内容を要約して依頼本文へ書き写したりもしない**（経由地点を増やすことが露出経路を増やすことになる）。

スキャンが失敗した場合は Step 4 の `build_review_request.py` が非ゼロ終了する。その場合は依頼を送信せず理由を報告して終了する（fail closed）。スキャンできなかったまま「AI が目を通したから大丈夫」とするのは、二段構えの片方を黙って落とすことになる。

検出 0 件でも依頼は送信する。機械検出が拾えない混入の捜索はレビュアーの担当であり、0 件はレビュー不要を意味しない。

`--secrets` では修正フェーズの allowlist（target_files）を持たない。混入箇所は検出結果が指すファイルであり、事前に確定できないため。Step 7 の安全検証は、この事情に合わせて後述のとおり扱う。

### Step 3: 関連ルール・仕様の収集

対象・種別に関連するプロジェクトルール・仕様を以下の別スキル呼び出しで収集し、返却されたパス一覧（プロジェクトルート相対）をそれぞれまとめる:

- `/forge:query-db-rules` → `--project-rules-json`
- `/forge:query-db-specs` → `--project-specs-json`

**`--project-rules` / `--project-specs` が渡された場合は、当該軸のクエリを行わずその値をそのまま使う** [MANDATORY]。Skill ツールで本スキルを起動する上流の SKILL（`/forge:start-implement` の Phase 3 等）が同じ検索を既に実行しているため、ここでやり直すと同一タスクに対して同じ検索が 2 回走る。片方だけが渡された場合は、渡されなかった軸のみクエリする。

> 渡された一覧が不足していても、forge 内蔵の観点文書はテンプレートが静的に名指ししているため、レビューが規範なしになるわけではない。内蔵の規範が薄い `code` / `uxui` については、テンプレート自身が「この欄が空、または対応する規約が見当たらない場合はその事実を所見として報告せよ」と指示しており、不足が所見として表に出る。

forge 内蔵の観点文書（criteria / principles / format）はクエリしない。**どの観点文書を渡すかはテンプレートに静的に書かれている**ため、SKILL 側で組み立てる必要がない。

### Step 4: 依頼本文の組み立て

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/build_review_request.py" \
  --pattern <diff|branch|code|requirement|design|plan|uxui|secrets> \
  --project-root "$(git rev-parse --show-toplevel)" \
  [--base-branch <base> --target-branch <target>] \
  [--files-json '["path1","path2",...]'] \
  [--dirs-json '["dir1","dir2",...]'] \
  [--project-rules-json '[...]'] [--project-specs-json '[...]'] \
  [--focus '<重点観点の1行>'] \
  [--scope '<到達目標と意図的な未実装（複数行可）>']
```

`templates/<パターン>_review_request_template.md` を読み、動的データを埋めた結果を JSON envelope `{"review_id": "...", "body": "..."}` として標準出力へ書く。**依頼本文の文言・レビュー観点の名指しはテンプレート側にあり、このスクリプトは散文を持たない。** 依頼内容を変えたいときはテンプレートを編集する（スクリプトには手を入れない）。

`--base-branch` / `--target-branch` は `branch` パターンのみ、`--files-json` / `--dirs-json` はファイル・ディレクトリ指定パターンのみで、**両者は排他**（同時に渡すとエラー終了する）。範囲指定パターンにファイル一覧・ディレクトリ一覧を渡すとエラー終了する。`--focus` は全パターン共通の任意引数であり、未指定なら依頼本文の重点観点欄が「（指定なし）」になる。改行を含む値はエラー終了する。

`--scope` も全パターン共通の任意引数で、未指定なら到達目標欄が「（指定なし）」になる（テンプレートがこれを「最終形とみなす」と定義している）。`--focus` と違い**複数行を渡せる**が、見出し行・コードフェンス行・共通契約行（`REVIEW_RESULT:`）で始まる行と CR を含む値はエラー終了する。`{{SCOPE}}` を持たないテンプレートに `--scope` を渡した場合もエラー終了する（黙って捨てると、渡したつもりで届いていない状態に気付けない）。

`secrets` パターンでは、このスクリプトが `--project-root` を起点にスキャンを実行してから本文を組み立てる（Step 2.3 参照）。

JSON の `review_id` はこのスクリプトが新規生成する不透明トークンである。`body` はバックエンド固有のワイヤヘッダを含まない純粋な共通本文である。**`review_id` は以後のすべての工程（バックエンドへの委譲・終了通知・対応バックエンドでの再開）で参照するためコンテキストに保持する。**

### Step 5: バックエンドへラウンドの実行を委譲する

Step 1.5 で解決したバックエンド SKILL を `Skill` ツールで起動し、`review_id`・ラウンド番号・Step 2 で確定した pattern・Step 4 の `body` を渡してラウンドの実行を求める。バックエンドは判定（`approved` / `findings` / `failure`）と所見配列（重大度・位置・本文）を返す。あわせて応答の解釈で生じた注意（`warnings`）が返ることがある。

**`warnings` を受け取ったら保持し、Step 8 の要約報告に載せる [MANDATORY]**。ここに載るのは位置未確定として受理した所見の件数など、判定にも所見配列にも現れない情報である。捨てると「位置を欠く所見を受理したこと」が利用者に見えないまま完了し、位置未確定として受理する扱いが黙って所見を薄める仕組みになる。バックエンドが `warnings` を返さない場合は載せる項目が無いだけであり、欠落として扱わない。

**バックエンドの内部に立ち入らない [MANDATORY]**。前提検査・送信・起床・待機・応答の解釈・セッション復旧・ワイヤプロトコルはバックエンド側に閉じている。本体からこれらのスクリプトを直接呼ばない。バックエンド固有の失敗（端末多重化ツールが無い・レビュアーが常駐していない等）は `failure` の理由として返るため、本体はそれを利用者へ報告するだけでよい。

### Step 6: 判定による分岐

| 判定       | 行き先                                                                     |
| ---------- | -------------------------------------------------------------------------- |
| `approved` | Step 8（終端処理）へ。`--judgment approved`                                |
| `findings` | Step 7（所見の評価と修正）へ                                               |
| `failure`  | Step 8（終端処理）へ。`--judgment failure`。理由をそのまま利用者へ報告する |

**`failure` を判定として扱わない [MANDATORY]**。所見なしの完了でも指摘ありでもなく、レビューが成立しなかったという結果である。別バックエンドへ暗黙にフォールバックせず、確定した失敗として利用者へ報告する（利用者が実行主体を選び直せるようにする）。

### Step 7: 所見の評価と修正

1. **所見評価 [MANDATORY]**: 依頼時にレビュアーへ渡したものと同じ観点文書（Step 2 で確定したパターンのテンプレートが名指ししている criteria / principles / format。以後の往復でも同一ファイルを Read する）**と、依頼時に渡した重点観点・到達目標**を基準に、**所見ごとに**以下の評価を行う。重点観点を渡した場合、それに直接応答する所見を「criteria に明文の規定が無い」ことのみを理由にドロップしてはならない（利用者が明示的に依頼した観点であるため）。ただし重点観点は severity を引き上げない。**手順 2 の振り分けは位置情報の有無を見るだけであり、この評価を代替・省略しない**（`located` に含まれる所見であっても、この評価を経ていない機械的な適用をしてはならない）:
   - **不要な指摘**: criteria・対象の実態に照らして妥当でないと判断した場合 → ドロップする。対応表には「対応しない（理由: 検証の結果、該当しないと判断）」と記載する
   - **レビュアーの勘違いに基づく指摘**: 対象・前提の理解に誤りがあると判断した場合 → ドロップするか、修正報告の中で確認・訂正を求める（次ラウンドで再考を促す。理由欄に具体的な確認事項を書く）
   - **到達目標の範囲外を指摘した所見**（`--scope` を渡した場合）: 「範囲外だから」を理由に**無条件でドロップしてはならない**。範囲外の項目を「実装漏れ」として報告している所見はドロップし、対応表に「対応しない（理由: 到達目標で範囲外と宣言した項目。担当は `<タスクID>`）」と記載する。一方、範囲外であることを前提に**設計書・仕様書の記述と現状が乖離している**ことを指摘している所見は**妥当な指摘として扱う**（修正対象は実装ではなく文書側になりうる。設計書に段階を注記する等）。今回のスコープ内で対処できない場合は Step 8 の未対応所見（`halted_with_open_findings`）として残し、要約報告に明記する
   - **妥当な指摘**: 鵜呑みにせず、**影響範囲・代替案・よりよい修正方法を検討したうえで**実施内容を決定する（実レビュー往復で、提案をそのまま採用した後に別の観点から反証を受け撤回した事例があり、この教訓を反映する）。**実施する修正は当該所見が指摘した内容に限定し、関連する体裁修正・リファクタリングを合わせて行わない**（所見が指摘していない箇所まで直すと、再レビューで「何が今回の修正か」が判別できなくなり往復が収束しない）

   **所見ごとに 2 つの確信を別々に判断する [MANDATORY]**。**対象が違う**——一方は指摘そのもの、もう一方は対策である。混ぜると「指摘は正しいが直し方が分からない」を表せなくなる。

   | 判断                          | 問い                                   | 値                                        |
   | ----------------------------- | -------------------------------------- | ----------------------------------------- |
   | 確信度（`confidence`）        | **レビュアーの指摘は正しいか**         | `confirmed` ☑️ / `inferred` / `unverified` |
   | 修正の可否（`fix_confident`） | **その修正を責任を持って実行できるか** | 真 / 偽                                   |

   確信度の語彙は `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` に従う（「いま述べている内容が正しいと言えるか」であり、修正の話ではない）。`confirmed` は実物を読んだ・実行して**指摘の妥当性を確認できている**場合、`inferred` は根拠はあるが未確認、`unverified` は記憶・推測だけの場合である。

   **`confidence` が `confirmed` でなければ `fix_confident` は真にならない [MANDATORY]**。指摘が正しいと確信できていないものを直すことはできない。両方が揃った所見だけが `✅`（修正まで任せられる）になる。

   **確信が低く、検証できるなら検証する**（実物を読む・実行する・調べる）。検証すれば `confirmed` になり、直し方まで詰めれば `✅` になる。**割に合わない場合だけそのまま出す。** 付け忘れはいずれも低い側（`unverified` / 偽）として扱う（付け忘れが確信を高く見せない向きにする）。

   **`secrets` パターンの例外 [MANDATORY]**: 混入の所見は自動修正しない。**介入軸が何であっても** `confirmed_fix` を空として扱い（手順 2〜5 と Step 7.5 を実行せず）Step 8 へ進む。`--interactive` でも段階的提示を行わない——採否を聞いても採用の行き先が修正であり、その修正が禁じられているためである。理由は 2 つある:
   - **削除だけでは修正が完了しない**。commit 済みの秘密は履歴・fork・CI ログに残るため、該当する秘密の失効・再発行を伴う。失効は AI が実施できず、実施したかを検証もできない
   - **修正を急ぐと痕跡が消える**。該当行を機械的に消すと、人間が影響範囲（いつから・どこに露出していたか）を調査する起点を失う

   要約報告には所見ごとに「該当箇所」「必要な失効対象」「人間が実施すべきこと」を列挙する。**検出値そのものは報告に書かない**。

2. **位置が確定している所見とそうでない所見を分ける**: バックエンドから受け取った所見配列を次に渡す（介入軸によらず実行する）:
   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/split_by_location.py" --findings-json '<所見配列>'
   ```

   - **`located`**: 位置が確定している所見
   - **`unlocated`**: 位置が確定しておらず、修正対象を特定できない所見。対応表には「対応しない（理由: 位置が確定していないため修正対象を特定できません。人間の確認が必要です）」と記載する

   **このスクリプトは判断をしない [MANDATORY]**。所見が位置情報を持っているかを見るだけで、対象のコードも文書も読まない。**修正できるか・修正してよいかを決めるのは手順 1 の判断であり、機械ではない。**

   次に `located` の各所見を、手順 1 の 2 つの判断で 3 群へ分ける。

   | 行き先           | 条件                                                            |
   | ---------------- | --------------------------------------------------------------- |
   | `confirmed_fix`  | 妥当と判断し、かつ **`--auto` で `✅`**（`confirmed` + 修正可） |
   | 提示（Step 7.5） | 妥当と判断したが `--interactive`、または `✅` でない            |
   | ドロップ         | 手順 1 で不要・勘違いと判断した所見。対応表に理由を記載         |

   **提示へ回る所見が 1 件でもあれば Step 7.5 へ進む [MANDATORY]**。`--auto` でも同じである。確信の無い修正を確認なしに適用すると、`--auto` が「間違えるもの」になる。

   **終了判定 [MANDATORY]**: `confirmed_fix` が空、かつ提示へ回る所見も無い場合（＝ドロップのみ・位置未確定のみ・所見自体が 0 件のいずれか）、手順 3〜5 を実行せず **Step 8 へ進む**（`--judgment findings --confirmed-fix-count 0`）。対応しなかった所見を残したまま再レビューを依頼すると、レビュアーが同じ所見を指摘し続け `findings` から抜け出せず往復上限まで往復し続けるためである。

3. **修正の実施（本スキルを実行している主体が直接修正 + 安全検証）**: 本スキルを実行している主体が直接、`confirmed_fix` の所見の修正を実施する（専用の evaluator/fixer Agent は起動しない）。全件をまとめて修正してから検証するのではなく、finding 単位で「適用 → 検証 → 判断 → 次へ」を逐次繰り返す:

   1. **baseline 取得（ループ開始前に1回）**:
      ```bash
      python3 "${CLAUDE_SKILL_DIR}/scripts/capture_syntax_baseline.py" --files-json '<target_files の JSON 配列>'
      ```
   2. `confirmed_fix` の finding を1件ずつ、以下を繰り返す:
      1. その finding の修正のみを実施する（他の `confirmed_fix` 所見の編集は同時に行わない）
      2. この finding のために実際に Edit したファイルパスを自己申告する
      3. 検出専用の安全検証を実行する（**ファイルは一切書き換えない**）:
         ```bash
         python3 "${CLAUDE_SKILL_DIR}/scripts/verify_fix_safety.py" \
           --allowed-files-json '<target_files>' \
           --modified-files-json '<この finding で自己申告したファイル群>' \
           --baseline-json '<baseline>'
         ```
      4. 結果を自分で判断する（スクリプトは自動でロールバックしない）:
         - `allowlist_violations` / `syntax_errors` が事故的な逸脱・意図しない構文破壊と判断した場合 → 自分で元に戻し、この finding を「対応しない（理由: 修正後の安全検証で問題を検出したため取り消し）」として記録する
         - `allowlist_violations`（target_files 外の関連ファイル修正）をレビュー基準に照らして正当な波及修正と判断した場合 → 変更を維持し、その理由を修正報告に明記する（沈黙したスコープ拡大を許さない）
         - `status: "ok"` の場合 → 「対応した」として記録し、次の finding へ進む
   3. **ラウンド終了時の独立検証 [MANDATORY]**: 上記ループの `--modified-files-json` は finding ごとの自己申告に基づく。申告漏れが起きると、そのファイルは allowlist・構文検証のいずれも通過しないまま見過ごされうる。すべての `confirmed_fix` 処理後、自己申告に依存しない形でこのラウンド全体の変更集合を独立に確認する。ファイルパスの抽出は行/矢印単位の手動パースでは行わない（`git status --porcelain` は空白・改行・非 ASCII を含むパスを quote し、rename/copy は `->` を含む1行で表現するため、手動パースでは実パスを取り違える）:
      ```bash
      python3 "${CLAUDE_SKILL_DIR}/scripts/collect_modified_files.py"
      ```
      出力の `files` 配列を、`target_files ∪ (このラウンドで正当な波及修正として維持したファイル)` を allowlist として `verify_fix_safety.py` に渡す。`allowlist_violations` が検出された場合、それはどの finding の自己申告にも含まれていなかった変更である。意図した変更であれば理由を修正報告に明記し、意図しない変更であれば元に戻す。この独立検証は「ラウンド終了時点で allowlist 外の変更が実際に存在するか」の粗い最終確認である。

4. **次ラウンドの依頼本文を組み立てる**: 所見ごとの対応表（対応した / 対応しない（理由））を書く。`unlocated` が空でない場合は「対応しなかった所見は今回のモードでは意図的に対象外としています。今回対応した所見が正しく解消されているかのみご確認ください」を明記する（手順 2 の終了判定が実際の歯止めであり、本文言は往復回数を減らすための補助に過ぎない）。

   **本文の構成は、Step 1.5 の可用性検査でバックエンドが申告した `retains_context` で決める [MANDATORY]**。backend 名から推測しない（名前からの推測は FNC-1318 が禁じる固有の事情の持ち込みにあたる）。

   | `retains_context` | 送る依頼本文                                                                                                                                                                                                                                                                |
   | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `true`            | 対応表のみ。対象・観点・返信形式契約は前ラウンドで届いている                                                                                                                                                                                                                |
   | `false`           | `build_review_request.py` を**再実行して得た完全な依頼本文**に対応表を添えたもの。**`--review-id` に Step 4 で得た値を渡す**（省略すると新しい `review_id` が振られ、仕分けファイルの照合と衝突する）。`--scope` には今回確定した判断（意図的にそうしてある事柄）を反映する |

   `false` のバックエンドへ対応表だけを送ってはならない。新しいレビュアーは対象も観点も返信形式契約も持たないため成果物を検査できず、**唯一与えられた依頼本文の記述そのものを検査対象にする**（実際に「報告に記載の無い変更が差分にある」という、成果物の欠陥ではない所見が返った）。

5. **Step 5 へ戻る**: バックエンドへ次ラウンドの実行を委譲する（`review_id` は同一、ラウンド番号をインクリメント、依頼本文は手順 4 で組み立てたもの）。返る判定に従って再び Step 6 へ進む。**依頼本文を出力してターンを終えてはならない [MANDATORY]**——往復の終端に到達するまで本体のループを抜けない。

> **この禁止の射程 [MANDATORY]**: 禁じているのは「レビュアーへ依頼を投げた状態でターンを終え、返信を引き取る主体を失うこと」である。Step 7.5 の段階的提示は**バックエンドへ次ラウンドを送る前**に行うため、未回収の依頼が存在せず、この禁止に当たらない。人間の応答を待つためにターンを終えてよい。

### Step 7.5: 段階的提示

手順 2 で提示へ回した所見を **1 件ずつ人間へ提示して採否を得る**。対象は介入軸で変わる。

| 介入軸          | 提示する所見                     |
| --------------- | -------------------------------- |
| `--interactive` | 修正できる所見すべて             |
| `--auto`        | `✅` でない所見だけ（`☑️`・無印） |

`--auto` で提示へ回る所見が 1 件も無ければ、本 Step を実行せず手順 3 へ進む。

提示の作法は `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` に従う。**本 SKILL.md に提示の規範を書き写さない**（定義点が 2 つになる）。ここが定めるのは手順だけである。

#### 7.5.1 仕分けファイルへ所見を入れる [MANDATORY]

**作成も更新も `update_triage.py` で行う。作り直す経路は無い [MANDATORY]**。既存ファイルが無ければ作る。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/update_triage.py" \
  --review-id "<review_id>" \
  --add-json '<提示へ回す所見・位置未確定の所見・ドロップした所見>' \
  --project-root "$(git rev-parse --show-toplevel)"
```

**受け取った所見をすべて渡す [MANDATORY]**。提示へ回すもの、`✅` として確認なしに直すもの、位置未確定のもの、ドロップしたもののいずれも渡す。**取り下げた事実・自動修正する事実・位置未確定の事実を、判断が要る所見と同じ 1 枚の表で見せるため**である。状態はスクリプトが決める（位置未確定なら `対象外`、`drop_reason` があれば `取り下げ`、それ以外は `未着手`）。

**`✅` を除外しない [MANDATORY]**。採否を聞くかどうかと、記録するかどうかは別の問いである。`✅` について採否を聞かないのは `--auto` の定義どおりだが、それは記録から外す理由にならない。除外すると、利用者は**何が変更されるかを見ないまま変更が適用される**。ドロップした所見を記録するのと同じ理由——**人間に諮らず AI が決めたことは、誤っていたときに気付ける形で残す**——が、自動修正にも同じだけ働く。

**所見ごとに次を足す [MANDATORY]**。

| キー            | 内容                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------- |
| `summary`       | **アジェンダ表に出す課題の所在を 1 行で**。所見本文は入れない（表が読めなくなる）。未指定はエラー |
| `confidence`    | 手順 1 の確信度（`confirmed` / `inferred` / `unverified`）                                        |
| `fix_confident` | 手順 1 の修正の可否（真偽値）                                                                     |
| `drop_reason`   | ドロップした所見のみ。取り下げ理由                                                                |

スクリプトは `confidence` が `confirmed` の行に `☑️`、`fix_confident` も真の行に `✅` を立てる。**渡さないと、利用者は「直せるものは任せる」と言えない**——判断は手順 1 で既に決まっているのに、一覧に出さなければどれがそれに当たるか見えない。

**追加は冪等である**。同じ所見（位置 + 本文）を再度渡しても増えない（`skipped_count` で返る）。識別子は既存の最大 + 1 で振られ、**既存は動かない**。

出力 JSON の `total_count` / `auto_fixable_count`（`✅` の件数）/ `open_count`（未決着の件数）を読み、**`absolute_path` をコンソールに 1 行で示す**（利用者がエディタで開くため。`triage_path` はプロジェクトルート相対であり、cwd が違うと開けない）。

段階的提示は設計上ターンをまたぐ。所見・評価・判断をコンテキストだけで持つと、圧縮で失われたときに再レビューからやり直しになり、失われたこと自体も検知できない。ファイルはその保険であると同時に、コンソールより読みやすい媒体でもある。**そのファイルを作り直してはならない**——作り直すにはコンテキストの所見が要るため、守りたかったものが失われた瞬間にファイルも作れなくなる。

#### 7.5.2 アジェンダを提示する [MANDATORY]

アジェンダの提示そのものは規範文書が定める。この場面に固有なのは次の 3 点である。

**`✅` の所見は、まとめて直す申し出を出す [MANDATORY]**。アジェンダと同時に「`✅` の N 件は修正まで任せられます。まとめて直しますか」を示す。**介入軸が `--interactive` でも出す**——`✅` は「指摘が正しく、修正も責任を持って実行できる」を意味し、この条件は介入軸と独立に成立する。利用者が承諾したらその N 件を `confirmed_fix` へ積み、残りを 1 件ずつ進める。申し出を省いて全件を 1 件ずつ聞くと、既に確信のある修正について利用者の時間を使うことになる。

**`取り下げ` と `対象外` の採否を 1 件ずつ聞かない [MANDATORY]**。どちらも決着済みの行として書き出されている。**件数と理由をアジェンダと同時にまとめて示す**にとどめる（不要と判断済みの所見を 1 件ずつ見せるのは、利用者の時間を使うだけで判断の質を上げない）。利用者が差し戻した行だけ `--state 未着手` に変えて提示に回す。節は既にあるため、所見の全文も決着欄も失われていない。

**2 つの状態を取り違えない [MANDATORY]**。`取り下げ` は指摘が誤りだったもの（AI の判断）、`対象外` は最初から範囲外と決めたもの（位置未確定で修正対象を特定できない）である。`対象外` は**人間が直接内容を確認する必要がある**ことを、アジェンダと同時に添える。後回しにすると、判断を終えた利用者が「全部片付いた」と誤解する。

#### 7.5.3 1 件ずつ進める [MANDATORY]

進行の作法（提示順・アジェンダの再掲・次の項目へ自分で進むこと・判断を迫らないこと・一括提示の例外）は規範文書が定める。ここで定めるのは、この場面に固有の 3 つだけである。

1. 各所見の提示に、**手順 1 の評価にもとづく推奨（採用する / 採用しない）と理由**、`ファイルパス:行`、判定（`✅` / `☑️` / 無印）を含める
2. **決着するたびに、次のコマンドでファイルを更新する [MANDATORY]**。コンソールの更新だけで済ませない。**議論の中で新しい所見が出たら `--add-json` で足す**（既存の識別子は動かない）
   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/update_triage.py" \
     --id <ID> --state 決着 \
     --result "<決まったことを 1 行で>" \
     --field 背景="<提示で述べた、なぜこれが問題か>" \
     --field 本質="<提示で述べた、判断を左右しているのはどこか>" \
     --field 対応="<何をどう直すか。採用しないなら「なし」>" \
     --field 推奨="<採用する / 採用しない。理由を 1 行>" \
     --field 決着="<理由と決定の帰属。AI が決めた場合はその旨>" \
     --project-root "$(git rev-parse --show-toplevel)"
   ```

   **提示で述べた内容をここで書き戻す [MANDATORY]**。`決着` だけを書くと、背景・本質・対応・推奨はプレースホルダのまま残り、**提示の内容は会話にしか存在しなくなる**。このファイルは、それがコンテキストから失われても残るためにある。`--state 決着` でこれらの欄が未記入なら `update_triage.py` はエラーで止まる（規約だけに頼らず構造でも止めている）。

   **一括で決着させた所見にも `対応` を書く**（何を変えたかが、そこにしか残らないため）。
3. 「採用する」と決まった所見を `confirmed_fix` として積む（7.5.5）

#### 7.5.4 中断

利用者が「残りは全部あとで」「ここで終える」と示したら、その時点で確定する。**未判断のまま残った件数を明示する。** 未判断を「対応不要」へ畳み込まない。

未判断の行は `状態` を `未着手` のまま残す。**ファイルは削除しない。** 次にレビューを起動したとき、Step 1.1 の確認で「続きから進める」を選べばここから再開できる。

**中断の行き先は Step 8 であり、判定は `findings` である [MANDATORY]**。それまでに「採用する」と決まった所見の修正は実施する（採用の帰結であるため）が、そのあと Step 7 手順 5 へは進まず Step 8 へ抜ける。`confirmed_fix` が空でなくても同じである——利用者が止めたのに新しいラウンドが走るのは、中断の指示に反する。判定を `interrupted` にしないのは、それが**レビューそのものの中止**を指す値だからで、取り違えると未対応所見の一覧が要約報告から落ちる。

#### 7.5.5 判断の反映

「採用する」と決まった所見が `confirmed_fix` である。手順 1 の評価は済んでいるが、**実施内容（影響範囲・代替案）は採用が決まってから詰める**。

次ラウンドへ進む場合、7.5.1 は同じファイルへ新しい所見を**足す**。**作り直す口は無い**（DES-066 §3.11）。前ラウンドの決着行はそのまま残り、新しい所見がその下に並ぶ。決着済みの行を消す操作も要らない——このラウンドで採用したものは修正として、採用しなかったものは対応表として、いずれも既に外へ出ているため、残っていても新しい判断を求めない。

以降は Step 7 手順 3〜5 と同じである（修正の実施 → 安全検証 → 対応表の組み立て → 再レビュー）。対応表には「採用しない」と決まった所見も理由付きで載せる。

**手順 4 と Step 8 が参照する `unlocated` は、仕分けファイルのアジェンダ表で `状態` が `対象外` の行から取る [MANDATORY]**。`--interactive` では手順 2（`split_by_location.py` の直接実行）を通らないため、`unlocated` 配列が手元に無い。位置未確定の所見はここにしか残っておらず、取り損ねると対応表と要約報告の両方から落ちる。

`confirmed_fix` が空の場合（全件が採用しない、または 1 件も判断しないまま中断した場合）、Step 7 手順 2 の終了判定と同じく **Step 8 へ進む**（`--judgment findings --confirmed-fix-count 0`）。

### Step 8: 終端処理 [MANDATORY]

**レビューを終える経路はすべてこの Step を通す**。承認・打ち切り・失敗確定・利用者の中止のいずれであっても、まず次を実行する:

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/finalize_review.py" \
  --judgment <approved|findings|failure|interrupted> \
  --review-id <review_id> \
  --backend <backend 名> \
  [--confirmed-fix-count <件数>]
```

`--confirmed-fix-count` は `--judgment findings` のとき必須（Step 7 手順 2 で確定した件数）。`interrupted` は利用者がレビューの中止を指示した場合に使う（バックエンドは返さない、本体由来の値）。

出力の `notify_backend` が非 null の場合、**その `backend` の SKILL を終了通知モードで起動し、`review_id` を渡す [MANDATORY]**。バックエンドはこれを保持資源の解放契機とする。資源を持たないバックエンドは無視してよい契約であるため、発行側で「通知が要る経路か」を選別しない。

> **なぜ単一の出口を通すのか [MANDATORY]**: 終了通知の発行漏れは、資源を持たないバックエンド（msg-review）では何も起きず、資源を自前で持つバックエンドを接続して初めてリークとして現れる。露見が遅れる失敗であるため、経路ごとに散文で発行を指示する形を採らない。同じ SKILL が送信・起床・待機で同型の失敗を 2 度起こしており、単一の入口へ畳んで解決した経緯がある。

`notify_backend` が null（`path: "continue"`）の場合は終端ではない。Step 7 手順 5 へ戻る。

続いて `path` に応じた要約報告を出力してターンを終える。

| `path`                      | 報告                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `approved`                  | 指摘の件数 / 対応した修正の概要 / 不採用とした所見とその理由                                               |
| `halted_with_open_findings` | 下記「未対応所見を残した完了」                                                                             |
| `failure`                   | レビューが成立しなかったこと・バックエンドが返した失敗理由・利用者が取りうる次の手（実行主体の選び直し等） |
| `interrupted`               | 中止した時点のラウンド数・実施済みの修正・未対応のまま残る所見                                             |

**バックエンドから受け取った `warnings` は、どの `path` でも要約報告に載せる [MANDATORY]**（Step 5 参照）。位置未確定として受理した所見の件数はここでしか利用者に届かない。`approved` で終わった場合も省略しない。

#### 未対応所見を残した完了（`halted_with_open_findings`）

Step 7 手順 2 の終了判定により到達する。**レビュアーはなお指摘ありと判定し続けている**ため、承認による完了とは異なる完了状態として扱う。要約報告には以下を明記し、承認された場合と混同しない形で人間の判断を仰ぐ [MANDATORY]:

- **レビュアーはなお指摘ありと判定していること**（承認ではない旨を冒頭で明示する）
- **修正しなかった所見全ての一覧と理由**（`unlocated` のみでは不十分。以下すべてを含める）:
  - 位置未確定による対象外（`unlocated` の全件。severity によらず対象外であり、人間の確認が必要である旨を添える）
  - 手順 1 の評価でドロップした所見とその具体的根拠
  - **利用者が「採用しない」と決めた所見とその理由**（`--interactive` のみ。仕分けファイルの `決着` 欄から取る。全件不採用なら次ラウンドの対応表自体が作られないため、ここで落とすと報告のどこにも残らない）
  - 手順 3 の安全検証で問題を検出し取り消した所見とその内容（allowlist 逸脱・構文エラーの別）
- 現在の介入軸と、その軸で対象外になった所見に対して人間が取りうる手（軸を変えて再実行する / 直接内容を確認する）
- **`--interactive` で中断した場合は、仕分けファイルの実パスと未判断の件数を示す**（利用者が続きを追えるようにするため）

## 再開モード

往復上限到達の通知を受けた利用者が、状況確認・再開を明示指示したターンで実行する。

**段階的提示の中断からの再開は本モードではない。** 依頼モードの Step 1.1（前回の仕分けファイルの確認）が入口である。

### Step 1: 対象 review_id の往復履歴を取得

対象の `review_id`（コンテキストに保持しているもの。失われていれば利用者に確認する）と、当該レビューで使ったバックエンド名を確定する。

履歴復元は任意拡張である。バックエンドが対応する場合だけ、バックエンド SKILL を履歴復元要求で起動し、往復履歴（`messages` / `round` / `resolved`）を得る。取得方法・保存場所はバックエンドごとに異なるため、本体はスクリプトを直接呼ばない。

バックエンドが `unsupported` を返した場合、空履歴として扱わない。`agent-review` など非永続バックエンドでは同一 `review_id` の再開はできないことを利用者へ明示し、継続を求められたら依頼モードの Step 1 へ戻って新しい `review_id` の新規レビューとして再実行する。

### Step 2: 未解決所見の集計・要約報告

`resolved` が `false` の場合、直近のレビュアー所見から未解決所見を抽出し、以下を含む要約報告を出力して人間の判断を仰ぐ:

- 往復回数（`round`）
- 未解決所見の一覧
- これまでの対応・不採用理由（本体側の返信メッセージから）

`resolved` が `true` の場合は、既に承認済みであることを報告する（上限到達通知と承認が競合した場合の整合性確認）。

**再開せずに終える場合も終了通知を発行する [MANDATORY]**。利用者が再開を望まないと判断した場合は Step 8 を `--judgment interrupted` で通す。

## 対象外（v1 スコープ外）

- **所見の評価・修正を専用 Agent へ委譲しない**: 本スキルを実行している主体が直接行う。allowlist 検証・構文検証（検出のみ、ロールバックの判断は実行主体が行う）は Step 7 に導入済み
- **レビュアーセッションの自動起動・管理**（バックエンドの責務であり、本体は関与しない）
- **段階的提示を外部スキルへ委譲しない**: 段階的提示を必要とする呼び出し元が本スキル以外に存在せず、利用者 1 つのための抽象化になるためである（`${CLAUDE_PLUGIN_ROOT}/docs/design_principles_spec.md` 「責務分割・凝集度規範」の Rule of Three）。**委譲が技術的に不可能だからではない**（バックエンドは Skill ツール経由で判定と所見配列を永続化なしに返しており、同じ経路で渡せる）

> **状態の持ち方**: `auto` 系のラウンドは 1 ターン内で受領・評価・修正・返信まで完結し、状態をファイルへ持たない。`--interactive` の段階的提示だけは人間の応答を挟むため設計上ターンをまたぐ。その分の状態は `.claude/.temp/review/triage.md`（常に 1 つ）に持つ（Step 7.5.1）。仕分けの外側（往復ラウンドの管理・レビュアーのセッション）は依然として状態を持たない。
