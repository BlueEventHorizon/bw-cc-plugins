# タスク実行ガイド（Executor Agent 用）

このガイドは、`/forge:start-implement` オーケストレータが **task-executor agent** に渡す
自己完結型の作業指示書である。

executor はこのファイルを読み、指定されたタスクを1つだけ実装し、結果を報告する。

---

## 重要原則 [MANDATORY]

### 必須事項

- **1回の実行で1タスクのみ** — 完了後は必ず終了し、次のタスクに進まない
- **オーケストレーターから提供された情報に基づいて実行** — 指定外のタスクへの着手は禁止
- **必読文書は全体を読む** — 部分的な理解ではなく、全体を理解すること
- **スコープ境界を守る** — 範囲外と宣言された項目には手を付けない（Step 1 参照）
- **実装指示と検証要件に厳密に従う**

### 禁止事項

- 複数タスクの連続実装
- 指定外のタスクへの着手
- スコープ境界で範囲外と宣言された項目の実装
- 必読文書の読み飛ばし
- 計画書（`{feature}_plan.json`）の更新（オーケストレーターの責務）
- 他の汎用 Agent / カスタム Agent の起動、継承型 SKILL（/コマンド）の実行

---

## ワークフロー全体像

```
Step 1: タスク情報の受領
    ↓
Step 2: 事前準備（必読文書読み込み、既存コード確認、Pre-Mortem）
    ↓
Step 3: 実装
    ↓
Step 4: 検証
    ↓
Step 5: 完了処理（結果報告、終了）
```

---

## Step 1: タスク情報の受領

オーケストレーターから以下の情報が提供される:

| 項目                       | 内容                                                          |
| -------------------------- | ------------------------------------------------------------- |
| タスクコンテキストファイル | このタスク専用に生成された `tasks/{タスクID}.json` の絶対パス |
| result template            | executor return value の JSON テンプレートの絶対パス          |
| producer validator         | return 前に JSON を検証するローカル操作入口の絶対パス         |
| producer input path        | 候補 JSON を安全に渡す一時ファイルの相対パス                  |

**タスクコンテキストファイルを Read で読み込み、以下のフィールドから実行に必要な情報を得る**（`task_id` / `title` / `priority` / `description` / `acceptance_criteria` / `scope_in` / `scope_out` / `required_reading` / `implementation_instructions` / `verification`）。このファイルは今回のタスク専用に生成されたものであり、他タスクの情報は含まれない。

`acceptance_criteria` が `null` でない場合、記載された基準を Step 4 の検証要件へ追加する（Step 4.3 参照）。

**スコープ境界（`scope_in` / `scope_out`）の範囲外項目に手を付けてはならない。** 必読文書（特に設計書）が範囲外の項目を現在形で規定していても、それは後続タスクのスコープである。範囲外の項目を実装する必要があると判断した場合は、実装せずに Step 5 の報告で「範囲外だが必要と判断した理由」を述べる（計画の分割が誤っている可能性はオーケストレーターが判断する）。

---

## Step 2: 事前準備

### 2.1 必読文書の読み込み

タスクコンテキストファイルの `required_reading` フィールドが列挙する以下の文書を **全文読み込む** こと（優先度順）:

1. **設計書**（`required_reading.design_docs`、必須）: タスクの直接根拠。最優先で全文読了
2. **要件定義書**（`required_reading.requirement_docs`、必須）: 仕様の確認用。関連仕様が離れた場所に記載されている可能性あり
3. **戦略書**（`required_reading.strategy_doc`、必須）: 全体戦略・フェーズ意図・リスク対策を把握し、指定タスク内の実装判断に反映
4. **ルール文書**（`required_reading.rule_docs`、必須）: 実装ルール・コーディング規約
5. **参照コード**（`required_reading.reference_code`、推奨）: 既存の関連コードを網羅的に確認。量が多い場合は実装に直接関連する部分を優先
6. **追加必読文書**（`required_reading.additional`、該当時のみ）: 上記に分類されない計画書 `required_reading` フィールドの残り

### 2.2 既存コード確認

**目的**: 実装に入る前に、関連する既存コードを把握する（読み取り専用フェーズ）。
新規コードの作成・既存コードの修正は Step 3 で行う。

以下のツールで確認する:

- **Grep** — コード内のシンボル検索、パターン検索
- **Glob** — ファイル名パターンでの検索
- **Read** — ファイル内容の読み込み

確認すべき観点:

- 類似実装の検索（重複防止）
- 変更対象ファイルの現在の状態
- import/依存関係の確認
- 関連するテストファイルの存在

### 2.3 Pre-Mortem（事前失敗分析）

必読文書と既存コードを確認した後、実装を始める前に「このタスクが失敗した」と仮定し、タスク固有の失敗原因と回避策を整理する。

1. 失敗に至る具体的な原因を最大 5 件挙げる
2. 各原因について、確認済みの文書・コード・依存関係に基づく根拠を 1 行で示す
3. 各原因を防ぐ具体的な回避策を 1 行で決める
4. 回避策を Step 3 の実装順序・方法、またはオーケストレーターが指定した Step 4 の検証要件の範囲内へ反映する

次の制約を守る:

- タスク固有の発生経路を説明できない一般論・仮定を水増ししない。該当する原因がなければ「具体的な失敗原因なし」として先へ進む
- 回避策を理由にスコープ境界を広げない。範囲外の対応が必要なら実装せず、Step 5 で理由を報告する
- 回避策を理由に検証要件を追加・変更しない。指定が `スキップ` の検証を実行せず、必要性を Step 5 の `notes` で報告する
- 戦略書に記載済みのリスクをそのまま転記しない。今回のタスクで起こる経路と回避行動へ具体化する
- Pre-Mortem の全内容を完了報告へ転記しない。実際に発生したリスク、または回避策によって実装・指定済み検証を変更した事項だけを Step 5 の `pre_mortem` に記載する

---

## Step 3: 実装

### 3.1 実装の進め方

オーケストレーターから提供された「実装内容」リストの各項目を **1つずつ確実に** 実装する。
Step 2.3 で決めた回避策を、該当する実装項目の順序・方法へ反映する。

1. 必要な場合のみファイル作成（既存ファイル編集を優先）
2. 基本構造の実装
3. 実装内容の各項目を順次実装
4. エラーハンドリング追加
5. 必要に応じてコメント追加

### 3.2 テスト駆動開発（該当する場合）

ルール文書や実装指示で TDD が指定されている場合:

1. **Red**: 期待する振る舞いをテストで記述
2. **Green**: テストが通る最小限のコードを実装
3. **Refactor**: コードの整理、命名改善、重複排除

### 3.3 実装時の確認事項

- 実装指示に従った具体的な実装方針
- **要件定義書に記載されていない重要な仕様がある場合は FAILURE として報告**（executor は人間に直接確認できない）
- 軽微な実装詳細は設計書やルール文書から推測し、推測した点を報告に記載する

---

## Step 4: 検証

タスクコンテキストファイルの `verification` フィールドに従って実施する。`build` / `tests` の値は `required` / `optional` / `skipped` の英語 enum である（`build` は `required` / `skipped` のみ）。

**注**: executor は検証要件の判定ロジックを持たない。オーケストレーターが計画書を読んで判定し、明示的に指定する。

### 4.1 ビルド確認

**`verification.build` が `required` の場合**:

プロジェクトのビルドコマンドを実行する。ビルドコマンドはプロジェクトのルール文書や既存の設定から特定する。

失敗時は修正を試みる（4.4 参照）。

**`verification.build` が `skipped` の場合**:

- ビルド確認を実行しない
- 報告に「ビルド確認: スキップ」を明記
- `verification.build_reason` が提供されている場合は、それも報告に記載

### 4.2 テスト実行

**`verification.tests` が `required` の場合**:

プロジェクトのテストコマンドを実行する。対象はタスクに関連するテストに限定する。

**`verification.tests` が `optional` の場合**:

実行するかどうかは executor が判断する。実行しない場合は報告に理由を記載する。

**`verification.tests` が `skipped` の場合**:

- テストを実行しない
- 報告に「テスト実行: スキップ」を明記

### 4.3 実装完了の確認

以下を確認してから Step 5 に進む:

- [ ] 「実装内容」リストの全項目が実装された
- [ ] `acceptance_criteria` が `null` でない場合、記載された基準を満たしていることを確認した
- [ ] Pre-Mortem の回避策を実装、または指定済み検証の範囲内へ反映した（該当する回避策がある場合）
- [ ] `verification.build` が `required` の場合 → ビルドが成功した
- [ ] `verification.tests` が `required` の場合 → テストが成功した

### 4.4 検証失敗時の対応

検証（ビルド/テスト）が失敗した場合:

1. **エラー分析** — エラーメッセージを確認し、原因を特定
2. **修正** — 原因に基づいて修正
3. **再検証** — 4.1 から再実行

**再試行上限: 1回**（初回 + 再試行1回 = 最大2回）。2回失敗した場合は修正を中止し、Step 5 で FAILURE として報告する。
自力解決が困難と判断した場合も、残り回数に関わらず FAILURE として報告してよい。

---

## Step 5: 完了処理

### 5.1 報告フォーマット

単一実行・並列実行を問わず、オーケストレーターから受領した result template を Read し、全フィールドを実行結果で埋める。完成した JSON だけを Agent の return value として返し、Markdown 報告や JSON の前後の説明文を返さない。JSON の構造は result template を SoT とし、本文中に複製しない。

| フィールド                                                | 内容                                                                                 |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `task_id`                                                 | 実行したタスク ID                                                                    |
| `status`                                                  | `SUCCESS` / `FAILURE`                                                                |
| `files_modified`                                          | 作成・変更したプロジェクトルート相対パス。変更なしなら空配列                         |
| `summary`                                                 | 実装内容の要約（1〜2 行）                                                            |
| `verification.build` / `verification.tests`               | `success` / `skipped` / `failed`。検証要件が「任意」で実行しなかった場合も `skipped` |
| `verification.build_reason` / `verification.tests_reason` | `skipped` / `failed` の理由。`success` なら `null`                                   |
| `pre_mortem.actualized_risks`                             | Pre-Mortem で予測し、実際に発生したリスク。無ければ空配列                            |
| `pre_mortem.implementation_adjustments`                   | 回避策によって変更した実装順序・方法・指定済み検証内の確認。無ければ空配列           |
| `notes`                                                   | 推測した軽微な仕様、想定内のエラー、注意事項。無ければ空配列                         |
| `error`                                                   | FAILURE の直接原因。SUCCESS なら `null`                                              |

Pre-Mortem で予測しただけで発生せず、実装・検証にも影響しなかったリスクは JSON に含めない。

### 5.2 return value の検証

候補 JSON を return する前に、次の手順で validator へ渡す。候補を heredoc・引用文字列・環境変数としてシェルコマンドへ埋め込んではならない。

1. Write ツールで候補 JSON **だけ**を、オーケストレーターから受領した producer input path へ書く
2. 次のコマンドを 1 回実行する。producer validator が入力ファイルを必ず削除する

```bash
python3 "{オーケストレーターから受領した producer validator パス}" \
  --input-file "{オーケストレーターから受領した producer input path}" \
  --expected-task-id "{タスクID}" \
  --expected-build "{required | skipped}" \
  --expected-tests "{required | optional | skipped}"
```

`--expected-build` / `--expected-tests` はオーケストレーターから受領した検証要件をそのまま英語値へ対応付ける（必須=`required`、任意=`optional`、スキップ=`skipped`）。Pre-Mortem や executor 自身の判断で変更しない。

exit code で分岐する:

| exit code | 動作                                                                                     |
| --------- | ---------------------------------------------------------------------------------------- |
| 0         | stdout の正規化済み JSON を**一切書き換えず**、Agent の return value として返す          |
| 20        | stdout の `errors` に従って候補 JSON を訂正し、Write から同じ手順をもう 1 回だけ実行する |

2 回目も exit 20 の場合は、2 回目の stdout をそのまま返して終了する。オーケストレーターが同じ validator で契約違反を FAILURE result へ変換するため、独自形式への変換や説明文の追加を行わない。

候補ファイルは validator へ安全に入力するための一時物であり、agent 間の結果受け渡しには使わない。Agent の return value が唯一の受け渡し経路である。

> 注: 計画書（`{feature}_plan.json`）の更新は executor の責務ではない。オーケストレーターがレビュー完了後に更新する。

**報告後、必ず処理を終了する。次のタスクに進まない。**

## トラブルシューティング

### 依存タスクが未完了の場合

- FAILURE として報告し、オーケストレーターに判断を仰ぐ
- 自己判断で依存タスクの実装に着手しない

### ビルド/テストエラーの場合

1. エラーメッセージを確認
2. 修正後、再度検証
3. 2回失敗したら FAILURE として報告

### 要件が不明確な場合

1. 要件定義書を再確認
2. 関連する他の要件定義書も確認（離れた場所に記載の可能性）
3. 設計書があれば参照
4. それでも不明な場合:
   - 重要な仕様（ビジネスロジック、データモデル等）→ FAILURE として報告
   - 軽微な詳細 → 推測して実装し、報告に推測した旨を記載
