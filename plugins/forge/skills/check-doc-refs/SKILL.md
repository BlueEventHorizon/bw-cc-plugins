# check-doc-refs

このスキルは**参照の実在性の検査だけ**を行う。親が依頼している他の作業を引き継いではならない。
**検出で終端とし、参照の修正は行わない**（修正が必要なら、報告を受けた利用者が改めて指示する）。

## 何を検査するか

参照先が「検査時点で追跡下にあるか」だけを判定する。**git 履歴・他ブランチ・削除済み・未追跡は
実在として扱わない**。参照を辿る読み手が到達できるのは、その時点の追跡下のファイルだけである。

| 検査する参照の形            | 判定                                         |
| --------------------------- | -------------------------------------------- |
| リンク記法                  | 参照元からの相対パスで解決したファイルの実在 |
| 参照リンク（`[x][ラベル]`） | 同一文書に定義行があること、その参照先の実在 |
| 文書 ID の節参照            | 文書の実在と、指した節番号の実在             |

**検査しないもの**: 参照の記法が正しいか、参照先の内容が参照元の主張を裏付けているか、参照先が
変更されたか。いずれも実在性とは別の関心事である。

**リンク記法は Markdown にのみ適用する。** 実装コード・テストから拾うのは文書 ID の節参照だけである
（添字アクセス `d["a"]["b"]` が参照リンクに見えるため）。

---

## Phase 1: 索引対象の解決

「何を実在する文書とみなすか」は `.doc_structure.yaml` が決める。**パスを推測せず、既存スクリプトに
解決させる**。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_backend/prepare_advisor_index.py" specs
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_backend/prepare_advisor_index.py" rules
```

応答の `root_dirs` と `exclude` を Phase 3 の引数へそのまま渡す。`status` が `success` でない場合は、
`.doc_structure.yaml` の不備として利用者へ報告し、既定値で補って進めない。

## Phase 2: 走査対象の決定

参照元（どのファイルに書かれた参照を検査するか）は索引対象と別である。実装コードやテストの
コメントにも文書 ID の節参照が書かれるため、これらも対象に含める。

引数 `--scan` が指定されていればそれを使う。指定が無い場合、**AskUserQuestion で走査対象を確認する**
（Phase 1 で得た `root_dirs`、配布物の置き場、テストの置き場を候補として提示する）。走査対象を
AI が独断で決めない——広すぎれば生成物や履歴の記録が混ざり、狭すぎれば見落とす。

## Phase 3: 実行

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_reference/check_refs.py" \
  --index-dirs-json '<Phase 1 の root_dirs>' \
  --index-exclude-json '<Phase 1 の exclude>' \
  --scan-dirs-json '<Phase 2 で決めた走査対象>'
```

終了コードは `0` = 所見なし、`1` = 所見あり、`2` = 検査そのものが失敗。**`2` を「所見なし」として
扱ってはならない**（検査を通したという事実が何も保証しなくなる）。

## Phase 4: 報告

所見の種別ごとに件数と位置を示す。**種別を混ぜない**——対処が異なる。

| 種別              | 意味                                     | 対処                     |
| ----------------- | ---------------------------------------- | ------------------------ |
| `broken_link`     | リンクの参照先ファイルが実在しない       | 参照の修正               |
| `missing_doc`     | 文書 ID に対応する文書が実在しない       | 参照の修正・除外の見直し |
| `missing_section` | 文書は実在するが、指した節が実在しない   | 参照の修正               |
| `missing_label`   | 参照リンクのラベルに定義行が無い         | 定義行の追加             |
| `ambiguous`       | 参照が一意に決まらない                   | 参照の表記を長くする     |
| `out_of_scope`    | 抽出が対応していない形（判定していない） | 人が確認する             |

**`out_of_scope` を所見なしへ畳み込まない。** 判定していないものを「問題なし」と報告すると、
見逃しがそのまま通る。

**検査した範囲がステージング済みまでであることを、報告に必ず添える。** 検査は git の index を読むため、
`git add` していない変更は対象に入らない。「検査を通した」が「手元のすべてを検査した」を意味しない。

**このスキルは commit を作る前に走らせるのが本来の位置である。** 参照切れの修復には「この ID は書式例か」
「節がどこへ移ったか」の判別が要り、それを安く行えるのは変更を行った主体が文脈を保っている間だけである。
文脈が失われた後に検出しても、判別をやり直すことになる。

所見が出た場合、**修正はこのスキルでは行わない**。何をどう直すべきかの候補を述べるまでに留め、
実施は利用者の指示を待つ。

## 禁止事項 [MANDATORY]

| 禁止                                           | 理由                                               |
| ---------------------------------------------- | -------------------------------------------------- |
| 参照の修正・ファイルの編集                     | 検出と修正は別である。修正は利用者の指示で別途行う |
| 終了コード `2`（検査失敗）を所見なしとして扱う | 検査を通した事実が何も保証しなくなる               |
| `out_of_scope` を報告から落とす                | 判定していないものが「問題なし」に見える           |
| 走査対象・索引対象のパスを推測して書く         | `.doc_structure.yaml` の解決結果と食い違う         |
| 検査対象を AI が独断で広げる・狭める           | 生成物や履歴の記録が混ざる／見落とす               |
