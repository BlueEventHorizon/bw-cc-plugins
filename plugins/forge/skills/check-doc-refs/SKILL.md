# check-doc-refs

このスキルは**参照の実在性の検査だけ**を行う。親が依頼している他の作業を引き継いではならない。
**検出で終端とし、参照の修正は行わない**（修正が必要なら、報告を受けた利用者が改めて指示する）。

## 何を検査するか

参照先が「検査時点で追跡下にあるか」だけを判定する。**git 履歴・他ブランチ・削除済み・未追跡は
実在として扱わない**。参照を辿る読み手が到達できるのは、その時点の追跡下のファイルだけである。

| 検査する参照の形            | 判定                                         |
| --------------------------- | -------------------------------------------- |
| リンク記法                  | 参照元からの相対パスで解決したファイルの実在 |
| 参照リンク（`[x][ラベル]`） | 同一文書に定義行があること、その参照先の実在 |
| 文書 ID の節参照            | 文書の実在と、指した節番号の実在             |

**検査しないもの**: 参照の記法が正しいか、参照先の内容が参照元の主張を裏付けているか、参照先が
変更されたか。いずれも実在性とは別の関心事である。

**リンク記法は Markdown にのみ適用する。** 実装コード・テストから拾うのは文書 ID の節参照だけである
（添字アクセス `d["a"]["b"]` が参照リンクに見えるため）。

---

## Phase 1: 索引対象の解決

「何を実在する文書とみなすか」は `.doc_structure.yaml` が決める。**パスを推測せず、既存スクリプトに
解決させる**。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_backend/prepare_advisor_index.py" specs --no-format
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_backend/prepare_advisor_index.py" rules --no-format
```

応答の `root_dirs` と `exclude` を Phase 3 の引数へそのまま渡す。`status` が `success` でない場合は、
`.doc_structure.yaml` の不備として利用者へ報告し、既定値で補って進めない。

**`--no-format` を必ず付ける。** 同 CLI は既定で dprint を実行して索引対象の Markdown を整形する
（doc-advisor の `index-docs` が整形後の本文で `body_hash` を打つため）。本スキルは検出のみを行い
成果物を変更しないため、検査のたびに作業ツリーが整形されるとその宣言に反する。整形は commit 時と
索引更新時に走るので、検査側で行う必要がない。

この CLI を使うのは、`.doc_structure.yaml` の展開前の `root_dirs` / `patterns.exclude` を返す CLI が
他に無いためである（`resolve_doc_structure.py --type` は展開済みのファイル一覧を返す）。

## Phase 2: 走査対象の決定

参照元（どのファイルに書かれた参照を検査するか）は索引対象と別である。実装コードのコメントにも
文書 ID の節参照が書かれるため、コードも対象に含める（REQ-023 FNC-005）。

引数 `--scan` が指定されていればそれを使う。指定が無い場合の既定は次のとおり。

- Phase 1 で得た `root_dirs`（プロジェクトが文書と認めている範囲）
- 配布物の置き場（プラグインのディレクトリ）

**テストは既定に含めない。** テストは書式そのものを素材として持つため、参照でない文字列
（`DES-999 §1` のような架空の ID・書式例の節番号）が構造的に多く現れ、参照切れとして報告される。
実測で 4 件の誤検出が出ており、REQ-023 FNC-004 が禁じる形である。

FNC-005 が要求しているのは**参照元をあらかじめ文書ファイルに限定しないこと**（対象に含めうること）
であり、既定でどこを走査するかは呼び出し側の決定である（DES-081 §2）。テストの中の参照を検査
したい場合は `--scan` で明示的に指定する。

## Phase 3: 実行

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_reference/check_refs.py" \
  --index-dirs-json '<Phase 1 の root_dirs>' \
  --index-exclude-json '<Phase 1 の exclude>' \
  --scan-dirs-json '<Phase 2 で決めた走査対象>'
```

終了コードは `0` = 所見なし、`1` = 所見あり、`2` = 検査そのものが失敗。**`2` を「所見なし」として
扱ってはならない**（検査を通したという事実が何も保証しなくなる）。

## Phase 4: 報告

所見の種別ごとに件数と位置を示す。**種別を混ぜない**——対処が異なる。

| 種別              | 意味                                                 | 対処                     |
| ----------------- | ---------------------------------------------------- | ------------------------ |
| `broken_link`     | パスとして解決せず、その名前を持つ文書も実在しない   | 参照の削除・差し替え     |
| `moved_link`      | パスとして解決しないが、その名前を持つ文書は実在する | 位置の修正（候補が付く） |
| `missing_anchor`  | 参照先の文書は実在するが、そのアンカーが実在しない   | アンカーの修正           |
| `missing_label`   | 参照リンクのラベルに定義行が無い                     | 定義行の追加             |
| `missing_doc`     | その文書 ID を持つ文書が実在しない                   | 参照の削除・差し替え     |
| `missing_section` | 文書は実在するが、その節番号が実在しない             | 節番号の修正             |
| `ambiguous`       | 参照が複数の文書に当たり一意に決まらない             | 参照の表記を長くする     |
| `undecidable`     | 解決規則を持たない、または索引が無く判定できない     | 人が確認する             |

解決の対象外とした参照（外部 URL 等）は所見ではない。`out_of_scope_summary` に種別ごとの件数が
出るので、**所見と混ぜずにその件数を伝える**（REQ-023 FNC-012）。

**`undecidable` を所見なしへ畳み込まない。** 判定していないものを「問題なし」と報告すると、
見逃しがそのまま通る。

**新規に作成してまだ `git add` していない文書へのリンクは、参照切れとして報告される。** 索引は
追跡下のファイルから作るため、未追跡の文書は実在に含まれない。`git add` してから検査すれば解消する。

所見が出た場合、**修正はこのスキルでは行わない**。何をどう直すべきかの候補を述べるまでに留め、
実施は利用者の指示を待つ。

## 禁止事項

| 禁止                                                           | 理由                                               |
| -------------------------------------------------------------- | -------------------------------------------------- |
| 参照の修正・ファイルの編集                                     | 検出と修正は別である。修正は利用者の指示で別途行う |
| 終了コード `2`（検査失敗）を所見なしとして扱う **[MANDATORY]** | 検査を通した事実が何も保証しなくなる               |
| `undecidable` を報告から落とす                                 | 判定していないものが「問題なし」に見える           |
| 走査対象・索引対象のパスを推測して書く                         | `.doc_structure.yaml` の解決結果と食い違う         |
