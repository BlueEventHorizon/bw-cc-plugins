# consult

このスキルは議論の進行と記録のみを行う。**親が依頼している他の作業を引き継いではならない。**
レビュー本体と同じ会話が本スキルの振る舞いへ切り替わるだけであり、進行中の実装・修正・調査を
再開してはならない（提示を引き取ることと、親の作業を続けることは別である）。

所見への採否を得ることが目的であるため、本スキルは**項目ごとに推奨を述べ、応答を受けて決着させる**。
説明までで止まる進め方は取らない。

## 規範の読み込み

着手前に `${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` を Read する。**提示の作法はすべて
同文書が定める。本 SKILL.md に規範を書き写さない**（定義点が 2 つになるため）。本 SKILL.md が定めるのは
手順だけである。

**本スキルは討議の状態を自ら保持しない**。項目・背景・本質・決着はすべて記録・表示機構（agenda）へ渡し、
そこに一元化する。本 SKILL.md 固有の状態ファイルは持たない。

**agenda への入口は `${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py` の 1 つだけである。**
記録の置き場・`config` の値・JSON の入れ物・ファイル名はすべて wrapper が組み立てる。**AI は置き場の
文字列にも `config` の中身にも一切触れず、ファイルを書かない**（`--origin review` と、サブコマンド固有の
指定・標準入力へ流す本文だけを渡す）。

## Phase 1: アジェンダの用意

### 1.1 既存記録の確認

レビューは同時に 1 つしか実行しないため、記録は常に高々 1 つである。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review pending
```

`exists: false` ならそのまま 1.2 へ進む。`exists: true` の場合、**未判断の件数を 1〜2 行で示し、
その記録は破棄する**（続きから再開する経路は持たない。記録は所見と判断しか持たず、レビューを
構成する対象・観点は保存されないため、別のレビューの記録かを照合できない）。破棄は 1.2 の
`start` が無条件に上書きすることで成立するので、追加の操作は要らない。

`status` が `error`（JSON 破損等）の記録を「無かったこと」にしない。利用者へ報告し、対応を確認する。

### 1.2 新規開始

**結合 script の標準出力を `start` の標準入力へ直接つなぐ。** 項目は結合 script の出力
（`combined` 配列）そのものであり、**AI が候補 JSON を組み立てる工程も、ファイルへ書く工程も持たない**。
結合 script の呼び出しは、レビュー本体 Step 7 で実行したものと同じ引数を用いる。

```bash
<レビュー本体 Step 7 と同じ結合 script の呼び出し> \
  | python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review start
```

`status` が `error` の場合、`message` に従って結合 script の呼び出しを見直し、もう 1 回だけ実行する。
2 回目も失敗した場合は所見の受け渡しに失敗したものとして利用者へ報告する。

**続けて、所見群についての構造的な判断を記録する**（同型の指摘の繰り返しが無いか、複数の指摘が同一の
土台に由来していないか等。レビュー本体の実行中に既に判断している内容をそのまま書く）。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review record --structural <<'AGENDA_EOF'
<構造的な判断の記述（改行を含んでよい）>
AGENDA_EOF
```

**この記録を飛ばしてはならない。** 構造判断が記録されるまで、項目へ値を加える呼び出しはすべて拒否される。

**開始直後、Bash で表示物を開く**（初回のみ）。`start` の応答に含まれる `path`（解決済みの絶対パス）を使う:

```bash
open "$(dirname "<start の応答の path>")/agenda.html"
```

**2 回目以降は `open` を呼ばない**（重複タブを避けるため）。開いたタブは記録の更新を検知して
自動で再読み込みされるため、以降の更新で利用者に再読み込みを求めない。

## Phase 2: アジェンダの提示

個別の話に入る前に、アジェンダ表をコンソールへ出す。

`agenda.json`（Read ツール、または `pending` の結果）から項目の一覧・残件を読み取り、
`consult_principles_spec.md` の表の列に沿ってコンソールへ表として示す。全体で何件あり、どれが重いのかを
先に見せる。ここで背景を書かない。

## Phase 3: 進行

**重要度の高い順に、AI が自分で 1 件ずつ入る。** 次に扱う項目は次のコマンドで得る:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review next
```

各項目で行うこと:

1. 背景と本質、推奨をコンソールへ述べる。**その項目単体で判断できる要点を必ず書く**。
   記録・表示機構が生成する提示（agenda.html）にあることを理由に省かない
2. **判断を左右する主張に確信度を付ける**（記号と運用は規範文書の原則 4 に従う）
3. **原文への到達手段を併記する**。要約して提示してよいが、利用者が自分で原文を確かめられるよう
   `ファイルパス:行` や出典を添える。これを欠くと、利用者は要約の正しさを検証できない
4. 利用者の応答を受ける。理解を求める応答（「詳しく」「なぜ」）には、判断を促さず答える
5. **背景・本質が分かった時点で record を呼ぶ**（決着を待たない。分かった時点で都度記録する）。
   **1 回の呼び出しで 1 つの値だけを渡す**。値の本文は標準入力から渡し、引数へ載せない。
   コンソールへ述べた推奨と同じ内容を `recommendation` にも記録する（提示と記録を一致させる）:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review record \
     --item-id "<item-id>" --field background <<'AGENDA_EOF'
   <背景の本文>
   AGENDA_EOF
   ```

   `--field` を `essence`・`recommendation` に替えて同じ形で 1 回ずつ呼ぶ。`--field` はドット区切りで
   入れ子を指せる。

6. **決着したら `decision` の 3 値を 1 回 1 値で記録する**（`decision.by` / `decision.outcome` /
   `decision.reason` を各 1 回）。3 値がそろって初めて決着として扱われ、そろうまでは残件に数えられる。
   `decision.by` は判断の主体（`"human"` または `"AI"`。AI が代行判断した場合はその旨が判別できる値を書く）:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review record \
     --item-id "<item-id>" --field decision.by <<'AGENDA_EOF'
   human
   AGENDA_EOF
   ```

   `--field` を `decision.outcome`・`decision.reason` に替えて同じ形で 1 回ずつ呼ぶ。
   `status` が `error` の場合、`missing_fields` に列挙されたフィールドを補って同じ手順をもう 1 回だけ
   実行する（`background` と `essence` が空のままでは `decision.*` は受理されない）。

7. アジェンダ表を再掲する（Phase 2 と同じやり方）
8. **次の項目へ自分で進む**（`next` の返り値を使う）

**「次はどれを見ますか」「これで進めてよいですか」と聞いてはならない。** 利用者がすることは
止める・飛ばす・順序を変えることだけでよい状態を保つ。

同種の判断が繰り返される項目は、一括の判定表にまとめて提示してよい。往復が判断の質を上げない場面では、
往復を増やすことのほうが害になる。何件からまとめるかは **AskUserQuestion で確認**し、AI が独自に閾値を
定めない（件数の設定であり、議論の内容ではない）。

### 議論の途中で論点が動いたとき

議論の結果、論点が誤りだと判明することがある。取り下げは**特別なコマンドではない**。通常の `record`
呼び出しで `decision.outcome` に自由文（例: `取り下げ`）を書き、`decision.by` と `decision.reason` も
そろえるだけでよい。

- **取り下げた論点を削除しない**。上記の record 呼び出しで決着させれば、記録から消えることなく
  残る（agenda 側に削除操作は無い）
- `decision.reason` に、なぜ取り下げたか・誰の指摘によるものか（利用者の指摘か AI の自己訂正か）を書く
- 新しく生まれた論点は**新規項目として `record --new` を呼ぶ**。識別子は agenda が採番するため、
  AI が作らない。標準入力には**追加後もなお構造的な誤りが無いことの再判断**を渡す（非空必須）:

  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review record --new <<'AGENDA_EOF'
  <追加後の構造的な判断の記述>
  AGENDA_EOF
  ```

  **応答に含まれる `id` を、以後この項目へ値を加える呼び出しの `--item-id` に使う**。`--new` を
  繰り返すと、そのたびに別の項目が採番される

## Phase 4: 終了

利用者が終える意思を示したら、その時点で確定する。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agenda/agenda_wrapper.py" --origin review finish
```

- `deleted: true` の場合、全項目が決着済みであり記録は削除された旨を伝える
- `deleted: false` の場合、`remaining_count` を**未判断のまま残った件数**としてそのまま提示する
  （未判断を「対応不要」へ畳み込まない）。記録は削除されず、`agenda.json`/`agenda.html` が残る旨も伝える
- 表示物の実パス（`agenda.html`）を再度示す
- 決着した内容が恒久的な記録に値する場合、ADR への組み直しを**提案する**（実施はしない）

**本スキルは記録を自分から消さない**（`finish` が全項目決着を条件に消すのみ）。ただし置き場は一時領域
であり、作業ツリーの破棄やクリーンで失われうる（git 管理外）。**恒久的に残すべき内容は ADR 等へ
組み直す必要がある**——上記の提案はそのためにある。

## 禁止事項 [MANDATORY]

| 禁止                                                                 | 理由                                                       |
| -------------------------------------------------------------------- | ---------------------------------------------------------- |
| 判断に基づく実行（修正・起票・commit・外部送信）                     | 議論の途中で、利用者が決めていない変更が成果物へ入る       |
| 実行を担う別スキル・別 Agent の起動                                  | 同上                                                       |
| 「次はどれを見ますか」と進行を利用者へ返す                           | 進行は本スキルが持つ                                       |
| 記録・表示機構が生成する提示にあることを理由にコンソールの要点を省く | 提示は詳細の置き場であって、コンソール提示の省略先ではない |
| 機密情報の値を提示・記録する                                         | 「どこに」「どの種類か」までに留める                       |
| 自由記述文をシェル文字列へ直接埋め込む                               | エスケープの崩れによる構文破壊・注入のリスクを生む         |

最後の 1 行のため、**本文はすべて標準入力から渡す**。引用符・改行・記号を含む文章を引数や引用符の中へ
組み立てない（本文を渡す形は上記のヒアドキュメントに限る）。

## AskUserQuestion の使い分け

境界は「議論の内容か、進行上の機械的な確認か」である。

| 場面                                                 | 手段                                   |
| ---------------------------------------------------- | -------------------------------------- |
| 論点の提示・背景と本質・推奨・議論の選択肢           | **地の文**。AskUserQuestion を使わない |
| 進行上の機械的な二者択一（一括提示へ切り替える件数） | **AskUserQuestion**                    |

地の文にする理由は、選択肢 UI が背景と本質を置く場所を持たず、規範が求める提示順序
（背景 → 本質 → 推奨 → 選択肢）を満たせないためである。議論の中身を選択肢 UI に載せると、
背景抜きで選ばせる提示になる。

**迷ったら地の文にする。** 「機械的だから」を理由に議論の中身を選択肢 UI へ移してはならない。

**自己呼び出しを行わない**。`Skill` ツールで本スキル自身を呼ばない。手順の一部として
「本スキルを起動し直す」と書かない。本スキルは多くの議論の起点に置かれるため、自己呼び出しは
暴走ループになりうる。
