# 実装戦略策定仕様書

このファイルは、`plan-strategist` カスタム Agent の処理手順である。役割・制約・必読文書は
[agents/plan-strategist.md](../agents/plan-strategist.md) が定める。

agent はこのファイルを読み、要件定義書・設計書・既存実装を分析し、実装戦略を策定して
結果を **return value (markdown 全文) として返却**する。ファイルへの書き出しは行わない。

---

## 入力パラメータ

オーケストレータ（start-plan）から agent に以下のパラメータが渡される:

| パラメータ         | 必須 | 説明                                         |
| ------------------ | ---- | -------------------------------------------- |
| `feature`          | ○    | 対象 Feature 名                              |
| `requirement_docs` | ○    | 要件定義書のファイルパス配列                 |
| `design_docs`      | ○    | 設計書のファイルパス配列                     |
| `rules_docs`       | -    | プロジェクト固有ルール文書のファイルパス配列 |

```yaml
feature: "<feature>"
requirement_docs:
  - docs/specs/<feature>/requirements/REQ-001_<name>_spec.md
design_docs:
  - docs/specs/<feature>/design/DES-001_<name>_design.md
rules_docs:
  - docs/rules/architecture.md
```

## 前提

- `requirement_docs` と `design_docs` にそれぞれ少なくとも1つのパスが含まれること
- 要件定義書・設計書は Read して全文を把握すること（部分読みは禁止）
- `rules_docs` が空またはなしの場合は、プロジェクト固有制約なしとして続行

---

## 処理手順

### Step 1: 要件定義書・設計書の全体構造分析

`requirement_docs` と `design_docs` に含まれる全文書を Read し、以下を把握する:

- この feature が何を実現するのか（要件定義書）
- モジュール数と各モジュールの責務
- モジュール間の依存関係（依存グラフの形状）
- 技術的な複雑度（新規技術の採用、外部サービス連携等）
- テスト設計の有無と範囲

あわせて、**この feature が差分開発型か純粋追加型かを判定する**。要件定義書・設計書の
frontmatter に `feature_type: temporary-feature` があれば差分開発型である。判定基準は
[additive_development_spec.md](additive_development_spec.md) §0 に従う。

- **差分開発型** → Step 2 へ進む
- **純粋追加型・初回立ち上げ** → Step 2 を飛ばし Step 3 へ進む（既存実装との不一致が存在しない）

### Step 2: 既存実装との不一致の分析（差分開発型のみ）

差分開発では、新しい要件・設計に対して既存実装が古い状態にある。**その不一致を洗い出し、
各々に何をするかを決める**のが本 Step である。

旧仕様の設計書ではなく **既存実装（コード）を対象とする**。実装が旧仕様の実体であり、
旧仕様の文書は実装期間中に書き換えないため（[additive_development_spec.md](additive_development_spec.md) §3）、
戦略が相手にするのはコードである。

#### 2.1 対象の特定

新しい要件定義書・設計書が触れている範囲の既存実装を特定する。設計書の「使用する既存
コンポーネント」欄にファイルパスがあればそれを起点とし、そこから参照を辿って範囲を広げる。
起点が得られない場合は、設計書のモジュール名・クラス名を手掛かりに Grep / Glob で探索する。

#### 2.2 不一致の洗い出し

特定した既存実装を Read し、新しい要件・設計と食い違う箇所を列挙する。列挙は
**タスク（作業単位）ではなく事実**である。「どのモジュール・クラス・ファイルが、
新仕様のどの記述と、どう食い違っているか」を書く。

#### 2.3 処置の決定

各不一致に対して、次のいずれかの処置を決める。

| 処置         | 適用する状況                                             |
| ------------ | -------------------------------------------------------- |
| **修正**     | 既存の実体を残したまま、新仕様に合わせて中身を直す       |
| **削除**     | 既存の実体が不要になる。新しい実体がその役割を引き取る   |
| **新規作成** | 既存のどこにも受け皿がない。新しいファイル・クラスを作る |
| **統合**     | 複数の既存の実体が、新仕様では 1 つになる                |
| **分割**     | 1 つの既存の実体が、新仕様では複数に分かれる             |

**どの処置を選ぶかの判断基準は定めない。** 新仕様と既存実装を読んだうえで判断する。
「既存があるから修正で済ませる」という惰性で決めないこと。全面的に作り直すほうが
正しい場合がある。

#### 2.4 旧実装を残す必要があるかの判定

処置が「削除」となる実体について、**本 feature の外**（他の呼び出し側・並行して進む
別 feature）がその動作に依存していないかを確認する。依存があり同時に壊せない場合に限り、
旧実装を残し、**依存が解消された時点で削除する**（[additive_development_spec.md](additive_development_spec.md) §3.1）。
その時点をどのフェーズに置くかは Step 5 で決める。

依存が無いなら残さない。使われない実装が残ると、次の実装者がどちらを正しいものとして
読むか判断できなくなる。

### Step 3: リスク分析

設計書の内容から技術的リスクを抽出する:

| リスクカテゴリ     | 着目点                               |
| ------------------ | ------------------------------------ |
| 技術的不確実性     | 未検証の技術・アルゴリズム・外部 API |
| 依存の複雑性       | 循環に近い依存、深いネスト           |
| インテグレーション | 複数モジュールの結合点               |
| データ整合性       | スキーマ変更、マイグレーション       |
| パフォーマンス     | 大量データ処理、リアルタイム性要求   |

### Step 4: アプローチ選択

設計書の特性とリスク分析に基づき、実装アプローチを選択する。
複数の組み合わせも可。選択の根拠を必ず記述すること。

| アプローチ           | 概要                          | 適用場面                             |
| -------------------- | ----------------------------- | ------------------------------------ |
| ボトムアップ         | 基盤層→上位層の順に積み上げ   | 安定した基盤が必要な場合             |
| スケルトン先行       | stub で全層を通す→肉付け      | 早期 E2E 検証が重要な場合            |
| リスク駆動           | 不確実性の高い部分から着手    | 技術的リスクが大きい場合             |
| フィーチャースライス | 最小機能セットを縦断実装→拡張 | 早期デモ・フィードバックが必要な場合 |

**選択の判断基準**:

- モジュール間依存が深い → ボトムアップ
- 結合テストが重要 → スケルトン先行
- 未検証技術を含む → リスク駆動
- ユーザーフィードバックが必要 → フィーチャースライス

### Step 5: フェーズ分割

実装全体を **2〜4 フェーズ**に分割する。各フェーズについて以下を定義:

- **目標**: このフェーズ完了時に何が動作するか（具体的な検証可能条件）
- **スコープ**: 対象とするモジュール・コンポーネント（設計書のセクション参照）
- **検証ポイント**: フェーズ完了時に確認すべき事項（ビルド・テスト・動作確認）

**フェーズ分割の原則**:

- 各フェーズは独立して検証可能な成果物を持つこと
- フェーズ間の依存は一方向（フェーズ N+1 はフェーズ N の成果物に依存してよい）
- 最初のフェーズにリスクの高い要素を含めること（手戻りの早期検出）
- フェーズ内が複数タスクの構造移設・新規モジュール作成で構成される場合、最後のタスクまで検証を先送りしないこと（最小の動作確認可能な単位＝多くはグループ内の最初の1〜2タスクの完成時点で検証ポイントを設ける）

**差分開発型の場合**: Step 2 で決めた処置をフェーズへ割り当てる。Step 2.4 で「依存が解消
されるまで残す」と判定した旧実装については、**どのフェーズで依存が解消し、どのフェーズで
削除するか**を明示する。削除時期を merge に紐づけない（merge は文書の齟齬を解消する作業であり、
コードの後始末を含まない）。

### Step 6: 戦略書の出力

以下のテンプレートに従い、戦略書 markdown を **return value として返却**する。ファイルへは書き込まない。

---

## 出力テンプレート

差分開発型でない場合、「既存実装との不一致」節は書かない（空の節を残さない）。

```markdown
# {feature} 実装戦略

## 既存実装との不一致

<!-- 差分開発型の場合のみ。純粋追加型・初回立ち上げでは本節ごと書かない -->

| 既存実装                       | 新仕様との食い違い           | 処置                                   |
| ------------------------------ | ---------------------------- | -------------------------------------- |
| {ファイル・クラス・モジュール} | {どの記述と、どう食い違うか} | {修正 / 削除 / 新規作成 / 統合 / 分割} |

**方針**: {個々の処置から見えてくる全体の方針。例「この機能は既存の構造では成立しないため
新規に作る」「これらは既存コードを全面的に置き換えるので、削除したうえで作り直す」}

**依存により残す旧実装**: {Step 2.4 で残すと判定したもの。無ければ「なし」}

## アプローチ

**選択**: {選択したアプローチ名}

**根拠**:

{なぜこのアプローチが最適か。設計書の特性との対応を記述}

## フェーズ

### フェーズ 1: {名前}

- **目標**: {完了時に何が動作するか}
- **スコープ**: {対象モジュール — 設計書のセクション参照}
- **検証ポイント**: {ビルド成功 / テスト通過 / 特定シナリオの動作確認}

### フェーズ 2: {名前}

- **目標**: ...
- **スコープ**: ...
- **検証ポイント**: ...

(フェーズ 3, 4 は必要に応じて追加)

## リスクと対策

| リスク | 影響度 | 対策（どのフェーズで潰すか） |
| ------ | ------ | ---------------------------- |
| ...    | ...    | ...                          |
```

---

## プロジェクト固有ルールの適用

`rules_docs` が渡された場合、以下の観点でルールを戦略に反映する:

- アーキテクチャルール（レイヤー構造、依存方向）→ フェーズ分割の制約
- テストルール（カバレッジ要件、テスト種別）→ 検証ポイントに反映
- コーディング規約 → 戦略への直接影響は少ないが、リスク判断の参考

---

## エラー時の振る舞い

- 設計書の Read に失敗した場合: エラー内容を orchestrator に報告し終了
- 設計書が不完全（モジュール一覧なし等）の場合: 読み取れる情報のみで戦略を策定し、不足事項を戦略書内に明記
- フェーズ分割が困難な場合（設計が単純で2フェーズ未満）: 「単一フェーズ（一括実装）」を明示し、理由を記述
