# ADR（アーキテクチャ決定記録）デフォルトフォーマット

プロジェクト固有の「ADR フォーマット」が見つからない場合に使用する汎用フォーマット。

作成トリガー（どのようなときに ADR を作成・更新するか）: [adr_principles_spec.md](adr_principles_spec.md)「書く対象・書かない対象」
運用（目的・書く対象・可変性・失効の扱い・棄却理由の書き方・読み手の義務）: [adr_principles_spec.md](adr_principles_spec.md)（**本ファイルは記法のみを定める**）
違反時の severity: [adr_principles_spec.md](adr_principles_spec.md) 重大度カタログを参照（本ファイルは severity を宣言しない）

---

## ファイル命名規則・配置

```
ADR-{NNN}_{topic}.md
```

- 設計書と同じディレクトリに配置する（ADR 専用ディレクトリは作らない）
- ID は手動で決めず、必ず `next-spec-id` スキルで採番する（`python3 scan_spec_ids.py ADR --share-prefixes ADR,DES`）。ADR と DES は同一ディレクトリで通し番号を共有するため `--share-prefixes ADR,DES` を必ず付与する

例: `ADR-032_path_schema_unification.md`

## 節の構成 [MANDATORY]

ADR の `##` 見出しは **`## 1. コンテキスト` / `## 2. 決定` / `## 3. 検討した代替案` / `## 4. 影響` の 4 つで固定**する。メタデータ表・ステータス履歴・関連文書一覧といった節を追加しない。

`###` 小節は**必ず親節の番号を継ぐ**（`### 2.1 …` / `### 4.1 …`）。番号を持たない `###` を作らない。

番号を要求する理由は 2 つある。**失効マーカーは節見出しに付ける**ため、宛先となる見出しが識別子を持っていなければならない。また `ADR-NNN §X.Y` 形式の外部参照が成立するのも番号があるときだけである。

節番号は一度付けたら**変えない**（外部参照が宛先を失う）。小節を後から足す場合は末尾に追加する。

### 旧書式の見分け方

本書式より前に作られた ADR は、次のいずれかを含む。これらは本書式の節ではない。

- `## メタデータ` 表
- `## 5. ステータス履歴` 節
- 番号を持たない `###` 小節

本書式へ合わせる手順は [adr_principles_spec.md](adr_principles_spec.md)「旧書式からの移行」に従う（本ファイルは記法のみを定める）。

## スコープ欄

H1 の直後、`## 1. コンテキスト` の前に引用ブロックで置く。**任意の要素**であり、書く条件は [adr_principles_spec.md](adr_principles_spec.md)「スコープ欄を書く条件」が定める。

```markdown
# ADR-XXX {決定のタイトル}

> **本文書のスコープ**
>
> - **定めること**: {この ADR が決定する範囲}
> - **定めないこと**: {隣接するが本 ADR の決定ではない事柄。どこが定めるかを示す}
> - **{隣接文書} との関係**: {置き換えるのか並立するのか}

## 1. コンテキスト
```

- `定めること` と `定めないこと` は**対で書く**。片方だけでは範囲の境界が引けない
- 第 3 項（隣接文書との関係）は任意である
- 節にしないのは、`## 1.`〜`## 4.` の 4 節構成を崩さないためである。スコープに節番号を与えると固定の節数が変わる
- **参照はマークダウンリンクで書く**。ID だけを書いて参照の代わりにしない（[adr_principles_spec.md](adr_principles_spec.md)「書く対象・書かない対象」）
- スコープ欄以外の引用ブロックをこの位置に置かない。決定の失効は失効マーカーで、決定の根拠は `## 1.`〜`## 4.` で表す

## 失効マーカー [MANDATORY]

決定が**別の ADR によって覆された**とき、該当する節の見出し末尾にマーカーを付ける。

```markdown
### 2.3 履歴復元を契約表へ明記する ⚠️失効（ADR-071 が任意拡張へ変更）
```

- **無印が有効**を意味する。有効な節に印は付けない
- 括弧内には**どの ADR が覆したか**を書く。本文で十分に説明されている場合は括弧を省略してよい
- 付けるのは「決定が別 ADR へ移った」場合**のみ**である。実装が変わった・古びた気がする、といった理由では付けない
- **失効した節も削除しない**。節番号も変えない
- 決定全体が覆された場合は `## 2. 決定` の見出しに付ける。**一部だけが覆された場合は該当する小節に付ける**（小節が無ければ先に小節へ分ける）
- `## 3. 検討した代替案` の表に status 列を足さない。棄却理由の失効は本文の更新で表す

## テンプレート

```markdown
# ADR-XXX {決定のタイトル}

## 1. コンテキスト

{この決定を迫られた背景・課題・制約を記述。決定の妥当性を後から再評価できる粒度で書く}

## 2. 決定

{採用した選択肢と、その決め手を記述}

{決定が複数あるなら、最初から `### 2.1` 形式の小節に分ける。置き換えは決定単位で起きるため、分けていないと後から部分失効を表せない}

## 3. 検討した代替案

| 代替案 | 棄却理由 |
| ------ | -------- |

{棄却理由は**将来その案が再提案されるときの語彙**で書き、**判断が依拠している前提を明示する**。当時の実装の語彙だけで結論を書くと、同じ案が別の言い方で提案されたときに突き合わせられず、前提が変わったかどうかも読み手が判定できない}

## 4. 影響

{この決定による帰結。得られるもの・失うもの・新たに生じる制約を正負両方記述}

**変更対象ファイルの具体パス列挙はここに書かない**。「どのファイルをどう変更するか」は決定そのものではなく実装計画の責務であり、ADR に書くと後のファイル移動・分割で陳腐化する。実装への波及が大きい決定であることを示したい場合は、対象コンポーネント名や種別（例: 「reviewer プロンプト」「plan.yaml マージロジック」）程度の抽象度に留め、詳細は実装計画に譲る。依存する要件・設計・ADR に触れる必要があるときは、本文中で ID に言及する。
```

**メタデータ表・ステータス履歴節を持たない**。ADR ID は H1 とファイル名にあり、決定日と状態遷移は git 履歴が持ち、関連文書は本文中の ID 言及で足りる。文書単位の状態を持たないのは、置き換えが決定単位で起きるため部分失効を表せないからである（「失効マーカー」節）。
