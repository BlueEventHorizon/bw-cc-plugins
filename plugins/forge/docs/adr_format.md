# ADR（アーキテクチャ決定記録）デフォルトフォーマット

プロジェクト固有の「ADR フォーマット」が見つからない場合に使用する汎用フォーマット。

作成トリガー（どのようなときに ADR を書く・更新するか）: [adr_principles_spec.md](adr_principles_spec.md)「書く対象・書かない対象」
運用（目的・書く対象・吟味の基準・可変性・否決の書き方・配置と ID 採番）: [adr_principles_spec.md](adr_principles_spec.md)（**本ファイルは記法のみを定める**）
ADR を根拠に判断する側の義務: [adr_usage_spec.md](adr_usage_spec.md)
違反時の severity: [adr_principles_spec.md](adr_principles_spec.md) 重大度カタログを参照（本ファイルは severity を宣言しない）

---

## ファイル命名規則

```text
ADR-{NNN}_{feature}.md
```

例: `ADR-001_foo.md`

1 つの feature につき ADR ファイルは 1 つである。`{feature}` は feature 名（`-` は `_` に直す）。番号は、ファイルを最初に作るときに 1 回だけ決め、以後は変えない。

---

## ファイルの構成

ADR ファイルは、次の構成を持つ。

- `#` 見出しは、ファイルのタイトル 1 つだけである: `# ADR-{NNN} {feature} の決定記録`
- 決定ごとに `## N. {決定のタイトル}` の節を持つ。`N` は 1 から順に振る
- 各決定の節は、`### N.1 コンテキスト` / `### N.2 決定` / `### N.3 検討した代替案` / `### N.4 影響` の 4 つの小節で固定する。メタデータ表・ステータス履歴・関連文書一覧といった節を追加しない

決定を足すときは、末尾に新しい節を追加する。番号を持たない `###` を作らない。複数の決定を 1 つの節に混ぜず、決定ごとに節を分ける。

節番号は、一度付けたら**変えない**。`ADR-NNN §N` 形式の外部参照が宛先を失うためである。決定の節を削除する場合も、他の節の番号を付け替えない。

---

## スコープ欄

H1 の直後、最初の決定の節の前に引用ブロックで置く。**任意の要素**であり、書く条件は [adr_principles_spec.md](adr_principles_spec.md)「スコープ欄を書く条件」が定める。

```markdown
# ADR-XXX {feature} の決定記録

> **本ファイルのスコープ**
>
> - **定めること**: {この ADR ファイルが決定する範囲}
> - **定めないこと**: {隣接するが本ファイルの決定ではない事柄。どこが定めるかを示す}

## 1. {決定のタイトル}
```

- `定めること` と `定めないこと` は**対で書く**。片方だけでは範囲の境界が引けない
- スコープ欄以外の引用ブロックをこの位置に置かない

---

## 否決の書き方

決定が否決された（撤回・転換・訂正された）ときは、**同じ決定の節を書き直す**。別の節・別のファイルを足さない。失効を示す印も使わない。

- `### N.2 決定` を、新しい決定に書き直す
- 旧い案は、`### N.3 検討した代替案` の表の行へ移し、否決の理由を添える。旧い理由が誤りだった場合は、誤りだった旨と正しい理由を書く。前提が変わっただけの場合は、当時は妥当だったことと、変わった前提を書く
- 旧い決定の本文と、誤っていた理由は残さない
- 節番号は変えない

運用の理由は [adr_principles_spec.md](adr_principles_spec.md)「可変文書である」が定める。

## テンプレート

```markdown
# ADR-XXX {feature} の決定記録

## 1. {決定のタイトル}

### 1.1 コンテキスト

{この決定を迫られた背景・課題・制約を記述。決定の妥当性を後から再評価できる粒度で書く}

### 1.2 決定

{採用した選択肢と、その決め手を記述}

### 1.3 検討した代替案

| 代替案 | 棄却理由 |
| ------ | -------- |

{棄却理由は**将来その案が再提案されるときの語彙**で書き、**判断が依拠している前提を明示する**。当時の実装の語彙だけで結論を書くと、同じ案が別の言い方で提案されたときに突き合わせられず、前提が変わったかどうかも読み手が判定できない}

### 1.4 影響

{この決定による帰結。得られるもの・失うもの・新たに生じる制約を正負両方記述。**根拠のある帰結だけを書く**。渡された内容や読んだ文書から導けないときは、推測で埋めず「渡された内容から導ける影響は示されていない」と書く。**決定の仕組みから論理的に類推できることは、「導ける」には当たらない**。たとえば「〜へ集約したので、可読性が上がる」「〜という構造にしたので、問題を防げる」のような、達成済みの効果の言い切りは、渡された内容にその効果が明言されていない限り書かない。根拠は [adr_principles_spec.md](adr_principles_spec.md)「吟味の基準」}

**変更対象ファイルの具体パス列挙はここに書かない**。「どのファイルをどう変更するか」は決定そのものではなく実装計画の責務であり、ADR に書くと後のファイル移動・分割で陳腐化する。実装への波及が大きい決定であることを示したい場合は、対象コンポーネント名や種別（例: 「reviewer プロンプト」「plan.json マージロジック」）程度の抽象度に留め、詳細は実装計画に譲る。他の要件・設計に触れる必要があるときは、マークダウンリンクで指し、ID だけを書いて参照の代わりにしない。

## 2. {次の決定のタイトル}

### 2.1 コンテキスト

…
```

**メタデータ表・ステータス履歴節を持たない**。ADR の番号は H1 とファイル名にあり、決定日と状態の変遷は git 履歴が持ち、関連文書は本文中のリンクで足りる。文書単位の状態を持たないのは、置き換えが決定単位で起きるため、文書単位では部分的な変更を表せないからである。
