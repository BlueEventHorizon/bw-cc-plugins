# 文書スタイル指針

このプラグインが生成・更新する文書（要件定義書・設計書・計画書）の汎用記述スタイル。
プロジェクト固有のスタイル指針がある場合はそちらを優先する。

例外として §5（文書参照記法）は、上記に加えて**本プラグイン自身の配布物**（内蔵 `docs/` と
`SKILL.md` / `agents/*.md` / `commands/*.md`）の参照記法も定める。参照先の解決可能性は配布物の
内部でも成立していなければならず、規定を分ける利点が無いためである。適用範囲は §5 冒頭の系統で
区別する。

---

## 1. タグの使い方

### 1.1 種類と配置

- 種類: `[MANDATORY]` / `[CRITICAL]` / `[IMPORTANT]`（3 種）
- 配置: 見出し行の末尾、タグ前のスペースは 1 個、タグ後に余分な空白を入れない

**正しい例**:

```text
## データ削除手順 [MANDATORY]
```

**誤った例**:

```text
## データ削除手順

下記を読むこと [MANDATORY] ← タグは見出しに付ける

## データ削除手順  [MANDATORY] ← スペース 2 個

## データ削除手順 [MANDATORY]  ← 末尾に余分な空白
```

### 1.2 信号価値の維持

**タグは「希少だから効く」信号**。乱用すれば AI も人間も注意を払わなくなる。
**「すべてが MANDATORY」=「どれも MANDATORY ではない」** と等価になる。

`[MANDATORY]` を付けてよい基準（いずれか 1 つを満たすときのみ）:

| # | 基準                                              | 例                                                                         |
| - | ------------------------------------------------- | -------------------------------------------------------------------------- |
| A | 違反で不可逆な損害が発生する                      | 本番データ削除、main への force push、秘密情報の commit                    |
| B | アーキテクチャ前提が崩壊する                      | Clean Architecture のレイヤー逆参照、Actor 境界違反                        |
| C | 法的・契約的に必須                                | ライセンス表示、個人情報取扱い                                             |
| D | 取り返しがつかない判断で人間確認                  | プロジェクトファイル変更、ビルド設定変更、ブランチ削除                     |
| E | AI が高確率で間違える罠の機構が現在も成立している | 散文の網羅に依存する手順、推測で埋めたくなる欠落、露見が遅い・不可逆の失敗 |

**付けてはいけない場面**:

- 章節見出しすべてに飾りとして付与
- 「推奨」「望ましい」「ベストプラクティス」程度の事項
- 体裁・命名・プロセス整理ルール
- 上位文書で既に宣言済みの前提の再強調

**格下げと頻度**: 迷ったら `[MANDATORY]` → `[CRITICAL]` → `[IMPORTANT]` → タグなし の順で格下げ。
1 文書あたり `[MANDATORY]` は **0〜3 箇所**を目安。4 箇所以上必要に感じたら基準 A〜E に該当するか再確認する。

**判定の証拠と理由の書き方**: 基準 E の判定は、罠の機構が現在も成立しているかを当該文書と対象の読解で確認して行う。事故の実績・回数・記録の所在（本文や決定記録に事故が書かれているか）を成立条件にしない——実績は機構の実在が疑わしいときの補強証拠にとどめる。タグを付けた規範の本文に書く理由は**現在形の機構 1〜2 文**に限り、経緯・回数（「かつて〜だった」「N 度起きた」）を置かない（履歴は git が持つ。§7 と同旨）。

## 2. 見出しレベル

`#` 〜 `####` のみ使用する。`#####` 以降は使わない（4 階層を超えるなら章立てを再構造化する）。

| レベル | 用途                         |
| ------ | ---------------------------- |
| `#`    | ファイルタイトル（1 個のみ） |
| `##`   | 主要セクション               |
| `###`  | サブセクション               |
| `####` | 詳細項目                     |

---

## 3. 強調・表記

### 3.1 強調フレーズ

説明文中で重要事項を強調するときは英語フレーズを併記すると AI への伝達が確実:

- `NEVER` / `NEVER skip.` / `MUST` / `DO NOT` / `ALWAYS`

### 3.2 長音ルール

JIS Z 8301 準拠。語尾の長音は省略する:

| 正（長音省略） | 誤（長音あり） |
| -------------- | -------------- |
| ディレクトリ   | ディレクトリー |
| カテゴリ       | カテゴリー     |
| メモリ         | メモリー       |
| エントリ       | エントリー     |
| リポジトリ     | リポジトリー   |
| プロパティ     | プロパティー   |

固有名詞・フレームワーク公式名称はそのまま使用する。

### 3.3 強調記法の使い分け

- `**bold**`: 重要語句の強調
- `*italic*`: 用語の初出や参照名
- `` `code` ``: ファイル名・パス・コード片・コマンド・識別子
- GFM アラート（`> [!TYPE]`）: 本文中の特定の記述への注意喚起。詳細は 3.4

### 3.4 GFM アラート

見出しタグ（§1）とは異なる粒度で注意を喚起する手段。見出しタグは節全体の重要度（走査時に
読み飛ばしていいかの判断材料）を示すのに対し、GFM アラートは本文中の特定の記述（引用ブロックの
範囲で境界が明示される）への重み付けを示す。両者は代替関係になく併用する。

**構文**（GitHub 公式仕様）: 引用ブロックの先頭行に種別を書き、対象範囲は同じ引用ブロックが続く
行までに限る。

```markdown
> [!IMPORTANT]
> ここに重要な内容を書く。
```

**種類と意味**:

| 記法           | 意味                                                 |
| -------------- | ---------------------------------------------------- |
| `[!NOTE]`      | 補足情報。読み飛ばしてはいけない参考情報             |
| `[!TIP]`       | 役立つヒント・コツ                                   |
| `[!IMPORTANT]` | 目的達成に必須の重要情報                             |
| `[!WARNING]`   | 注意が必要な危険性・重大な結果につながりうる緊急情報 |
| `[!CAUTION]`   | 行動のネガティブな結果・リスク                       |

**短く保つ**: 引用ブロック構文は範囲を明示するが、長さまでは保証しない。数段落にわたる
アラートは見出しタグと同じ希薄化を起こす。1 ブロックは数行以内に収める。

**見出しには使えない**: GFM アラートは引用ブロック構文であり、見出し行には付けられない。
節全体の重要度は §1 の見出しタグで示す。

## 4. 構造化要素

### 4.1 コードブロック

言語指定を必ず付ける（`bash` / `yaml` / `python` / `markdown` 等）。構造説明のみで言語が無い場合は `text` を指定。

### 4.2 リスト

- 順序なし `-`: 列挙
- 順序あり `1.`: 手順・優先順位
- 入れ子は 2 階層まで（それ以上はサブセクション化する）

### 4.3 表

- 列数は 6 列以内
- 長文セルはリストや別セクションに分離
- 表セル内ではコードブロックや複数段落を使わない

---

## 5. 文書参照記法 [MANDATORY]

他文書を参照するときの規定。違反すると AI が他文書を読みに行けなくなり致命的（基準 A・E）。

参照は次の 3 系統に分かれ、系統ごとに「書くべき参照」の判定と記法が異なる。

| 系統 | 参照元                                                      | 参照先                    | 執筆者                 |
| ---- | ----------------------------------------------------------- | ------------------------- | ---------------------- |
| (1)  | 本プラグインの `docs/` 内                                   | 本プラグインの `docs/` 内 | プラグイン開発者       |
| (2)  | 本プラグインの `SKILL.md` / `agents/*.md` / `commands/*.md` | 本プラグインの `docs/` 内 | プラグイン開発者       |
| (3)  | 利用プロジェクトの文書                                      | 同じプロジェクトの他文書  | 利用プロジェクト開発者 |

系統 (1)(2) は本プラグイン自身の配布物に対する規定である。系統 (3) は本プラグインが生成・更新する文書
（要件定義書・設計書・計画書）と、それらが参照するプロジェクト側の文書に対する規定である。

### 5.1 パス表記

**系統 (1): `docs/` 内の文書から `docs/` 内の他文書を参照する場合**:

- 参照元ファイルの配置を起点とした相対パスで、Markdown リンク構文を使う: 同一ディレクトリの
  兄弟ファイルなら `[design_format.md](design_format.md)`、サブディレクトリ配下から `docs/`
  直下の文書を参照する場合は `[review_priorities_spec.md](../review_priorities_spec.md)` の
  ように `../` で辿る
- 地の文でのファイル名のみの言及（リンク構文なし）は使わない。曖昧さを避け、人間が読んだ
  ときにもクリック可能にするため

**系統 (2): `SKILL.md` / `agents/*.md` / `commands/*.md` から `docs/` 内の文書を参照する場合**（これらは
`docs/` の外側にあり、相対パスでは誤った場所を指す）:

- フルパスで記述する: `${CLAUDE_PLUGIN_ROOT}/docs/design_format.md`
- 同一段落内で複数回参照する場合のみ 2 回目以降をファイル名のみに省略可
- 表セル内では省略しない（セル単位で完結させる）

`${CLAUDE_PLUGIN_ROOT}` は SKILL/agent/command が実際に起動されコンテキストへ注入される経路
でのみ実パスへ置換される。`docs/` 内の文書同士は起動を経由せず直接 Read されることが多い
（プラグイン開発・レビュー・監査作業）ため、`docs/` 内部の参照にこのプレースホルダーを
使うと、置換されないまま生の文字列として残り実体解決の手間が生じる。

**系統 (3): 利用プロジェクトの文書から同じプロジェクトの他文書を参照する場合**:

参照先が ID 体系を持つかどうかで分かれる。

- **ID を持つ文書**（`{ID}_{name}` 形式で命名される要件定義書・設計書・ADR 等）: 本文が指す対象の
  識別子として ID を書くのは参照リンクではなく、そのまま書いてよい。参照先を**実際に読ませる**必要が
  ある場合のみ、Markdown リンクを併記する
- **ID を持たない文書**（プロジェクトのルール文書・ワークフロー定義・書式定義等）: 参照手段がパスしか
  ない。参照元ファイルの配置を起点とした相対パスで、Markdown リンク構文を使う

どちらの場合も、**リンクとして到達できること**（人がクリックで飛べ、AI が検索を経ずそのまま Read
できること）を優先する。地の文でのパス直書き（コードスパン表記を含む）・リンクなしのファイル名のみの
言及は使わない。

相対パスが参照元の移動で壊れる問題には **reference-style link** で対処する。本文には `[表示名][ラベル]`
だけを書き、`[ラベル]: <相対パス>` の定義を文書末尾に集約する。パスの出現が文書内の 1 箇所に集まるため、
移動・改名時に直すのは定義行だけで済む。単発の参照でも用いてよい。

プロジェクトルート起点の絶対パスをコードスパンで書く方式は**採らない**。参照元の移動に強いという利点は
あるが、リンクとして到達できず、読み手が実体へ辿り着く手間を負う。§5 冒頭が示すとおり、到達できない
ことが最大の損失である。参照元の移動には reference-style link で対処する。

> reference-style link のラベル定義は、§8 が禁じる「関連文書セクション」ではない。§8 が禁じるのは
> 本文から参照されていない文書をリスト形式の節に列挙することであり、ラベル定義は本文中の参照そのもの
> （見出しを持たない定義行）である。同じ理由で、上記の「地の文でのパス直書き」にも当たらない——
> ラベル定義に現れるパスは、本文中のリンクが解決する先を書いた**リンク構文の一部**である。

### 5.2 例

```markdown
<!-- 系統 (1): docs/ 内の同一ディレクトリから兄弟ファイルを参照する場合 -->

設計書のテンプレートは [design_format.md](design_format.md) を参照する。

<!-- 系統 (1): docs/ 内のサブディレクトリ配下から docs/ 直下の文書を参照する場合 -->

このレビュー基準は [review_priorities_spec.md](../review_priorities_spec.md) に従う。

<!-- 系統 (2): SKILL.md / agents / commands から docs/ を参照する場合 -->

設計書のテンプレートは `${CLAUDE_PLUGIN_ROOT}/docs/design_format.md` を参照する。
`design_format.md` 内の書式定義に従うこと。

<!-- 系統 (3): ID を持つ文書への参照（識別子としての言及。リンクは不要） -->

判定の閾値は DES-001 が定義する Foo 構造に基づく。

<!-- 系統 (3): ID を持つ文書への参照（実際に読ませる必要があるためリンクを併記） -->

境界値の根拠は [DES-001_<name>_design.md](../design/DES-001_<name>_design.md) §3.2 にある。

<!-- 系統 (3): ID を持たない文書への参照（reference-style link） -->

命名は [bar_rules.md][bar-rules] §2 に従う。

[bar-rules]: ../../<rules-dir>/bar_rules.md
```

## 6. 抽象例の命名

ルール文書や指針文書に登場する例文・コード例では、特定プロジェクトを連想させる固有名を使わない:

- 推奨: `Foo` / `Bar` / `Hoge` / `Fuga` + 型サフィックス（`FooService`、`BarRepository`、`HogeViewModel` 等）
- 非推奨: 「連絡先」「ユーザー管理」「商品カタログ」等の具体ドメイン

OS フレームワーク名（SwiftUI、UIKit、Combine 等）は固有名でも一般語として許容する。

---

## 7. 歴史的記録を置かない

文書内に「改定履歴」「変更履歴」等の履歴セクションを置かない。文書は**現在の内容**のみを記述する（要件定義書・設計書・ルール・原則文書のすべてに適用）。

- 変更の履歴は `CHANGELOG.md`（および git 履歴）を SoT とする
- 設計判断の変更（なぜ A から B に変えたか）は ADR に記録する
- **例外**: ADR は棄却の経緯（一度採って戻した事実を含む）を保持する。ただし日付と状態遷移を並べた表は ADR にも置かない（[adr_principles_spec.md](adr_principles_spec.md)）

---

## 8. 関連文書セクションを置かない

文書末尾に「関連文書」「参考文献」「See also」等の **リスト形式の節を置かない**。理由:

- **必読文書** (前提として読まないと意味が通らない) は **冒頭または本文中** で触れる。リスト末尾に置いても読まれない
- **前提ではないが関連がある文書** は `/forge:query-db-rules` / `/forge:query-db-specs` で探すべきもの。明示リンクは陳腐化するうえ、検索で代替できる
- リスト形式の関連文書節は **更新されないまま腐敗** しがち (リンク切れ・SoT 移動の追従漏れ)

### 8.1 例外

以下に限り、関連リンクを置いてもよい:

- **外部 URL** (query で取得できないもの): 公式ドキュメント・RFC・外部仕様等
- **本文中で参照済みのファイル一覧** を 1 箇所にまとめて再掲したい場合 (ただし本文中の参照を省略するのと引き換え)

> 関連リンクが必要に感じたら、まず「query で見つかるか」を確認し、見つかるなら書かない。
