# 文書スタイル指針

このプラグインが生成・更新する文書（要件定義書・設計書・計画書）の汎用記述スタイル。
プロジェクト固有のスタイル指針がある場合はそちらを優先する。

---

## 1. タグの使い方

### 1.1 種類と配置

- 種類: `[MANDATORY]` / `[CRITICAL]` / `[IMPORTANT]`（3 種）
- 配置: 見出し行の末尾、タグ前のスペースは 1 個、タグ後に余分な空白を入れない

**正しい例**:

```text
## データ削除手順 [MANDATORY]
```

**誤った例**:

```text
## データ削除手順

下記を読むこと [MANDATORY] ← タグは見出しに付ける

## データ削除手順  [MANDATORY] ← スペース 2 個

## データ削除手順 [MANDATORY]  ← 末尾に余分な空白
```

### 1.2 信号価値の維持

**タグは「希少だから効く」信号**。乱用すれば AI も人間も注意を払わなくなる。
**「すべてが MANDATORY」=「どれも MANDATORY ではない」** と等価になる。

`[MANDATORY]` を付けてよい基準（いずれか 1 つを満たすときのみ）:

| # | 基準                             | 例                                                           |
| - | -------------------------------- | ------------------------------------------------------------ |
| A | 違反で不可逆な損害が発生する     | 本番データ削除、main への force push、秘密情報の commit      |
| B | アーキテクチャ前提が崩壊する     | Clean Architecture のレイヤー逆参照、Actor 境界違反          |
| C | 法的・契約的に必須               | ライセンス表示、個人情報取扱い                               |
| D | 取り返しがつかない判断で人間確認 | プロジェクトファイル変更、ビルド設定変更、ブランチ削除       |
| E | AI が高確率で間違える既知の罠    | 過去にインシデント化した規約違反、繰り返されるリグレッション |

**付けてはいけない場面**:

- 章節見出しすべてに飾りとして付与
- 「推奨」「望ましい」「ベストプラクティス」程度の事項
- 体裁・命名・プロセス整理ルール
- 上位文書で既に宣言済みの前提の再強調

**格下げと頻度**: 迷ったら `[MANDATORY]` → `[CRITICAL]` → `[IMPORTANT]` → タグなし の順で格下げ。
1 文書あたり `[MANDATORY]` は **0〜3 箇所**を目安。4 箇所以上必要に感じたら基準 A〜E に該当するか再確認する。

---

## 2. 見出しレベル

`#` 〜 `####` のみ使用する。`#####` 以降は使わない（4 階層を超えるなら章立てを再構造化する）。

| レベル | 用途                         |
| ------ | ---------------------------- |
| `#`    | ファイルタイトル（1 個のみ） |
| `##`   | 主要セクション               |
| `###`  | サブセクション               |
| `####` | 詳細項目                     |

---

## 3. 強調・表記

### 3.1 強調フレーズ

説明文中で重要事項を強調するときは英語フレーズを併記すると AI への伝達が確実:

- `NEVER` / `NEVER skip.` / `MUST` / `DO NOT` / `ALWAYS`

### 3.2 長音ルール

JIS Z 8301 準拠。語尾の長音は省略する:

| 正（長音省略） | 誤（長音あり） |
| -------------- | -------------- |
| ディレクトリ   | ディレクトリー |
| カテゴリ       | カテゴリー     |
| メモリ         | メモリー       |
| エントリ       | エントリー     |
| リポジトリ     | リポジトリー   |
| プロパティ     | プロパティー   |

固有名詞・フレームワーク公式名称はそのまま使用する。

### 3.3 強調記法の使い分け

- `**bold**`: 重要語句の強調
- `*italic*`: 用語の初出や参照名
- `` `code` ``: ファイル名・パス・コード片・コマンド・識別子

---

## 4. 構造化要素

### 4.1 コードブロック

言語指定を必ず付ける（`bash` / `yaml` / `python` / `markdown` 等）。構造説明のみで言語が無い場合は `text` を指定。

### 4.2 リスト

- 順序なし `-`: 列挙
- 順序あり `1.`: 手順・優先順位
- 入れ子は 2 階層まで（それ以上はサブセクション化する）

### 4.3 表

- 列数は 6 列以内
- 長文セルはリストや別セクションに分離
- 表セル内ではコードブロックや複数段落を使わない

---

## 5. 文書参照記法 [MANDATORY]

他文書を参照するときの記法。違反すると AI が他文書を読みに行けなくなり致命的（基準 A・E）。
参照元が `docs/` の内側か外側かで記法を使い分ける。

### 5.1 パス表記

**`docs/` 内の文書から `docs/` 内の他文書を参照する場合**:

- 参照元ファイルの配置を起点とした相対パスで、Markdown リンク構文を使う: 同一ディレクトリの
  兄弟ファイルなら `[design_format.md](design_format.md)`、サブディレクトリ配下から `docs/`
  直下の文書を参照する場合は `[review_priorities_spec.md](../review_priorities_spec.md)` の
  ように `../` で辿る
- 地の文でのファイル名のみの言及（リンク構文なし）は使わない。曖昧さを避け、人間が読んだ
  ときにもクリック可能にするため

**`SKILL.md` / `agents/*.md` / `commands/*.md` から `docs/` 内の文書を参照する場合**（これらは
`docs/` の外側にあり、相対パスでは誤った場所を指す）:

- フルパスで記述する: `${CLAUDE_PLUGIN_ROOT}/docs/design_format.md`
- 同一段落内で複数回参照する場合のみ 2 回目以降をファイル名のみに省略可
- 表セル内では省略しない（セル単位で完結させる）

`${CLAUDE_PLUGIN_ROOT}` は SKILL/agent/command が実際に起動されコンテキストへ注入される経路
でのみ実パスへ置換される。`docs/` 内の文書同士は起動を経由せず直接 Read されることが多い
（プラグイン開発・レビュー・監査作業）ため、`docs/` 内部の参照にこのプレースホルダーを
使うと、置換されないまま生の文字列として残り実体解決の手間が生じる。

### 5.2 例

```markdown
<!-- docs/ 内の同一ディレクトリから兄弟ファイルを参照する場合 -->

設計書のテンプレートは [design_format.md](design_format.md) を参照する。

<!-- docs/ 内のサブディレクトリ配下から docs/ 直下の文書を参照する場合 -->

このレビュー基準は [review_priorities_spec.md](../review_priorities_spec.md) に従う。

<!-- SKILL.md / agents / commands から docs/ を参照する場合 -->

設計書のテンプレートは `${CLAUDE_PLUGIN_ROOT}/docs/design_format.md` を参照する。
`design_format.md` 内のメタデータセクションを必ず含めること。
```

### 5.3 参照の実在性

参照は書いた時点ではなく、**読まれる時点で解決できなければ意味がない**。記法が正しくても、参照先が
そこに無ければ AI は文書を辿れず、§5 冒頭の致命性がそのまま現実になる。

- リンク先のファイルが実在すること
- 見出しアンカー（`design_format.md#メタデータ` 形式）を付ける場合、その見出しが参照先に実在すること
- 文書・コードを移動・改名・削除したら、それを指す参照を **同じ変更の中で** 直すこと。参照元を残した
  ままの移動は、移動した本人にしか気づけない壊れ方をする

参照の実在性は記法の正しさとは独立に確認する。相対パスの階層数（`../` の個数）の誤りは記法上は正しく
見えるため、目視では通過しやすい。

### 5.4 重大度カタログ（文書参照）

§5 と §8 の違反に対する severity。レビュアーはここから finding へ転記する。

| # | 違反                                                             | severity    |
| - | ---------------------------------------------------------------- | ----------- |
| 1 | リンク先のファイルが実在しない（リンク切れ）                     | 🔴 critical |
| 2 | 移動・改名・削除した文書を指す参照が他文書に残っている           | 🔴 critical |
| 3 | `SKILL.md` / `agents` / `commands` から `docs/` を相対パスで参照 | 🔴 critical |
| 4 | 見出しアンカーが参照先に実在しない                               | 🟡 major    |
| 5 | 地の文でのパス直書き・リンクなしのファイル名のみの言及           | 🟡 major    |
| 6 | `docs/` 内部の参照に `${CLAUDE_PLUGIN_ROOT}` を使用              | 🟡 major    |
| 7 | §8 に反する関連文書セクションの設置                              | 🟢 minor    |

1〜3 を critical とするのは、いずれも **参照先へ到達できない**（AI が読みに行って失敗する）ためである。
4〜6 は到達自体は可能で、解決の手間・曖昧さが残るに留まる。

## 6. 抽象例の命名

ルール文書や指針文書に登場する例文・コード例では、特定プロジェクトを連想させる固有名を使わない:

- 推奨: `Foo` / `Bar` / `Hoge` / `Fuga` + 型サフィックス（`FooService`、`BarRepository`、`HogeViewModel` 等）
- 非推奨: 「連絡先」「ユーザー管理」「商品カタログ」等の具体ドメイン

OS フレームワーク名（SwiftUI、UIKit、Combine 等）は固有名でも一般語として許容する。

---

## 7. 歴史的記録を置かない

文書内に「改定履歴」「変更履歴」等の履歴セクションを置かない。文書は**現在の内容**のみを記述する（要件定義書・設計書・ルール・原則文書のすべてに適用）。

- 変更の履歴は `CHANGELOG.md`（および git 履歴）を SoT とする
- 設計判断の変更（なぜ A から B に変えたか）は ADR に記録する
- **例外**: ADR は棄却の経緯（一度採って戻した事実を含む）を保持する。ただし日付と状態遷移を並べた表は ADR にも置かない（[adr_principles_spec.md](adr_principles_spec.md)）

---

## 8. 関連文書セクションを置かない

文書末尾に「関連文書」「参考文献」「See also」等の **リスト形式の節を置かない**。理由:

- **必読文書** (前提として読まないと意味が通らない) は **冒頭または本文中** で触れる。リスト末尾に置いても読まれない
- **前提ではないが関連がある文書** は `/forge:query-db-rules` / `/forge:query-db-specs` で探すべきもの。明示リンクは陳腐化するうえ、検索で代替できる
- リスト形式の関連文書節は **更新されないまま腐敗** しがち (リンク切れ・SoT 移動の追従漏れ)

### 8.1 例外

以下に限り、関連リンクを置いてもよい:

- **外部 URL** (query で取得できないもの): 公式ドキュメント・RFC・外部仕様等
- **本文中で参照済みのファイル一覧** を 1 箇所にまとめて再掲したい場合 (ただし本文中の参照を省略するのと引き換え)

> 関連リンクが必要に感じたら、まず「query で見つかるか」を確認し、見つかるなら書かない。
