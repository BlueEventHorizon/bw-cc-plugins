# エラーと、エラーでないもの

## 1. 目的

「失敗したらエラー値を足す」と考えると、値は際限なく増える。増えた値の多くは、受け取る側の振る舞いを変えない。

本文書は、**何をエラーとして定義し、何をしないか**を定める。対象は、失敗を区別して伝えるあらゆる仕組みである——script の終了コード、agent が返す終了の値、要件定義書のエラーケース節、API の応答コード。値をどう表すかは対象ごとに異なり、本文書は踏み込まない。

## 2. エラーとは何か

**エラーとは、正しい状態で正しく使っていても起こりうることである。**

3 つがそろって初めてエラーとして定義する。

| # | 条件                                     | 満たさない場合                                               |
| - | ---------------------------------------- | ------------------------------------------------------------ |
| 1 | 正常な状態で起こりうる                   | 壊れた状態でしか起こらないなら、それはバグか障害である（§3） |
| 2 | 受け取る側の振る舞いが、他の失敗と変わる | 変わらないなら、値を分けても読み手の負担が増えるだけである   |
| 3 | 起こったときに、誰かが何かできる         | 誰にも何もできないなら、伝えても行動に変わらない             |

利用者が存在しないパスを指定した、指定されたブランチが無い、外部サービスが認証を拒んだ——これらはエラーである。使い方が正しくても起こり、起こったときに何をすべきかを受け取る側が判断できる。

## 3. エラーではないもの

### 3.1 バグ

**正常な状態では起こらないもの。** 配布物に含まれる固定の文書が読めない、内部で組み立てた JSON の形が壊れている、呼ぶはずの script が無い——いずれも実装か配置が誤っている。

これらにエラー値を与えてはならない。値を定義すると、**バグが運用の一部として扱われる**。起きたときに直すのではなく、値を見て振る舞いを分けることになり、壊れたまま動き続ける。

### 3.2 障害

**自分ではどうしようもないもの。** プロセスの突然の終了、ファイルシステムの破損、ディスクの枯渇、ハードウェアの故障。

これらは条件 3 を満たさない。前提が崩れた状況で、局所の値を 1 つ定義しても救えない（[scope_proportionality_spec.md](scope_proportionality_spec.md) §3 が、同じ理由でこれらへの防御実装を抑止している）。

### 3.3 判定できるもの

**失敗に見えて、実は判断の材料であるもの。** 所見が指すファイルが存在しないとき、それは「読めなかった」のではなく「その所見は成立しない」という判定である。

エラーにすると、判定できるはずのものが処理の中断になる。**まず判定できないかを確かめてから、エラーにするかを決める。**

## 4. エラーでないものをどう扱うか

**区別のない失敗として扱う。** 値を持たせず、何が起きたかは自然文で伝える。

これは握りつぶすことではない。失敗したことは必ず外へ出す——黙って成功を返したり、空の結果で代えたりしない。伝えないのは**種別**であって、失敗そのものではない。

バグと障害を区別のない失敗へ畳むと、正常に動いていない状態が「よく分からない失敗」として現れる。それでよい。分からないから調べることになり、調べれば直す対象だと分かる。

## 5. 値を足すときの問い

エラー値を 1 つ足す前に、次を確かめる。

- **この失敗は、正常な状態で起こるか。** 起こらないならバグである（§3.1）
- **受け取る側は、この値を見て何を変えるか。** 答えられないなら足さない（§2 条件 2）
- **他の値と畳めないか。** 畳んで振る舞いが変わらないなら、畳んだほうがよい
- **判定できないか。** 判定できるなら、それは失敗ではない（§3.3）

## 6. 重大度カタログ

| 違反パターン                                                   | 違反時の重大度 | 理由                                                           |
| -------------------------------------------------------------- | -------------- | -------------------------------------------------------------- |
| 失敗を黙って握りつぶす（成功を返す・空の結果で代える）         | 🔴 critical    | 失われたことが誰にも見えない。最も検出が遅れる                 |
| バグでしか起こらない事象にエラー値を定義した                   | 🟡 major       | バグが運用の一部として扱われ、壊れたまま動き続ける             |
| 受け取る側の振る舞いが変わらないエラー値を足した               | 🟢 minor       | 値が増えるだけで、読み手の負担が上がる                         |
| 判定できる事象をエラーにした                                   | 🟡 major       | 判定できるはずのものが処理の中断になり、残りの仕事まで止まる   |
| 障害（自分ではどうしようもないもの）に専用の値と経路を用意した | 🟢 minor       | 前提が崩れた状況を局所の対処では救えず、対策コストに見合わない |
