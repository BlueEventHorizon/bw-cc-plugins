# 文書定義書

**目的**: forge が扱う文書型の責務を定義する。

本書は**判断を持たない**。どちらに書くかの判定手順、各文書型の書き方、違反の重大度は持たず、それぞれ委譲先が定める（末尾の表）。

**対象**: SDD の成果物である 5 種の文書。プロジェクトのルール文書・レビューの記録・CHANGELOG は対象外。差分 feature は要件群を区別する名前空間であって文書型ではない（[additive_development_spec.md](additive_development_spec.md) §0）。

---

## 一覧

| 文書型     | 答える問い    | 一文の責務                                     |
| ---------- | ------------- | ---------------------------------------------- |
| 要件定義書 | What          | 何を作るか。その機能がユーザーにもたらす価値   |
| 設計書     | How           | 要件をどう実現するか                           |
| ADR        | Why           | なぜその決定を採り、何を採らなかったか         |
| 実装戦略書 | In what order | 設計を実装へ到達させる順序                     |
| 計画書     | What next     | 実装すべきタスクと、次に着手できるタスクの決定 |

---

## 要件定義書

- **責務**: ユーザーの視点で、何を作るかを書く。必要な機能・データ・ルールと、それらがユーザーにもたらす価値。読者はステークホルダー全員
- **書かないもの**: 実装方法（設計書の責務）。ただし既に決まっていて選択の余地が無い事項は、要件定義書に具体的に書く
- **存在期間**: 恒久。ただし不変ではない
- **改訂**: 差分開発によって修正されうる。差分開発の期間中、その範囲の現在の仕様は差分側の要件定義書であり、旧要件定義書の記述は既に置き換わっている。旧側は実装期間中は書き換えず、実装完了後の merge で改訂する（[additive_development_spec.md](additive_development_spec.md) §2・§3・§4）

## 設計書

- **責務**: 要件を実現する構造・モジュール・処理フロー
- **書かないもの**: 要件定義書に無い機能（承認を ADR に記録した場合を除く）／決定の理由の正式な記録（ADR の責務）／時間軸・順序（実装戦略書の責務）
- **存在期間**: 恒久。ただし不変ではない
- **改訂**: 差分開発によって修正されうる。扱いは要件定義書と同じ（[additive_development_spec.md](additive_development_spec.md) §2・§3・§4）

## ADR

- **責務**: なぜその決定を採ったか。何を検討し、なぜ採らなかったか。**記録しなければ後から理由を辿れない決定に限る**
- **書かないもの**: 仕様・ルールの本文（真実源が 2 つになる）／コード・ルール・仕様を見れば理由が分かる決定／選択の余地が無かった決定／単に採用した・指示されたという作業の経緯
- **例外**: 要件定義書に無い設計をユーザーの承認のもとで採った場合は、承認の事実と理由を書く。承認は仕様にもコードにも現れないため、記録が無ければレビューは規範違反と区別できない（[spec_design_boundary_spec.md](spec_design_boundary_spec.md) §10）
- **存在期間**: 恒久。拘束力を持たない
- **改訂**: 決定の撤回・転換により節の中身を更新する。追記型ではない。一度採って戻した事実は残し、節番号は変えない（[adr_principles_spec.md](adr_principles_spec.md)「可変文書である」）
- **作る対象の判定**: [adr_principles_spec.md](adr_principles_spec.md)「書く対象・書かない対象」

## 実装戦略書

- **責務**: 実装アプローチの選択、フェーズ分割、各フェーズの検証ポイント、リスクと対策。差分開発では、旧仕様と相反する実装をどの順序で処理していくか
- **書かないもの**: 構造の設計（設計書の責務）／個々のタスクの実行単位（計画書の責務）
- **存在期間**: 一時。計画書と同じライフサイクルで扱い、全タスク完了時に計画書とともに存廃を利用者が選択する
- **正式名称**: 実装戦略書。ファイルは `{feature}_strategy.md`

## 計画書

- **責務**: タスクの集合、優先度と依存関係、要件・設計とのトレーサビリティ
- **書かないもの**: 設計書を参照すれば分かる実装詳細
- **存在期間**: 一時。破棄するか残すかは利用者が選択する
- **形式**: JSON（`{feature}_plan.json`）
