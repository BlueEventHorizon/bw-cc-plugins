# ADR（アーキテクチャ決定記録）運用原則

ADR を作る・直す・根拠に使うときの規範。**書式**（テンプレート・節の構成・失効マーカーの記法）は [adr_format.md](adr_format.md) を参照する。

ADR は設計書ではない。設計書の規範は [design_principles_spec.md](design_principles_spec.md) にあり、本書はそれとは別の文書種別を扱う。

---

## 目的と受益者

ADR の受益者は**提案しようとする AI** である。「より良い方法があるのに採られていない。提案しよう」と考えた瞬間、およびレビューで所見を書く・所見を評価する瞬間に、「その案は検討済みで、こういう理由で採らなかった」と答えるための記録である。

したがって ADR が運ぶべき積荷は、決定そのものよりも**何を検討して、なぜ採らなかったか**である。§3 の棄却理由が本体であり、§2 の決定はその文脈にあたる。

---

## 書く対象・書かない対象 [MANDATORY]

**ADR は仕様を書く場所ではない。** 仕様の単一の真実源は要件定義書・設計書であり、ADR がそれを写すと真実源が 2 つになる。仕様は参照で示し、書いてよいのは決定の理解に必要な範囲の簡潔な記述に限る。仕様書と同等の粒度で書かない。

参照は [document_style_guide.md](document_style_guide.md) §5 の記法（マークダウンリンク）に従う。節を指す場合はリンクに `§X.Y` を添える。**ID だけを書いて参照の代わりにしない**（[spec_format.md](spec_format.md)「文書参照の記法」）。

**ルール・規約を ADR に書かない。** 規範の置き場はルール文書・原則文書であり、ADR に写すと同じ問題が起きる。ADR に書けるのは「そのルールをなぜ採ったか／別案をなぜ採らなかったか」だけである。

**これは ADR に書いてよいものの上限であって、理由の置き場を ADR に限る規定ではない。** ルール文書は守らせるための理由を持ってよい——ADR を作るほどでない小さな理由、または ADR の要約である。ADR は拘束力を持たず（「拘束力を持たない」節）、読まれる保証も無いため、遵守を ADR に依存させられない。両者は重複ではなく受益者が違う。ADR の理由は**提案しようとする者**に再検討を促すため、ルール文書の理由は**実行する者**に守らせるためにある。

**ADR を作る対象を絞る**。次の 2 つが**同時に**成り立つときだけ作る。

1. 将来もっともらしい提案・所見が出る見込みがある
2. その提案が誤りであることが、コード・ルール・仕様を見ても分からない

いずれかを欠く場合は作らない。実装の出所メモ・一度きりの事故の記録・一般論で答えられる判断は対象外である。**些末な ADR を足すことは、ADR 全体の機能を薄める**——受益者は「検討済みか」を引くために全体を見渡す必要があり、引けない量になれば読まれなくなる。

### スコープ欄を書く条件

スコープ欄（記法は [adr_format.md](adr_format.md)「スコープ欄」）は**任意**である。次の場合にだけ書く。

> 同じ対象について別の ADR・要件・設計が並立しており、**その ADR がどこまでを決めたのかを読み手が判別できない**とき。

全件に必須としない。境界が自明な ADR にも定型文が増え、読み通す量だけが増えるためである。

逆に、上の条件に当たるのに書かないと、隣接文書の担当範囲まで本 ADR が決めたと読まれる。受益者はこれを提案を見送る根拠に使うため、範囲を誤ると**決めていない事柄が決定済みとして扱われる**。

## 拘束力を持たない

ADR は指示ではなく気づきである。**棄却理由を読んでもなお正しいと判断したなら、提案してよい**。過去の判断が現在の前提の下でも妥当とは限らず、前提が変わったことに気づけるのは提案しようとしている側だけである。

読み手には次の義務がある。

- ADR を根拠に提案・所見を見送るときは、**棄却理由が依拠する前提が今も成立しているか**を確かめる。成立していなければ ADR を根拠にしない
- 見送った場合は、根拠にした **ADR ID を添える**（見送りの判断を後から追跡できるようにするため）

### 抑止の到達率は上げない

ADR に書いたことが提案時に必ず読まれる保証はない。到達率を上げる仕組み（全 ADR の事前読み込み等）は**設けない**。ADR は拘束力を持たないため、届かなかったことの損失は「重複した提案が 1 度出る」に留まる。読み込み量を増やす代償に見合わない。

## 可変文書である [MANDATORY]

ADR は追記型ではない。**節の中身は更新してよい**。

- 既存の記述は**追記**で更新する。全面的に書き直すのは、簡潔さのために必要なときだけに限る
- 書き直す場合も、**一度採って戻した事実（A → B → A）は残す**。これは履歴ではなく、現在の棄却理由が依拠する前提の一部である
- **節番号は変えない**。`ADR-NNN §X.Y` 形式の外部参照がコード・テストを含む各所にあり、付け替えると宛先を失う
- 変遷は該当する節の中に書く。**専用の変遷ログ節・ステータス履歴節は作らない**

履歴セクションの禁止と ADR の例外は [document_style_guide.md](document_style_guide.md) §7 に従う。

### 決定の撤回・転換：同一節への追記か、別 ADR かの判定 [MANDATORY]

決定を撤回・転換するとき、新しい決定を**別 ADR にするか本節への追記で済ませるか**は、その新しい決定自体が「書く対象・書かない対象」の 2 条件（将来もっともらしい提案が出る見込みがあり、かつそれが誤りであることがコード・ルール・仕様を見ても分からない）を満たすかどうかだけで判定する。

- **満たす**（新しい決定も独立して再提案を止める必要がある）→ 新しい ADR を作り、旧 ADR の該当節に「失効の扱い」に従い失効マーカーを付ける
- **満たさない**（新しい決定はルール・仕様の変更を見れば分かる、または旧決定の前提が崩れただけ）→ **新 ADR は作らず**、本節の規定どおり該当節へ追記して撤回を記録する。旧決定の文面は削除せず残し、その後に撤回の事実と理由を追記する。失効マーカーは使わない（別 ADR が存在しないため宛先を持てない）

「グレーゾーン許容範囲」表の「決定の転換」行、および重大度カタログの該当行は、この判定を前提にしている。

### 旧書式からの移行

[adr_format.md](adr_format.md) が定める書式より前に作られた ADR を、本書式へ合わせる作業がある。この作業は上記「節番号は変えない」および重大度カタログの「節番号の付け替え・節の削除」に**当たらない**。これらが守っているのは `## 1.`〜`## 4.` とその小節であり、書式に無い節（メタデータ表・ステータス履歴節）はその対象ではないためである。

移行時は次を守る。

- 削除する節に**本文にしか無い情報が含まれていないか確認し、含まれていれば §1〜§4 の該当箇所へ移してから削除する**（ステータス履歴の備考に決定の経緯だけが書かれている例がある）
- 番号を持たない小節へ番号を与える場合、**その見出しを名前で参照している箇所を同時に直す**
- `## 1.`〜`## 4.` の番号は移行でも変えない

## 失効の扱い [MANDATORY]

決定が**別の ADR によって覆された**場合に限り、該当する節の見出し末尾に失効マーカーを付ける。記法は [adr_format.md](adr_format.md) に従う。**別 ADR を作るかどうかの判定は「可変文書である」§決定の撤回・転換に従う**。別 ADR を作らず同一節への追記で撤回する場合、本節の失効マーカーは使わない。

- **無印が有効**である。有効な節に印は付けない
- 失効は決定単位で起きるため、文書単位の状態（`accepted` / `superseded` 等）は持たない。**部分失効を表せないため**である
- 失効した節も削除しない。「その案は一度採られ、こういう理由で置き換えられた」こと自体が、再提案に対する答えになる

**失効の検出契機**: 仕様・設計を変更したときは、その変更が既存 ADR の棄却理由の前提を崩していないか確かめる（[design_principles_spec.md](design_principles_spec.md)「設計書の保守」の更新が必要なケース）。誰も気づかないまま失効した棄却理由は、どの仕組みでも検出できない。

---

## 棄却理由の書き方

棄却理由は、**将来その案が再提案されるときの語彙**で書く。当時の実装の語彙だけで書くと、同じ案が別の言い方で提案されたときに突き合わせられない。

あわせて、**その判断が依拠している前提を明示する**。結論だけを書くと、前提が変わったかどうかを読み手が判定できず、失効した棄却理由が生き続ける。

---

## 配置と ID 採番

- ADR は設計書と同じディレクトリに配置する（ADR 専用ディレクトリは作らない）
- ID（`ADR-NNN`）を手動で決めず、必ず `next-spec-id` スキルで採番する（`python3 scan_spec_ids.py ADR --share-prefixes ADR,DES`）。ADR と DES は同一ディレクトリで通し番号を共有するため `--share-prefixes ADR,DES` を必ず付与する。手動採番は並行ブランチで同一 `ADR-NNN` が別内容で衝突する原因になる
- 設計ディレクトリ配下に置くため、`.doc_structure.yaml` に ADR 専用ディレクトリを定義しなくても `next-spec-id` の git スキャンで既存 ADR を検出できる

## グレーゾーン許容範囲

| 論点                                           | ✅ 許容                                                         | ❌ 不許容                                                                                   |
| ---------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 既存 ADR の書き換え                            | 簡潔化のための整理・語彙の言い換え・追記による変遷の記録        | 往復した事実の削除・節番号の付け替え・節の削除                                              |
| 決定の転換（新決定が「書く対象」を満たす）     | 新しい ADR を作り、旧 ADR の該当節に失効マーカーを付ける        | 新 ADR を作らず、旧 ADR の決定本文を差し替えるだけで済ませる                                |
| 決定の転換（新決定が「書く対象」を満たさない） | 新 ADR は作らず、旧決定の文面を残したまま該当節へ撤回を追記する | 撤回の事実・理由を書かずに旧決定を差し替える。存在しない別 ADR を示して失効マーカーを付ける |
| 失効マーカー                                   | 決定が別 ADR へ移ったことを示す                                 | 「古くなった気がする」「実装が変わった」等、別 ADR を伴わない理由で付ける                   |
| 仕様への言及                                   | マークダウンリンクで指す。決定の理解に要る範囲の簡潔な記述      | 仕様書と同等の粒度で書く。仕様の写し。ID だけを書いて参照の代わりにする                     |
| ADR を作る対象                                 | 将来の提案を止める必要があり、他の文書では答えられないもの      | 実装の出所メモ・一度きりの事故・一般論で答えられる判断                                      |
