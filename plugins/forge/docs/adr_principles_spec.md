# ADR（アーキテクチャ決定記録）運用原則

ADR を作る・直すときの規範。**書式**（ファイルの構成・節の構成・テンプレート）は [adr_format.md](adr_format.md) を参照する。ADR を根拠に判断する側の義務は [adr_usage_spec.md](adr_usage_spec.md) が定める。

ADR は設計書ではない。設計書の規範は [design_principles_spec.md](design_principles_spec.md) にあり、本書はそれとは別の文書種別を扱う。

---

## ADR の定義

- **責務**: 優れた方式がありそうなのに採らなかった決定について、なぜ採らなかったかを残す。**記録しなければ後から理由を辿れない決定に限る**。ADR は決定の理由の正式な置き場であり、設計書は理由を簡潔に触れてよいがそこが正式な置き場ではない
- **書かないもの**: 仕様・ルールの本文（真実源が 2 つになる）／コード・ルール・仕様を見れば理由が分かる決定／選択肢の余地が無かった決定／選んだ方式が誰が見ても正しい決定／単に採用した・指示されたという作業の経緯
- **例外**: 要件定義書に無い設計をユーザーの承認のもとで採った場合は、承認の事実と理由を書く。承認は仕様にもコードにも現れないため、記録が無ければレビューは規範違反と区別できない（[spec_design_boundary_spec.md](spec_design_boundary_spec.md) §6）
- **存在期間**: 恒久。拘束力を持たない（[adr_usage_spec.md](adr_usage_spec.md)）
- **改訂**: 決定の撤回・転換・訂正は、同じ決定の節を書き直して行う。追記型ではない（下記「可変文書である」）

## 受益者

主たる受益者は**提案しようとする AI** である。「より良い方法があるのに採られていない。提案しよう」と考えた瞬間、およびレビューで所見を書く・所見を評価する瞬間に、「その案は検討済みで、こういう理由で採らなかった」と答えるための記録になる。この受益者に届くのは「検討した代替案」の棄却理由であるため、そこを薄く書かない。

## 書く対象・書かない対象

**ADR は仕様を書く場所ではない。** 仕様の単一の真実源は要件定義書・設計書であり、ADR がそれを写すと真実源が 2 つになる。仕様は参照で示し、書いてよいのは決定の理解に必要な範囲の簡潔な記述に限る。仕様書と同等の粒度で書かない。

参照は [document_style_guide.md](document_style_guide.md) §5 の記法（マークダウンリンク）に従う。節を指す場合はリンクに `§X.Y` を添える。**ID だけを書いて参照の代わりにしない**（同 §5.1 系統 (3)）。

**ルール・規約を ADR に書かない。** 規範の置き場はルール文書・原則文書であり、ADR に写すと同じ問題が起きる。ADR に書けるのは「そのルールをなぜ採ったか／別案をなぜ採らなかったか」だけである。

**これは ADR に書いてよいものの上限であって、理由の置き場を ADR に限る規定ではない。** ルール文書は守らせるための理由を持ってよい——ADR に書くほどでない小さな理由、または ADR の要約である。ADR は拘束力を持たず、読まれる保証も無いため、遵守を ADR に依存させられない。両者は重複ではなく受益者が違う。ADR の理由は**提案しようとする者**に再検討を促すため、ルール文書の理由は**実行する者**に守らせるためにある。

**ADR に書く対象を絞る**。次の 2 つが**同時に**成り立つときだけ書く。

1. 将来もっともらしい提案・所見が出る見込みがある（優れた方式がありそうに見える）
2. その提案が誤りであることが、コード・ルール・仕様を見ても分からない

いずれかを欠く場合は書かない。実装の出所メモ・一度きりの事故の記録・一般論で答えられる判断は対象外である。**些末な決定を足すことは、ADR 全体の機能を薄める**——受益者は「検討済みか」を引くために全体を見渡す必要があり、引けない量になれば読まれなくなる。

**選んだ方式が誰が見ても正しい決定には書かない。** 棄却した代替案が、説明されなくても明白に劣り、優れた方式がありそうに見えないなら、条件 1 を満たさない。その理由を残しても、読み手の得は無く、読む context を消費するだけである。他に選択肢が無い決定・誰が考えてもそうなる決定も同じである。

### スコープ欄を書く条件

スコープ欄（記法は [adr_format.md](adr_format.md)「スコープ欄」）は**任意**である。次の場合にだけ書く。

> 同じ対象について別の要件・設計が並立しており、**その ADR ファイルがどこまでを決めたのかを読み手が判別できない**とき。

全件に必須としない。境界が自明な ADR にも定型文が増え、読み通す量だけが増えるためである。

逆に、上の条件に当たるのに書かないと、隣接文書の担当範囲まで本 ADR が決めたと読まれる。受益者はこれを提案を見送る根拠に使うため、範囲を誤ると**決めていない事柄が決定済みとして扱われる**。

## 吟味の基準

ADR にしたい内容を渡されたとき、次の基準で判定する。

| 判定         | 条件                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 棄却         | 決定に至っていない（提案・未承認・未確認）。決定後に改めて渡すよう返す                                                                  |
| 棄却         | 「書く対象・書かない対象」の 2 つの条件を満たさない（コード・ルール・仕様から分かる、選択肢が無い、一般論で答えられる、一度きりの事故） |
| 棄却         | 選んだ方式が誰が見ても正しい（棄却した代替案が、説明されなくても明白に劣る）                                                            |
| 棄却         | 作業の経緯や文書整理の記録（git の履歴の領分）                                                                                          |
| 棄却         | ADR に書くほどでない小さな理由。参照元の文書へ 1 文で書くよう返す                                                                       |
| 修正して記載 | 経緯・実装状況・後続作業・日付入りの訂正を本文から除く                                                                                  |
| 修正して記載 | 規範・仕様の本文を写さず、決定の要旨・理由・参照に絞る                                                                                  |
| 修正して記載 | 棄却理由を、「なぜ優れていそうに見える案を採らなかったか」に絞り、将来の別案の語彙で書く。実装の語彙を除く                              |
| 不足         | 棄却理由が依拠する前提が、渡された内容から分からない。補って書かない（作り話になる）                                                    |
| 不足         | 承認記録で、要件へ戻せない理由、または利用者の承認の引用（発言そのまま）が欠けている                                                    |

**承認記録は棄却しない。** 「ADR に値するか」ではなく、「義務の記録が成立しているか」で検査する。記録の無い承認は承認として扱われず、棄却すると設計を進められない。

**1 つの決定の節は、それだけで完結させる。** 他の決定の節を前提にしないと理解できない書き方をしない。ID だけを書いた参照、変更対象ファイルの具体パスの列挙も書かない。

**ADR に書く事実・理由・帰結は、渡された内容と読んだ文書に根拠があるものだけにする。** 書式が小節を固定していても、材料が無い小節を、推測で埋めない（作り話になり、読み手は将来、決定済みの事実として扱う）。とくに「影響」は、渡された内容や読んだ文書から導ける帰結だけを書く。導ける帰結が無いときは、「渡された内容から導ける影響は示されていない」と書く。棄却理由も同じで、渡された内容に無い理由を足さない。渡された内容に棄却の理由が無い代替案は、理由が分からないものとして「不足」にする。

## 可変文書である

ADR は追記型ではない。**節の中身は更新してよい**。書き損じは、書き直して正す。

- 既存の決定を直すときは、**その決定の節を書き直す**。全面的に書き直すのは、簡潔さのために必要なときに限る
- **節番号は変えない**。`ADR-NNN §X.Y` 形式の外部参照がコード・テストを含む各所にあり、付け替えると宛先を失う
- 変遷は該当する節の中に書く。**専用の変遷ログ節・ステータス履歴節は作らない**

履歴セクションの禁止と ADR の例外は [document_style_guide.md](document_style_guide.md) §7 に従う。

### 決定の否決：同じ節を書き直す

決定が否決された（撤回・転換・訂正された）とき、**否決された内容を、新しい決定の中へ取り込む**。

- 「決定」を、新しい決定に書き直す
- 旧い案は、同じ節の「検討した代替案」へ移し、否決の理由を添える
  - 旧い理由が**誤り**だった場合: 誤りだった旨と、正しい理由を書く（例:「この設計は誤りである。理由は〜」）
  - **前提が変わっただけ**の場合: 当時は妥当だったことと、変わった前提を書く。前の案が再び提案されたときの答えになる
- **旧い決定の本文と、誤っていた理由は残さない**。誤りを残しても、読み手は間違った理由を読むだけである
- **別の ADR を作らない。ADR ファイルを分けない。「失効」の印を付けない**。新しい決定は、旧い決定と同じ節で述べる

否決を、単に「棄却」と記して、新しい ADR を丸ごと別に足してはならない。

## 配置と ID 採番

- ADR は、feature ごとの `adr/` ディレクトリ（`docs/specs/<feature>/adr/`）に置く。文書種別 `adr` を `.doc_structure.yaml` が宣言する。宣言が無いプロジェクトでは、置き場を他の文書種別のキーから導出せず、宣言を促す
- **同じ feature の ADR は、すべて 1 つの ADR ファイル（`ADR-{NNN}_{feature}.md`）に書く**。決定ごとにファイルを分けない
- 新しい ADR ファイルを作るのは、その feature に ADR ファイルがまだ無いときだけである。ある場合は、そのファイルへ書く
- ファイルの番号（`ADR-NNN`）は、ファイルを最初に作るときに、`next-spec-id` スキルで 1 回だけ採番する（`python3 scan_spec_ids.py ADR --share-prefixes ADR,DES`）。ADR と DES は `docs/specs/` 全体で通し番号を共有するため `--share-prefixes ADR,DES` を必ず付与する。手動採番は並行ブランチで同一番号が別内容で衝突する原因になる。以後、番号は変えない
- 複数のコンポーネントに跨る決定は、feature に `common` を指定して書く
- ADR を作る・更新するのは、`/forge:write-adr` である

## グレーゾーン許容範囲

| 論点                     | ✅ 許容                                                        | ❌ 不許容                                                                                          |
| ------------------------ | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 既存の決定の書き換え     | 同じ節の書き直し・簡潔化・語彙の言い換え                       | 節番号の付け替え・節の削除                                                                         |
| 決定の否決               | 同じ節を書き直し、旧い案を代替案へ、正しい理由とともに移す     | 旧い決定を残して「失効」の印を付ける。別の ADR・別のファイルを足す。誤った理由を残したまま追記する |
| 前提が変わっただけの転換 | 旧い案を代替案へ移し、当時は妥当だったことと変わった前提を書く | 変わった前提を書かない                                                                             |
| 仕様への言及             | マークダウンリンクで指す。決定の理解に要る範囲の簡潔な記述     | 仕様書と同等の粒度で書く。仕様の写し。ID だけを書いて参照の代わりにする                            |
| ADR に書く対象           | 将来の提案を止める必要があり、他の文書では答えられないもの     | 実装の出所メモ・一度きりの事故・一般論で答えられる判断・誰が見ても正しい方式の理由                 |
