# 要件定義書と設計書の境界ガイド

**目的**: What（要件定義書）と How（設計書）の境界を明確化し、記載内容の判断を支援する

各文書型の責務そのものは [requirement_principles_spec.md](requirement_principles_spec.md) / [design_principles_spec.md](design_principles_spec.md) が定める。本書は 2 者の振り分け判定だけを持つ。

---

## 1. 基本原則

### 要件定義書（What）

- **目的**: 何を作るか
- **視点**: ユーザー視点
- **内容**: 必要な機能、データ、ルール、およびそれらがユーザーにもたらす価値
- **読者**: ステークホルダー全員
- **詳細度**: 概念レベル。ただし既に決まっていて動かせない事項は、抽象化せず具体的に書く
- **技術**: 技術中立（実装方法に依存しない）。ただし採用する技術・形式・手段が既に決定済みで選択の余地が無い場合は、それを具体的に書く

### 設計書（How）

- **目的**: どう作るか
- **視点**: 開発者視点
- **内容**: 実装方法、アーキテクチャ、処理フロー
- **読者**: 開発者、AI
- **詳細度**: 実装レベル
- **技術**: 技術依存（フレームワーク・実装パターン等）

### ADR との関係

設計書は**現在の設計**を書く。理由は簡潔に触れてよい（設計を納得して読むために要る）が、**理由の正式な置き場は ADR（アーキテクチャ決定記録）である**。

ADR には**設計そのものを転記しない**。決定を理解するのに要るポイントだけ触れる。

**他に選択肢が無い設計・誰が考えてもそうなる設計に ADR は作らない。** 作る条件・書く対象・拘束力は [adr_principles_spec.md](adr_principles_spec.md) が定める。

## 2. 判断基準

### 最初の判断基準

**「それは既に決まっていて、選択の余地が無いか？」**

- **Yes** → 要件定義書（具体的に書く。抽象化すると、決まっていることが決まっていないことになる）
- **No** → 次の判断基準へ

決定済みの根拠は、ADR・プロジェクト規約・上位仕様など、その決定を記録した文書である。「一般にそうすることが多い」は決定ではない。

### 主要な判断基準

**「ユーザーマニュアルに書くか？」**

- **Yes** → 要件定義書
- **No** → 設計書

最初の判断基準で Yes となったものには適用しない（決定済みの事項を、この基準で設計書へ振り分けてはならない）。

### 判断基準に掛けないもの

機能の存在理由・ユーザーにとっての価値は、要件定義書にのみ現れる構成要素であり、本節の判断基準には掛けない。「ユーザーマニュアルに書くか」では拾えないが、設計書に書く対象でもないためである（§3.2）。

## 3. カテゴリ別ガイド

§2 の判断基準だけでは振り分けを誤りやすいカテゴリを扱う。

### 3.1 定量目標関連

| 内容                                                         | 要件定義書 | 設計書 |
| ------------------------------------------------------------ | ---------- | ------ |
| ユーザー要求・ビジネス制約・既存契約として確定済みの定量目標 | ✓          |        |
| 定量目標を達成するための構造・方針                           |            | ✓      |
| 「この設計なら X を達成する」という保証的記述                | ✗          | ✗      |
| 定量値の実地検証結果（負荷試験・本番計測等）                 |            |        |

実行後に人間が「少し遅い」「十分速い」等を体感して決める性質の値は、AI が数値例から推測して要件・設計に書いてはならない。未確定の定量目標は、要件定義書の未確定事項として当事者判断に委ねる。

定量目標の**達成可否は運用・測定段階で初めて検証される**（負荷試験・プロファイリング・本番計測）。設計書は「どう達成を狙うか」の構造・方針を示すまでが責務であり、「達成を保証する」体裁で定量値を書くのは越権である。

構造品質（責務分割・境界・依存方向）の定量化は別論点であり、そもそも数値化すべきでない。→ [spec_priorities_spec.md](spec_priorities_spec.md) §3 参照。

許容する記述・許容しない記述の具体例は §5.3。

### 3.2 機能の存在理由・価値

| 内容                                 | 要件定義書 | 設計書 |
| ------------------------------------ | ---------- | ------ |
| その機能がユーザーにもたらす価値     | ✓          |        |
| なぜその機能が必要か（解決する課題） | ✓          |        |
| 設計がその価値に寄与することの説明   |            | ✗      |

**例**:

- 要件定義書 ✅:「検索履歴を残すことで、利用者は同じ条件を入力し直さずに再検索できる」
- 設計書 ❌:「本設計により利用者の入力負担が下がる」（§3.1 の保証表現と同類）

価値は設計書に書く対象ではない。設計書に価値を書けば、その設計が価値を実現することの保証になる。

## 4. 重大度カタログ

本文書内の各規範を、違反時の重大度に対応付ける。本節は重大度判定の SoT であり、criteria 側は本節を MANDATORY 参照する（判断は criteria に持たせない）。

**本節の違反パターンは、いずれも §2 の最初の判断基準で「決まっていない」と判定される事項に適用する。** 決定済みの事項を要件定義書へ具体的に書くことは違反ではない。

### 4.1 What/How 境界違反

| 違反パターン                                                                                                               | 出典 | 違反時の重大度 | 理由                                                                     |
| -------------------------------------------------------------------------------------------------------------------------- | ---- | -------------- | ------------------------------------------------------------------------ |
| 実装手段（データフロー・状態クラスや enum の実装名・処理フロー・アルゴリズム・バリデーションの実装手順）を要件定義書に記載 | §2   | 🔴 critical    | 実装手段を What に混入させる典型。読者がステークホルダーから開発者に縮退 |
| テストケースを要件定義書に記載                                                                                             | §2   | 🟡 major       | What/How 境界違反だが、ビジネスルール例示と紛らわしい (gray zone)        |
| 「本設計により X を達成する」等の保証表現を設計書に記載                                                                    | §3.1 | 🔴 critical    | 設計段階で担保できない事項を保証する越権記述                             |
| 設計書に手段+数値目標 (Redis を使って 200ms を切る) を混入                                                                 | §3.1 | 🟡 major       | 要件と設計の責務混在                                                     |
| 要件定義書に手段を含む数値目標 (Redis を使って 200ms 切る等)                                                               | §3.1 | 🔴 critical    | 実装手段を要件に混入 (技術依存)                                          |
| 機能の存在理由・ユーザーにとっての価値が要件定義書に記載されていない                                                       | §3.2 | 🟡 major       | 何のために作るかが要件から辿れず、設計・実装の判断根拠が失われる         |

### 4.2 グレーゾーン (型 / 図表)

§5 の許容範囲の外側を見落とすケースがあるため、重大度カタログで補強する。

| 違反パターン                                                         | 出典 | 違反時の重大度 | 理由                                                                 |
| -------------------------------------------------------------------- | ---- | -------------- | -------------------------------------------------------------------- |
| 要件定義書に詳細な型設計 (Generic 制約 / 内部構造) を記載            | §5.1 | 🟡 major       | 概念型・実装型は許容するが、詳細型設計は How 領域                    |
| 要件定義書にシーケンス図・クラス図・データフロー図を記載             | §5.2 | 🔴 critical    | 内部実装図は How 専用                                                |
| 設計書に画面遷移図・ナビゲーション構造図のみ (内部構造図なし) を記載 | §5.2 | 🟢 minor       | 補助的に置く分には許容。本来は要件側だが、設計書に再掲する選択は許容 |

## 5. グレーゾーン許容範囲

判定が割れやすい論点について、許容する解釈と許容しない解釈を断定形で示す。レビュー時の false positive 警告は principles 側で執筆者にも見える形で持つ。criteria 側に「false positive 注意」を書いてはならない。

### 5.1 G.1 データモデルの型

| 論点                 | ✅ 許容                                                                      | ❌ 不許容                                                        |
| -------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 要件定義書での型表記 | 概念型 (文字列 / 数値 / 日時 / 真偽値) / 実装型 (String / Int / Date / Bool) | 詳細型設計 (Generic 制約 / 内部 struct 階層 / Optional 設計理由) |
| 設計書での型表記     | 詳細型設計を含むすべての型表現                                               | (制約なし)                                                       |

要件レベルでも型の明示は有用であるため、実装型の表記まで許容する。詳細な型設計は設計書で扱う。

### 5.2 G.2 図表

| 論点                            | ✅ 許容 (要件定義書側) | ❌ 不許容 (要件定義書側)    |
| ------------------------------- | ---------------------- | --------------------------- |
| 画面遷移図 (ユーザー視点の遷移) | ✅                     |                             |
| ナビゲーション構造図            | ✅                     |                             |
| ユースケース図 (外部相互作用)   | ✅                     |                             |
| シーケンス図                    |                        | ❌ (内部処理ステップは How) |
| データフロー図 (内部の流れ)     |                        | ❌                          |
| クラス図                        |                        | ❌                          |

### 5.3 G.3 定量目標

| 論点                                 | ✅ 許容 (要件定義書側)                                  | ❌ 不許容 (要件定義書側)                                    |
| ------------------------------------ | ------------------------------------------------------- | ----------------------------------------------------------- |
| ユーザー要求・契約・実測由来の確定値 | ✅ 「顧客契約上、検索結果は 200ms 以内」「SLA 99.9%」等 | (実装手段の混入は不可)                                      |
| 未確定値                             | TBD として明示                                          | AI が一般論で補完した数値を要件として確定すること           |
| 手段を含む目標                       |                                                         | ❌「Redis を使って 200ms 切る」(達成手段の選択は設計の判断) |

| 論点                 | ✅ 許容 (設計書側)                                                         | ❌ 不許容 (設計書側)             |
| -------------------- | -------------------------------------------------------------------------- | -------------------------------- |
| 達成を狙う構造・方針 | ✅ 「Redis キャッシュ + debounce で応答性を狙う」                          |                                  |
| 達成保証表現         |                                                                            | ❌ 「本設計により X を達成する」 |
| 達成可否の判定       | 運用・測定段階 (負荷試験 / プロファイリング / 本番計測) で検証する旨を明示 | 設計段階で達成可否を断定すること |

## 6. トレーサビリティ規範 (軽量版)

設計書レビュー時、以下が成立しない場合に検出する。

| 規範                                                                         | 違反時の重大度 |
| ---------------------------------------------------------------------------- | -------------- |
| 設計書本文が参照する要件 ID が、要件定義書に実在する (孤立参照禁止)          | 🟡 major       |
| 要件定義書に存在しない機能を、承認の記録を伴わずに設計書で新規追加していない | 🔴 critical    |

**承認の記録**: 要件定義書に無い設計を採るときの手続き（設計を止め、ユーザーへ説明し、承認を得る）は `/forge:start-design` が定める。本書が持つのは判定条件だけであり、判定は**当該節から承認を記録した ADR へのリンクがあるか**で行う。ADR を作る対象・書き方は [adr_principles_spec.md](adr_principles_spec.md) に従う。記録の無い承認は承認として扱わない。

**差分開発の場合**: 差分開発の設計書における「要件定義書」は、当該範囲の現在の仕様である**差分側の要件定義書**を指す（[additive_development_spec.md](additive_development_spec.md) §2）。旧要件定義書に記載が無いことを根拠に、新規追加と判定しない。

詳細なトレーサビリティ規約 (要件 ID とタスクの対応等) は計画書側 (`plan_principles_spec.md`) で扱う。
