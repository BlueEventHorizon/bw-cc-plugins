# 比例性の原則（過剰設計の抑止）

## 1. 目的

「理論上あり得る異常事態」への対処を無制限に積み増すと、システムは肥大化し保守不能になる。
本文書は、ある対策（修正・新機能・防御的実装）を採用すべきかどうかを判断する際の一般原則を定める。

**本文書は「見つかった指摘を fix にするか」を広く判定するものではない。** 以下 §2 の3類型に該当する指摘・提案にのみ適用するゲートである。3類型に該当しない指摘は、本文書を根拠に `skip` してはならない（Issue #182）。

## 2. 適用対象の限定 [MANDATORY]

本文書の3点チェック（§4）を適用するのは、指摘・提案が以下の3類型のいずれかに該当する場合に限る:

1. **カタストロフィックな外部要因への防御**（§3 参照）
2. **発生経路を具体化できない投機的な防御実装**（「理論上あり得る」以外の根拠を示せないもの）
3. **設計・要件・プロジェクトルールに根拠のない品質改善の即時修正化**（執筆者の主観的な「より良い書き方」を、根拠なく fix として押し通すもの）

### 2.1 3点チェックを適用してはならない指摘 [MANDATORY]

以下は本文書の対象外であり、3点チェックを理由に `skip` してはならない。criteria 自身の判定ルール（`fix` 採用条件）に従う:

- 明示された要件・設計・プロジェクトルールへの違反
- 実行時に壊れる具体的なリスク（再現条件を示せるバグ）
- データ損失・セキュリティ・破壊的操作・テスト必須違反など、MVP でも止めるべき問題

**「レビューで発見されたこと」自体は、上記いずれの類型にも該当しない。** 通常のコードレビューが検出する不具合はすべてこの経路（人間または AI によるレビュー）で見つかるのが通常であり、「レビューで見つかったから顕在化済みで skip でよい」という解釈は本文書の意図と正反対である。

## 3. スコープ外の明示: 通常運用と異常事態の区別 [MANDATORY]

対象プロジェクトが通常の開発・運用フローで遭遇する不具合（ロジックバグ・データ不整合・設定ミス・競合状態等）への対処は、本文書のスコープ外（＝通常通り fix 対象）である。
以下のような**カタストロフィックな外部要因への防御は、明示的に依頼された場合を除きスコープ外**とする（§2 類型1）:

- OS レベルの異常（プロセスの突然の kill、電源断）
- ファイルシステムの破損
- ディスク容量の枯渇、ハードウェア故障
- その他「対象システム自体がすでに壊れている」ことを前提にした障害シナリオ

これらへの対処は通常運用では検証も再現もできず、限定的な防御をどれだけ積み増しても実効性を検証できない。
前提が破綻した状況を局所的な対策一つで救おうとしても、実質的な価値を持たない。

## 4. 3点チェック [MANDATORY]

**§2 の3類型に該当する指摘・提案にのみ**、以下 3 点をすべて確認する。いずれかを満たさない場合は採用しない:

1. **トリガー条件の成立時点で、他の前提もすでに壊れていないか**: 壊れているなら、その一箇所だけ直しても実質的な保護効果はない（例: プロセスクラッシュを前提にした1箇所のみのアトミック化提案）
2. **対策が防ごうとしている失敗そのものが、レビュー対象コードとは独立した既存の安全網（型検査・CI・他レイヤーのバリデーション等）によって、実害が生じる前に確実に食い止められるか**: 食い止められるなら緊急性は低く、サイレントな実害ではない。**「この指摘がレビューで見つかったこと」自体は独立した安全網ではなく、この条件の充足根拠にならない**（Issue #182）
3. **対策コストと実際に防げる被害は釣り合っているか**: 「理論上あり得る」だけでは根拠にならない。既存の安全網をすり抜けて実害に至る具体的経路を示せない場合は採用しない

## 5. 判定に迷う場合

対象が §2 の3類型に該当するかどうか自体が不明瞭な場合は、**該当しない（＝通常通り fix 対象）として扱う**。false negative（過剰防御の見逃し）より false positive（正当な指摘の skip）を避けることを優先する。

3類型に該当すると判断した上で3点チェックのいずれかが不明瞭な場合は、対策を採用せず、判断根拠とともに `skip` または `create_issue`（要検討事項として起票）とする。
