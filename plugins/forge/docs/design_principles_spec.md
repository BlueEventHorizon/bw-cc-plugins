# 設計書 作成原則

プロジェクト固有のルールがない場合に参照する汎用原則。
プロジェクト固有のルールがある場合はそちらを優先すること。

文書記述スタイル（タグ・見出し・参照記法）は [document_style_guide.md](document_style_guide.md) を参照。本文書は設計書固有の構成要素・判断基準を扱う。

---

## 設計書の基本方針

**設計書は「How（どう作るか）」を記述する。「What（何を作るか）」は要件定義書に記載する。**

→ 境界の詳細: [spec_design_boundary_spec.md](spec_design_boundary_spec.md)

---

## 必須構成要素 [MANDATORY]

設計書には以下の要素を**必ず**含めること:

| 要素                           | 形式                       |
| ------------------------------ | -------------------------- |
| モジュールリスト               | 表形式（責務と依存を記載） |
| コンポーネント図またはクラス図 | Mermaid 推奨               |
| ユースケース一覧               | 表形式                     |
| シーケンス図                   | Mermaid 推奨               |

セクション名・番号は設計内容に応じて柔軟に調整してよい。

---

## 記載すべき内容 / 記載してはいけない内容

### 記載すべき内容

- ✅ 実装方法（クラス名、メソッド名、デザインパターン）
- ✅ 技術的詳細（フレームワーク・ライブラリの選定と**採用理由**）
- ✅ 処理フロー・アルゴリズム
- ✅ データフロー（コンポーネント間のデータの流れ）
- ✅ シーケンス図、クラス図
- ✅ テストケース設計（正常系/異常系）
- ✅ 使用する既存コンポーネント（具体的なファイルパス）

### 記載してはいけない内容

- ❌ ソースコード（説明用の小規模例・5〜10行程度は許容）
- ❌ 技術選択の理由を記載しないままフレームワークを指定
- ❌ 要件にない機能の追加
- ❌ 「本設計により X ms を切る」等、定量目標の達成を保証する記述
- ❌ 実行後に人間が体感して決める値を、AI が数値例から推測した設計目標

---

## 定量目標の扱い [MANDATORY]

設計書は、定量目標の達成を保証する文書ではない。
要件で確定した定量目標がある場合でも、設計書に書くのは達成を狙うための構造・方針・代替案までとする。

| 内容                                               | 扱い                             |
| -------------------------------------------------- | -------------------------------- |
| キャッシュ層、debounce、非同期化、冗長化などの方針 | ✅ 記載してよい                  |
| 「本設計により X ms を切る」等の保証表現           | ❌ 記載しない                    |
| 未確定値を AI が推測した設計目標                   | ❌ 記載しない                    |
| 負荷試験・プロファイリング等の実地検証結果         | 設計書ではなく検証結果として扱う |

定量目標の最終的な達成可否は、負荷試験・プロファイリング・本番計測・人間の受け入れ判断など、実行後の検証で確定する。

構造品質（責務分割・境界・依存方向）の数値化禁止、および未確定定量値の捏造禁止は [spec_priorities_spec.md](spec_priorities_spec.md) に従う。
要件定義書との振り分けは [spec_design_boundary_spec.md](spec_design_boundary_spec.md) §4.6 に従う。

## 判断基準

**迷ったら「実装者がこれで実装できるか？」で判断**

- **Yes** → 設計書に記載
- **No** → より詳細化が必要、または要件定義書の領域

**具体例**:

| シナリオ                                            | 判断      | 理由                     |
| --------------------------------------------------- | --------- | ------------------------ |
| 「検索処理を実装する」                              | ❌ 不十分 | どのように検索するか不明 |
| 「SearchService.search() でデータをフィルタリング」 | ✅ 十分   | 実装方法が明確           |
| 「300ms debounce で検索 API を呼び出す」            | ✅ 十分   | 技術的詳細が明確         |

## 階層構造ガイドライン

設計規模が大きい場合は、1つのファイルにまとめず階層で分割する:

```
トップレベル設計書（全体アーキテクチャ）
├── 子設計書（モジュールA詳細）
├── 子設計書（モジュールB詳細）
└── 子設計書（画面/機能詳細）
```

- **分割の目安**: 単一ファイルが500行を超える場合は分割を検討（トップレベルは例外）
- **子設計書のメタデータ**に親設計書 ID を記載すること
- **トップレベル設計書**に子設計書の一覧を記載すること

```
{設計ID}_{対象名}_design.md
```

- 設計 ID をファイル名先頭に付与
- スネークケース使用
- 末尾に `_design.md` を付与
- 英語で記載

例: `DES-001_<name>_design.md`

## 図表使用ガイドライン

設計書での図表は Mermaid 形式を推奨する。

| 図種別         | 用途                         | Mermaid 構文      |
| -------------- | ---------------------------- | ----------------- |
| フローチャート | アーキテクチャ図・処理フロー | `flowchart TB`    |
| クラス図       | モジュール構造・型関係       | `classDiagram`    |
| シーケンス図   | ユースケース・データフロー   | `sequenceDiagram` |

**注意**: flowchart で小文字の `end` は使用禁止（`End` または `END` を使用）

- [Flowchart](https://mermaid.js.org/syntax/flowchart.html)
- [Class Diagram](https://mermaid.js.org/syntax/classDiagram.html)

## 歴史的記録を置かない [MANDATORY]

設計書に「改定履歴」「変更履歴」等の履歴セクションを置かない。設計書は**現在の設計**のみを記述する。

- 変更の履歴は `CHANGELOG.md`（および git 履歴）を SoT とする
- 設計判断の変更（なぜ A から B に変えたか）は ADR に記録する

ADR が保持する棄却の経緯は、この規範が禁じる履歴セクションではない。**一度採って戻した事実（A → B → A）は、現在の棄却理由が依拠する前提の一部**であり、削除すると同じ案が再提案される。日付と状態遷移を並べた表（「いつ proposed から accepted になったか」）だけが履歴であり、これは置かない。

## 設計書の保守 [MANDATORY]

実装が設計書の記述と乖離した場合（バグ修正・リファクタリング・設計判断の変更）、実装を正とみなせるなら設計書を更新する。設計書が古いまま放置されると、次の実装者（AI 含む）が誤った前提で作業する。

### 更新が必要なケース

| 乖離の種類                             | 対応                                              |
| -------------------------------------- | ------------------------------------------------- |
| API シグネチャ・戻り値型の変更         | 設計書のインターフェース記述を修正                |
| 設計判断の変更（選択肢 A → B）         | ADR を作成または既存 ADR を更新                   |
| パラメータ・定数・閾値の変更           | 設計書の該当セクションを修正                      |
| 新機能追加（設計書に記載なし）         | 設計書にセクションを追加、または新規設計書を作成  |
| ADR の棄却理由が依拠する前提が変わった | 該当 ADR の該当節を更新する（下記「ADR の運用」） |

### 更新時のルール

- 設計意図（なぜそう変えたか）を記述する。コードの転記は不要
- ADR の**書式**（テンプレート・節の構成・失効マーカーの記法）は [adr_format.md](adr_format.md) に従う。**運用**（目的・可変性・失効の扱い・棄却理由の書き方・読み手の義務）は下記「ADR の運用」に従う
- ADR（Architecture Decision Record）は設計書と同じディレクトリに配置する
- ADR を新規作成する際は、ID（`ADR-NNN`）を手動で決めず、必ず `next-spec-id` スキルで採番する（`python3 scan_spec_ids.py ADR --share-prefixes ADR,DES`）。ADR と DES は同一ディレクトリで通し番号を共有するため `--share-prefixes ADR,DES` を必ず付与する。手動採番は並行ブランチで同一 `ADR-NNN` が別内容で衝突する原因になる
- ADR は設計ディレクトリ配下に置くため、`.doc_structure.yaml` に ADR 専用ディレクトリを定義しなくても `next-spec-id` の git スキャンで既存 ADR を検出できる

### 更新不要なケース

- 内部リファクタリングで外部インターフェースが不変の場合
- コメント・ログメッセージのみの変更
- テストコードのみの変更

## ADR の運用 [MANDATORY]

### 目的と受益者

ADR の受益者は**提案しようとする AI** である。「より良い方法があるのに採られていない。提案しよう」と考えた瞬間、およびレビューで所見を書く・所見を評価する瞬間に、「その案は検討済みで、こういう理由で採らなかった」と答えるための記録である。

したがって ADR が運ぶべき積荷は、決定そのものよりも**何を検討して、なぜ採らなかったか**である。§3 の棄却理由が本体であり、§2 の決定はその文脈にあたる。

### 拘束力を持たない

ADR は指示ではなく気づきである。**棄却理由を読んでもなお正しいと判断したなら、提案してよい**。過去の判断が現在の前提の下でも妥当とは限らず、前提が変わったことに気づけるのは提案しようとしている側だけである。

読み手には次の義務がある。

- ADR を根拠に提案・所見を見送るときは、**棄却理由が依拠する前提が今も成立しているか**を確かめる。成立していなければ ADR を根拠にしない
- 見送った場合は、根拠にした **ADR ID を添える**（見送りの判断を後から追跡できるようにするため）

### 可変文書である

ADR は追記型ではない。**節の中身は更新してよい**。

- 既存の記述は**追記**で更新する。全面的に書き直すのは、簡潔さのために必要なときだけに限る
- 書き直す場合も、**一度採って戻した事実（A → B → A）は残す**。これは履歴ではなく、現在の棄却理由が依拠する前提の一部である
- **節番号は変えない**。`ADR-NNN §X.Y` 形式の外部参照がコード・テストを含む各所にあり、付け替えると宛先を失う
- 変遷は該当する節の中に書く。**専用の変遷ログ節・ステータス履歴節は作らない**

### 失効の扱い

決定が**別の ADR によって覆された**場合に限り、該当する節の見出し末尾に失効マーカーを付ける。記法は [adr_format.md](adr_format.md) に従う。

- **無印が有効**である。有効な節に印は付けない
- 失効は決定単位で起きるため、文書単位の状態（`accepted` / `superseded` 等）は持たない。**部分失効を表せないため**である
- 失効した節も削除しない。「その案は一度採られ、こういう理由で置き換えられた」こと自体が、再提案に対する答えになる

**失効の検出契機**: 仕様・設計を変更したときは、その変更が既存 ADR の棄却理由の前提を崩していないか確かめる（「設計書の保守」の更新が必要なケース）。誰も気づかないまま失効した棄却理由は、どの仕組みでも検出できない。

### 棄却理由の書き方

棄却理由は、**将来その案が再提案されるときの語彙**で書く。当時の実装の語彙だけで書くと、同じ案が別の言い方で提案されたときに突き合わせられない。

あわせて、**その判断が依拠している前提を明示する**。結論だけを書くと、前提が変わったかどうかを読み手が判定できず、失効した棄却理由が生き続ける。

### 抑止の到達率は上げない

ADR に書いたことが提案時に必ず読まれる保証はない。到達率を上げる仕組み（全 ADR の事前読み込み等）は**設けない**。ADR は拘束力を持たないため、届かなかったことの損失は「重複した提案が 1 度出る」に留まる。読み込み量を増やす代償に見合わない。

### グレーゾーン許容範囲

| 論点                | ✅ 許容                                                  | ❌ 不許容                                                                 |
| ------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------- |
| 既存 ADR の書き換え | 簡潔化のための整理・語彙の言い換え・追記による変遷の記録 | 往復した事実の削除・節番号の付け替え・節の削除                            |
| 決定の転換          | 新しい ADR を作り、旧 ADR の該当節に失効マーカーを付ける | 新 ADR を作らず、旧 ADR の決定本文を差し替えるだけで済ませる              |
| 失効マーカー        | 決定が別 ADR へ移ったことを示す                          | 「古くなった気がする」「実装が変わった」等、別 ADR を伴わない理由で付ける |

## よくある失敗パターン

| パターン                                                   | 問題               | 対策                                     |
| ---------------------------------------------------------- | ------------------ | ---------------------------------------- |
| 既存資産を1パターンの検索で諦め重複実装                    | 無駄な実装・不整合 | 複数キーワード・複数ツールで網羅的に検索 |
| プロジェクトの定数・デザイントークンを無視してハードコード | 不整合             | 定数定義を必ず参照                       |
| 同種機能の既存実装を確認せず独自設計                       | 重複・不整合       | 既存の類似パターンを必ず確認             |
| 設計判断の根拠を記載しない                                 | 保守困難           | 技術選択の理由・代替案を文書化           |
| 実装詳細（コード）を多量に記載                             | 設計書と実装の乖離 | 設計意図を記述し、詳細はコードで表現     |
| 実装後に設計書を更新しない                                 | 次回実装時に誤解   | 上記「設計書の保守」に従い即座に更新     |

## アーキテクチャ依存方向規範 [MANDATORY] (Appendix A.7 由来)

採用したアーキテクチャパターンの根本原則は設計書レビューで照合する。

### 規範

1. 採用したアーキテクチャパターン (レイヤード / クリーンアーキ / ヘキサゴナル等) の依存方向ルールを設計書に明示する
2. レイヤードでは下位層が上位層に依存してはならない
3. クリーンアーキでは Domain → Infrastructure を直接参照してはならない
4. 循環依存 (A → B → C → A 等) を作ってはならない

### グレーゾーン許容範囲

| 論点                                                   | ✅ 許容                                                | ❌ 不許容                                      |
| ------------------------------------------------------ | ------------------------------------------------------ | ---------------------------------------------- |
| 意図的な依存方向例外                                   | 設計書内に「この例外を採用する理由」が明文化されている | 例外理由が記載されないまま依存方向ルールを破る |
| ファサード/アダプタによる依存反転                      | 明示的なインターフェース定義を伴うもの                 | 「便利だから」の理由なき直接参照               |
| 単方向データバインディング由来の View → ViewModel 参照 | フレームワーク慣習として定着しているもの               | フレームワーク文脈外での同パターン             |

## 責務分割・凝集度規範 [MANDATORY] (Appendix A.8 由来)

### 規範

1. 各モジュール・コンポーネントは単一の責務を持つ
2. 1 コンポーネントが複数の異なる責務 (例: ユーザ認証 + レポート生成) を持つ設計は禁止
3. インターフェースを介さない直接的な内部構造への依存 (密結合) を避ける
4. 現在の利用箇所が 1 つしかない汎用フレームワーク的構造を作らない (YAGNI)
5. 資産 (コード・文書・手順書・設定) は、それを責務として使い保守するコンポーネントの配下に置く。責務を移したら資産も移す (生成の経緯や借用の既成事実で置き場所を決めない)

### グレーゾーン許容範囲

| 論点                                      | ✅ 許容                                         | ❌ 不許容                                                  |
| ----------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| ファサードパターン (意図的な複数操作集約) | 設計書に集約意図と境界が明示されているもの      | 単に肥大化した結果としての多責務クラス                     |
| ユーティリティクラス                      | 純粋関数の集合で副作用がないもの                | 状態を持ち複数の責務 (DB アクセス + ロジック等) を持つもの |
| 抽象化の早期導入                          | 既知の 3 箇所以上で使われるもの (Rule of Three) | 1 箇所のみで使われる「将来のための」汎用化                 |

## 可用性・SPOF 規範 [MANDATORY] (Appendix A.9 由来)

### 規範

1. 単一障害点 (SPOF) を持つ構成では、冗長化または代替経路を設計書に明示する
2. 外部 API 連携にはリトライ戦略 / タイムアウト / フォールバックを設計レベルで定義する
3. 異常系のデータフローと障害時の振る舞いを設計書に含める

### グレーゾーン許容範囲

| 論点                         | ✅ 許容                                                                               | ❌ 不許容                          |
| ---------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------- |
| シングル DB インスタンス依存 | 開発環境 / プロトタイプ / ローカルツール / 可用性要件が低いことが要件で明示されている | 本番運用前提なのに冗長化方針未記載 |
| リトライ戦略の省略           | 冪等性が保証されない処理で意図的にリトライしない判断 (記載必須)                       | リトライ要否を未検討・未記載       |

## 重大度カタログ [MANDATORY]

本文書内の各規範を、違反時の重大度に対応付ける。

### 「記載してはいけない内容」(本文書既存)

| 違反パターン                                       | 違反時の重大度 | 理由                                                   |
| -------------------------------------------------- | -------------- | ------------------------------------------------------ |
| 設計書にソースコードを多量に記載 (5〜10行を超える) | 🟡 major       | 設計書と実装の乖離源。MAJOR (≠ 即修正でないが品質問題) |
| 技術選択の理由を記載しないままフレームワーク指定   | 🔴 critical    | 設計判断の根拠喪失                                     |
| 要件にない機能の追加                               | 🔴 critical    | スコープクリープ。設計駆動の破壊                       |
| 「本設計により X を達成する」等の保証表現          | 🔴 critical    | spec_design_boundary §4.6 違反                         |
| AI が数値例から推測した設計目標                    | 🔴 critical    | spec_priorities §3.4 違反                              |

### 必須構成要素 (本文書既存)

各構成要素は「該当する場合に限り」必須とする。設計種別 (バッチ処理 / 内部 API / 文書-only feature 等) によっては不要な要素があり、画一的な必須化は false positive を生むため (軽量レビュー思想との整合)。

| 違反パターン                                                                         | 違反時の重大度 | 理由                                                            |
| ------------------------------------------------------------------------------------ | -------------- | --------------------------------------------------------------- |
| モジュールリスト欠如 (複数モジュール構成の場合)                                      | 🟡 major       | 設計書の構造把握困難。単一モジュール構成の場合は省略可          |
| コンポーネント図/クラス図欠如 (コンポーネント関係・クラス継承構造が複数存在する場合) | 🟡 major       | 構造関係が単純 (1〜2 コンポーネントの直列構成等) な場合は省略可 |
| ユースケース一覧欠如 (ユーザ操作・外部相互作用を伴う場合)                            | 🟡 major       | バッチ処理・内部 API のみ・文書-only feature 等の場合は省略可   |
| シーケンス図欠如 (該当する処理がある場合)                                            | 🟢 minor       | 処理がシンプルな場合は省略可                                    |

スコープ条件 (例: 「複数モジュール構成の場合」) は、reviewer が target_files の内容から判定する。判定根拠を finding に記録すること。

### よくある失敗パターン (本文書既存)

| 失敗パターン                                           | 違反時の重大度 | 理由                       |
| ------------------------------------------------------ | -------------- | -------------------------- |
| 既存資産を 1 パターン検索で諦め重複実装                | 🔴 critical    | 重複・不整合の温床         |
| プロジェクトの定数・デザイントークン無視のハードコード | 🟡 major       | 一貫性・保守性低下         |
| 同種機能の既存実装未確認 → 独自設計                    | 🔴 critical    | 重複・不整合の温床         |
| 設計判断の根拠未記載                                   | 🟡 major       | 保守時の意思決定再現性低下 |
| 実装後に設計書未更新                                   | 🟡 major       | 次回実装時の誤解源         |

### ADR 運用 (「設計書の保守」「歴史的記録を置かない」対応)

| 違反パターン                                                                           | 違反時の重大度 | 理由                                                                                       |
| -------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------ |
| 設計判断の変更（選択肢 A → B）を ADR に記録せず、設計書または既存 ADR 本文のみ書き換え | 🟡 major       | 判断変更の経緯の受け皿は ADR のみ。喪失すると再現不能                                      |
| ADR にコンテキスト / 決定 / 検討した代替案のいずれかが欠如                             | 🟡 major       | `adr_format.md` 必須構成。意思決定の再評価が不能になる                                     |
| 別 ADR が覆した決定に失効マーカーが無い                                                | 🔴 critical    | 失効した規範が有効なものとして読まれる。ADR は AI が提案を見送る根拠に使うため被害が大きい |
| 節番号の付け替え・節の削除                                                             | 🔴 critical    | `ADR-NNN §X.Y` 形式の外部参照（コード・テストを含む）が宛先を失う                          |
| 往復した事実（A → B → A）を書き直しで消した                                            | 🟡 major       | 一度戻した選択を再提案する経路が開く。棄却理由が依拠する前提の一部である                   |
| 棄却理由に依拠する前提が書かれていない（結論のみ）                                     | 🟡 major       | 前提が変わったかどうかを読み手が判定できず、失効した棄却理由が生き続ける                   |
| 文書単位の Status を復活させた                                                         | 🟡 major       | 置き換えは決定単位で起きるため、文書単位では部分失効を表せない                             |
| 部分失効なのに `## 2. 決定` 全体へマーカーを付けた                                     | 🟡 major       | 有効な決定まで失効扱いになり、現役の参照先が根拠を失う                                     |
| 棄却理由が当時の実装語彙のみで書かれ、提案の語彙になっていない                         | 🟢 minor       | 同じ案を別の言い方で提案されたときに突き合わせられない                                     |
| ADR を根拠に提案・所見を見送ったのに ADR ID を添えていない                             | 🟢 minor       | 見送りの根拠が追跡できず、棄却理由が失効していた場合に遡れない                             |
| 「決定が別 ADR へ移った」以外の理由で失効マーカーを付けた                              | 🟢 minor       | マーカーの意味が薄まり、本当に失効した決定が埋もれる                                       |

### アーキテクチャ・責務分割・可用性 (forge-review feature 統合で追加)

| 違反パターン                                                                  | 違反時の重大度 |
| ----------------------------------------------------------------------------- | -------------- |
| 採用アーキテクチャパターンの依存方向違反 (Domain → Infra 等)                  | 🔴 critical    |
| 循環依存                                                                      | 🔴 critical    |
| 1 コンポーネントの多責務化 (例: 認証 + レポート生成)                          | 🟡 major       |
| YAGNI 違反 (1 箇所のみ利用の汎用化)                                           | 🟢 minor       |
| 資産の置き場所が現在の責務と不一致 (責務外配下の手順書・借用参照の既成事実化) | 🟡 major       |
| 本番運用前提なのに SPOF を未冗長化・未記載                                    | 🔴 critical    |
| 外部 API 連携のリトライ戦略・タイムアウト未記載                               | 🟡 major       |
| 異常系データフロー・障害時挙動未記載                                          | 🟡 major       |

### 追加 feature 用 frontmatter

判定（追加 feature か否か）は [`additive_development_spec.md`](additive_development_spec.md) §1（適用条件 / 対象外）に従う。判定は変更の実質（分離管理価値・旧仕様との衝突リスク）で行い、main 初期立ち上げ、および分離して管理する価値のない軽微な追記・修正は対象外（false positive 防止）。frontmatter の定義は [`design_format.md`](design_format.md)「追加 feature 用 frontmatter」節を参照。

| 違反パターン                                                            | 違反時の重大度 | 理由                                                                         |
| ----------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------- |
| 追加 feature 設計書に `type: temporary-feature-design` frontmatter 欠如 | 🟡 major       | 旧設計書との優先関係・merge 予定が宣言されず、生成経路を問わず取りこぼされる |
