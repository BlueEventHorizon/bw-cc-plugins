# consult 提示原則

AI が人間に判断や議論を求めるときの原則。

前提として、**やり取りが流れるコンソールは読み返しに向いていない**。無関係な話が混在し、情報量も
多く、どこに何があるかが分からなくなる。読み返せないのではなく、探し出すのに労力がかかりすぎる。
したがってコンソールでの提示は**その場で完結**していなければならない。

短く書くのは、読み手に読む余裕がないからではない。**理解には読むことが必要であり、短さは理解の
代替にならない**。絞るのは媒体の制約に合わせるためであって、削ってよい内容があるからではない。
大事なのは順序と分量と置き場所であり、形式の作り込みではない。

---

## 1. 背景と本質を先に述べる

いきなり選択肢を出さない。まず次の 2 つを述べる。

- **背景**: 何が問題で、なぜ今それが論点になったのか
- **本質**: その中で判断を左右しているのはどこか（枝葉と区別する）

これを欠くと、読み手は「何の話が始まったのか」を自分で再構成することになる。その労力を負わせるなら
AI を使う意味がない。

## 2. 相談が複数あるなら、アジェンダ表で進める

一覧は目次であると同時に**進捗表**である。出しっぱなしにせず、進むたびに更新して再掲する。

1. 個別の話に入る前に、アジェンダを**表**で示す
2. **背景や本質は表に書かない**。表に収まらないし、書けば表が読めなくなる
3. **1 件ずつ**進める。その項目に入ったところで、背景・本質・推奨を詳しく述べる（原則 1・原則 3）
4. 1 件決着するごとに、**アジェンダ表を再掲する**。状態を更新し、決まったことを最後の列に書く
5. **次の項目へは AI が自分で進む**。「次はどれを見ますか」と聞かない。重要度の高い順に進め、
   読み手がすることは止める・飛ばす・順序を変えることだけでよい

5 を明文化するのは、表を出すことが安く、背景を書くことが高いためである。表だけを出して
「次はどれを見ますか」と問う形は、1〜4 のどれにも違反していないように見えて、実際には進行の判断を
読み手へ返している。形式を満たしたまま中身を空にできる経路を塞ぐ。

**同種の判断が繰り返される項目は、一括の判定表で提示してよい。** 1 件ずつの往復が判断の質を上げない
場面では、往復を増やすことのほうが害になる。ただし一括へ切り替える件数の閾値を AI が独自に定めない。

こうすると読み手は毎回、「今どこにいて、あと何が残っていて、これまで何が決まったか」をその場で
確認できる。流れたやり取りを探さずに済む（原則 5 を複数項目の相談で成立させる仕組みでもある）。

### 表の列と値

| 列         | 値                                                                 |
| ---------- | ------------------------------------------------------------------ |
| 項目       | 短い名前                                                           |
| 重要度     | 🔴 critical / 🟡 major / 🟢 minor（レビュー所見と同じ語彙を使う）  |
| 状態       | 未着手 / 進行中 / 決着 / 保留 / 対象外 / 取り下げ                  |
| 結果・課題 | 決着していれば決まったこと、していなければ**何が解決していないか** |

**この表は、進捗を追うために何を書くかを示す参考である。列名を規定するものではない。** 目的が
満たされるなら、扱う対象に合わせて名前や構成が違ってよい（レビュー所見のように項目名を持たない
対象では、`項目` の代わりに位置が識別子になる）。

**最後の列を空にしない**。決着した項目には決まったことを書き、決着していない項目には
**何が解決していないのかを 1〜2 行で書く**。項目名は短い名前でしかなく、それだけでは何が残って
いるのかが分からない。空欄が並ぶ表は、残件の一覧としては機能しない。

ここに書くのは**課題の所在**であって、背景（なぜ問題か）・本質（判断を左右するのはどこか）では
ない。後者は表に収まらないため、その項目に入ってから述べる（原則 1）。

**決定の帰属は AI が決めた場合にだけ書く**。既定は人が決めるものであり、全行に書けばノイズになる。
可視化したいのは、独断で決めた例外のほうである。

- **保留**: 今回は扱わないが、扱う可能性がある論点。脱線もさせず、取りこぼしもしないために行として残す
- **対象外**: 最初から今回の範囲外と決めた項目（＝今回やらないこと）。行に残しておくと、「なぜそれに
  触れないのか」を読み手が疑わずに済む。範囲を別途書き起こす必要もない
- **取り下げ**: 論点として誤りだったので取り消した項目。**消さずに残し、なぜ取り下げたか・誰の指摘に
  よるか（読み手の指摘か AI の自己訂正か）を書く**。消すと、誤りを出したこと自体が見えなくなる

レビュー結果の提示がこの典型である。所見が何件あり、どれが重いのかを先に示さないまま
1 件目の説明を始めると、読み手は終わりの見えない列に付き合わされる。

## 3. 推奨と理由があるなら、先に述べる

すでに判断がついているのに、それを伏せて選択肢を並べない。

- 推奨は **1 つだけ**。理由は簡潔に添える
- 「どちらでも良い」なら、それ自体が答えである。選択を求めない

## 4. 確信度を示す

断定形で書くと、確認した事実も推測も同じ強さに見える。**判断を左右する主張**には確信度を付ける。

| 記号   | 意味                           |
| ------ | ------------------------------ |
| ☑️      | 確認済み。実物を見た・実行した |
| 🤔     | 推論。根拠はあるが未確認       |
| (無印) | 未検証。記憶・推測のみ         |

- **判断を左右する主張を並べた表**では確信度の列を作る。地の文では主張に記号を添える。
  アジェンダ表（原則 2）は項目の進捗を示すものであって主張ではないため、確信度の列は作らない
- **無印が未検証を意味する**。付け忘れても確信度を高く見せないため、この向きにする
- 理由を言葉で添えるのは、確信度が判断を変えるときだけ。常に書くと結局長くなる
- 確信度が低く、検証できるなら**検証する**（実物を読む・実行する・調べる）。割に合わないなら無印のまま出す

## 5. 前の話を参照するときは、要点を再掲する

「前述の通り」「さっきの A 案」では伝わらない。流れたやり取りの中から該当箇所を
探す労力を読み手に負わせることになる。

- 過去の内容を持ち出すたびに、**それが何かを 1〜2 行で言い直す**
- 自分が付けた記号（ID・項目番号・案の名前）も同じ。記号だけで通じると仮定しない
- 参照リンクや位置の明示は、再掲の代わりにならない

## 6. コンソールには短く書く

コンソールへ大量に流すと、直後は読めても後から辿れなくなる。ただし**絞るのは分量であって、理解に
必要な内容ではない**。削れば読み手は判断できなくなる。短さは理解の代替にならない。

- 背景・本質・推奨を合わせて **10 行程度**に収める（暫定値。運用して調整する）
- **並列する項目は表にまとめる**。散文で列挙しない。表は読む労力を下げる
- 詳細は**求められてから**出す。先回りして書かない
- 表・コード片を並べない。使うなら 1 つまで。再掲するアジェンダ表（原則 2）はこの数に含めない
- **詳細をファイルへ置く場合、同じ内容をコンソールへ重ねて書かない**。書く場所を 1 つに決めれば
  総量は増えない。ただしコンソールには、**その項目単体で判断できるだけの要点を必ず書く**。
  ファイルは詳細の置き場であって、提示の省略先ではない

## 7. 議論の場では判断を迫らない

たたき台のレビュー・壁打ち・方針の相談では、**説明までで止まる**。

- 論点を挙げるのはよい。挙げた論点を順に問い詰めない
- 決めるフローへ移すのは、そうしてほしいと明示されてからにする
- **禁じているのは選択肢の提示だけではない**。「どれから見ますか」「これで進めてよいですか」も、
  形が違うだけで判断の投げ返しである。選択肢の形をとらなければよい、と読まない

## 8. 選択肢を出すとき

上記を満たしたうえで、なお選択が必要な場合のみ。

- 各選択肢が**何であるか**を 1 行ずつ示す（「A 案」「B 案」とだけ書かない）
- 選ぶと**何が変わるか**を示す
- 推奨 1 つと理由を添える
- 数は 2〜3 個に絞る

---

## 適用しない場面

- 説明する・教える場面 → 通常の説明で済ます
- 判断が定まっていて確認だけの場面 → 短い確認 1 つで足りる

## やってはいけないこと

| やってはいけないこと                    | なぜ                                               |
| --------------------------------------- | -------------------------------------------------- |
| 背景を書かずに選択肢から始める          | 読み手が文脈を再構成する羽目になる                 |
| 複数あるのに一覧を出さず 1 件目から話す | 全体量と軽重が見えないまま判断させることになる     |
| アジェンダを最初に出したきり更新しない  | 現在地と決着済みの内容が分からなくなる             |
| 未決着の項目の欄を空のままにする        | 何が残っているのかが項目名だけでは分からない       |
| 背景や本質を一覧の表に詰め込む          | 表が読めなくなる。詳細は各項目に入ってから述べる   |
| 推測を断定形で書く                      | 確認済みの事実と区別できなくなる                   |
| 扱わないと決めた項目を表から消す        | 「なぜ触れないのか」が読み手に分からない           |
| AI が決めたことを人が決めたように書く   | 独断の混入が後から見分けられない                   |
| 「前述の通り」で済ませる                | 読み手に探させることになる。要点を言い直す         |
| 並列する情報を散文で並べる              | 表にすれば一目で済む                               |
| 複数の論点を続けて問う                  | 1 つ提示 → 応答 → 次、の往復にする                 |
| 次に何をするかを読み手に選ばせる        | 進行は AI が持つ。読み手は止める・飛ばすだけでよい |
| ファイルに書いたからとコンソールで省く  | ファイルは詳細の置き場。提示の省略先ではない       |
| 同種の判断が並ぶのに 1 件ずつ往復する   | 往復が判断の質を上げないなら、往復自体が害になる   |
| 推奨を出さない / 複数出す               | 判断を投げているだけになる                         |
| 章立てを細分化する                      | 読む量が増え、要点が沈む                           |
| 詳細を先回りして全部書く                | 求められてから出せばよい                           |

```markdown
ユーザーへ判断・議論を求める場面では、`${CLAUDE_PLUGIN_ROOT}/docs/consult_principles_spec.md` を
Read し、背景と本質を先に述べてから提示すること。
```
