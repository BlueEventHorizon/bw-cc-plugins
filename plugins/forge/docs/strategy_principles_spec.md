# 実装戦略書 作成原則

プロジェクト固有のルールがない場合に参照する汎用原則。
プロジェクト固有のルールがある場合はそちらを優先すること。

本書は実装戦略書の定義と原則を定める。**誰が書く場合にも当たる**——`/forge:start-plan` が起動する `plan-strategist` カスタム Agent が書く場合と、設計フェーズ中などにユーザーの指示を受けて書く場合の双方である。

`plan-strategist` の策定手順（Step 1〜6・出力テンプレート）は、同 Agent の定義（`agents/plan-strategist.md`）が持つ。

---

## 実装戦略書の定義

- **責務**: 要件定義書と設計書を、どういう筋道で実装へ到達させるか。実装アプローチの選択、フェーズ分割、各フェーズの検証ポイント、リスクと対策。**差分開発では、新しい要件・設計を既存の実装へどう行き渡らせるかを書く**——既存と反するもの、既存に新規に加わるもの、既存と微妙に変わったもの、などについて、どのファイルをどう修正・削除・統合・分割するのかを決める。戦略書が書くのはこれだけではないが、差分開発では中心になり、かつ最も難しい
- **設計への依存**: 既存をどう扱うかの戦略は、設計に深く依存する。設計が新しい構造を示しているなら、既存の削除・統合・分割はその帰結であって戦略が自由に選ぶものではない。戦略の判断が要るのは、設計から導けない部分だけである
- **次工程との関係**: 実装戦略書は、計画書のタスクを作るための前提である。既存との不一致を詳細に吟味し、破綻なく処理する筋道を立てておかなければ、タスクは根拠を持たずに作られる
- **書かないもの**: 構造の設計（設計書の責務）／個々のタスクの実行単位（計画書の責務）
- **存在期間**: 一時。計画書と同じライフサイクルで扱い、全タスク完了時に計画書とともに存廃を利用者が選択する
- **正式名称**: 実装戦略書。ファイルは `{feature}_strategy.md`

## 計画書との線引き

実装戦略書と計画書は、扱う単位が違う。

| 文書       | 単位                       |
| ---------- | -------------------------- |
| 実装戦略書 | **フェーズ単位の順序**     |
| 計画書     | **タスク単位の実行可能性** |

戦略書はフェーズをどういう順序で通すかを決める。計画書は 1 つのタスクが単独で実行・完結できるかを決める。**フェーズの順序は、計画書ではタスクの優先度へ変換して反映される**（計画書にフェーズという構造は無い）。

この線引きを保てないと、戦略書がタスクを列挙し始めるか、計画書がフェーズの意図を抱え込むかのどちらかになる。

## 差分開発で最も難しいこと

差分開発では、既存の要件・設計に反する変更が起きる。What や How 自体を修正することになる（[additive_development_spec.md](additive_development_spec.md) §0 差分開発型）。

このとき既存の実装との関係はさまざまで、それぞれ扱いが異なる。

- **既存と反するもの** — 既存を否定する。衝突として現れるため気づきやすい
- **既存に新規に加わるもの** — 既存に対応物がない。どこに置き、既存とどう繋ぐかを決める必要がある
- **既存と微妙に変わったもの** — 一見同じに見えるが条件や範囲が変わっている。**既存と共存できてしまうため、気づかないまま両方が残る**

これらを見極め、どのファイルをどう修正・削除・統合・分割するのかを決める。**この判断は、他のフローとは比べ物にならないほど難しく、高度である。** 設計と現状を解析して整合させ、実装と修正を繋ぎ合わせる必要があるためである。

**だから実装戦略書は、計画段階の内部工程として片手間に済ませるものではない。**

### 手順で縛らない

どの扱いを選ぶかを、条件表や判断基準で縛らない。既存の構造と新しい設計を読んだうえで判断する以外にない。

縛らない代わりに、次を守る。

- **既存があるから修正で済ませる、という惰性で決めない。** 全面的に作り直すほうが正しい場合がある
- **設計から導けるものは設計に従う**（上記「設計への依存」）

### 対象は実装であって旧仕様の文書ではない

差分開発の期間中、旧仕様の要件定義書・設計書は書き換えない（[additive_development_spec.md](additive_development_spec.md) §3）。したがって戦略が突き合わせる相手は**既存の実装（コード）**である。旧仕様の文書は、実装がそうなっている理由を知るために読むに留める。

## 追加開発ワークフローとの関係

実装戦略書は [additive_development_spec.md](additive_development_spec.md) と密接な関係にある。同文書が定めるのは差分開発そのものの規範であり、実装戦略書はその規範のもとで**具体的にどう進めるか**を決める。

| 参照先                          | 戦略書が受ける制約                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| §2 実装期間中の旧仕様の置き換え | 当該範囲の現在の仕様は差分開発側である。旧仕様に合わせる戦略を立てない                                              |
| §3 実装期間中に書き換えないもの | 旧仕様の文書を書き換える戦略を立てない。実装は新要件に従って修正してよい                                            |
| §3.1 この制約は実装を縛らない   | 旧実装を残してよいのは、本 feature の外が依存していて同時に壊せない場合だけ。残すなら依存が解消された時点で削除する |
| §4 merge タイミングと手順       | merge は文書の齟齬を解消する作業であり、コードの後始末を含まない。旧実装の削除時期を merge に紐づけない             |
