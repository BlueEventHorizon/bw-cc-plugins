# ID 分類カタログ

プロジェクト固有の `spec_format.md` が見つからない場合に参照するカタログ。
プロジェクトの性質に合わせて必要なものを選んで使用する。使わない ID は定義しない。

要件・設計の境界ガイド: [spec_design_boundary_spec.md](spec_design_boundary_spec.md)

---

## Feature（フィーチャー）

Feature とは、仕様の断片をグループ化した開発単位である。

### いつ使うか

| 開発パターン       | Feature の使い方                                                     |
| ------------------ | -------------------------------------------------------------------- |
| 追加開発           | 既存のメイン仕様に後から追加する機能群を Feature として分割する      |
| アジャイル開発     | イテレーションごとに Feature 単位で開発・デリバリーする              |
| 小規模プロジェクト | Feature 分割せず、プロジェクト全体を1つの Feature として扱ってもよい |

### forge での扱い

forge のスキル（start-requirements / start-design / start-plan / start-implement）は、Feature 単位で処理を実行する。スキル実行時に **どの Feature に対して処理するか** を決定する必要がある:

- Feature が1つしかない → そのまま対象とする
- 複数の Feature がある → ユーザーに確認する
- Feature が未定義 → 新規 Feature として作成する

### ディレクトリ構造

Feature ごとに要件定義書・設計書・計画書をサブディレクトリで管理する:

```
specs/
  {feature}/
    requirements/   # 要件定義書
    design/         # 設計書
    plan/           # 計画書
```

実際のパスはプロジェクトの `.doc_structure.yaml` で定義される。上記は推奨構造であり、プロジェクトの都合に合わせて変更可能。

## 設計ID カタログ

| ID prefix | 対象                          | 主な用途                             |
| --------- | ----------------------------- | ------------------------------------ |
| `DES-xxx` | 設計書（汎用）                | モジュール設計・画面設計・機能設計   |
| `ADR-xxx` | アーキテクチャ決定記録（ADR） | 設計判断の根拠・選択した代替案の記録 |

ADR（Architecture Decision Record）は設計書と同じディレクトリに配置する。したがって `.doc_structure.yaml` に ADR 専用ディレクトリを定義しなくても、設計ディレクトリ配下に置く限り `next-spec-id` の git スキャンで採番できる。ADR の ID 採番は手動で決めず、必ず `next-spec-id` スキル（`python3 scan_spec_ids.py ADR --share-prefixes ADR,DES`）で取得する。ADR と DES は同一ディレクトリで通し番号を共有するため `--share-prefixes ADR,DES` を必ず付与する。書式（テンプレート・節の構成・失効マーカーの記法）は [adr_format.md](adr_format.md) に、運用は [design_principles_spec.md](design_principles_spec.md)「ADR の運用」に従う。

## タスクID カタログ

| ID prefix  | 対象           | 主な用途                               |
| ---------- | -------------- | -------------------------------------- |
| `TASK-xxx` | タスク（汎用） | プロジェクト構造に依存しない汎用タスク |

プロジェクトがレイヤードアーキテクチャを採用している場合、層別にプレフィックスを定義すると依存関係の整理に役立つ（例: ドメイン層・UI 層・インフラ層等）。具体的な命名はプロジェクトのアーキテクチャルールに従うこと。

## 文書参照の記法

### 第 1 原則: 必要でない参照は書かない

関連文書の発見は `/forge:query-db-specs` / `/forge:query-db-rules` が担う。「関連しそうだから」「念のため」の参照は書かない。

参照を書いてよいのは、**それを書かなければ本文の主張・規定が理解・検証できない場合に限る**。

### 第 2 原則: 書く場合はマークダウンリンク方式

必要と判断した参照は `[表示名](相対パス)` 形式で書く。

```markdown
判定の閾値は [DES-001_<name>_design.md](../design/DES-001_<name>_design.md) §3.2 に定義がある。
```

使わない記法:

- 地の文でのパス直書き（`docs/specs/.../xxx.md` を参照）
- リンクなしのファイル名のみの言及
- ID のみで「ここを見ろ」を意味させる参照（ID の用途は下記のとおり依存関係の記録に限る）

### メタデータの関連要件・関連設計は ID のみ

`関連要件` / `関連設計` に列挙する ID はナビゲーションではなく**依存関係の記録**である。ID のみを書き、リンクにしない。

| 場面                           | 形式    | 例                         |
| ------------------------------ | ------- | -------------------------- |
| メタデータの関連要件・関連設計 | ID 列挙 | `BL-017, FNC-009, SCR-016` |

```markdown
## メタデータ

| 項目     | 値                       |
| -------- | ------------------------ |
| 要件 ID  | BL-019                   |
| 関連要件 | BL-017, FNC-009, SCR-016 |
```

### 説明文中で ID に言及する場合

本文が指す対象の識別子として ID を書くのは差し支えない（`BL-006 で定義された Entity 構造に基づく` 等）。これは参照リンクではないため第 2 原則の対象外である。参照先を実際に読ませる必要がある場合のみ、第 2 原則に従いリンクを併記する。

### 禁止

- `## 関連文書` セクションを設けてリンクを列挙する（冗長。メタデータの「関連要件」で十分）

## ID 番号空間（namespace）と採番

### 新規 ID 採番は SKILL 経由で必須化 [MANDATORY]

新規 ID は **必ず `start-requirements` / `start-design` / `start-plan` 等の forge SKILL を経由して採番する**。これらの SKILL は内部で `next-spec-id` を呼び、プロジェクトの全 spec ディレクトリ・全ブランチ（ローカル + リモート）を横断してスキャンし、プレフィックスごとの `max + 1` を返す。

**意図的に番号を被せて新規ファイルを作成してはならない**。手作業で番号を選ばず、必ず SKILL 経由で採番する。

### namespace は spec ディレクトリ単位

ID 番号空間は **spec ディレクトリ単位で独立** している。プロジェクトが複数の spec ツリー（例: 配布単位ごとの `docs/specs/forge/`, `docs/specs/anvil/`, `docs/specs/common/`）を持つ場合、各ツリーの `docs/specs/{spec-dir}/` の `{spec-dir}` が暗黙の namespace として機能する。

### 既存の同居の扱い（過去事例の容認）

歴史的経緯で同じ ID が複数 spec ディレクトリに同居しているケース（例: 異なる 2 つの spec ツリーに同じ `DES-001` が存在する）は **過去事例として容認** する。互いに別物として共存し、`{spec-dir}` 修飾子で区別する（後述）。

ただしこれは **既存の歴史的状態に対する容認** であり、新規採番では発生させない。新規 ID は前項の SKILL 経由で全 spec ディレクトリ横断の一意番号を取得する。

### 横断プレフィックス

複数 spec ディレクトリで共有する横断仕様には、プレフィックスを変えて表現する（例: `COMMON-DES-xxx` は `docs/specs/common/` 配下の横断仕様用）。横断プレフィックスを持つ ID はそれ自体が namespace を兼ねる。

## クロス参照の原則

仕様文書間の参照は **同一 spec ディレクトリ内に閉じる** ことを基本とする。spec ディレクトリ境界を跨ぐ依存は、まず **SKILL（CLI コマンド）境界**で表現し、内部 ID のクロス参照は **必須のときのみ** に限定する。

### 基本: SKILL 境界で表現する

別の spec ディレクトリの仕様に依存する場合、可能な限り SKILL 名（`/forge:query-db-rules`, `/forge:query-db-specs` 等）でインターフェイスを記述する。SKILL.md が公開する引数・出力契約に依拠し、内部設計 ID（その SKILL の DES/FNC/ADR）は引かない。

**推奨**:

```markdown
プロジェクトのルール／仕様を参照するときは forge ラッパー (`/forge:query-db-rules` / `/forge:query-db-specs`) を呼ぶ（バックエンド選択はラッパーが内部で行う）。
実行ロジックの詳細は `/forge:query-db-rules` の SKILL.md を参照する。
```

**非推奨**（内部 ID への直接依存）:

```markdown
forge の auto モード起動仕様は DES-006 §2 の判定ロジックに従う。
```

### 例外: 別 spec ディレクトリの文書を参照する必要がある場合

参照先の規定が参照元の本文に転記されておらず、**参照先を読まないと本文の主張・規定が理解・検証できない**ときに限り、境界を越えて参照する。該当するのは次のような場合である:

- 横断規約（`COMMON-*`）の SoT 文書
- 出力契約・引数契約の SoT 文書
- 別 spec ツリーの設計判断を根拠として引く場合

この参照は「文書参照の記法」第 2 原則に従い**マークダウンリンク**で書く。ID のみを書いて「ここを見ろ」を意味させない:

```markdown
出力フォーマットの根拠は [DES-001_<name>_design.md](../../<spec-dir>/design/DES-001_<name>_design.md) §2 にある。
```

### メタデータで別 spec ディレクトリの ID を列挙する場合の修飾子記法

メタデータの `関連要件` / `関連設計` はリンクにせず ID を列挙する（「文書参照の記法」参照）。このとき別 spec ディレクトリの ID は **`{spec-dir}:{ファイル名}` 形式（フルファイル名、拡張子 `.md` なし）** で修飾する。同一 spec ディレクトリ内は修飾しない。

| 場面                               | 形式                      | 例                                 |
| ---------------------------------- | ------------------------- | ---------------------------------- |
| 同一 spec ディレクトリ内           | ID のみ                   | `DES-001`                          |
| 別 spec ディレクトリ               | `{spec-dir}:{ファイル名}` | `<spec-dir>:DES-001_<name>_design` |
| 別 spec ディレクトリの ID なし文書 | `{spec-dir}:{ファイル名}` | `<spec-dir>:<name>_strategy`       |
| 横断プレフィックス                 | プレフィックスのみ        | `COMMON-DES-001_<name>`            |

```markdown
| 関連要件 | <spec-dir>:REQ-001_<name>, COMMON-REQ-001_<name> |
| 関連設計 | <spec-dir>:DES-001_<name>_design, COMMON-DES-001_<name> |
```

**`COMMON-DES-` / `COMMON-REQ-` 等の横断プレフィックスを持つ ID は既に namespace として機能している** ため、修飾子を二重付与しない。

#### フルファイル名形式を採用する理由

- **grep 一発で命中**: メタデータの記載も、ファイル名そのものも、同一文字列で grep ヒットする
- **ID なし文書にも適用可能**: 計画書など ID を持たない ephemeral 文書も同一規約で記録できる
- **表記揺れの防止**: タイトル（説明文）併記は記載者により揺れる。ファイル名は一意で安定
- **ファイル命名規則との直接対応**: `{ID}_{name}_design.md` / `{ID}_{name}_spec.md` の命名規約と 1:1 対応
