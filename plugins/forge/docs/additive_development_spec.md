# 追加開発ワークフロー仕様

**目的**: 既存プロジェクトに機能を追加する際の「追加開発」ワークフローの判定基準と手順を定義する。

---

## 0. フィーチャーの概念定義

**フィーチャー**とは、要件群を区別するための **名前空間** である。複数の機能群を並行して管理するプロジェクトで、各機能群に属する文書を区別するための識別子であり、機能そのものの名前とは異なる。

### フィーチャーが持つ 2 つの性質

この名前空間は、既存仕様との関係によって次の 2 つの性質のいずれかを持つ。

| 型         | 既存仕様との関係                                                     | 性質                                                                                                           |
| ---------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 純粋追加型 | 既存の要件定義書・設計書と一切重複・矛盾しない、完全に独立した新機能 | 齟齬がそもそも存在しない。§2 が扱う置き換えの関係が生じず、§4 の merge の対象も生じない                        |
| 差分開発型 | 既存の要件定義書・設計書の一部を変更・拡張する                       | **新旧 2 つの仕様が一時的に並行して存在し、実装を経て 1 つへ統合される、時間軸を持ったトランザクションになる** |

どちらに該当するかは、上記の性質で判断し、**文書操作の形式では判定しない**。
名前空間を分けていても、既存文書への変更が不要なら純粋追加型である。

### 差分開発型が時間軸を持つ理由

§1〜§4 の個別ルールは、いずれもこの 1 つの性質から導かれる。

1. 実装完了まで旧仕様の文書を書き換えない（§3）。書き換えると、文書が現実とも新仕様とも食い違う中間状態が生まれる
2. 書き換えないため、実装期間中は新旧の仕様が並行して存在する
3. 並行している間、どちらが現在の仕様かが定まっていなければ、実装は旧仕様に従って作られる。これを定めるのが §2 である
4. 並行状態は永続しない。旧仕様側へ反映して齟齬を解消した時点で終わる。これが §4 の merge である

§3 の「旧仕様を書き換えない」は型を問わず常に成立する前提である。純粋追加型は旧仕様に触れる理由が無いため自然に満たすが、齟齬が無いという判定を誤ればこの禁止を破る。

フィーチャー名前空間（`specs/{feature}/` というディレクトリの切り方）は、この性質を運用するための入れ物にすぎない。名前空間を分けたこと自体は、差分開発型であることを意味しない。

### フィーチャー名が不要な場合

プロジェクトの **初回立ち上げ**（既存仕様がない）の場合、フィーチャー名は不要。要件定義書は `specs/requirements/` に直接配置する（`specs/{feature}/requirements/` のような階層は作らない）。

### フィーチャー名が必要な場合

以下のケースではフィーチャー名を付ける（本書 §1「適用条件」参照）:

- 既存仕様がすでに存在する
- 新しい要件群を既存要件と **分離して管理** する必要がある

### 基盤要件のフィーチャー名

初回立ち上げの要件に後からフィーチャー名を付ける場合は `base` または `core` を使う慣習がある。

### AI による置き換え禁止 [MANDATORY]

引数で指定されたフィーチャー名（`base` / `core` を含む）を AI が別の名前に置き換えてはならない。フィーチャー名はユーザーが決定する識別子である。フィーチャー名が指定されていない場合のみ、AI は確認または推定を行う。

### ディレクトリ例

```
# フィーチャー名不要（初回立ち上げ）
specs/
├── requirements/
│   └── REQ-001_xxx.md
└── design/
    └── DES-001_xxx.md

# フィーチャー名あり（追加開発）
specs/
├── requirements/        ← 既存
└── {feature}/
    ├── requirements/
    └── design/
```

## 1. 適用条件（いつ差分開発として feature を使うか）

**原則**: 実装の修正に伴い文書（要件定義書・設計書・計画書）側も変更が必要になる場合、追加・修正・削除のいずれの方向であっても差分開発として feature を使う。「新機能の追加」か「バグ修正」かという変更の名目では判定しない。

以下をすべて満たすときに feature が必要と判定する:

- 旧仕様（既存のコード・設計書・計画書・要件定義書）が既に存在する
- 実装の修正に伴い、既存の要件定義書・設計書のいずれかに変更が必要になる（実装のみを直し、文書側の記述を一切変更しない場合はこの条件を満たさない）
- 次の除外条件（本節末尾）のいずれにも該当しない

### 文書操作の形式は判定条件ではない [MANDATORY]

「要件定義書を新規作成したか／既存要件定義書へ追記したか」という文書操作の形式で判定してはならない。既存要件定義書への追記で書けてしまう場合でも、上記を満たす要件群は差分 feature として扱い、独立した一時要件定義書に切り出す。既存要件定義書へ先に追記した事実は、差分 feature 扱いを回避する理由にならない。

### feature 不要の除外条件（両方を満たす場合のみ）

以下の **両方** を満たす場合に限り、feature を使わず既存文書を直接編集してよい:

1. **規模が小さい**: 変更対象の文書が定量的に少ない（目安: 差分行数が少数〔例: 数行〕、かつ変更が要件定義書・設計書のうち1ファイル以内に収まる）
2. **質的レッドフラグに該当しない**: 以下のいずれにも該当しない
   - 旧仕様との一時的な矛盾（新旧が食い違った状態が実装完了まで残る）
   - ID 連番競合・並行開発上の衝突
   - 実装完了後の統合（merge）が必要になる規模の変更

上記 1 のみでは不十分であり、2 の質的レッドフラグに1つでも該当する場合は、たとえ差分が1行であっても feature を使う（例: 1行の文言修正だが既存の別要件と矛盾する場合）。

**対象外（feature 判定の土台にすら乗らないケース）**:

- 既存仕様が存在しない初回立ち上げ
- 実装のみを修正し、文書側は一切変更しない場合（バグ修正で仕様自体は正しかったケースを含む）
- **純粋追加型の feature（§0）**: 既存の要件定義書・設計書と一切重複・矛盾せず、既存仕様への merge を予定しない新規 feature namespace。この場合、当該 feature 配下の要件定義書・設計書・計画書は §6 の一時 frontmatter を付与しない（frontmatter の意味論「旧仕様が現在の仕様より古い状態にあり、実装完了後に齟齬を解消する必要がある」が成立しないため）。**判定は配置ではなく、既存仕様との重複・矛盾の有無で行う**（§0）。トップレベル namespace の新設でも既存仕様の一部を変更するなら差分開発型であり、既存 namespace 配下のサブ機能でも既存仕様と齟齬が無いなら純粋追加型である。なお frontmatter の付与は「いずれこの文書が消える」ことを意味しない。齟齬の解消後にその文書を残すか否かは §4.2 のスコープ判断で決まる

差分開発に該当する場合は、**作成する要件定義書・設計書の先頭に差分 feature 用 frontmatter を付与する**。各種別の frontmatter 定義は [frontmatter_format.md](frontmatter_format.md) に集約する。計画書には付与しない（同文書 §1.3 参照。`requirements_traceability` 経由で辿れるため不要）。

## 2. 実装期間中の旧仕様の置き換え

差分開発の要件定義書・設計書は、**その文書が対象とする範囲の現在の仕様**である。

旧仕様の記述（既存の要件定義書・設計書・計画書・ソースコード）は、その範囲について現在の仕様ではない。まだ更新されていないだけであり、内容としては差分開発側の文書へ**置き換わっている**。

### 置き換えに条件を付けない [MANDATORY]

**「矛盾する場合は差分開発側に従う」という形にしてはならない。** 条件を付けると、読み手に矛盾の判定を要求することになる。矛盾を見落とせば旧仕様のまま実装され、その見落としは成果物にも報告にも現れない。現在の仕様がどちらであるかは、矛盾の有無と無関係に決まっている。

判断例:

- 新要件「ユーザーはゲスト状態でも閲覧可能」／旧要件「全機能は認証必須」 → 現在の仕様は新要件である。旧要件は置き換わっている
- 新要件で既存 API の仕様が変わる → 新要件に従って実装する（旧設計書の記述は merge 時に更新する）

### どの文書が並行状態にあるかは読み手に探させない

並行状態にある文書は、その状態を機械可読な形で持つ（§6）。実装を担う者へは、自らが読む文書のうちどれが並行状態にあるかを、着手前に機械的に判定して渡す。読み手が文書を開いてマーカーを探すことに依存させない。

## 3. 実装期間中に書き換えないもの

追加開発の実装期間中、**旧仕様の文書（要件定義書・設計書・計画書）は書き換えない**。

| 対象                               | 判断                                                             |
| ---------------------------------- | ---------------------------------------------------------------- |
| 旧仕様の要件定義書・設計書・計画書 | 書き換えない。当該範囲の現在の仕様は差分開発側の文書である（§2） |
| 実装（ソースコード）               | 新要件に従って修正する（§2）。旧実装を温存する義務は無い         |
| 新機能のコード                     | 新規ファイル・新規ディレクトリに作成する                         |

**理由**: 旧仕様の文書を実装完了前に書き換えると、文書が現実とも新仕様とも食い違う中間状態が生まれ、並行して作業する者が誤った前提で判断する。merge タイミングで一括して整合を取ることで、仕様と実装の一貫性を保つ。

### 3.1 この制約は実装を縛らない

**本節の制約は文書に対するものであり、実装の形を指定しない。** 既存関数のシグネチャ変更・既存定数の変更・既存分岐の修正はいずれも通常どおり行ってよく、旧実装を残す義務は無い。§2 の判断例「新要件で既存 API の仕様が変わる → 新要件に従って実装する」がこれを示している。

旧実装を残す判断がありうるのは、次の場合に限る。

- 本 feature の外（他の呼び出し側・並行して進む別 feature）が旧実装の動作に依存しており、同時に壊せない

この場合は旧実装を残し、**依存が解消された時点で削除する**。削除時期を merge に紐づけない——merge は文書の齟齬を解消する作業であり（§4.1）、その手順（§4.3）にコードの後始末は含まれない。依存が無いなら残さない（使われない実装が残ると、次の実装者がどちらを正しいものとして読むか判断できなくなる）。

### 3.2 実装は本流から隔離した作業コピーで行う

**本流の作業ツリーを直接書き換えず、隔離した作業コピー（git worktree・専用のクローン等）で実装する。**

追加開発は既存の契約を作り替えるため、実装の途中はビルドもテストも壊れる。壊れている状態が本流に置かれていると、そこで別の作業をする者——同じ端末の別セッション、動作確認をする利用者——が巻き込まれる。巻き込まないために途中を取り繕おうとすると、要件にも設計にも無い互換コードが生まれる。

隔離すれば次が成り立つ。

- 途中がどれだけ壊れていても本流は動き続ける
- 壊してよいので、契約変更を一度に行える（段階的な互換層が不要になる）
- 捨てるときは作業コピーごと捨てられる

**「壊さないように直す」ではなく「壊してよい場所で直す」を既定とする。**

## 4. merge タイミングと手順

### 4.1 merge の定義 [MANDATORY]

**merge とは意味の統合であり、文書の物理的な結合ではない。**

追加開発の期間中、旧仕様は古いまま据え置かれる（§3）。その結果、実装完了時点では旧仕様の記述が
現実と食い違っている。merge が解消するのはこの**齟齬・不足・誤り**であり、新しい仕様を正として
旧仕様の記述を更新する作業を指す。

したがって次の 2 つは merge の目的ではない。

- 追加 DIR を消すこと
- 文書の本数を減らすこと

「追加 DIR が空になった」ことは完了条件ではない。完了条件は「旧仕様の記述が新しい仕様と矛盾
しなくなったこと」である。

### 4.2 何を移し、何を分離したまま残すか

判断は **スコープが同じか** で行う。文書の物理的な位置ではなく、内容が意味的にどこに属すかで決める。

| 内容の性質                                                     | 扱い                                                 |
| -------------------------------------------------------------- | ---------------------------------------------------- |
| 旧仕様の記述と矛盾する・旧仕様を変更する                       | 旧仕様側を改訂して解消する                           |
| 旧仕様に対応する記述が無く、**意味的に旧仕様と同じ文書に属す** | 旧仕様側へ移す（追加側の該当記述は移動後に残さない） |
| **旧仕様とはスコープが異なる**（独立した機能群・サブシステム） | 分離したまま維持する。旧仕様側へ移さない             |

**スコープが異なるものを無理に一体化してはならない。** 独立したサブシステム相当の
仕様を既存文書へ押し込むと、1 つの文書が複数の関心事を抱え、以後の改訂で毎回無関係な記述を
読まされることになる。分離できるものは分離したまま維持する。

スコープが同じかどうかは、次の問いで判断する。

- その記述を旧仕様の文書に置いたとき、**前後の文脈と地続きに読めるか**
- 旧仕様の読者が、その記述を**自分に関係する内容として読むか**
- 独立した名前空間として扱い続ける価値があるか（別 backend、別サブシステム、別配布単位など）

**言い換え**: 追加側の内容を「旧仕様と矛盾する部分」と「旧仕様のどこにも書かれていない新しい機能の部分」に分けて考える。

- **矛盾する部分**は旧仕様側を直して解消するので、追加側からは消える
- **新しい機能の部分**は、旧仕様のどこにも移す先が無いので、追加側にそのまま残る

追加側文書の内容がこの 2 種類のどちらで構成されているかによって、§4.3 手順 4 の削除・分離が決まる。

### 4.3 手順

1. **前提条件の確認**
   - 実装が完了している（計画書の全タスクが completed）
   - `/forge:review` によるレビューと修正が完了している
   - テストが通っている
2. **対象の仕分け**（§4.2 の基準で内容単位に分類する。ファイル単位で決めない）
   - 旧仕様と矛盾する内容 → 旧仕様を改訂する
   - 旧仕様と同一スコープの新規内容 → 旧仕様側へ移す
   - スコープが異なる内容 → 分離したまま維持する
   - 追加開発の計画 → 破棄（既に実装済み）
3. **旧仕様の改訂**
   - 旧仕様の記述を新しい仕様に合わせて更新し、前後の整合を取る
   - 意味を失った旧記述は削除する（痕跡を残すと矛盾源になる）
4. **追加側の後始末**
   - **追加側の全内容が「旧仕様と矛盾する部分」だけで構成されていた場合**: 旧仕様側の改訂（手順3）で
     解消済みのため、追加側に残る内容が無い。その文書を**削除**する
   - **追加側に「旧仕様のどこにも書かれていない新しい機能」の部分が残る場合**: その文書は**残す**。
     この場合、一時 feature 用 frontmatter（§6）を外し、恒久的な仕様として扱う
   - 計画書は破棄する
5. **ToC 再生成**
   - `/forge:update-db-specs` で specs ToC を更新

齟齬の解消が完了するまで、追加側の文書は残す。

## 6. frontmatter 定義

追加 feature 文書の frontmatter キー定義（`feature_type`/`feature_note`/`doc_status`）は [frontmatter_format.md](frontmatter_format.md) を単一の真実源とする。
