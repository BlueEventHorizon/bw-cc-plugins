# /anvil:triage-issue

GitHub Issue を実装着手前に吟味するスキル。責務は次の 2 つに限り、親が依頼している他の作業を引き継いではならない。

1. **Issue の内容が正しいか**を、既存仕様書・実装ルール・既存コードの実体で検証し、誤り・不足・過剰があれば Issue を正しい内容に書き直す
2. **やるべきことを TASK として列挙できるか**で、「ワンショット実装」（`anvil:impl-issue` を起動）と「要件定義から開始」（`/forge:start-requirements` を起動）のどちらへ進むかを判定する

**コード・設計書・PR の作成/実装は自らは行わない**。修正のための調査（類似 PR の学習・実装パターンの特定）も本スキルの責務ではなく `impl-issue` が行う。本スキルの調査はすべて「Issue の記述は正しいか」「やるべきことは列挙できるか」を答えるためのものである。

> 判定基準はヒューリスティックであり、使用しながら随時改良する。判定根拠を必ず明示し、後から「この判定は妥当だったか」を検証できるようにする。

## Goal

Issue の事実主張を実体で裏取りし、必要なら Issue を書き直し、TASK 化の可否でルートを判定して報告する。判定結果は会話での報告に加え、Issue コメントに監査記録として残す（Phase 8）。

不確定性は入力として受け入れるものではなく、**トリアージ中に解消する調査課題**である。調査で確認できる事実を未確認のまま次工程へ渡してはならない。

## ワークフロー

| # | Phase                                    | 成果                                                      |
| - | ---------------------------------------- | --------------------------------------------------------- |
| 0 | 前処理（リポジトリ解決）                 | `<owner>/<repo>`                                          |
| 1 | Issue 取得・構造化                       | 事実主張と解決提案の分離リスト                            |
| 2 | 仕様書調査                               | 関連仕様書の一覧と、Issue の記述と食い違う箇所の記録      |
| 3 | 実装ルール調査                           | 関連ルール文書の一覧と、解決提案が抵触する箇所の記録      |
| 4 | 既存コード調査                           | 変更対象・影響範囲の候補一覧                              |
| 5 | Issue 正誤判定と是正                     | 検証済みの Issue（必要なら全面改訂済み）                  |
| 6 | 影響範囲の深掘りと TASK 化               | TASK 一覧、または TASK 化できない理由                     |
| 7 | ルート判定                               | ワンショット実装 / 要件定義から開始 + 根拠                |
| 8 | 報告・Issue コメント・次工程への引き渡し | 監査コメント、impl-issue または start-requirements の起動 |

### Phase 0: 前処理（リポジトリ解決）

`.git_information.yaml` があれば `github.owner` / `github.repo` を読み、なければ `gh repo view --json nameWithOwner --jq '.nameWithOwner'` で `<owner>/<repo>` を解決する。以降の `--repo` 引数と `gh api` のパスにこの値を使う。

引数が Issue URL の場合は URL から `<owner>/<repo>` と `<N>` を取り出し、解決したリポジトリと一致することを確認する。不一致なら警告して**中断する**。URL 側と現在のリポジトリを示し、対象リポジトリで再実行するよう案内して終了する（別リポジトリの Issue を本文の全面置換とコメント全削除の対象にしない）。

### Phase 1: Issue 取得・構造化

1. `gh issue view <N> --repo <owner>/<repo>` と `--comments` で本文・コメント・ラベルを取得する
2. **主張と提案を分離する**: Issue 本文（コメント含む）を次の 2 つに仕分けて列挙する。この分離が無いと、Issue 起票者の推測を事実として調査せずに引き継いでしまう
   - **事実主張**（症状・現状の記述）— Phase 2〜4 で実体を確認する対象。確認が取れるまで事実として扱わない
   - **解決提案**（修正方針・実装案・スコープ）— 判定の入力であって要件ではない。Phase 5 で「提案より単純な解決で足りないか」「提案のスコープは起票者の意図と一致するか」を検証する対象
3. **非構造化 Issue の補完**: `<!-- issue-driven-flow:user-content:start -->` マーカーが無く、背景・現象（または要望）・期待される動作・再現手順（バグの場合）のいずれかが読み取れない場合、読み取れない項目を `AskUserQuestion` で 1 回にまとめて確認する（`create-issue` への差し戻しはしない）。回答は Phase 5 の是正の入力になる

### Phase 2: 仕様書調査

`Skill` ツールで `/forge:query-db-specs` を呼び、関連仕様書を特定する。`args` には Issue 本文をそのまま貼らず、Issue のタイトル・本文から**抽出した検索キーワード**または**短い自然文のタスク記述**を渡す。

- 特定した仕様書は**すべて** Read で本文を読む。見出しや検索結果の要約で済ませない
- Issue が触れる API・画面・制約・バリデーション・用語定義を、仕様書の記述として把握する。Issue の事実主張と食い違う箇所はその場で記録する（Phase 5 の入力）
- 関連する可能性がある周辺文書（同じ feature の要件定義書・設計書・ADR）も読む。ADR は「その案は検討済みで採らなかった」を答える記録であり、Issue の解決提案が過去に棄却された案と同じでないかを確認する
- **仕様書が見つからない場合も「該当なし」と記録する**（「調査したが 0 件」と「未調査」を区別する）

**外部リポジトリ・symlink**: 仕様書ディレクトリが symlink で別 Git リポジトリを指している場合、ローカルパスがローカルに存在しなくても仕様書が無いと判断しない。実体の GitHub リポジトリを直接参照して有無を確認し、記録には**実体の GitHub URL** を使う（`/forge:query-db-rules` で「外部仕様書リポジトリ」「symlink」等を検索し、リポジトリ名・URL 形式の規約を得る）。

### Phase 3: 実装ルール調査

`Skill` ツールで `/forge:query-db-rules` を呼び、Issue に関連するルール文書を特定する。`args` は Phase 2 と同じく抽出キーワードまたは短いタスク記述に限る。

- 特定したルール文書は**すべて** Read で本文を読む
- CLAUDE.md（プロジェクトルート）に記載されたプロジェクト構造・アーキテクチャ・禁止事項を確認する
- 「architecture」「coding」「layer」「ディレクトリ構造」等の一般クエリも 1 回投げ、Issue の話題に直接出てこない基盤ルールを取りこぼさない
- Issue の解決提案がルールに抵触しないかを確認し、抵触する箇所を記録する（Phase 5 の入力）
- 該当が無ければ「該当なし」と記録する

### Phase 4: 既存コード調査

Grep / Glob（利用可能であればコードシンボル検索ツール）で、Issue が指す現象の発生箇所と、変更されうる実装を特定する。この Phase の目的は**事実主張の裏取りと影響範囲の把握**であり、再利用資産の洗い出し・実装パターンの学習は `impl-issue` が行う。

探索対象:

- Issue が指す症状・機能の**発生箇所**（当該関数・クラス・設定・文書）。「Issue に書かれた場所」を信じず、Grep で実体を確認する
- 発生箇所の**参照元・呼び出し元**（変更が波及する範囲）。テスト・文書・設定・他スキルからの参照も含める
- 同じ症状が別の場所にも存在しないか（Issue が挙げていない同種箇所）
- `git log` で当該箇所の直近の変更履歴を確認し、既に修正済み・進行中の変更が無いかを見る

見つかったものはパスと一言メモ（何が書かれているか・Issue とどう関係するか）で記録する。見つからなかった場合も「該当なし」を記録する。

### Phase 5: Issue 正誤判定と是正

Phase 1 で分離した事実主張・解決提案を、Phase 2〜4 で得た実体と突き合わせて判定する。

#### 5-1: 判定

各事実主張・解決提案について、次のいずれかに分類し、根拠（仕様書・ルール・コードのパスと該当箇所）を添えて会話に提示する:

| 分類     | 意味                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 正しい   | 実体と一致する                                                                                         |
| 誤り     | 実体と食い違う（症状の場所・原因の推定・現状の記述が実体と異なる。仕様書・ルールと矛盾する提案を含む） |
| 不足     | 実体には存在するが Issue に書かれていない（同種の別箇所、影響を受ける参照元、前提となる制約）          |
| 過剰     | Issue の提案スコープが必要な範囲を超えている、またはより単純な解決で足りる                             |
| 判定不能 | 実体で確認できず、起票者・利用者の意図を確認しないと決まらない                                         |

「判定不能」は `AskUserQuestion` で選択肢と帰結を添えて確認し、結論を得る。質問は未決事項を集約して 1 回にまとめる。認証・権限不足・参照先の消失で調査できない場合は**調査ブロッカーとして終了**し、何を確認できず、何があれば再開できるかを報告する。

#### 5-2: 是正（Issue の書き直し）

「誤り」「不足」「過剰」が 1 件以上ある場合、Issue を**正しい内容に書き直す**。是正の範囲は**全面改訂を含む**: 本文を新たに書き起こし、既存コメントをすべて削除してよい。

誤った記述を Issue に残さない理由は、後続の工程（`impl-issue` / `start-requirements`、および将来この Issue を読む AI）が旧文言を引用し、正しい記述を旧文言に合わせて改変する事故を防ぐためである。「参考として残す」「打ち消し線で残す」は採らない。

手順:

1. 新しい本文を組み立てる。構造は `/anvil:create-issue` が生成する形（`<!-- issue-driven-flow:user-content:start -->` 〜 `<!-- issue-driven-flow:user-content:end -->` のマーカー対の中に、種別に応じた必須セクション）に揃える。既存本文にマーカー対があればそれを保ち、無ければ新たに付ける。タイトルも誤っていれば書き直す
2. 新本文の中身は Phase 2〜4 で確認した**実体**だけで構成する。確認していないことを書かない。起票者の解決提案のうち妥当なものは「解決の方向性」として残してよいが、事実主張と区別して書く
3. `AskUserQuestion` で新タイトル・新本文の全文と、削除するコメントの一覧（ID・投稿者・先頭 1 行）を提示し、承認を得る。選択肢は「承認する / 承認しない」の 2 つとする。承認前に書き込み・削除を行わない。承認されなかった場合は書き直しを実行せず、Phase 6 以降へ進まずに利用者の指示を待つ（誤りがあると判定した Issue のまま TASK 化・ルート判定・実装工程の起動へ進まない）
4. 承認後、実行する。一時ファイルは `mktemp -d` で作り、固定パスを使わない。後始末は `trap` で行う（途中の `gh` が失敗しても消える）:

   ```bash
   workdir=$(mktemp -d)
   trap 'rm -rf "$workdir"' EXIT
   tee "$workdir/issue_body.md" <<'BODY'
   <新本文>
   BODY
   gh issue edit <N> --repo <owner>/<repo> --title "<新タイトル>" --body-file "$workdir/issue_body.md"
   # コメントの全削除（1 件ずつ。id は gh api repos/<owner>/<repo>/issues/<N>/comments --jq '.[].id' で取得済みのもの）
   gh api -X DELETE "repos/<owner>/<repo>/issues/comments/<comment_id>"
   ```

5. `gh issue view <N> --repo <owner>/<repo> --comments` で結果を確認し、新本文が反映され、コメントが残っていないことを検証する

**誤り・不足・過剰が 1 件も無い場合は Issue に触れない**（書き直しは是正のためだけに行う。文言の好みで書き換えない）。

### Phase 6: 影響範囲の深掘りと TASK 化 [MANDATORY]

是正済みの Issue を入力に、「やるべきこと」を TASK として列挙できるかを試みる。

1. **影響範囲の確定**: Phase 4 で把握した変更対象と参照元について、不明な点が 1 つでも残っていれば再調査する。「影響範囲は不明だが小さいだろう」で進めない。影響範囲の再調査で変更対象が増えることは通常起こり、増えた分も TASK に含める
2. **TASK の列挙**: 次の 3 項目が埋まる粒度で列挙する。埋まらない TASK は「TASK 化できない」に分類する
   - 対象（ファイル・モジュール・文書。実在をパスで確認済み）
   - 変更内容（何をどう変えるか。「調査する」「検討する」は変更内容ではない）
   - 完了の確認方法（テスト・実行結果・文書の照合など）
3. **TASK 化できない理由の分類**: 埋まらない TASK があれば、なぜ埋まらないかを次のいずれかで記録する
   - 要件が定まっていない（何を達成すべきかが利用者の判断に依存し、その判断に要件レベルの合意が要る）
   - 妥当な解が複数あり、選択基準が要件に依存する
   - 影響範囲が閉じない（再調査しても変更対象が確定しない）

TASK 化の判定は**内容の明確さ**で行う。TASK の数・変更量・修正規模は判定に使わない（数千行の機械的な置換でも TASK として明確ならワンショットで足りる）。逆に 1 行の変更でも「どう変えるべきか」が要件に依存すれば TASK 化できない。

利用者に確認すれば決まることは `AskUserQuestion` で確認して決める（Phase 5-1 と同じ規律）。確認して決まったことは「TASK 化できない」に数えない。

### Phase 7: ルート判定

| ルート           | 条件                                 | 次工程                                            |
| ---------------- | ------------------------------------ | ------------------------------------------------- |
| ワンショット実装 | Phase 6 で全 TASK が列挙できた       | `anvil:impl-issue` を起動する（Phase 8）          |
| 要件定義から開始 | TASK 化できない項目が 1 つ以上残った | `/forge:start-requirements` を起動する（Phase 8） |

判定には**一文の根拠**を必ず添える。ワンショット実装なら TASK 一覧そのものが根拠になる。要件定義から開始なら、TASK 化できなかった項目とその理由（Phase 6 の分類）を根拠として具体的に書く。

**アンチパターン（すべて誤判定）**:

- 「修正量が膨大なので要件定義から」— 量は判定根拠にならない
- 「やり方が未定なので要件定義から」— Phase 6 の解消義務違反。その場で決められることは決める
- 「Issue に書かれていないので要件定義から」— Phase 2〜4 で調べれば分かることを未確定にしない
- 「TASK は列挙できたが念のため要件定義から」— 誤判定は両方向とも失敗である。軽量で足りる修正を要件定義に送るのは分岐点の機能不全であり、判定への信頼を壊す

### Phase 8: 報告・Issue コメント・次工程への引き渡し

#### 8-1: 会話での報告

```text
## Issue #<N> トリアージ結果

### Issue の正誤
- 判定: <正しい / 誤り n 件・不足 n 件・過剰 n 件（是正済み）/ 是正せず>
- 主な是正点: <要旨>

### TASK 一覧（ワンショット実装の場合）
| # | 対象 | 変更内容 | 確認方法 |

### TASK 化できない項目（要件定義から開始の場合）
- <項目>: <理由の分類> — <何を試してなぜ決まらなかったか>

### 結論
- ルート: ワンショット実装 / 要件定義から開始
- 根拠: <一文>

### 調査結果（impl-issue / start-requirements が参照できる）
- 関連仕様書: <ローカルパス> / <GitHub URL> / 該当なし
- ルール文書: <path> / 該当なし
- 既存コード: <path>（<一言メモ>） / 該当なし
```

#### 8-2: Issue への監査コメント

`gh issue comment <N> --repo <owner>/<repo> --body-file -` で 8-1 と同内容を Issue にコメントとして残す。目的は判定の監査記録であり、後続工程はこれを参考にしてよいが、これを根拠に自らの調査を省いてはならない（`impl-issue` は修正のための調査を自ら行う）。

Phase 5-2 でコメントを全削除した場合、このコメントは是正後の最初のコメントになる。是正の要旨（何が誤っていて何に直したか）を必ず含める。

書く内容の境界: 判定結果と根拠、是正の要旨、Phase 2〜4 で特定した参照先のパス一覧、TASK 一覧。具体的な実装方法・クラス名レベルの実装計画は書かない（`impl-issue` の責務）。

#### 8-3: 次工程への引き渡し

**ワンショット実装の場合**: `AskUserQuestion` で起動確認を 1 回だけ行う:

```text
Issue #<N> はワンショット実装（TASK <n> 件を列挙済み）と判定されました。このまま実装（impl-issue）に進みますか？
- はい: impl-issue を起動する
- いいえ: ここで終了する（後で /anvil:impl-issue #<N> を直接実行できる）
```

「はい」の場合、`Skill` ツールで `anvil:impl-issue` を起動する（args: `<N>`）。同一セッションのため Phase 2〜4 の読了内容は共有されるが、`impl-issue` は修正のための調査を自らの手順で行う。`impl-issue` が中断・失敗した場合はその内容をそのまま報告する（本スキル側でリトライや代替経路の提案は行わない）。

**要件定義から開始の場合**: TASK 化できなかった項目（＝要件定義で合意すべき論点）を提示したうえで、`AskUserQuestion` で起動確認を 1 回だけ行う:

```text
Issue #<N> は要件定義から開始（TASK 化できない項目 <n> 件）と判定されました。このまま要件定義（forge start-requirements）に進みますか？
- はい: start-requirements を起動する
- いいえ: ここで終了する（後で /forge:start-requirements を直接実行できる）
```

「はい」の場合、起動契約を確定してから `Skill` ツールで `forge:start-requirements` を起動する。確定するのは次の 3 つである。

| 要素              | 決め方                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| モード            | `interactive`                                                                                                                     |
| `--new` / `--add` | 新規アプリの立ち上げであれば `--new`、既存アプリへの機能追加であれば `--add` と判定し、`AskUserQuestion` で確認する               |
| feature 名        | Phase 2 で Issue が属する既存 feature を特定できた場合のみ、その名前を `AskUserQuestion` で確認して渡す。特定できなければ渡さない |

確定した値を args として渡す（feature 名を渡す場合は `{feature} --mode interactive {--new または --add}`、渡さない場合は `--mode interactive {--new または --add}`）。**Issue 本文・是正内容・調査結果を args に貼らない**。これらは同一セッションの context で共有されるため、再供給は不要である。

起動後の対話では、是正済みの Issue 本文・TASK 化できなかった論点・Phase 2〜4 の調査結果から**既に答えが得られている事柄を提示して確認を取る**（ゼロから聞き直さない）。答えが得られていない事柄だけ、その旨を前置きしたうえで利用者に尋ねる。

ルール文書・既存仕様の取得は `forge:start-requirements` 側の手順どおり実行し、Phase 2〜3 の調査結果で代替しない（調査の目的が正誤検証と要件定義で異なるため）。
