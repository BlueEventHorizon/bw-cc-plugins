# /anvil:triage-issue

GitHub Issue を実装着手前にトリアージし、「ワンショット実装」「SDD（`/forge:start-requirements` または `/forge:start-design` から始まる連続フロー）」「plan モードでの検討提案」のどれに委ねるべきかを判定する、**開発フロー全体の唯一の分岐点**となるスキル。**コード・設計書・PR の作成/実装は自らは行わない**（ワンショット実装は `impl-issue` を起動して委ね、SDD・plan モードは提案する）。判定結果は会話での報告に加え、Issue 側にも申し送りとして記録する（Phase 8 参照）。

> ワンショット実装ルートの入口は本スキルに一本化されている。`anvil:impl-issue` は `user-invocable: false` であり、本スキルの Phase 8-3 からの Skill ツール起動が唯一の開始経路。

> 判定基準はヒューリスティックであり、使用しながら随時改良する。判定根拠を必ず明示し、後から「この判定は妥当だったか」を検証できるようにする。

## Goal

**本スキルの中核機能は、フロー選定の前に Issue を吟味し、その場で調整・決定できることを実施すること**（Phase 5.5）である。その上で、Issue の内容・関連仕様書・類似実装・既存コードを「判定ができる水準」まで調査し、次を判定して報告する。

1. **判定 A（ワンショット充足性）**: 要件定義と整合したまま、文書作業ゼロまたは設計書の軽微な追随修正だけで完結するか。No なら SDD ルートとし、エントリポイント（`start-requirements` / `start-design`）を特定する
2. **判定 B（決め事の残余。判定 A = Yes の場合のみ）**: 解消手段を尽くしても対話の往復でしか決着しない決め事が残るか。残るなら plan モードでの検討を提案し、残らなければワンショット実装（`anvil:impl-issue` による直接対応）へ進む
3. **feature 要否判定（SDD ルートの場合のみ）**: `additive_development_spec.md` §1 の適用条件で判定する

不確定性は入力として受け入れるものではなく、**トリアージ中に解消する調査課題**である。調査で確認できる事実を未確認のまま `start-*` へ渡してはならない。

## ワークフロー

### Phase 0: 前処理（リポジトリ解決）

`.git_information.yaml` があれば読み、なければ `gh repo view --json nameWithOwner --jq '.nameWithOwner'` で `<owner>/<repo>` を解決する。

### Phase 1: Issue 確認・構造化度チェック

1. `gh issue view <issue番号> --repo <owner>/<repo>` と `--comments` で本文・コメントを取得する
2. **構造化度を判定する**:
   - `<!-- issue-driven-flow:user-content:start -->` マーカーがある → `/anvil:create-issue` 経由で作成された構造化 Issue
   - マーカーがなく、本文が簡潔・テンプレート不完全（例: 「不具合の説明」「再現手順」のみで内容が数行） → 非構造化（メモ書き）Issue
3. **主張と提案を分離する [MANDATORY]**: Issue 本文（コメント含む）を次の 2 つに仕分けて列挙する:
   - **事実主張**（症状・現状の記述）— Phase 2〜5 で実体を確認する対象。確認が取れるまで事実として扱わない
   - **解決提案**（修正方針・実装案・スコープ）— 判定の入力であって要件ではない。Phase 5.5 で「提案より単純な解決で足りないか」「提案のスコープは利用者の意図と一致するか」を検証する対象
4. **非構造化の場合**: 以下が Issue から読み取れるか確認し、読み取れない項目は `AskUserQuestion` でユーザーに確認する（`create-issue` 相当の聞き取りをこのスキル内で完結させる。`create-issue` への差し戻しはしない — 差し戻す先の入力経路をそもそも経由していない Issue のため）:
   - 背景・現象（何が問題か）
   - 期待される動作（あるべき姿）
   - 再現手順（バグの場合）
5. 確認できた不足情報は、この後の Phase での判定材料として使う（Issue 本文そのものを書き換えることはしない。書き換えは後続の実行スキル — `impl-issue` / `start-requirements` 等 — の責務とする）

### Phase 5.5: 不確定性の解消【本スキルの中核機能】

フロー選定の前に Issue を吟味し、**その場で調整・決定できることは実施する**。Phase 1〜5 で認識した不明点・判断分岐を列挙し、Phase 6 の前に 1 件ずつ解消する。

1. **実物で確認できること**: 仕様書・ルール・コード・テスト・git 履歴・類似 PR・外部公式文書を追加調査する。安全な read-only コマンドで確認できる場合は実行する
2. **既存パターンで決まること**: Phase 2〜5 で特定した規範・先例と照合して結論を出す
3. **利用者の意思決定が必要なこと**: 選択による具体的な差を示し、`AskUserQuestion` で確認して結論を得る
4. **解消結果を記録する**: 各不確定性について、結論と根拠を Phase 8 の申し送りへ含める

**不確定性台帳 [MANDATORY]**: 認識した不明点・判断分岐を台帳形式（項目 / 解消手段の分類 / 結論 / 根拠）で列挙し、会話に提示する。解消手段は上記 1（実物確認）/ 2（既存パターン）/ 3（利用者確認）のいずれかに分類する。Phase 1 で分離した「解決提案」の検証（より単純な解決で足りないか・スコープは利用者の意図と一致するか）も台帳の項目として扱う。項目が 1 件も無い場合は「不確定性なし」と明記する（台帳の省略と区別するため）。

**Phase 6 への進入条件**: 台帳に未解消の項目が残る状態で Phase 6 へ進んではならない。

- 手段 3（利用者確認）に分類した項目は、選択肢と帰結を添えた `AskUserQuestion` を**実行して回答を得るまで未解消**である。質問は未決事項を集約して 1 回にまとめて行う
- どの手段でも解消できなかった項目だけを「真の未確定」とし、**何を試してなぜ決まらなかったか**を 1 文で記録する。この記録を持たない項目を Phase 6 で「未確定」の根拠に使ってはならない
- 修正スコープの広さ・症状の複数性は SDD 行きや plan モード行きの根拠ではなく、手段 3（スコープ選択の利用者確認）で解消する

**禁止事項**:

- 「Issue に書かれていない」「未調査」「要確認」だけを理由に未確定と判定する
- 調べれば分かる事実を、`start-requirements` / `start-design` に調査させるため未確定のまま残す
- 利用者へ確認できる選択を、質問せずに「決め事が残る」と判定する
- 調査不能の原因を SDD ルートで解消できると仮定する

認証・権限不足、参照先の消失などにより調査を完了できない場合は、SDD へ進めず**調査ブロッカーとして終了**する。何を確認できず、何があれば再開できるかを報告する。

### Phase 6: ルート判定

#### フローの責務定義（判定の土台）

フロー選択は各フローの責務への照合としてのみ行える。判定するのは、**この変更の検証・追跡に必要な開発文書の種別**である。**変更量・修正規模・AI の判断量を判定の根拠にしてはならない**（5 万行の変更でも script で機械的に書き換えられるならワンショットで足りる）。

| フロー                    | 文書作業                                                 | 責務（何を検証可能にするか）                                                                                     |
| ------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| ワンショット実装          | なし、または設計書の一部の追随修正（同じ変更の中で直す） | 要件定義と整合したまま完結する変更。量は無関係                                                                   |
| SDD: `start-requirements` | 要件定義書から連続フローを開始                           | What の痕跡。要件が変わる変更、または有効な要件定義書が無い状態で文書の裏付けが必要な変更                        |
| SDD: `start-design`       | 設計書から開始（**入力にする要件定義書の実在が前提**）   | How の痕跡。設計の本質を新たに起こさないと良し悪しを判定できない変更（計画書以降は SDD の連続フローの中で続く）  |
| plan モード（提案）       | 不要（開発文書は作らない）                               | 文書は不要だが、作業の形・決め事が対話の往復でしか決着しない作業（利用者と対話しながら計画・調査・検証を進める） |

SDD は要件定義 → 設計 → 計画 → 実装の**連続フロー**であり、エントリポイントは「チェーン先頭から最初に作成・改訂が必要な文書」で決まる。途中から入るには上流文書の実在が前提になる（`start-design` は入力の要件定義書を特定できなければ提案できない。存在しなければ「作成が必要」なので `start-requirements` が入口になる）。

**アンチパターン（すべて誤判定）**:

- 「修正量が膨大なので SDD」— 量は判定根拠にならない
- 「やり方が未定なので SDD」— Phase 5.5 の解消義務違反でもある。その場で決められることは決める
- 「設計書に触るので SDD」— 軽微な追随修正はワンショットの範囲

> 誤判定は両方向とも失敗である。SDD が必要な変更をワンショット実装へ流すのは品質の失敗であり、軽量で足りる修正を SDD へ送るのは分岐点の機能不全である（文書工程のコストを不要に課し、判定への信頼を壊す）。判定に迷ったら SDD に倒すのではなく、Phase 5.5 へ戻って迷いの原因を解消してから判定する。

#### 判定 A: ワンショット充足性

**この変更は、要件定義と整合したまま、文書作業ゼロまたは設計書の軽微な追随修正だけで完結するか**。Yes/No と一文根拠を必須記載する。

- **Yes（文書は不要、または設計書の軽微な追随のみ）** → 判定 B へ
- **No（開発文書の作成・本質的な改訂が必要）** → SDD ルート。エントリポイント特定へ

**No には立証が必須**: どの文書に、なぜ本質的な作成・改訂が必要かを、Phase 5.5 の台帳の項目で具体的に挙げる。挙げられなければ Yes とする（挙証責任はワンショット側ではなく SDD 側にある）。

**エントリポイント特定（判定 A = No の場合）** — チェーン先頭から「最初に作成・改訂が必要な文書」を特定し、Phase 7 へ:

- 要件が変わる・要件の合意形成が必要・有効な要件定義書が存在しない → `/forge:start-requirements`
- 要件定義書は健在で、設計書の作成・本質的な改訂が必要 → `/forge:start-design`（Phase 8 の提案に、入力となる要件定義書の実在パスを必ず添える）

#### 判定 B: 決め事の残余（判定 A = Yes の場合のみ）

**Phase 5.5 の解消手段（実物確認・既存パターン・質問 1 回）を尽くしてなお、対話・調査・検証の往復でしか決着しない決め事が残るか**。Yes/No と一文根拠を必須記載する。

- **Yes** → **plan モードルート**（作業の形・決め事が未決: 規範文書の整理・一括是正・基準適用型の作業等）。Phase 8 へ。判定 B を Yes にできるのは、台帳で「真の未確定」と記録された項目（何を試してなぜ決まらなかったかの記録つき）を具体的に挙げられる場合に限る。**検討に有益だから、では Yes にしない**（必要な場合に限る。過剰トリガーはワンショット実装を空洞化させる）
- **No** → **ワンショット実装**（Phase 7 はスキップし Phase 8 の「ワンショット実装の場合」へ）

> **既知の制約**: 判定 A・B には Phase 2〜5.5 の調査結果が必要なため、「軽量と分かった Issue でもフル調査コストがかかる」という非対称は受け入れる。調査を省いて誤った分岐を返すより、入口で不確定性を解消することを優先する。

### Phase 7: feature 要否判定（SDD ルートの場合のみ）

他プラグイン（forge）の内蔵文書へは直接パス参照しない。`Skill` ツールで `/forge:query-forge-rules`（args 例: `差分開発フィーチャー 判定基準 additive development spec`）を呼び、返された文書パスを Read して `additive_development_spec.md` §1 の適用条件・除外条件を取得し、そのまま適用する。

- まず判定する: 実装の修正に伴い既存の要件定義書・設計書のいずれかに変更が必要か（文書側が一切変わらない＝実装のみのバグ修正なら、ここで **feature 不要**・Phase 7 終了）
- 文書側の変更が必要な場合、§1 の除外条件（規模が小さい **AND** 質的レッドフラグに該当しない）を両方満たすかを判定する
  - 両方満たす → **feature 不要**（既存の要件定義書・設計書を直接編集する経路）
  - いずれか満たさない → **feature 必要**（`--new` または `--add`）。「バグ修正だから」という名目のみを理由に不要と判定してはならない

### Phase 8: 判定結果の報告 + Issue への申し送り + （ワンショット実装のみ）impl-issue 起動

**forge の start 系スキル（`start-requirements` / `start-design`）は起動せず、plan モードへの遷移も自動では行わない**（いずれもユーザー判断に委ね、提案に留める）。**ワンショット実装と判定した場合のみ**、8-1・8-2 の後に 8-3 で `impl-issue` を起動する。

**plan モードルートの提示の作法（AskUserQuestion 規約の例外宣言）**: 本スキルはユーザーへの確認に AskUserQuestion を使うが、plan モードの提案だけは**議論の内容そのものの提示**として、背景（何が決め事として残ったか）と本質を添えて**地の文で提示**する。選択肢 UI は背景を置く場所を持たず、「これでも行けますか」と利用者が問い返して議論できる形を保つためである。例外はこの提示までであり、進行上の機械的な確認（8-3 の impl-issue 起動確認等）には従来どおり AskUserQuestion を使う。

#### 8-1: 会話での報告

```
## Issue #<N> トリアージ結果

### 判定
- 解消した不確定性: <件数と要旨（利用者確認の結果を含む）/ なし>
- 判定A（ワンショット充足性）: Yes / No — <根拠（No の場合は、どの文書に、なぜ本質的な作成・改訂が必要か）>
- エントリポイント: start-requirements / start-design（入力の要件定義書: <パス>） — <根拠（判定A = No の場合のみ）>
- 判定B（決め事の残余）: なし / あり — <根拠（判定A = Yes の場合のみ。あり の場合は、何を試してなぜ決まらなかったか）>
- 結論: ワンショット実装 / SDD（エントリポイント: start-requirements / start-design） / plan モードでの検討を提案

### 推奨ワークフロー（SDD ルートの場合のみ）
- feature 要否: <必要（--new|--add） / 不要（既存文書直接編集）>
- 判定根拠: <Phase 7 の適用条件との照合結果>

### 次のアクション
<ワンショット実装: "8-3 で impl-issue の起動を確認します" / SDD: "<エントリポイント> から始めることを推奨します（起動はユーザー判断）" / plan モード: 残った決め事と検討の進め方を地の文で提案する（自動遷移しない）>
```

#### 8-2: Issue への申し送りコメント（`gh issue comment`）

会話での報告とは別に、`gh issue comment <N> --repo <owner>/<repo> --body-file -` で 8-1 と同内容の要約を Issue にコメントとして残す。

このコメントは監査記録であると同時に、**セッションを跨いだ場合に `impl-issue` が調査結果を復元する永続ストア**を兼ねる（`impl-issue` Phase 0-2 参照）。調査結果の4カテゴリ（関連仕様書・ルール文書・類似 PR・既存コード）は省略せず、該当が無かったカテゴリも「該当なし」と明記する（「調査したが 0 件」と「未調査」を区別可能にするため）。

**機械可読マーカーで囲む**: このマーカーが効くのは同一セッション内の連続フローではなく、**セッションが途切れた後**（再開・PR失敗からの再開）に限られる。その場面では複数回 triage・手書きコメントが混在しうるため、「どれが最新の正本か」という位置特定に、AI の読解力ではなく本スキルのテンプレートだけが書く固有マーカーを使う（手書きコメントが偶然似た文言を含んでも誤って一致しない）。**ワンショット実装と判定した場合のみ**、コメント本文全体を以下のマーカーで囲む:

```
<!-- anvil:triage-result:v1:start -->
（8-1 と同内容の要約）
<!-- anvil:triage-result:v1:end -->
```

SDD ルート・plan モードルートの場合はマーカーを付けない（`impl-issue` はワンショット実装 Issue に対してしか起動されないため、それ以外の判定コメントを機械的に見分ける必要がない。SDD・plan モードの判定も監査記録として平文コメントには残すが、マーカー対象外）。

ワンショット実装かどうかの判別自体は、マーカー内の見出し文言（「## トリアージ結果: ワンショット実装」）で行う。この文言は `impl-issue` がどのみち読んで理解する調査結果本文の一部であり、専用の `route:` フィールドを別途設けても読み違えのリスクは実質的に下がらないため設けない。

マーカーを含まないコメント（手書き・旧スキーマ・SDD / plan モード判定）は無視する。マーカー内のスキーマを変更する場合は `v1` を `v2` へ上げ、`impl-issue` 側の復元ロジックも同時に更新する。

**書く内容の境界**:

- 書く: 判定結果（判定 A・判定 B・エントリポイント・feature 要否）とその根拠、Phase 2〜5 で特定した関連仕様書・ルール文書・類似 PR・既存コードのパス一覧、Phase 5.5 で解消した不確定性の結論と根拠（要約のみで詳細分析は書かない）
- 書かない: 具体的な実装方法・クラス名・ファイルパスレベルの実装計画（`impl-issue` Phase 8 の責務。越境しない）

**参照の種別を明記する [MANDATORY]**: 関連仕様書・ルール文書の各パスには `kind: local_path`（ローカルの相対パスで `impl-issue` が Read できる）または `kind: github_url`（外部リポジトリ・symlink 経由で実体の GitHub URL のみ記録、`references/phase-02-spec-investigation.md` 参照）を付す。`impl-issue` はこの種別で取得方法を分岐する（Phase 2 参照）。

- ルール文書: <path> (kind: local_path) / 該当なし
- 類似 PR: #<N>（<一言メモ>） / 該当なし

#### 8-3: impl-issue 起動（ワンショット実装の場合のみ）

8-1・8-2 の完了後、`AskUserQuestion` で起動確認を 1 回だけ行う:

```
Issue #<N> はワンショット実装（文書作業は不要または軽微な追随のみ、決め事の残余なし）と判定されました。このまま実装（impl-issue）に進みますか？
- はい: impl-issue を起動する（Phase 2〜5.5 の調査・解消結果を引き継ぐため再実行されない）
- いいえ: ここで終了する（後で /anvil:triage-issue #<N> を再実行すれば再開できる）
```

「はい」の場合、`Skill` ツールで `anvil:impl-issue` を起動する（args: `<Issue 番号>`）。調査結果は同一セッションのコンテキストで共有され、セッションを跨いだ再開時は 8-2 のコメントから復元される（引き渡し用の一時ファイルは作らない）。

`impl-issue` が中断・失敗した場合はその内容をそのままユーザーに報告する（本スキル側でリトライや代替経路の提案は行わない）。
