# agent とのデータ受け渡し

SKILL（呼び出し側）とカスタム Agent の間で、**1 回の処理の間だけ存在するデータ**をやり取りするときの規範。この規範に従って作れば、データの大きさに関係なく受け渡しが壊れない。

各機能は自分の script を持ち、この規範に従う。仕組みの実装を 1 つに共有することは求めない。

## 適用範囲

| 対象                                                    | 扱う文書                                                       |
| ------------------------------------------------------- | -------------------------------------------------------------- |
| 処理の間だけ存在し、終われば消えるデータ（依頼・結果）  | **本文書**                                                     |
| 恒久的に置かれている文書（内蔵 docs・プロジェクト文書） | [forge_doc_access_principle.md](forge_doc_access_principle.md) |

両者はライフサイクルが違う。forge_doc_access_principle.md が「ファイル経由の受け渡しは採用しない」とするのは恒久的な文書への到達経路のことであり、本文書が定める一過性のデータには当たらない。

## なぜ prompt と return value で運ばないか

prompt と return value に全文を載せると、次のことが起こる。

- **大きくなると破綻する。** 渡す側も受ける側も、全文を自分のコンテキストに抱える
- **AI が中継することになる。** 中継のたびに要約・欠落・書き換えが入りうる。受け取った側は、それが元のままかを確かめる手段を持たない
- **形が決まらない。** AI が組み立てた出力は、受け取る側に検査を要求する（[deterministic_generation_spec.md](../../plugins/forge/docs/deterministic_generation_spec.md)）

## 基本原則

### 運ぶのは識別値だけ [MANDATORY]

呼び出し側が agent へ渡すのは、データの置き場を一意に決める**識別値だけ**である。中身は渡さない。

- 識別値は script が生成し、AI は返された値をそのまま運ぶ。自ら生成・加算しない
- 置き場は識別値から script が決める。AI はパスを組み立てない
- 識別値の構成（1 つか複数か、何を区別するか）は各機能が決める

### 書くのは script [MANDATORY]

データは script が書く。AI は JSON を組み立てない。

- AI は値を script へ渡し、script が構造を作って置く。値は生成・要約・改変せずにそのまま置く
- 組み立て途中のものを読ませない。完成するまで下書きとして保持し、完成後に 1 回の操作で公開する

### 読む側はパスを得て直接読む

読む側は識別値を script へ渡し、返された絶対パスのファイルを直接読む。

- script は JSON 本文を標準出力に載せない。返すのはパスだけである
- 読み出してよい状態か（公開済みか、正常に書き終えたか）は script が判定し、そうでなければパスを返さずに失敗する

### 値は変形せずに届く

値は途中で欠落・変形・分断されない。改行・引用符・バッククォート・非 ASCII を含んでも、渡した内容と同一のまま届く。

- 値の内容を理由に受け渡しを拒まない
- 書き込みの経路で、値が構文として解釈される経路を作らない

### 意味は定義が持つ [MANDATORY]

JSON を直接読む以上、読む側は各フィールドの意味を事前に知っていなければならない。書く側も、どの script がどのフィールドを書くかを知らなければ書けない。

- **script の呼び方と、フィールドの意味は、読み書きする主体自身の定義（SKILL.md / agent 定義）が持つ**
- 意味を値に添えて運ばない。同じ意味が 2 箇所に置かれ、片方だけが古くなる
- 定義を読めない主体は、この仕組みに参加できない

### 確定してから書き、上書きしない

- 判断をすべて確定させてから書き出す。1 件ずつ渡すのはよいが、判断しながら逐次書き出さない
- 上書き・修正の操作を持たない。持たせれば「後から直せる」前提が生まれ、逐次の書き出しを誘発する

### 終了の値で成否を表す

書き出しを終えたら、結果の一部として**終了の値**を書く。別の記録機構を設けない。

- **正常時にだけ印が残る形にする。** 異常時に何かを書かせる形では、落ちた・黙って終えた・起動に失敗した場合を取りこぼす。終了の値が取れないことを異常として扱えば、それらがすべて収束する
- 終了の値は文字列とし、正常は `"0"` とする。エラー値は閉じた集合とし、定義に無い値は異常として扱う
- 何をエラー値にするかは [error_classification_spec.md](../../plugins/forge/docs/error_classification_spec.md) に従う。挙げるべきものが無ければ、集合は空でよい
- 成否の判定は script が行う。AI に終了の値を確かめさせて進退を決めさせない

### 形式の検証を置かない

script が組み立てる以上、形が壊れるのはバグである。実行時に形式を検査しない。

検査を置くのは、**script が組み立てても自動的には満たされないもの**だけである（例: 2 つの結果の間の対応関係）。

### パスは絶対パスでよい

一過性で配布されないため、データの中のパスは絶対パスでよい。書く側も読む側も演算を要しない。配布物に絶対パスを書いてはならないこととは扱いが違う。

- プロジェクトルートをデータで運ばない。各主体は自分の定義から実パスを知る

### 終わったら削除する

処理が終わったら、その処理のために保持したものをすべて削除する。

## 各機能が決めること

本文書は受け渡しの型だけを定める。次は各機能の要件定義書・設計書が決める。

- 識別値の構成と生成の仕方
- 置き場
- 依頼と結果のフィールドと、その意味
- エラー値の集合
- 受け渡し以外の振る舞い（採番・終端条件等）
