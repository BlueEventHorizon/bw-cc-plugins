# 実装ガイドライン

プラグインのスクリプト（Python / Bash）および SKILL.md 実装時のルールを定義する。

---

## スクリプト言語の選定 [MANDATORY]

処理内容に応じて Python または Bash を選定する。

| 条件                                           | 言語   | 理由                                          |
| ---------------------------------------------- | ------ | --------------------------------------------- |
| データ変換・パース・YAML/JSON 操作             | Python | 構造化データ処理に強い                        |
| 外部コマンド呼び出し・ファイル操作・パイプ処理 | Bash   | シンプルで高速。Python 起動オーバーヘッドなし |
| 両方の特性が必要                               | Python | Bash の複雑化を避ける                         |

**Python スクリプトは標準ライブラリのみ使用する**（外部依存禁止。**例外: PyYAML のみ許容**。標準ライブラリに YAML パーサーがないための唯一の例外であり、他の外部ライブラリへは拡張しない）。
**Bash スクリプトは外部コマンド（codex, git, curl 等）の呼び出しに使用してよい。**

---

## テスト必須 [MANDATORY]

`plugins/` 配下の Python スクリプトにはテストが必須。Bash スクリプトは手動テストまたは統合テストで確認する。

### 対象と例外

| 対象                    | テスト必須         | 理由                                           |
| ----------------------- | ------------------ | ---------------------------------------------- |
| `plugins/` 配下の `.py` | 必須               | プラグインとして配布されるコード               |
| `plugins/` 配下の `.sh` | 推奨（統合テスト） | 外部コマンド依存のため単体テスト困難な場合あり |
| SKILL.md                | 例外               | AI の振る舞いを記述するもので自動テスト困難    |
| `.claude/` 配下         | 対象外             | ローカルスキル・プロジェクト固有スクリプト     |

### テストの配置

`tests/` にプラグイン名・スキル名で分類して配置する:

```
tests/
├── common/                 # プラグイン横断（マニフェスト整合性等）
├── forge/
│   ├── review/             # plugins/forge/skills/review/scripts/ のテスト
│   └── scripts/            # plugins/forge/scripts/ のテスト
└── {plugin}/               # 新プラグイン追加時も同構造
```

テストディレクトリ名はスキルディレクトリ名と一致させる。スキルを rename した場合はテストディレクトリも同時に rename する（片方だけ変えると、旧名のテストが新スキルのスクリプトを参照して静かに壊れる）。

命名規則: `test_{module}.py`（例: `test_session_manager.py`）

### テスト実行

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

## SKILL.md にインラインスクリプトを書かない [MANDATORY]

処理ロジックを SKILL.md 内にインラインで記述してはならない。

### 理由

AI が SKILL.md 内のスクリプトを解釈して実行する際、コードを勝手に改変・省略して失敗するリスクがある。独立したスクリプトファイルであれば、AI はそのまま実行するだけで済む。

### 正しいパターン

処理ロジックは独立したスクリプトファイル（Python または Bash）として実装し、SKILL.md からはそのスクリプトを呼び出す。

```markdown
# ❌ NG — SKILL.md 内にロジックを記述

以下の Python コードを実行してデータを集計する:

    import json
    data = json.load(open('plan.yaml'))
    # ... 50行のロジック ...

# ✅ OK — 外部スクリプトを呼び出す

以下のスクリプトを実行して集計結果を得る:

    python3 "${CLAUDE_PLUGIN_ROOT}/scripts/<domain>/<operation>.py" {入力パス} {出力パス}
```

### スクリプト・文書の配置

| 配置先                                     | 用途                                     |
| ------------------------------------------ | ---------------------------------------- |
| `plugins/{plugin}/skills/{skill}/scripts/` | スキル固有のスクリプト                   |
| `plugins/{plugin}/scripts/`                | プラグイン共通のスクリプト               |
| `plugins/{plugin}/skills/{skill}/docs/`    | スキル固有の文書（そのスキルのみが使う） |
| `plugins/{plugin}/docs/`                   | プラグイン共通の文書（複数スキルが使う） |

配置は「その資産を使うスキルが1つだけか、複数か」で決める。1つだけなら `skills/{skill}/` 配下、2つ以上のスキルが使うなら `plugins/{plugin}/{scripts,docs}/` 直下へ配置する。

**他スキルの `skills/{skill}/` 配下を直接参照してはならない** [MANDATORY]。あるスキルが別スキルの `skills/{他スキル}/docs/xxx.md` を `${CLAUDE_PLUGIN_ROOT}/skills/{他スキル}/docs/xxx.md` のようにハードコード参照すると、参照元スキルの視点では「他人の持ち物への無断参照」になり、参照先スキルの内部構成が変わった際に静かに壊れる（実例: criteria文書がスキル固有の場所にあった時、別スキルから直接参照されており、プラグイン共通の場所へ移動した際に参照が壊れた）。複数スキルから必要だと判明した時点で、対象資産をプラグイン共通の場所へ昇格する（コピーではなく移動）。

SKILL.md からの参照には `${CLAUDE_SKILL_DIR}` または `${CLAUDE_PLUGIN_ROOT}` を使用する。

forge 内蔵ルール（`/forge:query-forge-rules` → `design_principles_spec.md`「設計書の保守」）に従う。

本リポジトリ固有の補足:

- ADR の配置先: `docs/specs/**/design/ADR-{NNN}_{topic}.md`（設計書と同じディレクトリ。feature が入れ子になる場合も同じ）

## 配布物はプロジェクト開発文書を参照しない [MANDATORY]

`plugins/` 配下のうち**利用者環境で読まれるもの**（SKILL.md / `agents/*.md` / `commands/*.md` / 配布物内蔵 `docs/*.md` / templates）から、**本リポジトリに実在する** `docs/` 配下の文書（`docs/specs/` / `docs/rules/` / `docs/readme/`）を参照しない。パス直書きも spec ID による出典表記も禁止する。

```text
❌ 複数文書間の優先順位は DES-028 §3.4.1 に従う
❌ 詳細は docs/specs/forge/design/DES-029... を参照
```

**script（`.py` / `.sh`）のコメント・docstring と、`scripts/` 配下の開発者向け README は対象外とする。** 基準は拡張子ではなく**誰が読むか**である。 利用者環境のフローでは読まれず（SKILL.md はコンテキストへ注入され内蔵 docs は SKILL から名指しで読まれるが、script はソースを開いた者にしか見えない）、開くのは実装を追う開発者だからである。実装の意図がどの決定に由来するかを実装のすぐ隣に残せる価値のほうが大きい（判断根拠は [ADR-055](../specs/common/design/ADR-055_distribution_boundary_for_doc_references.md) §2.3）。

```text
⭕ 本スクリプトは REQ-012 FNC-004 の実装である    （script のコメント）
```

**ID 体系・書式の抽象例は許容する。** プレースホルダ番号（`DES-001` / `REQ-001` / `TASK-001` 等）や、対象プロジェクト側の構造を示すプレースホルダパス（`docs/specs/<feature>/design/*.md`、`docs/specs/**/design/` 等）は、実在文書を指していないため対象外である。format 文書・設定例・出力例がこれらを使えないと成立しないため、禁止してはならない。

```text
⭕ - requirement_id: REQ-001          （plan.yaml の書式例）
⭕ docs/specs/<feature>/design/*.md    （対象プロジェクトの構造を示すプレースホルダ）
⭕ "docs/specs/**/design/": design     （.doc_structure.yaml の設定例）
```

代わりに:

| 目的                             | 書き方                                                               |
| -------------------------------- | -------------------------------------------------------------------- |
| 規範の根拠を示す                 | 下記「規範の置き場は 2 通り」から選ぶ                                |
| プロジェクト固有ルールを参照する | `/forge:query-db-rules` / `/forge:query-db-specs` で動的に発見させる |
| 設計判断の経緯を残す             | `docs/specs/` 側に書く（配布物からは参照しない）                     |

逆方向（`docs/` の設計書が `plugins/` の実装を参照する）は許容する。

### 規範の置き場は 2 通り。どちらを選んでもよい

| 方式                                    | 書き方                                                                       | 向いているケース                                                         |
| --------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **A. 参照元に本文を持たせる**           | 規範本文を参照元（SKILL.md / agent / 内蔵 docs）にそのまま書く               | 分量が小さい。1 箇所でしか使わない                                       |
| **B. 配布物内に別文書を作って参照する** | 規範本文を `plugins/<plugin>/docs/` 配下の新規文書に書き、参照元から参照する | 分量が大きい。複数の SKILL / agent から使う。SKILL.md を肥大させたくない |

方式 B の参照記法は参照元の位置で決まる（forge の `document_style_guide.md` §5.1）:

- `SKILL.md` / `agents/*.md` / `commands/*.md` から → `${CLAUDE_PLUGIN_ROOT}/docs/xxx.md`
- 配布物内蔵 docs 同士 → 相対パスのマークダウンリンク

方式 B で新規文書を作ったら、その配布物の ToC を再生成する（forge なら `update-forge-toc`）。再生成しないと `/forge:query-forge-rules` から発見できない。

判断根拠: [ADR-055_distribution_boundary_for_doc_references.md](../specs/common/design/ADR-055_distribution_boundary_for_doc_references.md)

## 使わないコードは削除する [MANDATORY]

非推奨マーカーやコメントアウトで残さない。残存コードは勘違いの原因になる。

- 削除の経緯はコミットメッセージへの記載で十分（CHANGELOG には `/forge:update-version` 実行時に git log から自動反映される）
- 「将来使うかもしれない」は削除の理由にならない。git 履歴から復元できる
- テストファイルも本体と同時に削除する

---

## AI が解釈すべき入力にスクリプトパーサーを使わない [MANDATORY]

ユーザー入力（コマンド引数等）は自然言語が混在するため、リジッドなトークンパーサーではなく AI が直接解釈する。

- スクリプトは構造化データ（YAML/JSON）の処理に限定する
- 引数が不足・曖昧な場合は AskUserQuestion で補完する
- コマンド構文は SKILL.md に記載し、AI がそれを参照して意図を汲み取る

## フォールバックを反射的に書かない [MANDATORY]

フォールバック自体が禁止なのではない。**その異常系に対する正しいリカバリーとして具体的に説明できるフォールバックは問題ない。** 禁止するのは、説明できないまま「一応の保険」として反射的にフォールバックを書く癖である。

### 禁止パターン（反射的フォールバック）

- 失敗時に「別モードに切り替えて続行する」「非同期に委ねて次工程へ進む」等と書くが、それが呼び出し元にとって何を意味するか（確定した結果を得られるのか、処理が実質的に進むのか）を詰めていない
- 例外を握りつぶして既定値やダミー結果で代替する
- 「具体的に何が起きるか」を自分で説明できないまま、設計書・要件定義書にフォールバック文言を書く

### 正しい判断手順

1. フォールバックを書きそうになったら、まず「これはこの異常系に対する正しいリカバリーか」を自問する。説明できないなら書かない
2. 正しいリカバリーとして採用する場合も、呼び出し元が受け取る結果（確定した成功/失敗なのか、何が保留されるのか）を明記する
3. リカバリーとして不適切、または説明できない場合は、フォールバックで隠さず**エラーとして明確に報告**し、呼び出し元が次の判断（再試行・手動対応・中断）をできるだけの確定した情報を返す。その上で、原因（リトライ不能な処理順序、タイムアウト値の欠如、境界条件の見落とし等）を特定し、エラーが構造的に起こらないよう設計・実装を見直す

### 理由

反射的なフォールバックは一見ロバストに見えるが、実態を詰めずに書かれることが多く、失敗を隠蔽して呼び出し元・利用者が異常に気づく機会を奪う。フォールバック先の経路が呼び出し元の前提（同一ターン内で結果を受け取る等）と矛盾する場合、処理は実質的に何も進んでいないのに「継続できた」ように見えてしまう。フォールバックを選ぶこと自体でなく、**それを吟味せず反射的に選ぶこと**が問題である。

## 検索インデックス（ToC）の commit は利用者に確認する [MANDATORY]

`.claude/.doc-advisor/toc/` 配下の ToC は git 管理下の生成物である。**再生成そのものは行ってよい**が、
main / develop 以外のブランチで**差分を commit 対象に含めるかは利用者に確認する**。

### 再生成を止めない理由

ToC が古いと、そのブランチで追加・改訂した文書が検索結果に出ない（false negative）。検索の正確さは
再生成でしか保てないため、禁止しない。索引更新は desired-state であり、**対象文書に変更がなければ
ToC は書き換わらず差分も出ない**。差分が出るのは、そのブランチで実際に文書を変えたときだけである。

### 確認する理由

他ブランチで commit すると、並行して作業している他のワークツリー・他の作業者の再生成結果と衝突し、
merge 時に破棄される。捨てられる作業を黙って積まないため、含めるかどうかを利用者が決める。

### 確認する場所

**commit 確認の場で問う**（`/anvil:commit` の Phase 3）。追跡済みファイルの一括ステージに ToC 差分を
混ぜず、別の選択肢として提示する。混ぜると「毎回確認する」が実際には成立しない。

### レビュー所見の扱い

**レビューで ToC の古さを指摘されても、commit 済みの ToC を feature ブランチで直そうとしない。**
指摘自体は事実（検索が削除済みパスを返す等）だが、解消するのは main / develop 側での再生成である。

## バージョン関連ファイルの編集禁止 [MANDATORY]

feature PR / fix PR / refactor PR 等の通常の作業 PR で、バージョン関連ファイルを編集してはならない。
バージョン更新の単一責任は `/forge:update-version` にあり、AI および開発者が個別 PR で先回りバンプしてはならない。

### 編集禁止対象

| 対象                                        | 内容                                              |
| ------------------------------------------- | ------------------------------------------------- |
| `plugins/*/.claude-plugin/plugin.json`      | 各プラグインの `version` フィールド               |
| `.claude-plugin/marketplace.json`           | 各プラグインエントリの `version` フィールド       |
| `README.md` / `README_ja.md` のバージョン表 | プラグインバージョン記載行（数値変更を伴う diff） |
| `CHANGELOG.md` 等の変更履歴ファイル         | 全エントリ（追加・修正・削除いずれも禁止）        |
| git tag（`v*` / `<plugin>-v*`）             | 作成・移動・削除いずれも禁止                      |

### 例外

以下に限り編集してよい:

- 新規プラグイン追加時の初期値記述（`0.0.1` 等の新規エントリ作成。既存値の変更ではないため）
- `/forge:update-version` を明示起動した場合（唯一の正規ルート）
- 本ルール文書自体の改訂

### 唯一の正規ルート

バージョン更新は `/forge:update-version` のみが担う:

- Step 3.5: `current > main` 検出時に二重バンプ確認 → **1 リリース = 1 バンプ**
- Step 5: git log から CHANGELOG エントリを自動生成 → PR ごとの CHANGELOG 編集は二重作業 + 競合源

詳細は `docs/specs/forge/design/DES-023_version_management_workflow_design.md` を参照。

### 理由

| 理由                           | 説明                                                                    |
| ------------------------------ | ----------------------------------------------------------------------- |
| リリース単位の一意性           | 誰がいつ何をまとめてリリースするかを `/forge:update-version` に集約する |
| CHANGELOG 自動生成との衝突回避 | git log 由来の自動生成と手動編集が二重化すると整合性が崩れる            |
| 並行 PR の merge conflict 回避 | 複数 PR が同時に同じ version 行を編集すると衝突が頻発する               |

**NEVER** feat / fix / chore コミットの流れで AI が自発的にバージョンをバンプしてはならない。
**MUST** バージョン更新が必要と判断したら、ユーザーに `/forge:update-version` の明示起動を提案する。
