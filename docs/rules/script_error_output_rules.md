# script のエラー出力

## 基本原則

### 終了コードの前提

| 値       | 意味                                                   | 意味を定める場所         |
| -------- | ------------------------------------------------------ | ------------------------ |
| `0`      | 依頼された操作が完了した                               | 本文書（全 script 共通） |
| `1`      | 完了しなかった。区別のない失敗であり、理由の区別は無い | 本文書（全 script 共通） |
| `2` 以上 | 完了しなかった。理由はその値ごとに異なる               | それを返した script だけ |

**全 script に共通の意味を持つのは `0` と `1` の 2 つだけである。** `1` はどの script でも同じ意味であり、**固有の理由を `1` に割り当ててはならない**。理由を区別する script は、その理由へ `2` 以降を割り当てる。

したがって `1` を見たらそれ以上の区別が無いと判断してよく、`2` 以上を見たら、それを返した script に意味の宣言がある。

### なぜ `2` 以上に共通の意味を置かないか

script のエラー出力の契約は、**その script 自身が持つ**。呼び出し側が持つと、別の場面から呼んだときに参照先がない。

原因の種類ごとに数値を割り当てる体系を中央に置けば、その体系をどこかで管理し続けることになり、管理コストが割に合わない。script の出力を読むのは基本的に AI であり、自然文からエラーの種別を読み取って分岐できる。

その代わり、**非 0 値の意味は、それを返した script の中に書かれていて読めば分かる状態**にする。中央の定義を置かないという選択は、局所の定義を書く義務と対になっている。定義がどこにも無ければ、読み手は他の script の実装を観察して規約を推測するしかなく、存在しない規約が生まれる。

## 詳細ルール

### 適用範囲

- 本リポジトリ `plugins/` 配下に**新規に配置する** Python script に適用する
- 既存 script は本文書の適用対象外とする。改修の機会に個別に寄せる
- 人間が読む shell script の表示形式（色・バナー・メッセージの体裁）は[CLI 出力フォーマット指針][cli-output]が定める。本文書は AI が読む機械可読な出力を対象とする

### 終了コード [MANDATORY]

- **「完了した」の判定に、結果の中身を混ぜない**。検査して所見が 0 件でも、変更の必要が無くても、対象が 0 件でも、依頼された操作そのものは完了している。いずれも `0` で返し、内容は標準出力の JSON で示す
- **`2` 以上の値の意味を、それを返した script 以外の記述から推論してはならない**。他の script の実装・他の script を説明する文書・値の並びは、いずれもその script の意味の根拠にならない

### 終了コードの宣言 [MANDATORY]

- **`2` 以上の値を返す script は、自身の module docstring に、返しうる全終了コードの完全な表を置く**。表には `0` も含める（成功側の条件も読めば分かる状態にする）
- 宣言を持たない script は `0` と `1` しか返さない
- 他の script の終了コードを透過するラッパーにも、この義務が同じように及ぶ。透過する値域を自身の docstring に宣言するか、宣言しないなら `0` と `1` に畳む

```python
"""Foo を Bar へ変換する。

## 終了コード

| code | 意味                     |
| ---- | ------------------------ |
| 0    | 変換が完了した           |
| 1    | 区別のない失敗           |
| 2    | 入力を受理できない       |
| 3    | 変換結果を書き込めない   |
"""
```

`2` 以上の数値の選び方は script が決めてよい。連番にしても飛ばしても、意味は表が与えるものだけである。**値の並びや間隔に分類を読み込ませようとしない**（`10` 番台・`20` 番台のような区分は、中央の体系があるという誤解を生む）。

### 呼び出し側 [MANDATORY]

- 値で分岐してよいのは、**産出側の docstring がその値を宣言している場合に限る**
- 宣言が無い場合、および `1` を受けた場合は、理由を区別せず失敗として扱い、エラーの内容を報告する
- 呼び出し側の文書（SKILL.md 等）に書くのは、宣言された値に対する**行動**である。値の**意味**を呼び出し側で定義しない

### 標準出力

- `0` のとき: 結果の JSON
- 非 0 のとき: エラーの JSON

エラーの JSON は `errors` を持つ。

- **値は常に配列とする**。1 件でも配列にする。単数と配列が混在すると、受け取る側が形状で分岐する必要が生じ、それ自体が判断になる
- 要素は**自然文の日本語**とする。機械可読なコード体系を導入しない
- **成否を表す field を重複して置かない**。操作が失敗したという事実は終了コードが表しており、同じ事実を JSON にも置くと正本が 2 つになる

```json
{ "errors": ["入力を受理できない: 期待する形式は {形式}"] }
```

### 標準エラー出力

診断情報を標準エラー出力へ加えることは禁じない。ただし**エラーの内容は標準出力の JSON に必ず含める**。標準エラー出力だけに置くと、標準出力を読む呼び出し側が失敗の理由を得られない。

## 例外

ハーネスが入出力契約を定める script（Claude Code の hook として起動されるもの等）は、その契約に従う。終了コードの意味・標準出力の形式をハーネスが指定している場合、本文書の規定は適用しない。
