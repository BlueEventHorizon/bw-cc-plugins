## 1. 概要

複数の議題項目（レビュー所見・議論の論点・未解決の問題）を、**人間が常に全体として把握でき、そのうえで個別に対応できる状態**に保つための記録層を定める。これは記録を残すための仕組みではなく、**会話のための道具**である。

利用者は、扱っている項目の全体と個別の状況が一目で分かり、AI の提示内容とファイルの内容が食い違わない状態で議論を進められる。記録の突き合わせを利用者自身が行う作業から解放されることが、本機構の価値である。

### 1.1 なぜ機構が要るのか

この目的だけであれば、規約を数行書いて AI に委ねる形もありうる。実際にそうしていた。

問題は、**記録の維持に AI の注意を使うほど、本来の仕事（所見の妥当性の検証・影響範囲の検討・議論の中身）の質が落ちる**ことである。注意は有限であり、書式を保つために使った分はそのまま本題から引かれる。

したがって本機構の存在意義は 1 つに定まる。

> **記録の維持に AI が使う出力量・読み取り量を減らすこと。減らさないなら機構を置かない。**

この判断基準は要件そのものであり、手段の選定基準ではない。機構を増やす方向の提案は、この基準に照らして棄却されうる。

### 1.2 対象システムの性質

本機構は開発者が自分の端末で使う作業記録であり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。ただし記録対象に機密情報が含まれうるため、その扱いは NFR-005 で定める。

## 2. 用語

本機構で使う語を以下に固定する。既存実装の語彙と異なる場合は本節が正である。

| 用語       | 定義                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 議題項目   | 人間の判断または議論を要する 1 単位。レビュー所見・議論の論点のいずれもこれに当たる  |
| アジェンダ | 議題項目の全体と各項目の状態を、一目で把握できる形にまとめたもの                     |
| 記録       | 議題項目の集合と各項目の状態を保持する実体。単一の真実源である                       |
| 提示       | 人間に向けて記録の内容を示したもの。記録から生成される                               |
| 呼び出し側 | 本機構を利用する SKILL。現時点では `/forge:review` と `/forge:consult` の 2 つである |

**`triage` の語を用いない。** トリアージは緊急度による切り捨てを指す語であり、全項目を扱う本機構の実態と合わない。加えて `/anvil:triage-issue` と語が衝突し、どちらを指すかが読み手に伝わらない。本機構および呼び出し側の記述では `agenda` を用いる。

## 3. スコープ

### 3.1 対象

- 議題項目の記録と、その状態の保持
- 記録から生成される、人間向けの提示
- 状態遷移の可否判定
- 呼び出し側から記録への入力と、記録から呼び出し側への出力
- 記録の置き場・個数・寿命
- 既存記録（`/forge:review` の仕分けファイル、`/forge:consult` の討議ファイル）の移行または破棄

### 3.2 対象外

- **いつ提示するか・何を問うか**。提示の契機と問いの立て方は呼び出し側ごとに異なり、各 SKILL が持つ。本機構が共有するのは記録であって手順ではない
- **提示の作法**（背景と本質を先に述べる、推奨は 1 つ、確信度を示す等）。[consult_principles_spec.md](../../../../plugins/forge/docs/consult_principles_spec.md) が定める
- **議題項目の内容の正しさ**。所見が妥当か、論点が的を射ているかは本機構の関心事ではない
- **判断に基づく実行**（修正・起票・commit）

## 4. 機能要件

### FNC-001: 俯瞰可能性

扱っている議題項目の全体・各項目の状態・残件が、**1 つのアジェンダで一目で分かること**。

- 項目を数え上げたり、複数の提示を突き合わせたりしなければ全体が分からない形にしないこと
- 扱わないと決めた項目（取り下げ・対象外）も提示から消さないこと。なぜ扱わないかを利用者が確認できる状態を保つこと

### FNC-002: 変更箇所の可視化

**直前の更新で変わった箇所が、提示上で他と区別できること。**

そのために、**記録は「直前の更新で何が変わったか」を判別できる情報を保持すること**。提示は記録から生成される（FNC-003）ため、記録がこの情報を持たなければ差分を示せない。保持の形式は設計で決める。

理由: 項目数が増えると、提示を再掲しても「今回何が変わったのか」が読み取れなくなる。利用者に差分を探させないため。

### FNC-003: 提示と記録の一致

提示の内容と記録の内容が食い違わないこと。

- 提示は記録から生成すること
- 同じ内容を、記録と提示のそれぞれに独立して書き込む経路を持たないこと
- AI が提示を直接書く経路を持たないこと

### FNC-004: AI が生成するのは判断の内容だけ

**記録の維持のために AI が生成する量が、現行より減っていること。**

AI が生成してよいのは**判断の内容**（各項目の背景・本質・推奨・決着の文と、状態の指示）に限る。次はいずれも AI が生成しないこと。

- 提示の書式・配置・記号
- 項目の並び順
- 件数・残件数の集計
- 記録と提示の整合

### FNC-005: 入力は 1 回の構造化された受け渡し

AI から記録への入力は、**1 回の構造化された受け渡しで足りること**。

- AI が渡し方そのもの（値の並べ方・書式）を組み立てる必要が無いこと
- 1 項目の更新が 1 回の受け渡しで完結すること

### FNC-006: 次の行動を数えずに得られる

AI が「次に何をすべきか」を、**自分で数えたり探したりせずに得られること**。

次を返す操作を持つこと: 次に扱う項目、記入されていない欄、残件。

### FNC-007: AI は人間向けの提示物を読まない

AI が状態を知るために、人間向けの提示物を読む必要がないこと。

理由: 提示物は人間が読むために整形されており、そこから状態を読み戻す実装は必ず書式の解釈を伴う。読み戻しの経路を持たないことで、書式と状態の乖離が原理的に生じなくなる。

### FNC-008: 状態遷移の必要条件は機械可読な定義として持つ

各状態へ遷移するための必要条件が**機械可読な定義として存在し、満たさない遷移が拒否されること**。

- 散文の禁止事項に依存しないこと
- 遷移が拒否された場合、何が不足しているかを呼び出し側が判別できること

理由: 「決着させる前に背景と本質を書く」という規約は、散文で書かれている限り守られないことがある。実際に、規約として明記した後も記入されないまま決着した事例がある。

### FNC-009: 呼び出し側の共通化

`/forge:review` と `/forge:consult` が**同一の機構を使うこと**。

呼び出し側ごとに異なる次の事項は、機構が持たず呼び出し側から受け取ること。

| 呼び出し側から受け取るもの | 例                                                 |
| -------------------------- | -------------------------------------------------- |
| 同時に存在する記録の個数   | 1 つに限る / 複数を同時に開ける                    |
| 記録の識別方法             | 固定の名前 / 主題を表す名前                        |
| 記録の寿命                 | 処理の終了時に削除する / 残す                      |
| 項目が持つ欄               | 重大度・位置・確信の記号 / 重要度・確信度          |
| 状態の語彙                 | 未着手・進行中・決着・保留・対象外・取り下げ 等    |
| 内容の妥当性の判定         | 呼び出し側が行う。機構は記録の存在と形式だけを見る |

**共通化する理由は制約の側にある。** 同じ枠組みが 2 つあれば、AI は 2 種類の操作を覚え、2 箇所で同じ失敗をする。これは FNC-004 が禁じている「記録の維持に注意を使う」状態そのものである。

### FNC-010: 既存記録の扱い

既存記録（`/forge:review` の仕分けファイル、`/forge:consult` の討議ファイル）について、移行するか破棄するかが決まっていること。

- 破棄する場合、利用者が失う内容を事前に把握できること
- 移行も破棄もされないまま放置される記録が残らないこと

### FNC-011: 検証の記録を遷移の必要条件とする [MANDATORY]

外部から与えられた指摘（レビュー所見等）を項目として扱う場合、**その指摘を検証した内容と、検討した対策が記録に存在しなければ、決着への遷移を拒否すること**。

記録すべきは次の 2 つである。

| 記録する内容 | 満たすべき条件                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| 検証         | 指摘の真偽を確かめるために**実際に参照した対象**を、位置（ファイルと行・コマンドと出力等）とともに書く |
| 対策         | 採否と、採る場合の対処。**採らない場合も理由を書く**                                                   |

- 採用する場合も検証を要求すること。**指摘を認める方向へ倒すときこそ検証が要る**
- 検証欄に、参照した対象を伴わない一般論・所感だけが書かれている状態を、記入済みとして扱わないこと

**判定の主体を分ける [MANDATORY]**。機構が課すのは**記録の存在と、位置情報を伴う形式**までである。**検証の内容が妥当かどうかの判断は呼び出し側が担う。** 機構には検証が本物かを判定する手段が原理的に無く、できるのは形式検査だけであるため、これを機構の責務にすると満たせない要求になる。この分担により §3.2（議題項目の内容の正しさは本機構の関心事ではない）と両立する。

**この要件は「欄を必須にする」ことではない。** 欄の存在だけを条件にすると、AI は欄を埋めることを学習し、内容が検証由来かどうかは誰も検査しないまま通過する。実際に、決着時に記入を要求するガードを設けた後も、内容が会話にしか存在しないまま決着した事例がある。**記述を検証可能にすること**——参照した対象が位置つきで書かれ、後から照合できること——が本要件の中身である。

理由: AI は外部から与えられた指摘を、検証せずに正しいものとして受け入れる傾向が強い。指摘の採否は本来こちら側の判断であり（forge:REQ-013 §1.4「レビュー結果は気づきであり、指示ではない」）、検証を経ない採用はその判断を放棄している。

### FNC-012: 個別処理の前に構造の妥当性を判定する [MANDATORY]

議題項目の集合を受け取ったとき、**個別項目の提示・決着に入る前に**、集合全体が構造の誤りを示していないかを 1 回判定し、記録すること。**判定が記録されるまで、個別項目の状態遷移を拒否すること。**

判定の対象は、**集合を見て初めて分かること**とする。

- 同型の指摘が繰り返されていないか
- 複数の指摘が同一の土台に由来していないか
- 個々を直しても、その土台が残ったままにならないか

「構造の誤りは無い」と判定した場合も、その判断と根拠を記録すること。**無記録と「誤りは無いと判断した」を区別できる状態を保つ。**

**判定するのは呼び出し側である。** 機構が課すのは、判定が記録されるまで個別項目の遷移を拒否することだけである（FNC-011 と同じ分担）。

**判定は最初に行う。** 個別項目を先に決着させると、局所の対処が既に適用された状態で土台の誤りが判明する。片付けた項目が判断を引きずり、土台を変える選択が採りにくくなる。実際に、レビュー所見 15 件がすべて「A と B が食い違う」型として 1 件ずつ処理され、**両者が誤った土台に立っていることは最後まで指摘されなかった**事例がある。この見落としは個々の項目を見ても現れず、集合を見て初めて分かる種類のものであった。

項目単位ではなく集合単位で 1 回だけ課すのは、FNC-004（記録の維持に AI が使う量を減らす）と両立させるためである。項目ごとに構造の妥当性を書かせると、量が増えるうえ、集合を見なければ分からない誤りには届かない。

## 5. 非機能要件

### NFR-001: 保存形式は値の境界を形式自身が持つ [MANDATORY]

記録の保存形式は、**値の境界を形式自身が持つものであること**。

- 実装に、保存形式を解釈するための自作パーサが存在しないこと
- 記録する内容に人間の文章が含まれることを前提とすること。区切り文字・行頭記号・空行といった、文章中に自然に現れうるものを値の境界にしないこと

理由: 表示のための形式は値の境界を持たない。保存に使えば境界を実装が発明することになり、保存する内容が人間の文章である以上、必ず衝突する。実際に、要約に含まれた 1 文字の記号によって以後すべての更新が失敗した事例、および本文が読み戻しで静かに切り落とされる事例が発生している。

**表示に用いる形式そのものが誤りなのではない。** 誤りは 1 つの成果物に保存と表示を兼ねさせたことである。読み戻さない生成専用であれば、提示が表示向けの形式であることは問題にならない。

本節は forge:REQ-001 の文書フォーマット選定基準（機械的なパース・更新が必要な文書は YAML、自由記述・図表を含む文書は Markdown）と同じ判断を、作業記録へ適用したものである。同基準は成果物文書を例に挙げており、一時的な作業記録を射程に含むかが文面から読み取れないため、本節で明示する。

### NFR-002: 提示は生成物であると読み取れる

生成物であることが、提示自体から読み取れること。

提示を記録から生成することは FNC-003 が定める。本節が課すのは、読み手が「これは生成されたものである」と判別できることだけである。

### NFR-003: 置き場・個数・寿命は導出根拠を持つ

記録の置き場・同時に存在する個数・寿命が、**その呼び出し側の性質からの導出として定義されていること**。慣習や既存実装の踏襲を根拠にしないこと。

導出に用いる性質の例を挙げる。

- 同時に 1 つしか成立しないなら、識別のための名前も、列挙のための境界も要らない
- 複数が同時に成立するなら、名前が主題を持ち、列挙のための境界が要る
- 内容が他所へ引き継がれるなら、処理の終了時に残す必要はない

### NFR-004: 検証可能性

本機構は単体テストを持つこと。何を検証するかは設計で定める。

### NFR-005: 機密情報の非記録

記録対象に機密情報が含まれる場合、その値そのものを記録にも提示にも含めないこと。記録するのは「どこに」「どの種類の」機密が含まれるかまでとすること。

### NFR-006: 失敗の可視性

記録の書き込み・読み戻しに失敗した場合、**既定値で補って進行しないこと**。何が失敗したかを、呼び出し側と利用者が判別できる形で止めること。

理由: NFR-001 が根拠に挙げた 2 つの事故（1 文字の記号によって以後すべての更新が失敗した／本文が読み戻しで静かに切り落とされた）は、いずれも**失敗が静かに進行した**ことで被害が広がった。保存形式の性質を課すだけでは、失敗時に黙って進む余地が残る。FNC-008 が定めるのは状態遷移の拒否であり、記録の入出力の失敗一般は覆わない。

## 6. 既存の記述との関係

本要件は、既存の記述のうち以下と両立しない。実装完了後の merge で既存側を改訂して齟齬を解消する。

**要件**

| 既存の条文                                                                    | 両立しない理由                                                                   |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| consult:REQ-017 NFR-001（状態は討議ファイルに閉じる）                         | 状態と提示を分離する FNC-003 / NFR-002 を禁じている                              |
| consult:REQ-017 §1（review と実装を共有しない）                               | 共通機構を求める FNC-009 を禁じている                                            |
| consult:REQ-017 TBD-001（委譲しない、で決着）                                 | 同上                                                                             |
| consult:REQ-017 FNC-011（討議ファイルの置き場と、形式は Markdown とする規定） | 保存形式に値の境界を求める NFR-001 と、置き場に導出根拠を求める NFR-003 に反する |

**設計・実装**

| 既存の記述                                                      | 両立しない理由                                                       |
| --------------------------------------------------------------- | -------------------------------------------------------------------- |
| forge:DES-066 §3.11（段階的提示。仕分けファイルの形式と置き場） | 保存と表示を 1 つの成果物に兼ねさせており NFR-001 / NFR-002 に反する |
| `/forge:consult` の討議ファイル（Markdown を保存と表示に兼用）  | 同上                                                                 |

**consult:REQ-017 NFR-001 は棄却ではなく再導出とする。** 同条の根拠は「状態の置き場が複数あると、どれが正かが失われる。人間が読める 1 つのファイルに閉じることで、記録と提示の食い違いを構造的に防ぐ」であり、これは本要件と同じ問題意識から出ている。本要件が満たすのは**同じ目的**であり、手段が異なるにすぎない——状態の実体が 1 つであり、提示がそこから生成される以上、食い違いは原理的に生じない。単に棄却すると、同じ懸念が後から別の形で戻る。

なお、`/forge:review` が段階的提示そのものを外部 SKILL へ委譲しない点は維持する。FNC-009 が共通化するのは記録であって手順ではない（§3.2）。
