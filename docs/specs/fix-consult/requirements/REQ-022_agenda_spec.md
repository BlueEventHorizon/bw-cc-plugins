# REQ-022 agenda 要件定義書

## 1. 概要

記録・表示機構（agenda）が呼び出し側から議題項目を受け取るときに、**呼び出し側が持っている情報がそのまま渡り、失われずに記録される**ことを定める。あわせて、その**書き込みを script が担い、記録が決められた場所に作られ、終了時にまとめて消える**ことを定める。

現行の実装では、呼び出し側が持つ情報の一部しか記録に残らない。残らなかった情報は提示にも現れないため、利用者は判断材料の一部を見られない。また、渡すために呼び出し側が情報を作り替える作業が発生しており、その作業を誤ると入力そのものが拒否される。

書き込みと後始末にも欠陥がある。呼び出し側がファイルを直接書いており、書式とファイル名の組み立てが呼び出し側の作業として残っている。記録の場所を決める基準も呼び出し側の状況に依存するため、書き込み先が変わりうる。しかも別の場所へ書かれても成功が返るため誤りに気づけない。さらに記録に属するものの一部が終了時の削除に含まれず、消す責任を誰も負わないまま残り続ける。

あわせて、agenda を使う経路のうち**利用者からの直接起動で議題を立てる経路を停止する**（FNC-007）。

## 2. 前提条件

- agenda は開発者が自分の端末で使う作業記録であり、外部公開・本番運用・個人情報の保持を伴わない（[agenda:REQ-019][req019] §1.2 と同じ）

## 3. 用語

本要件で使う語を以下に固定する。[agenda:REQ-019][req019] §2 の語を継承し、本要件が新たに導入する語と、定義を改める語のみを挙げる。

| 用語            | 定義                                                                                                                                                                                                                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 呼び出し側      | agenda へ渡す内容を決める主体（SKILL を実行する AI）。[agenda:REQ-019][req019] §2 の定義を改める。起点ごとの事情を閉じ込めるために agenda 側が用意した script は、SKILL の配下に置かれていても呼び出し側ではなく agenda に属する |
| JSON データ項目 | 議題項目が JSON 上に持つ名前と値の組。agenda は意味を解釈せず、呼び出し側が用途に応じて決める                                                                                                                                    |
| 作り替え        | 呼び出し側が持っている情報を、渡すために別の形へ変える作業                                                                                                                                                                       |

## 4. 機能要件

### FNC-001: 呼び出し側は持っている情報をそのまま渡せる

**呼び出し側が渡すために情報を作り替える作業が、一切発生しないこと。**

- JSON データ項目の名前の変更・階層の付け替え・JSON データ項目の削除を、渡す前に行う必要が無いこと
- 持っていない値（識別子・名前等）を、渡すために作る必要が無いこと
- 渡す形を呼び出し側が組み立てる工程を持たないこと
- 1 回の更新で加える複数の欄（背景・本質・推奨等）を、欄ごとの受け渡しに分けてよいこと。[agenda:REQ-019][req019] FNC-005 が求める「1 項目の更新が 1 回の受け渡しで完結すること」は、この粒度において本要件が差し替える

理由: 作り替えを人手が行う限り、誤りが入力の拒否として現れる。呼び出し側が書く複数の文章を 1 回で渡すには、それらを区切る書式を呼び出し側が組み立てる必要があり、上の 3 点と両立しない。拒否を避けるには呼び出し側が agenda の内部形式を正確に把握している必要があり、これは [agenda:REQ-019][req019] FNC-005 が無くそうとした負担そのものである。

### FNC-002: 渡されたデータをそのまま保存する

**呼び出し側から渡された JSON データ項目を、そのままの形で記録に保存すること。**

- agenda が意味を知らない JSON データ項目も保存すること
- 保存する JSON データ項目の種類を、あらかじめ決められた範囲に限らないこと

理由: 記録に無い内容は提示できない（[agenda:REQ-021][req021] FNC-003「提示は記録から生成すること」）。保存されなかった情報は、表示層がどう作られていても利用者へ届かない。

**増えた JSON データ項目を提示にどう反映するかは本要件が求めるものではない。** 本要件が保存を求めるのは、それを反映する後続の変更が、記録を読むだけで行える状態にするためである。

### FNC-003: 現行の提示が動き続ける

**保存する JSON データ項目が増えても、現行の提示が正しく生成され、表示され続けること。**

- 増えた JSON データ項目が保存されていることを理由に、提示の生成が失敗しないこと
- 現行の提示が示している内容が、欠けたり崩れたりしないこと

理由: 本要件が変えるのは記録の入口だけであり、利用者から見た提示の振る舞いを変える意図はない。増えた JSON データ項目を提示へ反映するのは後続の変更であり、それまでの間も提示は現行のまま動く必要がある。

### FNC-004: データの書き込みは script が行う

**記録および記録へ渡すデータについて、ファイルへの書き込みを script が行うこと。**

- 呼び出し側がファイルへ直接書き込む経路を持たないこと
- 呼び出し側がファイル名を組み立てる工程を持たないこと

呼び出し側が担うのは内容を決めることだけであり、それをどう書くかには関与しない。

理由: 書き込みを呼び出し側が担う限り、書式の組み立てとファイル操作が呼び出し側の作業として残る。FNC-001 が渡す内容について求めていることを、書き込みという行為についても求める。

### FNC-005: 記録は決められた場所に作られる

**呼び出し側がどこから agenda を呼んでも、記録が同じ場所に作られること。**

- 呼び出し側が置かれた状況によって、記録の場所が変わらないこと
- 決められた場所以外に記録が作られたまま、成功として扱われないこと

理由: 書き込みを script が担っても、場所を決める基準が呼び出し側の状況に依存していれば、書き込み先は変わる。しかも場所を取り違えても呼び出しは成功を返すため、別の場所へ書かれたことに気づけない。作り替えの誤りが入力の拒否として現れるのとは異なり、この誤りは表に出ないまま記録が失われる。

### FNC-006: 記録に属するものが一括で削除できる

**1 つの記録に属するものが、一括で削除できること。**

- 記録の終了時に、その記録に属するものがすべて削除されること
- 記録に属するものが、削除の及ばない場所に取り残されないこと

理由: 記録の生存期間は短く（[agenda:REQ-019][req019] NFR-003）、終了時に消えることが前提になっている。消える対象から漏れたものは、誰も消す責任を負わないまま残り続ける。

### FNC-007: 利用者からの直接起動で議題を立てる経路を停止する

**利用者が議論スキルを直接起動して議題を記録する経路が、動かないこと。**

- 直接起動の経路から記録が作られないこと
- 停止した経路の手順が、動く経路の手順に混ざったまま残らないこと

理由: FNC-002 が「渡されたものをそのまま保存する」ことを求めるのは、渡すデータを上流の script が組み立てているためである。直接起動の経路にはその上流が無く、AI が組み立てたものが検査を経ずに保存される。この経路をどう成立させるかは本要件の範囲外であり、範囲外のまま動かし続けると FNC-002 の前提が片方の経路で崩れる。

**停止であって廃止ではない。** 直接起動の経路に関する既存の要件・設計文書は残す。

## 5. 非機能要件

### NFR-001: 検証可能性

本要件の充足を自動テストで検証できること。何を検証するかは設計で定める。
