# ADR-065 バックエンド契約に failure・終了通知・位置情報の 3 要素を追加する

## 1. コンテキスト

[ADR-060](ADR-060_review_backend_axis.md) はレビュー実行主体の固定を撤回し、`--backend <name>` で切り替えるバックエンド軸を導入した（REQ-013 FNC-1318）。その影響欄には「契約が 1 実装しかない期間は、その実装の形をなぞっただけの抽象になっているリスクがある。この検証は 2 つ目の接続まで持ち越される」と記していた。

2 つ目のバックエンド（codex-appserver。自前スレッドを所有し起床を不要にする実行主体）を接続する仕様策定で、この検証が実際に行われ、契約に 3 つの不足が顕在化した（[REQ-015](../../codex-appserver/requirements/REQ-015_codex_appserver_review_backend.md) TBD-005〜007）。

1. **failure の表現が無い**。出力は判定（`approved` / `findings`）と所見配列のみで、バックエンドがラウンドを成立させられなかったこと（前提不成立・応答を得られない・応答を書式として解釈できない）を戻り値で表せない
2. **レビュー終了の通知が無い**。入力はラウンドごとの依頼のみで、レビューが終わったこと（承認・打ち切り・失敗確定・利用者中断）をバックエンドへ伝える経路が無い。自前で資源（プロセス・スレッド・記録）を保持するバックエンドは解放契機を得られない
3. **位置情報の形式が規定されていない**。所見配列はファイルパス・行を必須とするが、共通書式（自由記述 markdown + 重大度マーカー + 完了宣言行）は位置の表現形式を定めておらず、位置を特定できない所見の扱いも未定義である。レビュアーが `パス:行` を明記した所見でも位置を抽出できなかった事例が実測されている

msg-review（唯一の既存実装）ではこれらが顕在化しなかった。失敗と終了は常駐セッションを操作する人間が吸収し、資源は人間が所有するため解放契機を要さなかったからである。無人で資源を自己保有するバックエンドを接続した時点で、吸収先が消えて契約の穴として現れた。

## 2. 決定

REQ-013 FNC-1318 の入出力契約に、判定の 3 値化（`failure` の追加）・終了通知の契約化・所見の位置情報の規定という 3 要素を追加する。各要素の条文は [REQ-013](../requirements/REQ-013_review_policy.md) FNC-1318 が定める。

決め手は、3 点とも**特定バックエンドの都合ではなく、契約が結果・寿命・スキーマを語っていなかったこと自体の欠落**である点にある。正常系しか定義しない契約は、失敗と終了を暗黙に「誰かが吸収する」前提を含んでおり、その誰かが msg-review では人間だった。契約を実行主体に非依存にする（ADR-060 の目的）には、吸収先を契約自身が持つ必要がある。

## 3. 検討した代替案

| 代替案                                                    | 棄却理由                                                                                                                             |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 失敗を `approved` または所見 0 件の `findings` で代替する | 本体が正常な判定として扱うため失敗が消える。所見 0 件の `findings` は自己矛盾した状態になる                                          |
| 失敗を呼び出しエラー（非ゼロ終了）で伝える                | 契約の戻り値に含まれない結果であり、本体側の扱いも定義されない。契約外の経路で伝えることは充足ではない                               |
| 終了通知を設けず、時間経過でバックエンドが資源を回収する  | 次回の起動が無ければ回収自体が走らず、最後のレビューの資源が残る。人間の介入で長時間中断中のレビューを経過時間だけを根拠に破棄しうる |
| `approved` 返却を終了の代替信号とする                     | レビューは `approved` 以外でも終わる（打ち切り・失敗確定・中断）ため解放漏れが残る                                                   |
| 位置の無い所見を破棄・推測補完・欠落のまま返す            | 破棄は指摘そのものを消す。推測は存在しない指摘箇所を本体に信じさせる。欠落は必須項目を満たさない出力になる                           |
| 契約は変えず codex-appserver 側で暫定挙動を定める         | 「契約を満たす」状態にならず（REQ-015 FNC-001）、バックエンドごとの暗黙挙動が増えて契約の意味が失われる                              |

## 4. 影響

**得られるもの**

- 無人で資源を自己保有するバックエンドが、契約の範囲内で失敗の確定と資源解放を実装できる（codex-appserver の実装ブロック 3 件が解消する）
- 失敗・終了・位置未確定の扱いがバックエンド間で統一され、本体の所見処理が実行主体に依存しない

**失うもの・新たに生じる制約**

- 本体（`/forge:review` SKILL）に終了通知の発行義務と `failure` の報告処理が加わる。すべての終了経路（承認・打ち切り・失敗確定・中断）で通知を発行する実装が必要になる
- msg-review バックエンドは改訂後の契約への適合確認が必要になる（`failure` の返し方・終了通知の受け方。保持する資源が無いため通知は無視してよいが、契約要素としての受理は必要）。この適合は後続作業とする
- 依頼テンプレートの返信形式契約に、位置未確定の明示の要求を追加する必要がある
