# ADR-073 レビュアーの read-only を能力の限定で保証する設計を採らない

## 1. コンテキスト

レビュアーは所見を返すだけで成果物を変更しない。この性質をどう扱うかが繰り返し論点になった。

当初は「変更する能力を与えないこと」で保証する形を採っていた。レビュアー Agent の `tools` から編集手段を外し、`permissionMode` を `plan` にし、役割定義で変更操作を禁じる。これらを read-only の担保として位置づけていた。

この位置づけに対して、次の反証が出た。

- レビュアーと本体は**同じ LLM** である。本体側の実行主体は編集を含むより広い能力を持ち、それは許容されている。レビュアーにだけ能力の不在を求め、それを信用の根拠とするのは筋が通らない
- レビュアーは対象を自分で確定する必要がある（`--diff` / `--branch` では差分から対象を導く）。そのため読み取り用途のコマンド実行が要る。許可の単位は汎用のコマンド実行であり、その内側を読み取りだけに絞って宣言する手段は無い。**能力を奪えば範囲指定のレビューが成立しない**

## 2. 決定

**read-only の担保となる機構を持たない。**

役割定義による禁止・ツールの限定・実行モードの制限は維持するが、これらは違反を**防ぐ**手段であり、担保ではない。担保を与える機構は置かない。

逸脱が起きた場合、その変更は git が差分として保持する。失われるのは、本体の修正とレビュアーの変更を切り分ける情報だけであり、変更そのものは隠蔽されない。

## 3. 検討した代替案

| 代替案                                                                  | 棄却理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| レビュアーから汎用コマンド実行（`Bash` 等）を外し、能力の不在で保証する | **前提**: レビュアーが対象を自分で確定する必要がある（範囲指定のレビューでは対象一覧を渡さない）。この前提が成立する限り、読み取り用途のコマンド実行は外せず、許可の単位が汎用である以上「読み取りだけ」を宣言する手段も無い。加えて、同じ能力を本体側の実行主体が持つため、レビュアーだけ奪っても成果物が変更されうるという性質は変わらない                                                                                                                                                                                                                                                                  |
| ラウンドの前後で変更集合を取得して比較し、レビュアーの変更を検出する    | **実装して破綻した**。比較対象が変更されたファイルのパス集合であるため、**すでに変更集合に入っているファイルを書き換えても集合が変わらず、検出できない**。未コミット差分を対象とするレビューでは対象が定義上すべて既に入っており、2 ラウンド目以降も直前に修正したファイルが入っている。最も起きやすい経路だけが漏れる。<br>**前提**: 検出力を確保できたとしても、逸脱の発生率が機構の維持費用と誤検出への対処に見合うこと。この前提も成立しない。ラウンド中に外部プロセス（formatter・他のワークツリー・エディタ）がファイルへ触れれば誤検出が出る。誤検出を抑える除外規則には例外が要り、例外には判定が要る |
| 上記の検出を、パスの集合ではなく内容の同一性で行い、検出力を上げる      | 上と同じ前提が成立しない。加えて、検出力を上げても取れる行動は増えない。逸脱を知った後に行うのは差分を見て判断することであり、それは検出機構が無くても git の差分でできる                                                                                                                                                                                                                                                                                                                                                                                                                                     |

いずれの棄却も、**逸脱を許容してよいから**ではなく、**その手段が費用に見合わないか、そもそも成立しないから**である。逸脱の発生率が大きく変わる、あるいはレビュアーが対象を自分で確定する必要が無くなる設計へ移った場合、1 案目・2 案目の前提は崩れる。

## 4. 影響

本決定の前は、レビュアーの read-only を担保として位置づける記述と、それを取り消す「これは担保ではない」という打ち消しが、要件・設計・SKILL に分散していた（9 箇所）。担保として位置づける記述を除いたことで打ち消しは不要になり、いずれも削除した。

同時に、ラウンドごとの変更集合の確認（本体側の検出機構）を廃止した。`collect_modified_files.py` は残るが、用途は修正が allowlist の外へ出ていないかの独立検証に限られる。
