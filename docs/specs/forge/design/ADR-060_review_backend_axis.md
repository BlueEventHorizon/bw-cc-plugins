# ADR-060 レビュー実行主体の固定を撤回し、バックエンド軸を導入する

## 1. コンテキスト

`/forge:review` は当初、レビュー実行主体を選ぶ「エンジン軸（`--codex` / `--claude`）」を持っていたが、REQ-013 FNC-1307 でこれを廃止し「レビュー実行主体は 1 つに固定する」と定めた。以後、実行主体は msg-sys 経由の常駐 Codex セッションに固定されている。

この固定には 2 つの問題がある。

**利用できる実行主体はプロジェクトごとに異なる。** 現行の唯一の実行主体は、常駐 Codex セッション・Stop フック・cmux による起床という前提の上に成り立つ。これを満たせないプロジェクトでは、レビュー依頼の組み立てから所見の処理までを含むレビューフロー全体が使えない。固定されているのは実行主体だけだが、失われるのはフロー全体である。

**実行主体に依存しない部分が大半を占める。** SKILL.md の手順のうち、実行主体に依存するのは前提検査・往復・セッション復旧・ワイヤプロトコルに限られる。対象解決・粒度保存・観点の名指し・所見の評価・修正の安全検証は、誰がレビューしても同じである。固定の代償として、非依存の資産まで一体で使えなくなっている。

## 2. 決定

レビュー実行主体の固定を撤回し、`--backend <name>` で切り替えられる軸を導入する（REQ-013 FNC-1318）。

決め手は、**分割の境界が既に見えていた**ことである。`/forge:review` は依頼本文を組み立ててレビュアーへ渡し、判定と所見の配列を受け取って処理している。この入出力は実行主体が誰であっても変わらない。したがって固定を外すために新しい抽象を発明する必要はなく、既にある入出力を契約として明示すればよい。

あわせて、所見の書式契約（自由記述 markdown + 重大度マーカー + 完了宣言行）は全バックエンド共通に固定する。ここを可変にすると依頼テンプレートがバックエンドごとに分岐し、テンプレートを対象軸ごとに増やさないという既存の判断と衝突する。構造化された形式で応答するレビュアーを使う場合、共通形式への変換はバックエンドの内部責務とする。

## 3. 検討した代替案

| 代替案                                               | 棄却理由                                                                                                                    |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 固定を維持し、実行主体を差し替えたい場合は fork する | 非依存部分の改善が各 fork へ伝播しない。本リポジトリが下流を導く SoT である前提と両立しない                                 |
| 設定ファイルで固定し、起動時には選べないようにする   | プロジェクトごとに 1 つという想定が成り立たない。同一プロジェクトでも対象や状況によって適した実行主体が変わりうる           |
| 実行主体ごとにレビュー SKILL 自体を分ける            | 非依存部分（対象解決・粒度保存・所見評価・安全検証）が SKILL の数だけ重複する。片方だけ修正して食い違う失敗が構造的に起きる |
| 書式契約もバックエンドごとに可変にする               | 依頼テンプレートがバックエンド軸で分岐し、テンプレートを増やさない既存判断と衝突する。変換はバックエンド内部で行えば足りる  |

## 4. 影響

**得られるもの**

- 実行主体の前提を満たせないプロジェクトでも、レビューフローの非依存部分をそのまま利用できる
- 実行主体に依存する記述がバックエンド側へ集まり、`/forge:review` 本体が依頼と所見処理の責務に絞られる
- 2 つ目のバックエンドが接続された時点で、契約が実際に非依存かどうかを検証できる

**失うもの・新たに生じる制約**

- 実行主体が可変になるため、所見の出どころが利用者に見えている必要がある。引数解釈結果の定型出力に選択されたバックエンドを含める必要が生じる
- 未知の backend 名は fail closed とする。既定バックエンドへ暗黙にフォールバックすると、利用者が意図しない実行主体でレビューが走る
- 契約が 1 実装しかない期間は、その実装の形をなぞっただけの抽象になっているリスクがある。この検証は 2 つ目の接続まで持ち越される
- `--codex` / `--claude` は backend 名として解釈せず、警告のうえ無視する扱いを継続する。既存の呼び出し元がこれらを付けて起動しており、backend 名として再解釈すると推測で実行主体を選ぶことになる
