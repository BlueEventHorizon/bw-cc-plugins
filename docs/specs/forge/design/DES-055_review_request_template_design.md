## 1. 概要

レビュー依頼本文を、**レビューのパターンごとに 1 枚の自然言語テンプレート**として持ち、スクリプトは動的データの埋め込みと検証のみを行う設計。共通本文はバックエンド中立とし、固有のワイヤプロトコルを含めない。

得られるもの:

- **テンプレート自体が「レビュアーに何を渡すか」の仕様になる**。仕様と成果物が二重管理にならず、散文のままレビューできる
- パターンごとに固定されるため、パターン間で条件分岐する動的組み立てが不要になる
- 埋め込むデータが正しいかをスクリプトで検証できる（自然言語でありながらテスタブル）

## 2. 制約

### 2.1 スクリプトは散文を持たない [MANDATORY]

依頼本文の文言をスクリプトの文字列リテラルとして持たない。本文をリテラルで組み立てる構造は、レビュー観点に相当する指示文をスクリプトへ書き足せてしまう。観点は criteria / principles にあり、スクリプトにあってはならない。

依頼内容を変えるときはテンプレートを編集する。スクリプトには手を入れない。

### 2.2 対象軸ごとの条件分岐を持たない [MANDATORY]

依頼本文の組み立てに対象軸の分岐を持たない。各テンプレートは自身のパターンだけを完全に記述し、分岐は「どのテンプレートを選ぶか」の 1 段に閉じる。

### 2.3 ワイヤプロトコルを持たない [MANDATORY]

共通テンプレートは、特定バックエンドの識別子、送信先、セッション情報、ワイヤヘッダを含めない。テンプレート展開後の本文は、どのバックエンドにも同じ入力として渡せる形式とする。

ワイヤプロトコルを必要とするバックエンドは、共通本文を受け取った後、送信直前に必要なヘッダを付加する。ヘッダの生成、検証、受信時の解釈は当該バックエンドの内部責務であり、`build_review_request.py` のトークン契約には含めない。

## 3. テンプレート一覧

配置: `plugins/forge/skills/review/templates/`（review スキルのみが使うため skill-owned）

| # | ファイル                                 | パターン                | 対象軸       |
| - | ---------------------------------------- | ----------------------- | ------------ |
| 1 | `diff_review_request_template.md`        | 未 commit 差分の全部    | diff         |
| 2 | `branch_review_request_template.md`      | base〜target の全変更   | branch       |
| 3 | `code_review_request_template.md`        | 指定したソースコード    | files / dirs |
| 4 | `requirement_review_request_template.md` | 指定した要件定義書      | files / dirs |
| 5 | `design_review_request_template.md`      | 指定した設計書          | files / dirs |
| 6 | `plan_review_request_template.md`        | 指定した計画書          | files / dirs |
| 7 | `uxui_review_request_template.md`        | 指定した UI/UX 関連文書 | files / dirs |
| 8 | `secrets_review_request_template.md`     | リポジトリ全体          | なし         |

`files` と `dirs` が同一テンプレートを共有する理由は §8.4。

`secrets` は対象軸を持たない（REQ-013 FNC-1315）。対象軸を持たせると、対象軸 × 観点の直積でテンプレートが増え、かつ差分に絞った時点でレビューの目的を達成できなくなる。対象軸を持たないことで、テンプレートは 1 枚に収まり §2.2 の「テンプレートは対象軸の条件分岐を持たない」も自然に満たす。

`diff` / `branch` は種別を問わない。未 commit 差分やブランチ差分にはコード・設計書・設定ファイル・`.gitignore` 等が混在するため、種別軸に載らない。

`diff` / `branch` に全観点を渡す理由: 対象の内容が混在しており、どの観点が必要かを事前に決められない。レビュアー側が対象を見て取捨選択する。

`document_style_guide.md` は文書を対象とするテンプレート（`requirement` / `design` / `plan` / `diff` / `branch`）に含める。当初は「文書執筆者向けの書式規範でありレビュー観点ではない」として除外していたが、§5 文書参照記法の違反（とくにリンク切れ）は参照先へ到達できないという実害を生むため、恒久的な検出対象へ移した（REQ-013 FNC-1314）。`code` には含めない（対象がコードであり文書記法の適用先が無いため）。`uxui` は criteria 側が既に委譲先として持つ。

`code` の観点が薄い理由: forge 内蔵にはコード規範がほぼ無く（`forge_anti_patterns.md` 25 行のみ）、コーディング規約・アーキテクチャ規約はプロジェクト側にしかない。テンプレート本文にこの事実を明記し、`query-db-rules` の結果が空だった場合に「観点なしでレビューした」と気づける形にする。

## 4. プレースホルダ契約

### 4.1 記法

`{{TOKEN}}` を使う。Markdown のバッククォート・コードブロック・波括弧と衝突せず、埋め込み漏れを機械検出できる。

### 4.2 トークン一覧

| トークン              | 置換値                                               | 使うテンプレート |
| --------------------- | ---------------------------------------------------- | ---------------- |
| `{{REVIEW_TYPE}}`     | レビュー種別（`diff` / `branch` / `code` / …）       | 全部             |
| `{{PLUGIN_ROOT}}`     | forge プラグインの絶対パス                           | 全部             |
| `{{PROJECT_ROOT}}`    | プロジェクトルートの絶対パス                         | 全部             |
| `{{PROJECT_RULES}}`   | `query-db-rules` の結果パス一覧（Markdown 箇条書き） | 全部             |
| `{{PROJECT_SPECS}}`   | `query-db-specs` の結果パス一覧（Markdown 箇条書き） | 全部             |
| `{{BASE_BRANCH}}`     | 利用者が確認して確定した base ブランチ名             | `branch`         |
| `{{TARGET_BRANCH}}`   | target ブランチ名                                    | `branch`         |
| `{{TARGET_PATHS}}`    | 対象ファイル一覧またはディレクトリ一覧（箇条書き）   | `code` 〜 `uxui` |
| `{{FOCUS}}`           | 依頼固有の重点観点（自然文 1 行 / 未指定時は既定文） | 全部             |
| `{{SCOPE}}`           | 到達目標と意図的な未実装（自然文・複数行可）         | 全部             |
| `{{SCAN_FINDINGS}}`   | 機械検出の結果（マスク済み・Markdown 箇条書き）      | `secrets`        |
| `{{SCAN_SUPPRESSED}}` | 抑制マーカーで分類された検出（同上）                 | `secrets`        |
| `{{SCAN_STATS}}`      | 走査統計（走査数・スキップ・除外内訳）               | `secrets`        |

`{{SCAN_*}}` の値は **`build_review_request.py` 自身が実行したスキャン**から得る（§8.3）。外部から受け取らない。

`{{TARGET_PATHS}}` はファイル指定（`--files-json`）とディレクトリ指定（`--dirs-json`）の**いずれか一方**から埋める（両方渡すとエラー終了する。§4.4）。ディレクトリの場合は絶対パスの末尾に `/` を付ける。ファイルかディレクトリかをレビュアーが本文から判別できるようにするための整形であり、§2.1 の「スクリプトは散文を持たない」に触れない（見出し・説明文はテンプレート側にある）。

`{{FOCUS}}` は未指定時に節ごと消すのではなく `（指定なし）` で埋める（`{{PROJECT_RULES}}` の `（なし）` と同じ扱い）。節の有無を動的に切り替えるとスクリプトが散文（見出し文言）を持つことになり、「文言はテンプレート側」という本設計の前提が崩れるため。

`{{SCOPE}}` も未指定時は `（指定なし）` で埋める。`{{FOCUS}}` と違い**複数行を許容する**が、見出し行・コードフェンス行・契約行（`REVIEW_RESULT:`）で始まる行と CR を含む値は拒否する（本文の構造と返信形式契約の偽装を防ぐため）。`{{SCOPE}}` を持たないテンプレートへ値を渡した場合もエラー終了する（黙って捨てると、渡したつもりで届いていない状態に気付けない）。

**`{{SCOPE}}` と `{{TARGET_PATHS}}` は別軸である [MANDATORY]**。前者は「どの完成度を基準に評価するか」、後者は「何を見るか」を伝える。両者を混同すると、対象指定のつもりで到達目標が渡る（またはその逆）という取り違えが起こる。この取り違えを名前の水準で防ぐため、対象側のトークンには `SCOPE` の語を使わない（§8.6）。

### 4.3 パスは絶対で渡す [MANDATORY]

`${CLAUDE_PLUGIN_ROOT}` は SKILL.md / agent.md がロードされるときにのみ実行時展開される変数であり、**テンプレートを Read したデータ本文の中では展開されない**。テンプレートに `${CLAUDE_PLUGIN_ROOT}/docs/...` と書いてもレビュアーは解決できない。

したがってテンプレートには `{{PLUGIN_ROOT}}/docs/criteria/review_criteria_code.md` のように書き、スクリプトが `Path(__file__)` から算出した絶対パスへ置換する。プロジェクト文書も同様に `{{PROJECT_ROOT}}` で絶対化する。

**どのファイルを参照するかの決定はテンプレートに静的に残り、絶対パスへの解決だけが動的**になる。

### 4.4 検証（fail-closed）

| 検査                       | 失敗時                                                                 |
| -------------------------- | ---------------------------------------------------------------------- |
| 未消化トークンの残存       | 埋め込み後に `{{` が残っていたらエラー終了                             |
| 未知トークンの指定         | テンプレートに存在しないトークンを渡したらエラー終了                   |
| 改行・CR の混入            | 埋め込む値に改行が含まれていたらエラー終了（プロトコル注入防止）       |
| ファイルパスが絶対         | 対象ファイル一覧・ディレクトリ一覧に絶対パスが混じっていたらエラー終了 |
| 対象軸の二重指定           | ファイル一覧とディレクトリ一覧の両方を渡したらエラー終了               |
| テンプレート必須項目の欠落 | `branch` でブランチ名が欠けていたらエラー終了                          |
| スキャン結果の欠落・失敗   | `secrets` でスキャン結果が無い / `status != ok` ならエラー終了         |

**検出値の混入は検証で防がない**。スキャン結果の生成元を信頼境界の内側に置くことで、マスクを経ていない値が本文へ到達する経路自体を無くしている（§8.3。REQ-013 FNC-1316）。

## 5. スクリプトの責務

| スクリプト                | 責務                                                                                                                                                                                               |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build_review_request.py` | テンプレートを Read → トークン置換 → 検証 → 単一 JSON envelope `{review_id, body}` を標準出力へ書く。**散文を持たない**。`secrets` では `scan_secrets.py` を import してスキャンも実行する（§8.3） |
| `analyze_branch_point.py` | base ブランチ候補を分岐点解析で列挙する（採用は決めない）                                                                                                                                          |
| `resolve_targets.py`      | `--files` / `--dirs` の存在検証と、修正フェーズ用 allowlist の供給                                                                                                                                 |
| `scan_secrets.py`         | 機密情報の決定論的検出。**値をマスクして**返す。文脈判断は持たない                                                                                                                                 |

`resolve_targets.py` は依頼本文の生成に関与しない。範囲指定（`diff` / `branch` / `dirs`）をファイル一覧へ展開して渡すことは REQ-013 FNC-1312 が禁じている。

`dirs` モードはディレクトリ配下のファイルを列挙して返すが、**これは allowlist 専用の値であり依頼本文には渡さない**。依頼本文へは `--dirs-json` でディレクトリのまま渡す。allowlist はレビュアーへ渡すものではないため FNC-1312 の制約を受けない一方、依頼本文は受ける。この非対称を SKILL 側で取り違えると（allowlist 用の展開結果をそのまま `--files-json` へ渡すと）粒度保存が黙って破れるため、SKILL.md の Step 3.2 に [MANDATORY] として明記している。

`build_review_request.py` がスキャン実行を持つのは `secrets` パターンのみの例外である。「テンプレート埋め込みに徹する」という原則より、「マスクを経ていない値が本文へ到達しないことを構造的に保証する」要件を優先した結果であり、他パターンの対象解決を取り込む根拠にはならない（§8.3）。

| 起動                                               | 選択されるテンプレート |
| -------------------------------------------------- | ---------------------- |
| `/forge:review diff` / 対象軸未指定                | `diff`                 |
| `/forge:review branch`                             | `branch`               |
| `/forge:review code --files …` / `--dirs …`        | `code`                 |

## 7. テスト設計

| 対象                               | 検証                                                                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トークン置換                       | 全トークンが置換され、`{{` が残らない                                                                                                                                                       |
| 未消化トークン検出                 | データを渡さないとエラー終了する                                                                                                                                                            |
| バックエンド中立性                 | 有効な `[msg-review] <種別> review_id=<review_id> round=<n>` ワイヤヘッダ行を、全テンプレートと生成本文の先頭に生成しない。説明文・引用としての単なる `[msg-review]` の文字列言及は許可する |
| 未知トークン検出                   | テンプレートに無いトークンを渡すとエラー終了する                                                                                                                                            |
| 改行注入                           | 値に改行を含めるとエラー終了する                                                                                                                                                            |
| 絶対パス解決                       | `{{PLUGIN_ROOT}}` が実在する forge プラグインの絶対パスへ置換される                                                                                                                         |
| テンプレートの網羅性（契約テスト） | §3 が定めるパターン全件のテンプレートが実在し、各テンプレートが使うトークンがスクリプトの供給トークン集合に含まれる                                                                         |
| 観点文書の実在（契約テスト）       | テンプレートが名指しする `{{PLUGIN_ROOT}}` 配下の観点文書が実在する                                                                                                                         |
| 重点観点（FNC-1313）               | 全テンプレートが `{{FOCUS}}` を持ち、値が埋め込まれ、未指定・空白時は `（指定なし）` になる。改行を含む値はエラー終了する。重点観点を渡しても内蔵観点の名指しが消えない                     |
| 文書参照の恒久観点（FNC-1314）     | 文書系 criteria が文書スタイル規約を名指しし、規約側に重大度カタログが存在する                                                                                                              |
| 機密情報の検出（FNC-1315）         | 既知形式を取りこぼさない。プレースホルダ・コード式・チェックサム表を誤検出しない                                                                                                            |
| 検出値の非再掲（FNC-1316）         | 出力・依頼本文のどこにも実値が現れない。実値を持つキーを含むスキャン結果はエラー終了する                                                                                                    |
| 除外の可視化（FNC-1317）           | 抑制マーカー付きの検出と機械的除外の件数が依頼本文に載る                                                                                                                                    |
| 対象指定の粒度保存（FNC-1312）     | ディレクトリ指定時に本文へディレクトリが載り、配下のファイル一覧が載らない。ファイル一覧とディレクトリ一覧の同時指定はエラー終了する                                                        |
| 対象欄の指示（§8.5）               | 対象を明示指定するテンプレートが能動的な列挙手順と差分レビュー否定の 2 文を持ち、生成された依頼本文にも載る。範囲指定テンプレートは差分レビュー否定文を持たない                             |

「観点文書の実在」以降の各件は、テンプレートを人が編集したときに参照切れ・トークン不整合を検出するための契約テストである（件数は上表を SoT とし、ここでは数えない。二重管理になると行を足したときに数値が嘘になる）。テンプレートが仕様を兼ねる設計では、テンプレートの誤りがそのまま依頼の誤りになるため必要になる。

## 8. 設計判断の根拠

### 8.1 パターンごとにテンプレートを分ける理由

1 枚のテンプレートに条件分岐を持たせると、分岐条件が散文の中に埋もれて「このパターンでは何が渡るのか」が読み取れなくなる。パターンごとに 1 枚なら、そのファイルを読むだけで渡す内容が確定する。動的な組み立てが要らないため、組み立てロジックの誤りという故障モード自体が消える。

共通部分（返信形式契約など）が全テンプレートに重複するが、これは許容する。重複を避けるために断片化すると、1 枚を読んで全体が分かるという利点を失う。テンプレートの整合は §7 の契約テストで担保する。

### 8.2 スクリプトを残す理由

散文を持たないなら SKILL 側の手作業で足りるように見えるが、以下は決定論的処理でありスクリプトに残す。

- `review_id` の生成（uuid4）
- 絶対パスの算出
- §4.4 の検証群

### 8.3 スキャン結果の生成元を信頼境界の内側に置く理由 [MANDATORY]

`secrets` パターンでは `build_review_request.py` が `scan_secrets.py` を import して自分でスキャンを実行し、外部からスキャン結果を受け取る引数（`--scan-results-file`）を持たない。

**当初は外部ファイルを受け取り、`masked` フィールドの形式を正規表現で検証していた**。検出値の実体を依頼本文へ載せないための「最後の防波堤」として設計したものである。しかしこの方式には原理的な欠陥があった。

- 形式検証は「値の形」しか見ておらず、**その値が本当にマスクを経たことの証明にならない**
- 実値がたまたま（あるいは意図的に）`ABCD***[99文字]` の形であれば通過する
- キー名の禁止（`value` / `secret` 等）も、`masked` フィールドに実値を置く入力には無効

検証を強める方向では解決しない（どれだけ厳しくしても「形が合っている実値」は通る）。そこで**生成元そのものを信頼境界の内側へ移した**。同一プロセスで `scan_secrets.scan()` を呼べば、`masked` は必ず `mask()` を通っており、実値が本文へ載る経路が構造的に存在しなくなる。

得られた副作用として、`masked` 形式検証・`counts` スキーマ検証・レコードの型検証がいずれも不要になり削除された。保証を強めながらコードは減っている。

**ただし改行の検証は残す [MANDATORY]**。信頼境界が保証するのは「`masked` がマスクを経た」ことだけであり、「データが本文構造を壊さない」ことは保証しない。`path` はファイルシステム由来の値で、git は改行を含むファイル名を許容するため、**正規のスキャン結果のまま**セクション構造・完了宣言行を偽装できる。マスクの保証と構造の保全は別問題であり、後者は生成元に関わらず埋め込み直前に防ぐ。

この区別は実装時に一度取り違えた（信頼境界を導入した際に改行検証もまとめて削除した）。削除してよいのは「生成元が保証されれば不要になる検証」だけであり、データの性質に起因する検証は残る。

**代償**: `build_review_request.py` の責務が「テンプレート埋め込みと検証」から広がった（§5 の但し書き）。この拡大は `secrets` パターンに限定し、他パターンの対象解決（`--files` の検証・分岐点解析）は引き続き別スクリプトに置く。

**API にも口を残さない [MANDATORY]**: `build_body()` はスキャン結果を受け取る引数を持たない。`secrets` パターンでは `build_body()` 自身が `scan_secrets.scan()` を呼ぶ。

引数で受け取れる設計では、外部由来の値を本文へ載せる経路が CLI から Python API へ移るだけで、保証は「呼び出し元が正しい値を渡す」という契約に依存したままになる。契約は構造ではないため、`ABCD***[99文字]` 型の生値を渡す経路が残る。CLI の口だけを閉じて API を開けたままにする案は、実装の途中でこの誤りを一度犯し、レビューで指摘されて修正した。

テストでスキャン結果を制御する場合は `scan_secrets.scan` を mock する。`build_body()` が純粋関数でなくなる（ファイルシステムを走査する副作用を持つ）代償は受け入れる。テスト容易性より、マスクを経ない値が本文へ入らないことを優先する。

テスト（`SecretsTrustBoundaryTest`）が、CLI に外部入力オプションが無いこと・`build_body()` の引数に `scan_result` が無いことの双方を検証する。

判断の経緯: 実 Codex レビュー（review_id=77bfe895…）で 3 ラウンドにわたり指摘を受けた。初回は責務分離を理由に形式検証で対応したが、「形式は生成元を認証できない」という指摘が原理的に正しく、責務分離（手段）より機密の非露出（目的）を優先すべきと判断して方針を変えた。

### 8.4 ディレクトリ指定でテンプレートを増やさない理由

対象軸に `--dirs` を追加したとき、`{{TARGET_FILES}}` を `{{TARGET_PATHS}}` へ汎用化し、ファイル指定とディレクトリ指定で同一テンプレートを共有する形にした。種別ごとに `dirs` 専用テンプレートを追加する案（8 → 13 枚）は採らなかった。

- **共通部分の重複が 13 箇所へ波及する**。§8.1 で述べたとおりテンプレート間の重複（返信形式契約・参照文書一覧）は意図的に許容しているが、それは「1 枚を読めば全体が分かる」利点との交換である。対象軸の違いは対象欄 1 箇所にしか現れないため、この交換が成立しない（得るものが無く、変更箇所だけが増える）
- **§2.2 に違反しない**。§2.2 が禁じているのは**組み立てロジックが対象軸で分岐すること**である。テンプレート本文が「ファイルでもディレクトリでも通じる文言」を持つことは分岐ではない。分岐は引き続き「どのテンプレートを選ぶか」の 1 段に閉じており、パターン ↔ テンプレートの 1 対 1 対応も保たれている
- 埋め込む値の側でも分岐は 1 箇所（`dirs` があればディレクトリ、なければファイル）に閉じる。両方渡された場合は推定せずエラー終了する（§4.4）

**代償**: テンプレートを読んだだけでは、その依頼がファイル指定なのかディレクトリ指定なのかが分からない（本文に埋まった値を見る必要がある）。ディレクトリには末尾 `/` を付けることで、生成後の本文からは判別できるようにしている。

### 8.5 対象欄は範囲を宣言せず、能動的な手順を指示する [MANDATORY]

対象を明示指定するテンプレート（§3 の `code` 〜 `uxui`）の対象欄は、**「配下のファイルをあなた自身が列挙し、各ファイルを全文読んでください」という能動的な手順**と、**「これは差分レビューではありません。未コミット変更の有無・git 履歴は対象の決定に関係しません」という枠組みの明示的否定**の 2 つを持つ。範囲を宣言するだけの文（「その配下の対象文書すべてをレビュー範囲とします」）では足りない。

**発見の経緯**: `--dirs` の初回実運用（review_id=1571fca6…、対象 `docs/specs/forge/design/` 15 文書 3242 行）で、レビュアーは返信の第一文に「対象ディレクトリの未コミット変更はありません」と書き、25〜35 秒で `REVIEW_RESULT: approved` を返した。後の確認でレビュアー自身が「全文は読んでおらず、変更有無・構造・参照記法の確認に留まった」「通常の差分レビューの癖で変更箇所中心の確認へ不適切に切り替えた」と認めた。**機構（粒度保存・allowlist 分離・起床・待機）はすべて正常に動作しており、失敗したのは依頼本文の指示だけである。**

**原因**: 当時の対象欄は範囲を宣言するのみで、**列挙という最初の作業を命じていなかった**。`--files` では渡されたファイル一覧そのものが手順として機能するため成立していたが、`--dirs` では列挙が先に必要になる。手順が空白のとき、レビュアーは自分の習慣で埋める。git リポジトリの中で最も手近な目的は「何が変わったか」であり、差分レビューの枠組みへ引き寄せられた。`diff` / `branch` テンプレートが「あなた自身が差分から確定してレビューしてください」と能動的な確定手順と探索対象を明示しているのと対照的だった。

**レビュアーの反実仮想の申告を採用しない [MANDATORY]**: 当該レビュアーは「追加で必要な文言はありません。今回の依頼文だけで十分でした」と述べた。この申告は採用しない。レビュアーの自己報告のうち**事実の報告**（何を読んだか・どう判断したか）は本人しか知り得ず信頼できるが、**反実仮想の判断**（どういう文言なら誤らなかったか）は信頼できない。枠組みを誤った直後の本人は、その誤りを防げた文言を判定する立場にない（事後に読み返せば「十分だと思える」のは当然であり、それは「読めば分かった」を意味するだけで「読み落とさなかった」を意味しない）。

**採らなかった案**:

- **強調を足す**（「必ず」「全ファイル」等の語を増やす）: 強調は読み手の注意力に依存し、注意力が落ちた場面では効かない。今回はまさに注意力が落ちた事例である
- **ファイルごとに 1 行の結果報告を求める**（読了の受領証として、こちら側の allowlist と機械照合する）: 実行されたかを判別可能にする点で上記 2 点と役割が異なり、上乗せとして検討したが、返信が対象ファイル数だけ冗長になる代償が大きいと判断して採用しなかった（ユーザー判断）。将来、静かな範囲縮小が再発した場合の対策候補として残す

### 8.6 対象側のトークンに `SCOPE` の語を使わない [MANDATORY]

到達目標（`--scope` → `{{SCOPE}}`）を追加した時点で、対象一覧のトークン名 `{{TARGET_SCOPE}}` と語が重なった。両者は軸も分布も異なる（前者は評価基準・全 8 枚、後者は対象・5 枚）にもかかわらず、名前からは後者が前者の派生に見える。対象側を `{{TARGET_PATHS}}` へ改名して語の重なりを解消した。

**`{{TARGET_CONTENTS}}` は採らなかった**。このトークンに入るのはパスの一覧であって対象の中身ではない。`CONTENTS` は「本文に対象が展開済みである」と読めるため、依頼本文には参照だけを載せてレビュアー自身に対象を確定させるという原則（REQ-013 FNC-1312 の粒度保存、および §8.5 の能動的手順）と衝突する。名前が原則と反対を示唆する状態は、単に紛らわしい状態より悪い。

**到達目標側（`{{SCOPE}}`）は動かさなかった**。こちらは CLI フラグ `--scope` と名前が対応しており、フラグとトークンの対応を崩す方が利用者・実装者の双方にとって追いにくい。対象側の `TARGET_*` は `--files` / `--dirs` の 2 つを束ねる合成名であり、特定のフラグ名に縛られていないため動かす自由度がある。
