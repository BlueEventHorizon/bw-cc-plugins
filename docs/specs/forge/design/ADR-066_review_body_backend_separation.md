# ADR-066 `/forge:review` 本体とレビューバックエンドを別 SKILL へ分離する

## 1. コンテキスト

[ADR-060](ADR-060_review_backend_axis.md) がバックエンド軸を導入し、[ADR-065](ADR-065_review_backend_contract_completion.md) が入出力契約に failure・終了通知・位置情報を追加した。しかし**配布物側にはバックエンドの概念が 1 つも実装されていない**。`plugins/forge/skills/review/SKILL.md` を検査したところ、`backend` / `バックエンド` / `failure` / `終了通知` のいずれの語も出現しない。

それどころか、本体 SKILL は自身の description で「msg-sys 通信基盤（常駐 Codex セッションとの Stop フック経由の非同期往復）の上で」と名乗り、Codex フックの自己修復（Step 1.5）・msg-sys の自己診断（Step 2）・`send_and_await_reply.py` による送信と待機（Step 6）・cmux による起床（Step 6.1）を直接手順として持つ。**現状の本体は msg-review バックエンドがインラインで書かれたものである**。

この状態では 2 つの帰結がある。第 1 に、2 つ目のバックエンド（codex-appserver）を接続する先が存在しない。第 2 に、ADR-065 が本体へ課した義務——全終端経路での終了通知の発行と `failure` の利用者報告——を実装する足場が無い。バックエンドという概念を持たない本体に、バックエンドへの通知を足すことはできない。

## 2. 決定

`/forge:review` 本体とレビューバックエンドを **別 SKILL** に分離する（[REQ-013](../requirements/REQ-013_review_policy.md) §3 適用対象が「`/forge:review` SKILL.md」と「レビューバックエンド SKILL」を別行として定めていることに従う）。既存の msg-sys 経由の往復は `msg-review` バックエンド SKILL として切り出し、本体はバックエンド名で起動先を切り替えるだけにする。

### 2.1 責務の境界

引数解釈・パターン確定・対象解決・依頼本文の組み立て・所見の評価と修正・終端判定を本体に置き、前提検査・レビュアーとの往復・応答の判定と所見配列化・ワイヤプロトコルをバックエンドに置く。責務の割り当ては [REQ-013](../requirements/REQ-013_review_policy.md) FNC-1318 が定める。

本体はバックエンドの内部を知らない。バックエンドは対象解決・所見評価・修正を行わない。

### 2.2 バックエンドは継承型 SKILL として起動する

バックエンドはカスタム Agent ではなく継承型 SKILL とし、本体が `Skill` ツールで起動する。理由は 2 つある。往復には利用者への確認（base ブランチの確定・前提不成立時の対処）が混ざるため、AskUserQuestion が使える継承型が適する。また msg-review の受信モードは Stop フックが差し戻したメッセージを契機に**主会話で**成立するため、隔離 context では受け取れない。

### 2.3 共有資産は配布物共通の場所へ昇格する

所見の共通書式の解釈規則は全バックエンド共通である（ADR-060）。したがってその実装を特定バックエンドの `skills/<skill>/scripts/` に置くと、他バックエンドから「他スキルの持ち物への無断参照」になる（`docs/rules/implementation_guidelines.md`「スクリプト・文書の配置」が禁じる）。共通書式の解釈は `plugins/forge/scripts/` 配下へ昇格させ、本体・全バックエンドがそこを参照する。

### 2.4 終了は単一の出口を通す

終端判定と終了通知の発行を、本体の散文に散らさず単一のスクリプトへ集約する。レビューを終える経路は複数ある（承認・打ち切り・失敗確定・利用者の中止）が、そのすべてがこのスクリプトを通り、スクリプトが「終端か」「どの経路か」「終了通知を要するか」を返す。

決め手は、同じ SKILL が既に同型の失敗を 2 度経験していることである。送信・起床・待機は当初 3 つの手順として並んでおり、そのたびに 1 つが抜けて往復が静かに止まった。守られることを期待する契約から、破れない構造（`send_and_await_reply.py` という単一の入口）へ移して解決している。終了通知も同じ性質を持つ——**発行漏れは、資源を持たないバックエンド（msg-review）では何も起きず、資源を持つバックエンド（codex-appserver）を接続して初めてリークとして現れる**。露見が遅れる失敗であるため、同じ構造化を適用する。

あわせて、この集約により終端判定が決定論的スクリプトとしてテスト可能になる（SKILL.md はテスト対象外のため、散文のままでは経路網羅を検証できない）。

## 3. 検討した代替案

| 代替案                                                                      | 棄却理由                                                                                                                            |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 本体を 1 SKILL のまま保ち、バックエンド固有部分を内蔵 docs として読み分ける | 前提検査・往復・受信契機は手順であって参照文書ではない。SKILL.md へ読み込ませても本体が全バックエンドの手順を抱える状態は変わらない |
| バックエンドをカスタム Agent にする                                         | 受信モードは Stop フック差し戻しを契機に主会話で成立するため隔離 context では受け取れない。往復中の利用者確認も失われる             |
| 共通書式の解釈を各バックエンドに複製する                                    | 書式契約を全バックエンド共通に固定した ADR-060 と衝突する。片方だけ直して食い違う失敗が構造的に起きる                               |
| 終了通知を各終端経路の散文に個別記述する                                    | 同型の失敗を 2 度起こした形と同じ。発行漏れが資源を持つバックエンド接続まで露見せず、テストによる経路網羅の検証もできない           |
| 契約実装を後回しにし、codex-appserver 側で本体を迂回して接続する            | バックエンド固有の事情を本体に持ち込まない境界（FNC-1318）が最初の 2 実装目で崩れる。以後のバックエンドが同じ迂回を必要とする       |

## 4. 影響

**得られるもの**

- 2 つ目のバックエンド（codex-appserver）の接続先が成立する。実機確認が済み次第 `--backend` で選択できる
- ADR-065 が本体へ課した義務（終了通知の発行・`failure` の報告）の実装先が定まる
- 本体 SKILL から msg-sys / cmux 固有の手順が抜け、実行主体の前提を満たせないプロジェクトでも本体の資産（対象解決・粒度保存・所見評価・安全検証）が使える

**失うもの・新たに生じる制約**

- 往復 1 回ごとに本体とバックエンドの間で SKILL 起動を挟む。継承型のため context は共有されるが、手順の往復は増える
- 既存の呼び出し元（`/forge:start-implement` 等）は本体を起動し続けるため互換だが、バックエンド未指定時に既定 `msg-review` が選ばれることに依存する
- `[msg-review]` プロトコルヘッダは msg-sys の DB に永続化された通信路上の識別子であり、SKILL 分離後も改称しない（既存の未解決スレッドが辿れなくなる）
- 共通書式の解釈スクリプトの移動に伴い、テストの配置も追随して移す必要がある
