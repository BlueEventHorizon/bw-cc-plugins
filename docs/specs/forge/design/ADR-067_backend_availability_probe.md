# ADR-067 可用性検査を契約の要求に追加し、既定バックエンドを解決順で決める

## 1. コンテキスト

現在の既定バックエンドは `msg-review` に固定されている（FNC-1318）。しかし msg-review は cmux による起床手段と常駐 Codex セッションの両方を必要とし、**どちらかが欠けると成立しない**。

この前提が満たされていないとき、現在の実装は依頼を送ってしまう。`check_setup.py` は Codex の常駐を「機械検査できない」として警告に落としており（fail-open）、cmux については検査自体を持たない。結果として利用者は最大 10 分の待機を経て `failure` を受け取る。

**「機械検査できない」という判断は事実に反する**。同じリポジトリの `find_codex_pane.py` はプロジェクトルート単位で Codex セッションの有無を判別でき、実測でも対象 worktree では `found`、Codex のないパスでは `not_found` を返す。`ps` とプロセスの作業ディレクトリからも判別できる。検出手段はあるのに、起床のときにしか呼ばれていない。

msg-review の設計は当時、「cmux を満たせない環境では本バックエンド自体が使えないものとして前提検査で検出し、利用者に別バックエンドの選択を促す」と定めていた。設計が要求している検査が実装されていない状態である。

加えて、前提が満たせない環境では**レビューが一度も成立しない**。forge は配布物であり、利用者の多くは cmux も Codex も導入しない。その環境で機能が存在しないのと同じ状態になっている。

## 2. 決定

### 2.1 可用性検査を契約の要求として追加する

本体からバックエンドへの要求に「可用性検査」を加える。バックエンドは自身が利用可能かと、不足している前提を返す。

前提の判定方法はバックエンドごとに異なる（cmux の有無・常駐セッション・外部プロセスの起動可否）。本体がこれを直接調べると、FNC-1318 が禁じる「バックエンド固有の事情を本体に持ち込まない」に反する。**判定はバックエンドの内側に閉じたまま、結果だけを本体が受け取る**形にする。

副作用を持たせない。検査は読み取りのみで、依頼を送らず、レビュアーのターンも起こさない。複数の候補を順に検査するため、検査自体が高価または破壊的であってはならない。

**不足している前提を個別に返す**。「使えません」だけでは利用者が対処できない。何が欠けているか（起床手段・相手の常駐・実行系の不在）を分けて返す。

### 2.2 既定バックエンドを固定値から解決順へ変える

明示指定が無い場合、候補を順に可用性検査して最初に使えたものを選ぶ。指定と利用不可時の挙動は [REQ-013](../requirements/REQ-013_review_policy.md) FNC-1318「バックエンドの解決順」が定める。

`.forge.yaml` の指定を「明示」に含めるのは、含めないとその指定が助言でしかなくなり、「設定したのに別の実行主体で走った」が起きるためである。プロジェクトが選択した以上、満たせないなら失敗させる。

**これは自動フォールバックではない**。[ADR-060](ADR-060_review_backend_axis.md) / FNC-1318 が禁じたのは「実行中に失敗したら別バックエンドへ暗黙に倒れる」ことであり、その危険は利用者が結果の出どころを知らないまま degrade を受け取る点にあった。本決定の解決は**依頼を 1 通も送る前に完了し**、選ばれたバックエンドは送信前の引数解釈結果表（FNC-1318 が `[MANDATORY]` とする欄）に出る。部分的な状態も残らない。ラウンド実行の失敗（`failure`）に対して代替を選ばない点は変えない。

候補の**順序**は本体が名前として持つ。名前を知ることは「固有の事情を持ち込む」ことに当たらない（現在も既定として `msg-review` という名前を持っている）。

### 2.3 履歴復元を契約表へ明記する ⚠️失効（ADR-071 が任意拡張へ変更）

バックエンド SKILL は「ラウンド実行 / 終了通知 / 履歴復元」の 3 要求で実装されているが、FNC-1318 の入出力契約表には履歴復元が無い。本体の再開モードが実際に使う要求であり、要件が実装を覆っていない状態である。可用性検査の追加と同じ表の改訂として埋める。

## 3. 検討した代替案

| 代替案                                                      | 棄却理由                                                                                               |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 本体が cmux / Codex の有無を直接調べる                      | 判定方法はバックエンドごとに異なる。本体が全バックエンドの前提を知ることになり FNC-1318 の境界が崩れる |
| 可用性検査を設けず、ラウンド実行の `failure` だけで済ませる | 前提不成立が判明するまで待機予算（最大 10 分）を消費する。かつ候補が複数あっても順に試せない           |
| 既定を固定のまま、前提不成立なら常に fail closed とする     | cmux も Codex も導入していない環境でレビューが一度も成立しない。配布物として機能が存在しないのと同じ   |
| 前提不成立を検出したら実行中に別バックエンドへ切り替える    | ADR-060 が禁じた自動フォールバックそのもの。利用者が出どころを知らないまま degrade を受け取る          |
| 可用性検査でレビュアーへ試験的な依頼を送って応答を確かめる  | 検査に副作用が生じ、候補ごとに依頼が飛ぶ。検査が高価になり複数候補の順次検査が成立しない               |
| `.forge.yaml` の指定は助言とし、満たせなければ他を選ぶ      | 設定したのに別の実行主体で走る。プロジェクトの選択が意味を持たなくなる                                 |

## 4. 影響

**得られるもの**

- 前提が満たせない環境で、待機予算を消費せず即座に判明する
- 前提を満たすバックエンドが 1 つも無い環境でも、候補に加われば（外部依存を持たない実行主体等）レビューが成立する
- 判定がバックエンドの内側に閉じるため、起床手段が将来変わっても本体は変わらない

**失うもの・新たに生じる制約**

- バックエンドは可用性検査を実装する義務を負う。副作用を持たない読み取りのみの検査でなければならない
- 本体は候補の順序を名前として持つ。候補を増やすときに本体（または `.forge.yaml`）の更新が必要になる
- 同じコマンドが環境によって別の実行主体で走る。選ばれた結果は送信前の定型出力に出るため利用者には見えるが、**環境間で承認の重みが異なることは記録上は区別されない**
- `.forge.yaml` の `review` セクションのスキーマ定義が必要になる（[DES-061](DES-061_forge_settings_file_design.md) §2.2 はセクションを新設する設計が自文書に定義することを求める）。定義先は [DES-066](DES-066_review_body_design.md)
