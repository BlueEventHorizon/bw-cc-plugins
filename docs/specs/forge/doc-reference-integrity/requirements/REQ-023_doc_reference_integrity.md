# REQ-023 文書参照の実在性検査 要件定義書

## 1. 概要

文書の中の文字列に対して、それが参照かどうかを判別し（判別）、参照であれば指す文書を特定する（特定）機構を定める。判別・特定の結果に応じて、書かれたパスの正誤と参照先の実在を検査し、必要な場合は報告する。

## 2. 前提条件

- 本機構は開発者が forge の SDD フロー内で使う検査ツールであり、外部公開・本番運用・個人情報の保持を伴わない。
- 必須ではない参照は禁止である（[spec_format.md][spec-format]「文書参照の記法」第 1 原則）。（一般）ユーザ文書を禁止にすることはできないが、開発で使う文書には適用する。plugin 文書のルールとしては規定できない（全世界のユーザ文書を禁止することになるため）。
- doc-advisor は、文書の検索のために文書の参照情報を使う。参照の間違いそのものには関知しない（それは forge や利用者の責任である）。
- doc-advisor は、マークダウンリンク・リファレンスリンク・文書名のみによる参照を理解する必要がある。
- 検査対象ディレクトリは、doc-structure の設定から取得する。

## 3. 用語

| 用語 | 定義                                                                 |
| ---- | -------------------------------------------------------------------- |
| 判別 | ある文字列が参照かどうかを決めること                                 |
| 特定 | 参照だとして、どの文書を指すかを決めること                           |
| 実在 | 検査対象ディレクトリのうち、git が追跡するファイルの中に見つかること |

## 4. スコープ

### 4.1 対象

- 文字列が参照かどうかの判別、および参照先の文書の特定（FNC-001）
- 判別・特定の結果の状態に応じた報告（FNC-002・FNC-003）
- 参照先の実在判定（FNC-004）
- 履歴の記録の除外（FNC-005）
- プロジェクトルートの外を指すパス参照の禁止（FNC-006）
- パスを伴わない、文書名のみによる参照の検出（FNC-007）
- 参照リンクの誤りの修正（AI による。FNC-009）
- SDD フローの各段階への検査の組み込み、および利用者が指定した範囲の随時検査（FNC-011）
- 参照が一意に決まらない状態の区別報告（FNC-012）
- 消えた文書への、名前による参照の検出（FNC-013）

### 4.2 対象外

- コードスパン・コードブロック内に書かれた文字列（例示とみなし、判別の対象外とする。FNC-008）
- 判別できない文字列（S4）に対する追加の規則。実在ファイルの一覧だけでは S4 は無くならないことを受け入れる
- script による参照リンクの一括自動修正（FNC-009）
- パスを伴わない、文書名のみによる参照を、正しい（パス付きの）リンクへ書き換えることの要求（FNC-007）
- 継続的インテグレーションでの検査（FNC-011）

## 5. 機能要件

### FNC-001: 判別と特定

文書の中の文字列に対して、それが参照かどうかを判別すること。参照だと判別できた場合、どの文書を指すかを特定すること。

### FNC-002: 状態に応じた扱い [MANDATORY]

判別・特定の結果は、次の 4 つの状態のいずれかに定まり、機構は状態に応じた扱いをすること。

| 状態   | 内容                                                               | すべきこと |
| ------ | ------------------------------------------------------------------ | ---------- |
| **S1** | 参照だと判別でき、指す文書も特定でき、書かれたパスも正しい         | 何もしない |
| **S2** | 参照だと判別でき、指す文書も特定できたが、書かれたパスが誤っている | 報告する   |
| **S3** | 参照だと判別できたが、指す文書が実在しない                         | 報告する   |
| **S4** | 参照かどうかを判別できない                                         | 追わない   |

S2 が生じるのは、参照がパスを含む場合だけである。

理由: パスが誤っていても名前で文書を特定できるため機構としては動作するが、[document_style_guide.md][style-guide] §5.1 系統 (3) は「人がクリックで飛べること」を求めており、パスが誤ったままでは人の導線が壊れる。したがって報告する。ただし修正するかどうかは利用者の判断であり、機構が処理を止める理由にもしないこと。

要求の中心は S1〜S3 を正しく扱うことであり、S4 はできる限り少なければよく、0 にする必要はない。実在ファイルの一覧だけでは S4 は無くならないことは受け入れる。

### FNC-003: S4 に残る種類

実測では、判別できない文字列（S4）として次の 3 種類が残った。

| 種類   | 内容                                                     | 機械で決まるか |
| ------ | -------------------------------------------------------- | -------------- |
| **N1** | 名前空間付きの他プロジェクトの ID を自分のものと誤認する | 決まる         |
| **N2** | 文書が消えたこと自体を述べている文                       | 決まらない     |
| **N3** | ID を持たない文書の名前が、ふつうの語と一致する          | 決まる         |

N2 は文脈の判断であり機械化できない。参照切れとして報告し、人が「これは記述である」と判断する以外に道が無い。この種類のためだけに追加の規則を設けないこと。

### FNC-004: 実在の判定基準 [MANDATORY]

参照先の実在は、検査対象ディレクトリのうち git が追跡するファイルによって判定すること。作業ツリーに在っても未追跡のファイルは実在に含めないこと。

SDD フローの途中で修正したファイルの一覧だけを渡す方式は採らないこと。削除・改名によって参照が壊れるのは触っていないファイルの側であり、差分だけの走査は構造的に取りこぼす。

書かれたパスに symlink が含まれる場合、実在の判定はその先の実体まで解決してから行うこと。字面の一致だけでは実在を確認したことにならない。

### FNC-005: 除外する文書

文書名のみによる参照の検出に限らず、すべての参照検出において、履歴の記録は対象外とすること。ADR は対象とする。

### FNC-006: プロジェクト外パス参照の禁止 [MANDATORY]

開発文書からの参照は、プロジェクトルートの外を指すパス参照を禁止すること。Web URL（配置も含めてリリースされた文書）への参照は許可すること。（一般）ユーザ文書に同じ禁止を課すことは難しく、行わない。

判定は、正規化した結果がプロジェクトルートの内側に収まるかの一点で行うこと。絶対パス、および `../` による脱出も同じ検査で扱うこと。

越境する symlink は、表記自体がプロジェクト相対であるため、この検査に例外条項を設ける必要はない。文書 ID による参照は索引の外では解決しないため、この禁止の対象にする必要はない。

### FNC-007: 文書名のみによる参照の検出

パスを伴わない、文書名のみによる参照も検出対象に含めること。この形の参照について、存在しないことは報告するが、正しい（パス付きの）リンクへの書き換えは要求しないこと。今後は doc-advisor が参照先を解決する。

### FNC-008: 参照でないものの除外

コードスパン・コードブロック内に書かれた文字列は、判別の対象外とすること。記法の説明としての例示とみなす。

### FNC-009: 修正の扱い

参照リンクの誤りを正すこと自体は必要であるが、script による自動修正は行わないこと。修正は AI に行わせること。修正するかどうかの最終判断は利用者に委ねること。

理由: 置換には様々な制約や書き方のバリエーションがあり、script ベースでの一括置換は問題が大きい。常時この検査を実行していればほぼ誤りは蓄積しないはずであり、AI の負荷も利用者の修正待ち時間も少ないと見込む。

### FNC-011: 検査を行う位置

文書を作成・変更する作業の**後**、かつ**その作業を行った主体がまだ文脈を持っているうち**に検査が行われる経路を持つこと。具体的には、forge の SDD フロー（要件定義・設計・実装・UI/UX 設計・仕様統合・レビュー）の各段階に組み込み、その段階が文書・コードを書き換えた場合に実行すること。

加えて、利用者が指定した範囲を随時検査できる経路を持つこと。判定を行う実装は、いずれの位置でも同一であること。

理由は 2 つある。**第 1 に、位置が後ろすぎると検出しても直せない。** 参照切れの修復には、参照でないものの判別と、移動先の特定が要る。これを安く行えるのは、その変更を行った主体が文脈を保っている間だけである。文脈が失われた後に検出しても、判別と特定をやり直すことになる。**第 2 に、検査の存在だけでは不十分である。** 変更を行った手順の中に検査が組み込まれていなければ、検査を持つことと、検査が効くことは別である。

**この位置の要求は、継続的インテグレーションでの検査を要件から外す。** commit 済みの状態しか見られない位置では、上記の第 1 の理由が満たされない。継続的インテグレーションへ置くかどうかは、除外規則が確定した後の別判断とする。

### FNC-012: 一意に決まらない状態の扱い

参照が一意に決まらない状態（同じ符号を持つ文書が複数実在する）は、実在しない状態と区別して報告すること。

理由: 前者は参照の修正で直るが、後者は参照元を一切変えていないのに他者が文書を追加しただけで発生しうる。同じ種別で報告すると、誤りのない参照元まで誤りとして扱われる。

### FNC-013: 消えた文書への、名前による参照の検出 [MANDATORY]

文書名のみによる参照が、現在実在する一覧に見つからない場合、過去に実在した名前・符号の記録と照合すること。該当すれば、消えた文書への参照であるとして実在しない状態（S3）として報告すること。該当しなければ、判別できない状態（S4）とすること。

過去に実在した名前・符号の記録は、次を満たすこと。

- 実在しなくなった名前を記録から削除しないこと。削除すると、その文書への参照を検出できなくなること
- 版管理下に置くこと。ローカルにのみ保持すると、利用者ごと・CI と手元とで判別結果が異なりうること
- 誤って記録された名前を、人が削除できる経路を持つこと

新規クローン・新規プロジェクトの初回検査では、この記録が無いため、過去に消えた文書への参照は検出できない。これは許容する制約とする。

## 6. 非機能要件

### NFR-001: 検出手段の網羅性と誤検出の許容

参照を判別する手段が複数存在する場合、いずれか 1 つを選ぶのではなく、すべてを用いて判別すること。取りこぼし（見逃し）は事後に回復できないが、誤って多く拾ったもの（誤検出）は読めば判別できるため、取りこぼしより誤検出を許容すること。

### NFR-002: 判定の決定論性 [MANDATORY]

判定は決定論的であること。LLM の推論に依存させないこと。判定結果に確信度・確度の概念を持たないこと。

### NFR-003: 検査失敗時の可視性

検査そのものが実行できなかった場合（対象を読めない等）、参照切れが無かったものとして扱わないこと。何が失敗したかを判別できる形で報告すること。

### NFR-004: 外部機構との一致

forge が持つ判別・解決の規則は、doc-advisor 等の外部機構が同種の判定を行う場合に一致させる手段を持つこと。置き場所は未定（TBD-003）。
