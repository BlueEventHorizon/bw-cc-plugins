# REQ-023 文書参照の実在性検査 要件定義書

## 1. 概要

文書の中に書かれた参照が、**参照先として実在するか**を機械的に判定する機構を定める。参照が指す先が存在しない状態（以下「参照切れ」）を、人間の目視や AI のレビュー観点に頼らず、決定論的に検出して報告する。

参照切れは、それ自体が独立した欠陥ではなく**他のすべての記述の信頼性を損なう**種類の欠陥である。参照が指す先へ到達できなければ、参照元の主張は検証できない。読み手が人間であれば探し回る労力を負い、読み手が AI であれば読みに行って失敗する。参照は文書間の依存を表すため、1 箇所の参照切れは、その参照を辿ろうとしたすべての読み手に波及する。

### 1.1 なぜ機構が要るのか

実在性は決定論的に判定できる。参照先のパスや ID が現在の文書集合に存在するか否かは、読めば必ず一意に決まる。

にもかかわらず、現在これはレビュー観点として扱われている。結果として、毎回のレビューで同じ判定を不安定に繰り返し、検出漏れが起きている。**実際に、文書統合の作業で削除された 2 つの文書（設計書 1 件・要件定義書 1 件）への参照が、実装コードとテストに 72 箇所残ったまま commit された。** この 72 箇所は、統合作業を行った時点でも、その後のレビューでも検出されていない。

したがって本機構の存在意義は 1 つに定まる。

> **決定論的に判定できるものを、判定の不安定な経路から機械的な経路へ移すこと。**

### 1.2 対象システムの性質

本機構は開発者が自分の端末と CI で使う検査ツールであり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

## 2. 用語

| 用語     | 定義                                                                                                                    |
| -------- | ----------------------------------------------------------------------------------------------------------------------- |
| 参照     | ある文書が別の文書・その一部・またはコード上の位置を指し示す記述                                                        |
| 参照元   | 参照を書いている側のファイル。Markdown 文書に限らない                                                                   |
| 参照先   | 参照が指し示す対象。ファイル・ファイル内の見出し・文書 ID のいずれか                                                    |
| 参照切れ | 参照先が、検査時点の文書集合に存在しない状態                                                                            |
| 文書集合 | 検査の対象として与えられたファイルの全体。何を含めるかは呼び出し側が決める                                              |
| 実在     | 参照先が文書集合の中に見つかること。git 履歴・他ブランチ・削除済みファイルに存在することは実在に**含めない**（FNC-003） |

## 3. スコープ

### 3.1 対象

- 参照の網羅的な抽出（参照でないものを参照として扱わないことを含む）
- 参照先の実在判定
- 参照切れの報告（位置と理由を特定できる形）
- 2 つの用途（配布物の検査・利用プロジェクト文書の検査）での同一実装の利用

### 3.2 対象外

- **参照の記法が正しいかの検査**。相対パスで書くべきか変数展開で書くべきか等は記法の規約の問題であり、実在性とは別の関心事である
- **参照表記の書き換え**（リンクなし参照のリンク化・正規化）。何を正しい表記とするかは文書規約の問題であり、本機構は判定のみを行い原本を書き換えない
- **参照先の内容が正しいかの判定**。参照先が実在したうえで、その内容が参照元の主張を裏付けているかは意味の問題であり、決定論的に判定できない
- **参照先が変更されたことの検出**（参照元が追随すべき変更の追跡）。これは実在性とは異なる問題であり、別の機構が扱う
- **参照切れの修復**。検出と修復は別であり、本機構は検出で終端とする

## 4. 機能要件

### FNC-001: 判定は決定論的であること

参照先が実在するかの判定が、**同じ入力に対して常に同じ結果を返すこと**。

- 判定を LLM の推論に依存させないこと
- 判定結果に確信度・確度の概念を持たないこと（実在するかしないかの 2 値である）

理由: 本機構の存在意義（§1.1）が、判定の不安定な経路から機械的な経路への移動そのものである。判定に推論が混ざれば、移動した意味が失われる。

### FNC-002: 検査する参照の種類 [MANDATORY]

次のいずれの形で書かれた参照も検査対象とすること。

| 参照の形               | 参照先                             |
| ---------------------- | ---------------------------------- |
| リンク記法             | ファイル                           |
| リンク記法 + 位置指定  | ファイル内の見出し                 |
| 定義を別行に持つリンク | 定義行、および定義行が指すファイル |
| 文書 ID の表記         | その ID を持つ文書                 |

**文書 ID の表記を含めることが必須である。** §1.1 が挙げた 72 箇所は、いずれもリンク記法ではなく文書 ID の表記であった。リンク記法だけを検査対象にすると、この事例は再び検出されない。

**抽出は参照先の実在に依らないこと。** 参照として書かれているものを、その参照先が実在するかを問わずに拾うこと。実在するものと実在しないものを別の手段で探し分けない。

理由: 実在する文書の一覧から出発して、その名前が書かれている箇所を探す方法では、**名前ごと存在しない参照先を持つ参照が得られない**。文書を削除・改名すると参照先の名前は一覧から消えるため、探す手がかりが無くなる。§1.1 の 72 箇所はまさにこの形（削除された 2 文書への参照）であり、実在するものから出発する方法では 1 箇所も検出されない。

### FNC-003: 実在の判定は検査時点の文書集合だけを見ること [MANDATORY]

参照先が実在するかは、**検査時点の文書集合の中にあるか**で判定すること。次はいずれも実在として扱わないこと。

- git の履歴に存在する（過去のコミットに含まれる）
- 他のブランチに存在する
- 削除済みである

理由: §1.1 の 72 箇所が指していた 2 文書は、いずれも git 履歴と他ブランチに存在している。履歴や他ブランチを実在に含めると、この事例は「実在する」と判定され検出されない。参照を辿る読み手が到達できるのは検査時点の文書集合だけである。

### FNC-004: 参照でないものを参照として扱わないこと

参照の形をしていても、参照ではない記述を参照切れとして報告しないこと。少なくとも次を区別すること。

- 記述の例示として書かれた参照（書式の説明・設定例・出力例に現れるもの）
- 構造そのものを示すための、実体を持たない仮の名前
- コードとして表示するために囲まれた範囲に含まれるもの

理由: 誤検出は検査を CI のゲートとして使えなくする。正しい記述が落ちる状態が続けば、検査は無効化されるか、警告として無視される。判定が決定論的であること（FNC-001）は、判定が正しいことを保証しない。

### FNC-010: 参照かどうかの判別は文書形式の標準仕様に従うこと

ある記述が参照であるか否かの判別を、**その文書形式の標準仕様に従って**行うこと。本機構の実装が独自に列挙した対応表を、判別の根拠にしないこと。

- 従う仕様を明示すること（版を含む）
- 判別が仕様に到達していない箇所は、その事実を残すこと

理由: FNC-004 が求める「参照でないものを参照として扱わない」の当否を、何を根拠に決めるかがこの要件である。根拠が実装の自己申告だと、実装と宣言が食い違ったときにどちらへ寄せるべきかが決まらず、判別をめぐる指摘が決着しない。標準仕様に従えば、同じ指摘が仕様への照合として決着する。

**この要件は FNC-004 の解決手段そのものではない。** どの記述が例示か・どの名前が実体を持たない仮の名前かは文書形式の仕様の外にあり、別に定める必要がある（TBD-001）。標準仕様が決めるのは「コードとして表示される範囲」「注釈として無効化された範囲」のように、**形式そのものが参照として解釈しない範囲**である。

### FNC-005: 参照元の種類を Markdown に限らないこと [MANDATORY]

参照元となるファイルの種類を、あらかじめ文書ファイルに限定しないこと。実装コード・テストコードのコメントに書かれた参照も検査対象に含めうること。

理由: §1.1 の 72 箇所のうち大半は、Markdown ではなく実装コードとテストのコメントにあった。参照元を Markdown に限定した走査は、この事例を構造的に検出できない。加えて、実装コードのコメントから文書を参照することは規約が明示的に許容している経路であり、許容された経路が検査範囲の外にある状態は不整合である。

### FNC-006: 検査結果から位置と理由が特定できること

参照切れを報告するとき、利用者と呼び出し側が**どこを直せばよいかを判別できること**。

- 参照元のファイルと位置
- 参照として抽出された記述そのもの
- なぜ実在しないと判定したか

理由: 報告が件数だけであれば、結果を受け取った側が同じ走査をやり直すことになる。

### FNC-009: 参照が一意に決まらない状態を、参照切れと区別して報告すること

参照先が見つからない状態と、**参照が複数の文書に当たって一意に決まらない状態**を、別の種別として報告すること。

理由: 対処が異なる。前者は参照の削除・修正であり、後者は参照の表記をより長くすることである。加えて後者は、**参照元を一切変えていないのに他者が文書を追加したことで発生しうる**。両者を同じ種別で報告すると、参照元に誤りがない場合まで参照元の誤りとして扱われる。

### FNC-011: 名前の不在と、配置の不一致を区別して報告すること

参照先が実在しないと判定した状態を、次の 2 つに分けて報告すること。

| 状態                                                       | 対処                                   |
| ---------------------------------------------------------- | -------------------------------------- |
| その名前を持つ文書が文書集合に存在しない                   | 参照の削除、または別の文書への差し替え |
| その名前を持つ文書は存在するが、書かれた位置では解決しない | 位置の修正（**移動先を提示できる**）   |

理由: FNC-009 と同じく対処が異なる。加えて後者は、参照元を一切変えていないのに**他者が文書を移動したことで発生する**。両者を同じ種別で報告すると、利用者は毎回「文書が消えたのか、位置がずれただけなのか」を自分で調べ直すことになり、FNC-006 が求める「どこを直せばよいかを判別できること」を満たさない。

### FNC-012: 解決の対象外とした参照を、対象外として扱ったことが分かる形にすること

参照として抽出したが、実在性の判定を行わないと決めた参照について、**その件数と種別が利用者と呼び出し側に見える形**にすること。判定した結果と混ぜないこと。

理由: 実在性の対象は文書集合であり、そこに含まれない参照先（外部の資源等）は判定できない。対象外は正しい設計判断だが、**黙って落とすと「判定した」と区別できない**。NFR-001 が禁じているのは判定不能を判定済みへ畳み込むことであり、本要件はそれと別に、意図して対象外にしたものにも同じ可視性を課す。

### FNC-007: 検査を行う位置と、実装の単一性

次の 2 つの位置で検査が行えること。**判定を行う実装は両者で同一であること。**

| 位置                 | 何を対象にするか                                   |
| -------------------- | -------------------------------------------------- |
| commit を作る前      | これから commit する内容（ステージング済みを含む） |
| 随時（利用者の指示） | 利用者が指定した範囲                               |

理由: 判定規則が 2 実装に分かれると、一方だけが更新され、同じ参照が位置によって異なる判定を受ける。検査対象の決め方は位置ごとに異なってよいが、判定そのものは 1 つに保つ。

### FNC-008: 検査は判断できる主体が居るうちに走ること

文書を削除・移動・改名する作業の**後**、かつ**その作業を行った主体がまだ文脈を持っているうち**に検査が行われる経路を持つこと。具体的には、commit を作る前の位置に検査を置くこと。

理由は 2 つある。

**第 1 に、位置が後ろすぎると検出しても直せない。** 参照切れの修復には、参照でないものの判別（この ID は書式例か）と、移動先の特定（節がどこへ移ったか）が要る。これを安く行えるのは、その変更を行った主体が文脈を保っている間だけである。文脈が失われた後に検出しても、判別と特定をやり直すことになる。

**第 2 に、検査の存在だけでは不十分である。** §1.1 の 72 箇所は文書統合の作業で発生した。その作業には参照整合を検証する手順が含まれていたが、検証はいずれも削除より**前**の段階にあり、削除によって生じた参照切れを捕まえる位置に検証が無かった。

**この位置の要求は、継続的インテグレーションでの検査を要件から外す。** commit 済みの状態しか見られない位置では、上記の第 1 の理由が満たされない。継続的インテグレーションへ置くかどうかは、除外規則が確定した後の別判断とする。

## 5. 非機能要件

### NFR-001: 見逃しと誤検出の双方を許さない

本機構は、**見逃し（実在しないのに実在と判定する）と誤検出（実在するのに実在しないと判定する）のいずれも許容しないこと**。

- 見逃しは参照切れをそのまま通し、本機構が存在しないのと同じ状態になる
- 誤検出は正しい記述を落とし、検査そのものが使われなくなる

一方を許して他方を厳しくする設計は採らない。判定に迷う入力が見つかった場合、いずれかへ倒すのではなく、**判定できない入力の存在自体を報告する**こと。

理由: 参照は他のすべての記述の検証経路であり（§1）、そこを守る機構が誤った結果を返せば、誤りは参照切れよりも広く波及する。

**ただし誤検出の重さは検査を行う位置で変わる。** FNC-008 が定める位置（判断できる主体が居るうち）では、判定できない入力を提示すればその場で切り分けられる。主体が居ない位置では、同じ提示が誰も判断できない残骸になる。この非対称があるため、**判定できない入力を許容できるかは位置の性質であり、機構が一律に決めることではない**。機構に課すのは、判定できないものを判定済みへ畳み込まないことだけである。

### NFR-002: 参照解決のアルゴリズムを外部の同種機構と一致させること

参照先のファイルを見つけるアルゴリズムについて、**同じ判定を行う外部の機構と規則を一致させる手段を持つこと**。

- 一致させる対象は、判定の規則と、規則が同じ結果を返すことを確認できる入力と期待結果の集合とすること
- 実装を共有することを要件としないこと。実装と所有は分かれていてよい

理由: 参照先を見つけるという処理は、実在性の検査に固有のものではなく、参照先の変更追随を扱う機構も同じ処理を必要とする。アルゴリズムが分かれると、同じ参照が機構によって別のファイルへ解決され、どちらが正しいか判定できなくなる。一方で、両者が解こうとしている問題は異なるため、実装を一体化すると関心事が混ざる。

### NFR-003: 実装の制約

- 検査の実装は追加の外部依存を持たないこと
- 検査は単体テストを持つこと。何を検証するかは設計で定める

### NFR-004: 失敗の可視性

検査そのものが実行できなかった場合（対象を解決できない・ファイルを読めない等）、**参照切れが無かったものとして扱わないこと**。何が失敗したかを、呼び出し側と利用者が判別できる形で報告すること。

理由: 検査の失敗を「問題なし」と区別できない状態は、検査を通したという事実が何も保証しない状態である。
