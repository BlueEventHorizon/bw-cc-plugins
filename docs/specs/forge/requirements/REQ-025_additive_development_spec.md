# REQ-025 差分開発の仕組み 要件定義書

## 1. 概要

既存仕様を変更・拡張する開発（差分開発）では、実装が完了するまで旧仕様の文書を書き換えない。書き換えると、文書が現実とも新仕様とも食い違う中間状態が生まれ、並行して作業する者が誤った前提で判断するためである。

この前提から、実装期間中は新旧 2 つの仕様が並行して存在する。本要件は、**並行状態にある文書を機械的に識別し、識別結果を実装者へ伝えること**を定める。

対象は forge を用いて要件定義書・設計書を作成し実装するすべての作業者（人間・AI）である。

### 1.1 なぜ機構が要るのか

並行状態にあるかどうかは、文書の内容や配置からは分からない。差分開発として作られた文書と恒久的な仕様の文書は、本文の書き方でも置き場所でも区別できない。

実装者には新旧両方の文書が必読文書として渡される。どちらが現在の仕様かを知らされなければ、実装者は旧仕様に従って実装しうる。さらに実装者には、**並行状態の文書を渡されなかったのか、並行状態の文書が存在しないのかの区別がつかない**。結果として旧仕様に従った実装が正常な成果物として提出され、レビューでも仕様どおりと判定される。誤りが検出される契機がどこにもない。

### 1.2 対象システムの性質

forge プラグイン内部の文書運用であり、外部公開・本番運用・個人情報の保持を伴わない開発支援ツール相当のスコープである（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

## 2. 用語

| 用語     | 定義                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 並行状態 | ある文書が既存仕様の一部を置き換えており、その置き換えが旧仕様の文書へまだ反映されていない状態           |
| 旧仕様   | 並行状態にある文書が置き換える対象となる、既存の要件定義書・設計書・計画書・ソースコード                 |
| 実装者   | 計画書のタスクを受け取り、そのタスクの実装を行う主体。必読文書として要件定義書・設計書を渡されて着手する |

## 3. スコープ

### 3.1 対象

- 並行状態にある文書の機械的な識別
- 識別結果を実装者へ伝えること
- 並行状態にある範囲について、旧仕様の記述をどう扱うかの定義

### 3.2 対象外（別途対応）

- **差分開発として扱うかどうかの判定条件** — 変更の規模・既存仕様との衝突の有無による判定であり、本要件は判定済みの文書をどう扱うかを定める
- **並行状態を終える作業（merge）の手順**
- **識別子の付け忘れを作成時に防ぐ機構** — 本要件は識別子が付与された文書の扱いを定める

## 4. 機能要件

### FNC-001: 並行状態の機械的な識別

差分開発として作成した要件定義書・設計書は、並行状態にあることを機械可読な形で示すこと。

- 識別は文書の内容の解釈を要さないこと。文書のどこを見ればよいかが一意に定まること
- 識別子は並行状態にある期間だけ存在し、並行状態を終えた時点で除去すること
- 計画書は識別子を持たないこと。計画書が並行状態にあるかは、計画書が参照する要件定義書を辿って判定すること

理由: 判定に推論が混ざると、同じ文書が実行ごとに違う分類を受ける。実装者へ伝える値が不安定であれば、伝達が行われたこと自体が何も保証しない。

### FNC-002: 識別結果は状態だけを運ぶ

実装者へ伝える識別結果は「どの文書が並行状態にあるか」だけを運び、**実装者が取るべき行動を含めないこと**。行動は規範文書と実行ガイドが定義する。

理由: 行動の定義が伝達経路の中に複製されると、規範を改訂しても複製側が古いまま残り、どちらに従うべきかが判別できなくなる。

### FNC-003: 実装者への伝達

実装者は、自らが読む文書のうちどれが並行状態にあるかを、**実装に着手する前に**知ること。

- 伝達は実装者の探索に依存しないこと。実装者が文書を開いて識別子を探す必要がないこと
- 並行状態にある文書が存在しない場合も、存在しないことが伝わること

理由: 「渡されなかった」と「存在しない」が区別できなければ、伝達が行われなかったことを実装者は検出できない。§1.1 が述べた検出契機の不在は、この区別が付かないことに起因する。

### FNC-004: 旧仕様の記述の扱い

並行状態にある文書が対象とする範囲について、**旧仕様の記述は現在の仕様ではない**。

- 旧仕様の記述はまだ更新されていないだけであり、内容としては並行状態にある文書へ置き換わっている
- 実装者は、当該範囲について旧仕様の記述を実装の根拠にしないこと
- この関係は、両者を比較して矛盾を見つけた場合にのみ成立するものではないこと。矛盾の有無に関わらず、当該範囲の現在の仕様は並行状態にある文書である

理由: 「矛盾する場合は新しい方を優先する」という形にすると、実装者に矛盾の判定を要求することになる。矛盾を見落とせば旧仕様のまま実装され、その見落としは成果物にも報告にも現れない。置き換えの関係は矛盾の検出に依存しないため、条件を付けてはならない。

### FNC-005: 識別できない場合の扱い

文書が並行状態にあることを識別できない場合、**その文書を並行状態にないものとして扱わないこと**。

- 識別の失敗と、並行状態にないことを区別すること
- 識別に失敗した場合、実装へ進む前にその事実を作業者へ伝えること

理由: 失敗を「並行状態にない」へ畳み込むと、実装者は旧仕様に従って実装しうる。その原因は識別の失敗であるにもかかわらず、失敗した事実がどこにも現れない。
