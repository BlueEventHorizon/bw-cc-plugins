# REQ-013 レビューポリシー要件

## 1. 背景

forge の AI レビューは、検出対象の網羅性を優先するあまり、本質的でない指摘・改善提案を大量に生成しがちであった。

1. **過剰提案**: 「修正必須」と「改善提案」が混在し、利用者が選別に消耗する
2. **複雑化への偏向**: 4 スキルを作るだけの計画に対して 27 ステップを生成する等、目的に対して過剰な構造を提案する
3. **緊急度の欠如**: 即時修正すべき項目と、将来的に検討すれば良い項目が同列に並ぶ
4. **二重検出**: ルールで担保されるべき品質特性（保守性・堅牢性・アーキテクチャ整合性等）を、レビューの独自観点として別途検出し、ルール違反を二重に指摘している

### 1.1 思想転換 — ドキュメント主義への純化

forge は SDD ベースのツール群であり、設計・実装・レビュー・テストすべてがドキュメント（要件定義書・設計書・ルール文書）を単一の真実源として駆動される。

この前提に立つと、**レビューだけに必要な独自観点が存在するということは、そのルールが設計段階で抜け落ちている証拠**である。レビューは「ドキュメントとの突合」に純化されるべきであり、ドキュメントでカバーできない問題は「ルール追加が必要なサイン」として Issue 化する流れが本来の rules 進化サイクルとなる。

```
レビュー = 優先度 1 (ルール合致)
        + 優先度 2 (内部矛盾検出)
        + 優先度 3 (不要な複雑化検出)
        + ルール抜け落ち発見時の Issue 化
```

各 criteria が固有に持っていた perspective（logic / resilience / maintainability / architecture / completeness 等）は廃止し、対応するルールへ委譲する。

### 1.2 設計時点での情報完全性 [MANDATORY]

レビュー時に適用する判断は、すべて執筆者が **設計時点で参照可能なドキュメント（principles / format / rules）** に明示されていなければならない。

- 「レビュアーだけが知っている判断基準」は許容しない（後出しの gotcha レビューは設計駆動を破壊する）
- 重大度判定（どの規範違反が 🔴 / 🟡 / 🟢 か）は principles 側に明文化する
- グレーゾーン（How/What 境界の判定が割れやすい論点）の許容範囲も principles 側に明文化する
- criteria は判断を持たず、principles を参照する索引と、レビュー運用上の戦術（チェック順 / 判定ルール）のみで構成する

criteria に判断が残っている状態 = 設計時点で執筆者から判断基準が隠されている状態。これを防ぐため principles の拡充を併せて要求する（FNC-1311）。

### 1.3 前提 — レビュー入力は呼び出し元が整える

レビューはフロー固有の文脈（新規機能 / 追加機能 / 設計監査 / 計画策定 / 実装直後 等）を持ち、入力（対象ファイル / 参照文書 / 委譲先ルール）の集め方はフローによって異なる。本要件はこの入力準備に立ち入らない。`/forge:start-design` 等の呼び出し元が対象を解決して `/forge:review` を起動する。

### 1.4 レビューの位置づけ [MANDATORY]

**レビュー結果は気づきであり、指示ではない。** レビュアーが返す所見は「見つけたこと」の報告であって、実施すべき変更の決定ではない。採るか捨てるかを決めるのは本体である。妥当でない所見は理由を記録して捨てる。全件が妥当でなければ全件捨てる。

**レビュアーが付けた重大度・判定は、採否の決定権を持たない。** 重大度は提示順の材料であり、実施する修正は本体の評価を経て確定する（確認なしに直してよいかは本体の確信が決める。FNC-1304）。`approved` も同様に、指摘が無かったことの報告であって承認の権限ではない。

**レビュー結果の品質を実行主体に保証させない。** 任意の入力に対する正しい所見集合は事前に定義できないため、出力の内容を契約にできない。契約にできるのは形式（判定・重大度・位置・完了宣言）だけである。**出力の期待値を上げる手段は、入力を適正にすることに限る**——渡す観点文書・規範・対象・重点観点・到達目標の適正さがレビューの質を決める。

**レビュー実行主体は、入力と出力でのみ規定する。** 本体はレビュアーが何であるかを知らない。観点文書・依頼テンプレート・書式契約・所見の振り分け・修正の安全検証はいずれも実行主体によらず共通であり、実行主体の違いはこの共通部分を変えない。実行主体固有の性質は、その実行主体を選ぶ判断の材料としてのみ記述する。

**最新の LLM を前提とする。** 特定モデルの癖・能力差に合わせた縮退や補正を設計へ持ち込まない。応答が共通書式を満たさない場合は書式契約の明示で対処し、推測による補完で救済しない。

## 2. 要件

### FNC-1301: レビュー観点の優先度体系

レビューが検出する観点は以下の 3 つに限定する。各 criteria は固有 perspective を持たない（FNC-1302）。

| 優先度 | 名称         | 判定方法                                                                                     |
| ------ | ------------ | -------------------------------------------------------------------------------------------- |
| **P1** | ルール合致   | 関連ルール文書を Read し、対象と照合する                                                     |
| **P2** | 矛盾・齟齬   | 同一対象への異なる記述を突き合わせる。**不足・欠落の検出は対象外**（網羅性確認は P1 で扱う） |
| **P3** | 不要な複雑化 | 代替案が存在 AND 既存案にそれを正当化する rationale が無い場合に Yes                         |

- P1 の対象ルール: プロジェクト固有ルール / forge 内蔵ルール / 関連仕様書。アーキテクチャ・コーディング規約・命名規則・設計原則・セキュリティ規約等、本来「品質を担保するためのルール」はすべて P1 で照合する
- P3 は「シンプルさ」「読みやすさ」等の主観評価に拡張しない（Goodhart の罠回避）

### FNC-1302: 固有 perspective の廃止と criteria の判断除去

`review_criteria_*.md` が持っていた固有 perspective を廃止し、criteria は **一切の判断（severity 判定 / グレーゾーン判定）を持たない**。判断はすべて principles 側に集約する（FNC-1311）。

| 区分                                        | criteria が持つか      | 配置                              |
| ------------------------------------------- | ---------------------- | --------------------------------- |
| 委譲先ルール文書（SSOT参照）                | **持つ**               | criteria                          |
| チェック順（どこから読むか）                | **持つ**（運用戦術）   | criteria                          |
| 判定ルール（fix / Issue化 / skip の切替）   | **持つ**（運用フロー） | criteria                          |
| 重大度マッピング（規範違反 → 🔴/🟡/🟢）     | 持たない               | principles（重大度カタログ）      |
| グレーゾーン許容範囲（How/What 境界の判定） | 持たない               | principles（許容範囲明示）        |
| 規範本体（執筆者が遵守すべき決まり）        | 持たない               | principles / format / style_guide |

委譲先ルールが未整備の場合は FNC-1305（フォールバック）および FNC-1306（Issue 化）が動作する。

### FNC-1303: 対象指定（対象軸）

レビュー対象は対象軸フラグで決定する。デフォルト（フラグ未指定）は `--diff` と等価。

| フラグ     | 役割                                                     |
| ---------- | -------------------------------------------------------- |
| `--diff`   | 現ブランチの未 commit 差分のみ。**未指定時のデフォルト** |
| `--branch` | base ブランチ分岐以降の全変更                            |
| `--files`  | 指定ファイル群を全文レビュー（カンマ区切り）             |
| `--dirs`   | 指定ディレクトリ配下を全文レビュー（カンマ区切り）       |

- 4 つは **相互排他**（同時指定はエラー）
- 行範囲指定（`a.md:30-50` 等）・セクション限定指定は採用しない（行番号や見出し構造は変動するため AI 誤生成の温床になる）
- 位置引数は **種別 1 個のみ**。Feature 名・ディレクトリ・自由入力を位置引数で受け付ける構文は持たない（FNC-1310 整合）。自由入力で呼ばれた場合は SKILL が対象を推測し AskUserQuestion で確認してから `--files` 相当へ展開する。**ディレクトリは位置引数ではなく対象軸フラグ `--dirs` で受ける**
- `--dirs` は種別を必須とする。ディレクトリ名から種別（適用する criteria）を推定しない。推定を誤った場合、なぜその criteria が適用されたのかが利用者から見えなくなるため

### FNC-1312: 対象指定の粒度保存 [MANDATORY]

レビュアーへ渡す対象指定は、**利用者が指定した粒度のまま**渡す。範囲で指定されたもの（`--diff` / `--branch` / `--dirs`）を、forge 側でファイル一覧へ展開して渡してはならない。ファイル一覧を渡してよいのは、利用者がファイル単位で指定した `--files` の場合に限る。

| 対象軸     | レビュアーへ渡すもの                                         |
| ---------- | ------------------------------------------------------------ |
| `--diff`   | 「現ブランチの未 commit 差分および未追跡ファイル」という指定 |
| `--branch` | base ブランチ名と target ブランチ名                          |
| `--files`  | ファイル一覧                                                 |
| `--dirs`   | ディレクトリ一覧                                             |

**採用理由**: 範囲指定をファイル一覧へ展開すると、展開処理の取りこぼしがそのままレビュー範囲の欠落になり、しかも欠落したことがレビュアーにも利用者にも見えない。削除されたファイルはワークツリーに存在せず Read できないため、展開側の都合で一覧から落ちる（削除が変更の大半を占める場合、レビュー範囲は変更集合の半分以下になりうる）。指定を粒度のまま渡せば、範囲の解釈はレビュアー自身が差分から行うため、この欠落は原理的に発生しない。

**base ブランチの決定**: `--branch` の base は、`git merge-base` による分岐点の解析で候補を推定し、AskUserQuestion で利用者に確認して確定する。設定値や既知ブランチ名の優先順位（`develop` → `main` → `master` 等）だけで黙って採用しない（feature から派生したブランチを誤って `develop` 起点と判定するため）。

**allowlist は本要件の対象外**: 修正フェーズの安全検証（編集がレビュー対象外へ波及していないかの検出）に使うファイル集合は、レビュアーへ渡すものではないため本要件の制約を受けない。ファイル一覧として保持してよい。`--dirs` ではディレクトリ配下を展開して allowlist を作るが、依頼本文へはディレクトリのまま渡す。この非対称（allowlist は展開してよい / 依頼本文は展開してはならない）が本要件の適用境界である。

### FNC-1304: 介入軸（interaction）

検出後に**どこまで人間へ確認するか**を介入軸フラグで決定する。デフォルトは `--interactive`。

| フラグ          | 動作                                                                                  |
| --------------- | ------------------------------------------------------------------------------------- |
| `--interactive` | 修正できる所見をすべて 1 件ずつ提示して採否を得る。**デフォルト**                     |
| `--auto`        | **確信のある所見だけ確認なしに修正する。確信のない所見は 1 件ずつ提示して採否を得る** |

- 2 つは **相互排他**（複数指定はエラー）
- 介入フィルタは介入軸でのみ機能する。検出段階では全 severity・全件を出力する
- **件数指定（`--auto N`）は採用しない** — 件数ベースの軸は AI が誤生成しやすい

#### 確信が自動修正の可否を決める [MANDATORY]

**確認なしに直してよいかを決めるのは、本体が持つ確信である。重大度ではない。**

**確信は 2 つに分かれる。対象が違うためである [MANDATORY]**。

| 記号   | 何についての確信か                              | `--auto` での扱い      |
| ------ | ----------------------------------------------- | ---------------------- |
| ✅     | **対策** — その修正を責任を持って実行できる     | 確認なしに修正する     |
| ☑️      | **所見** — レビュアーの指摘は正しい（修正は別） | **提示して採否を得る** |
| (無印) | 指摘そのものの妥当性に確信が無い                | **提示して採否を得る** |

順序があるため 1 つの尺度で足りる。`✅` は `☑️` を含み、**指摘が正しいと確信できていないものを直すことはできない**。

確信度（`☑️`）の語彙は forge の consult 提示原則が定めるものを流用する（レビュー専用の尺度を作らない）。**そこでの確信度は「いま述べている内容が正しいと言えるか」であり、修正についての確信ではない。** この意味をレビュー文脈で読み替えてはならない。

**2 つを 1 つにまとめない理由**: まとめると「指摘は正しいが直し方が分からない」を表せない。その状態は、そのまま自動修正へ流れる（誤った修正）か、正しい指摘まで無印へ落ちる（人間が判断材料を失う）かのどちらかになる。

**重大度を可否の基準にしない理由**: 重大度は「問題の重さ」であって「修正が正しい自信」ではない。🔴 critical でも直し方に確信が無ければ直すべきでなく、🟢 minor でも確信があれば直してよい。重さを自信の代理に使うと、**確信の無い修正を重大度が高いという理由で通してしまう**。

**確信が無いものを黙って直さない理由**: そこで誤れば `--auto` は「間違えるもの」になる。人間が `--auto` を選ぶのは「確信のある作業を任せる」ためであって、「不確かな判断を代行させる」ためではない。確信が無い箇所で止まることが、`--auto` を信頼できるものにする。

**`--auto` でも人間の応答を待つ場合がある [MANDATORY]**。`✅` でない所見があれば提示して採否を得るため、`--auto` は必ずしも 1 ターンで完結しない。自動で走り切ることを前提にした呼び出し元は、この性質を織り込む。

**確信は介入軸と独立である [MANDATORY]**。`--auto` は `✅` の所見を自動で直すモードにすぎず、`✅` の成立条件そのものは `--interactive` でも同じである。したがって `--interactive` でも記号を一覧に出し、利用者が「`✅` のものは任せる」と選べるようにする。介入軸を成立条件へ混ぜてはならない。

- 重大度は**提示順の材料**として残る（どれが重いのかを先に示すため）。自動修正の可否からは外れる
- 位置を特定できない所見は、確信によらず修正の対象外とする（修正対象を確定できないため）
- **重大度も確信も、実施する修正を確定しない**。修正は本体の評価を経て確定する（§1.4）

### FNC-1313: 重点観点（focus）

依頼ごとに「今回特に注意を払う対象」を自然文 1 行で渡せる任意の軸を持つ（`--focus "<自然文>"`）。既定は指定なし。

| 性質               | 内容                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| 内蔵観点との関係   | 置き換えではなく **加算**。テンプレートが名指しする criteria・規範文書によるレビューはそのまま実施される |
| 優先度体系との関係 | P1〜P3 を変えない。P1 ルール合致の照合において注意を払う対象を伝えるに留まる                             |
| severity との関係  | 指定できない。重大度は委譲先 principles の重大度カタログから決まる                                       |
| 受信側（所見評価） | 重点観点に応答する所見を「criteria に明文規定が無い」ことのみを理由にドロップしない                      |
| 形式               | 単一行。改行を含む値は依頼組み立て時にエラー終了する（プロトコル注入の防止）                             |

**採用理由**: 恒久的な観点は criteria に載せるのが正しく、実際にリンク観点は FNC-1314 で恒久化している。一方で「この PR ではここを重点的に見てほしい」という依頼固有の強弱は、criteria へ書き込むべきものではない（毎回の依頼で内容が変わり、恒久ルールとして明文化できない）。本軸はその強弱だけを担う。

**FNC-1307 の廃止軸との関係**: 本軸は廃止した depth 軸の復活ではない。depth 軸は「観点をいくつ適用するか」を段階的に増減させるものであり、重点観点は適用する観点集合を変えない。

**口頭指示からの解釈**: 利用者がフラグを明示せず「特に〜を中心にレビューして」と述べた場合も、AI が意図を汲んで重点観点として解釈する（AI が解釈すべき入力にスクリプトパーサーを使わない方針に従う）。解釈結果は送信前の引数解釈結果表に、実際に渡す 1 行として出力する。

### FNC-1318: レビューバックエンド軸（backend）

レビューの実行主体を切り替えられる軸を持つ（`--backend <name>`）。明示指定が無い場合は候補を順に可用性検査して決める（下記「バックエンドの解決順」）。

- `/forge:review` 本体はレビュー**依頼の組み立て**と**所見の処理**のみを担い、レビュアーとの往復はバックエンドへ委譲する
- 未知の backend 名を指定した場合は依頼を送信せずエラー終了する（fail closed。既定バックエンドへ暗黙にフォールバックしない）
- `--codex` / `--claude` は backend 名として解釈せず、警告のうえ無視して続行する（既存の呼び出し元が壊れないようにするため。バックエンドの指定は `--backend` のみで行う）

#### バックエンドの解決順 [MANDATORY]

| 指定                              | 対象が利用不可のとき                   |
| --------------------------------- | -------------------------------------- |
| `--backend X`（起動時の明示指定） | **fail closed**。代替を選ばない        |
| `.claude/.forge.yaml` の指定      | **fail closed**。代替を選ばない        |
| どちらも無い                      | 候補順で解決する。全滅なら fail closed |

`.forge.yaml` の指定を明示扱いとするのは、そうしないとその指定が助言でしかなくなり「設定したのに別の実行主体で走った」が起きるためである。候補の順序は本体が名前として持つ（名前を知ることは「固有の事情を持ち込む」ことに当たらない）。

**これは自動フォールバックではない**。解決は**依頼を 1 通も送る前に完了し**、選ばれたバックエンドは送信前の引数解釈結果表に必ず出る。ラウンド実行が失敗（`failure`）したときに代替を選ばない点は変えない（ADR-071）。

明示指定がない場合の既定候補順は次のとおりとする。

1. `agent-review`
2. `msg-review`

外部依存を持たずプラグイン単体で利用できる実行主体を第一候補とする。DB・端末多重化ツール・常駐セッションを必要とする実行主体は、その性質を利用者が明示的に選ぶ場合、または先位候補を利用できない場合に選ばれる。

#### 入出力契約 [MANDATORY]

| 要求         | 本体 → バックエンド                                                             | バックエンド → 本体                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 可用性検査   | なし                                                                            | 利用可能か + 不足している前提（利用者が読める説明。不足は個別に返す）+ 往復の文脈を保持するか                                                                                              |
| ラウンド実行 | `review_id`、ラウンド番号、レビューのパターン、依頼本文（テンプレート展開済み） | 判定（`approved` / `findings` / `failure`）。`findings` は所見配列を伴い、`failure` は失敗理由の説明を伴う。解釈時に生じた注意（位置未確定として受理した所見の件数等）は破棄せず添えて返す |
| 終了通知     | `review_id`（レビューの終了。終了の経路を問わない）                             | なし（受理して終える）                                                                                                                                                                     |

**パターンを渡すことは固有の事情の持ち込みではない**: レビューのパターンは本体が種別・対象軸から確定する本体自身の概念であり（依頼本文のテンプレート選択に使う）、依頼本文はそのパターンから組み立てられている。バックエンドがこれを何に使うか（ワイヤ上の識別に使う・使わない）はバックエンドの内側の判断であり、本体はパターンを渡すだけで用途を知らない。

**解釈時の注意を落とさない [MANDATORY]**: バックエンドは応答の解釈で生じた注意を判定と所見配列だけに畳まず、本体へ渡す。本体はそれを要約報告に載せる。畳むとバックエンドを替えるだけで通知が消え、下記「位置表記の欠落でラウンドを失敗させない」が要求する件数通知が成立しなくなる。

**可用性検査 [MANDATORY]**: バックエンドは自身が利用可能かを、依頼を送る前に判定して返す。判定方法（起床手段の有無・相手の常駐・実行系の起動可否等）はバックエンドの内側に閉じ、本体はこれを直接調べない。

**2 ラウンド目以降の依頼本文は、バックエンドの特性に応じて変える [MANDATORY]**: レビュアーが往復の文脈を保持するかはバックエンドによって異なる。保持しないバックエンドへ前ラウンドからの差分だけを送ると、レビュアーは対象・観点・返信形式契約を持たないまま応答することになり、成果物ではなく依頼本文の記述を検査対象にしてしまう。**この特性はバックエンド自身が可用性検査で申告し、本体は名前から推測しない**（名前からの推測は固有の事情の持ち込みにあたる）。本体が特性ごとに何を送るかは設計が定める。

- **副作用を持たない**。読み取りのみで、依頼を送らず、レビュアーのターンも起こさない。本体は候補を順に検査するため、検査が高価または破壊的であってはならない
- **不足している前提を個別に返す**。「使えません」だけでは利用者が対処できない。何が欠けているかを分けて返す
- **判定できないことを「利用可能」に畳み込まない**。検査できない前提がある場合はその旨を不足として返す（fail-open にして依頼を送り、待機予算を消費してから失敗させない）

**所見のスキーマ**: 所見は重大度・本文に加え、位置として「ファイルパス + 行番号」または「位置未確定の明示」のどちらかを必ず持つ。位置未確定の所見を、本体・バックエンドのいずれも推測で補完したり黙って破棄したりしない。

**位置表記の欠落でラウンドを失敗させない [MANDATORY]**: レビュアーの応答から位置を取り出せない所見は、位置未確定として受理し、その件数を利用者へ通知する。**位置を欠く所見が 1 件あることを理由に、他の所見を破棄してはならない**。位置が確定していない所見は修正の対象外とし、人間の確認へ回す（どこを直すかが確定していない修正は、実施も検証もできないため）。重大度マーカーの欠落・完了宣言行の異常は従来どおり fail closed とする（そちらは所見の同定そのものが成立しないため）。

**レビュアーの役割 [MANDATORY]**: レビュアーは所見を返すだけで成果物を変更しない。バックエンドは役割定義でこれを禁じ、その役割に反する能力を与えない。実現手段はバックエンドの内側に閉じる。

この性質を能力の限定で保証する案、および本体側でラウンドごとに検出する案を採らなかった経緯は ADR-073 にある。

**failure の扱い [MANDATORY]**: `failure` は、バックエンドがそのラウンドを成立させられなかったこと（前提不成立・応答を得られない・応答を共通書式として解釈できない等）の表現である。バックエンドは失敗を `approved`（所見なし）にも所見 0 件の `findings` にも畳み込まず、契約外の経路（呼び出しエラー等）だけで伝えない。本体は `failure` を判定として扱わず、レビューの失敗として利用者へ報告する（別バックエンドへ暗黙にフォールバックしない）。

**終了通知 [MANDATORY]**: 本体は、レビューがどの経路で終わる場合も（承認・介入軸による打ち切り・失敗の確定・利用者の中断）、終了をバックエンドへ通知する。バックエンドはこの通知を保持資源（プロセス・スレッド・記録等）の解放契機としてよく、保持する資源が無いバックエンドは無視してよい。バックエンドがレビューの終了を推測してはならない（`approved` を返したことや時間経過を終了の代替信号にしない）。

**履歴復元は任意拡張とする**。往復記録を永続化するバックエンドは、`review_id` を受け取って当該レビューの往復履歴と解決状態を返す拡張を提供してよい。履歴を持たないバックエンドに、共通契約を満たすためだけの DB・記録層・空履歴応答を要求しない。

- 本体の再開モードは、選択済みバックエンドが履歴復元拡張を提供する場合に限って利用する
- 履歴復元に対応しないバックエンドで中断したレビューは、同一 `review_id` で再開しない。依頼本文を再構築し、新しい `review_id` の新規レビューとして実行する
- 履歴を提供するバックエンドは、復元不能を空履歴へ畳み込まず、その旨を明示する

- **所見の書式契約は全バックエンド共通とする**。共通書式は「自由記述 markdown + 重大度マーカー + 所見ごとの位置情報（`ファイルパス:行`。特定できない場合はその旨の明示）+ 完了宣言行」とする。**重大度マーカーは所見ごとに、その所見の 1 行目の行頭に置く**（重大度を見出しにまとめ、その配下へ所見を並べる形は共通書式に含めない。所見ごとのマーカーが無い応答から重大度を推測しないため）。この置き場は依頼テンプレートの返信形式契約でレビュアーへ明示する。完了宣言行は `approved` / `findings` の 2 値であり、`failure` はレビュアーの応答には存在しない（バックエンドが本体へ返す結果にのみ存在する）。バックエンドごとに依頼テンプレートを分岐させない。構造化された形式で応答するレビュアーを使う場合も、共通形式への変換はバックエンドの内部責務とする
- **バックエンド固有の事情を本体に持ち込まない**。前提検査・レビュアーとの通信・セッション復旧・ワイヤプロトコルはバックエンド側に閉じる。共通依頼本文には特定バックエンドのワイヤヘッダを含めず、必要なバックエンドが送信直前に付加する

**採用理由**: 利用できるレビュー実行主体はプロジェクトごとに異なる。単一の実行主体に固定すると、その前提を満たせないプロジェクトでレビューフロー全体が使えなくなる。一方で、レビュー依頼の組み立て（対象解決・観点の名指し・粒度保存）と所見の処理（評価・振り分け・修正・安全検証）は実行主体に依存しないため、この境界で分割できる。failure・終了通知・位置情報の 3 要素は、2 つ目のバックエンド（無人で資源を自己保有する実行主体）の接続で契約の不足として顕在化し追加した。正常系しか定義しない契約は、失敗と終了を暗黙に「誰かが吸収する」前提を含み、その吸収先が人間である実行主体でしか成立しないためである。

### FNC-1319: 到達目標（scope）

依頼ごとに「今回の変更が到達すべき範囲」と「意図的に含めなかった項目」を渡せる任意の軸を持つ（`--scope "<自然文>"`）。既定は指定なし。

| 性質                 | 内容                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 伝えるもの           | **評価基準**（どの完成度を基準に見るか）。重点観点（FNC-1313）が伝える「注意を払う対象」とは別軸                         |
| 未指定時の意味       | 対象を最終形とみなす。情報が無いことと最終形であることを取り違えないよう、未指定である旨を依頼本文に明示する             |
| 範囲外の指摘との関係 | **範囲外の指摘を封じない**。宣言された未実装が設計書・仕様書の記述と矛盾を生んでいる場合は、所見として報告させる         |
| 形式                 | 複数行を許容する。見出し行・コードフェンス行・完了宣言行等の契約行で始まる行は依頼組み立て時にエラー終了する（注入防止） |
| 受信側（所見評価）   | 範囲外を指摘した所見を「範囲外だから」の一語で機械的に破棄しない（下記）                                                 |

**採用理由**: 段階分割された実装をレビューすると、後続タスクで実装予定の項目が欠陥として報告され、依頼側が毎回スコープを口頭で説明する往復が発生する。評価基準は依頼ごとに変わるため criteria へ書けず、重点観点とも性質が異なる（重点観点は観点の強弱、到達目標は完成度の基準）。

**範囲外所見の扱い [MANDATORY]**: 到達目標の範囲外を指摘した所見を、範囲外であることのみを理由に無条件で破棄してはならない。範囲外項目を「実装漏れ」として報告している所見は対応不要として理由付きで記録し、範囲外であることを前提に**文書と現状の乖離**を指摘している所見は妥当な指摘として扱う（修正対象が実装ではなく文書側になりうる）。前者と後者を区別せず捨てると、段階分割の宣言が文書の陳腐化を隠す手段になる。

### FNC-1320: 規範の持ち込み

呼び出し元が既に収集済みのルール・仕様のパス一覧を渡せる任意の軸を持つ（`--project-rules` / `--project-specs`）。既定は指定なしで、その場合は本体が自ら検索する。

- 渡された軸については**検索を行わず、渡された値をそのまま使う**。上流スキル（`/forge:start-implement` 等）が同一タスクに対して既に実行した検索を二重に走らせない
- 片方のみ渡された場合は、渡されなかった軸だけを検索する
- 渡された一覧の不足を本体は検証しない。forge 内蔵の観点文書はテンプレートが静的に名指ししており、プロジェクト固有ルールが空でもレビューが規範なしになるわけではない
- ただし**内蔵の規範が薄い種別**（コード・UI/UX。forge 側にコーディング規約・デザインシステム規約を持たない）では、プロジェクト固有ルールが空のとき実質的に規範なしのレビューになる。この 2 種別の依頼本文は「該当する規約が見当たらない場合はその事実を所見として報告せよ」を含める（規範なしでレビューしたことが分からないまま承認されるのを避けるため）

**採用理由**: 検索は決定論的ではなく費用も小さくないため、同一タスク内での重複実行は待ち時間と結果のぶれの両方を生む。呼び出し元が既に持っている情報を捨てて引き直す理由が無い。

### FNC-1321: 全所見の自己検証

レビュアーは各所見を返信する前に、Chain-of-Verification 型の自己検証を行う。

1. 所見の根拠となる主張を検証質問へ分解する
2. 各質問を対象ファイル・参照文書・利用可能な実体から独立に検証する
3. 反証・例外・重大度カタログとの不一致があれば、所見を修正または撤回する

検証過程は返信せず、検証後も成立する所見だけを出力する。所見の真偽は severity と独立しているため、critical / major / minor のすべてを対象とする。すべてのレビューバックエンドへ同じ指示を渡すため、バックエンド固有の定義ではなく全依頼テンプレートの返信形式契約に記載する。

**採用理由**: major 所見も `--auto` では自動修正の対象となり、minor 所見も誤っていれば人間の確認コストとレビューへの信頼低下を生む。severity は修正緊急度であって真偽の確度ではないため、検証対象を critical に限定する根拠にならない。

### FNC-1322: 所見評価の独立検証と機械的結合

各所見は、返信前の自己検証（FNC-1321）に加えて、所見を返した主体とは別の主体による独立評価（disposition・severity・confidence の確認）を経ること。

- 独立評価は、所見を返した主体自身が行わないこと（同一主体による自己評価では、その主体固有の見落とし・思い込みが評価にも引き継がれる）
- 所見と独立評価の対応付けは機械的に検証すること。件数の不一致・対応関係の欠落や重複を検出せずに結合しないこと
- この対応付けを、確認済みの検証手段を経ずに記憶に頼って行わないこと
- 対応付けが検証できない場合は結合を行わず、当該ラウンドを未解決のまま終端処理へ回すこと

**採用理由**: 所見自体の自己検証（FNC-1321）は所見を返す主体自身が行うため、その主体固有の見落とし・思い込みは検出できない。独立した第二の評価によって、単一の視点に依存しない確からしさを担保する。対応付けを記憶に頼ると、件数の不一致・欠落・重複を検証しないまま結合してしまう危険があり、この危険は記憶力ではなく機械的な検証で防ぐべきものである。

### FNC-1314: 文書参照の恒久観点化

文書内の他文書への参照（記法と実在性）を、依頼ごとの指定に依存しない恒久的なレビュー観点として扱う。

- 規範本体と重大度カタログは forge 内蔵の文書スタイル規約に置く（criteria は severity を持てないため。FNC-1302）
- 文書を対象とする criteria（design / requirement / plan / generic / uxui）は P1 の委譲先としてこの規約を参照する
- 計画書は YAML であるため、Markdown リンク記法は適用せず参照先パスの実在性のみを対象とする

**採用理由**: 参照先へ到達できない参照は、AI が文書を辿れなくなるという意味で致命的であり、口頭で依頼されたときだけ検査される観点にしておくのは本末転倒である。

### FNC-1315: 機密情報レビュー（独立起動）

機密情報の混入だけを対象とする独立したレビューを持つ（`--secrets`）。既存 7 パターンの延長ではなく、独立したテンプレート・観点・起動オプションを持つ。

**独立させる理由**:

- **既存の種別軸に載らない**。種別（位置引数）は `--files` / `--dirs` のときだけ有効で `--diff` / `--branch` では無視される（FNC-1303）。機密情報を種別に足すと、範囲指定と組み合わせたときに黙って無視される
- **観点が対象の種類と直交する**。既存パターンは「対象が何か」で分かれているが、混入は対象の種類を問わない
- **完了判定の意味が違う**。混入は 1 件の見落としで目的を達成できず、承認の意味が他種別と異なる

| 性質             | 内容                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| 対象軸           | **持たない**。常にリポジトリ全体（git 管理下 + `.gitignore` されていない未追跡ファイル） |
| 種別・対象軸併記 | エラー終了する（どちらを優先すべきか推定できないため、既定動作での続行をしない）         |
| 検出方式         | 決定論的スキャンと AI 読解の二段構え。片方に寄せない                                     |
| 自動修正         | **行わない**。介入軸が `--auto` でも未対応所見を残した完了として扱う                     |
| 重点観点         | 併用できる（FNC-1313）                                                                   |

**対象を差分に絞らない理由**: 過去のコミットで混入した秘密は今回の差分に現れないが、リポジトリには残っており漏洩の対象である。差分に絞った時点でこのレビューの目的を達成できない。

**二段構えとする理由**: 既知形式の網羅は機械検出が確実だが、形式に当てはまらない混入・文脈依存の判断は AI にしかできない。逆に AI だけに任せると、見落としても見落としたと分からない。両者の不得意が相補的であるため併用する。AI には検出結果の真偽判定に加えて、**スキャンが拾えない混入の捜索**を明示的に課す（これを省くとスキャンのパターン網羅性がそのままレビューの上限になる）。

**自動修正しない理由**: commit 済みの秘密は削除しても履歴・fork・CI ログに残るため、修正は該当する秘密の失効・再発行を伴う。失効は AI が実施できず、実施したかを検証もできない。加えて、該当行を機械的に消すと人間が影響範囲を調査する起点を失う。

#### FNC-1316: 検出値の非再掲 [MANDATORY]

検出した秘密の実体を、レビュー依頼本文・所見・ログに載せない。種別・位置・長さ・先頭数文字までに留める。

レビュー依頼と応答はレビュアーへ渡され、選択したバックエンドやホストによって記録される場合がある。実値を載せると、混入を検出する行為そのものが新たな複製経路になる。

- スキャン側が出力時点でマスクする
- **依頼組み立て側はスキャンを自分で実行し、外部からスキャン結果を受け取らない**（下記「検証ではなく信頼境界で担保する」）
- 検証エラーのメッセージにも入力値を含めない。例外メッセージは stderr・ログへ流れるため、検証そのものが露出経路になりうる
- レビュアーにも、返信本文へ実値を書かないよう依頼本文で要求する

**検証ではなく信頼境界で担保する [MANDATORY]**: 「渡された値がマスク済みか」を形式検証で確かめる方式は採らない。形式は生成元の証明にならず、実値がたまたまマスク形式に一致すれば通過するためである。代わりに、依頼組み立てが自らスキャンを実行し、マスクを経ていない値が本文へ到達する経路自体を持たない構造にする。

**スキャン結果を受け取る口を CLI にも API にも持たない**。CLI のオプションだけを閉じても、関数引数で受け取れるなら保証は「呼び出し元が正しい値を渡す」という契約に依存したままであり、構造的な保証にならない。

**採用理由**: 当初は外部ファイルでスキャン結果を受け取り、形式検証を「最後の防波堤」としていた。しかし検証を強めても「形が合っている実値」は通るため、保証にならない。実 Codex レビューで 3 ラウンドにわたり指摘を受けたのち、責務分離（手段）より機密の非露出（目的）を優先し、生成元を信頼境界の内側へ移す方針へ変更した。副作用として形式検証・スキーマ検証がいずれも不要になり、保証を強めながら実装は小さくなっている。

#### FNC-1317: 機械的な除外を黙って行わない

スキャンが「秘密ではない」と機械的に判定して除外したもの（プレースホルダ・コード式・パスに見えるキー）と、抑制マーカーで分類したものは、**いずれも件数を依頼本文へ報告する**。

抑制マーカーはレビュアーの目から隠す機能ではなく、機械検出のノイズを分類する機能である。除外規則が強すぎる兆候をレビュアーが察知できる状態を保つ。

### FNC-1305: forge 内蔵ルールのフォールバック

プロジェクト固有ルールが未整備または不十分な場合、forge 内蔵ルールが基本ルール群として常に有効化される。

- 業界標準のアンチパターン集（God Object・循環依存・ハードコード密結合・SQL インジェクション等）は `forge_anti_patterns.md` として配布物に配置する
- **AI による自動追記は行わない**。レビュー実行中に発見した場合は Issue 化（FNC-1306）し、ファイル本体の追記は通常の PR フローで行う。配布対象ファイルがレビュー実行中に変わるとリリース管理が破綻するため
- プロジェクト固有ルールと内蔵ルールが衝突するときはプロジェクト固有を優先する

### FNC-1306: ルール抜け落ち発見時の Issue 化

「明文ルールでカバーできないが指摘すべき問題」を発見した場合、ルール追加を促す Issue を起票する。検出内容と追加すべきルールの草案を Issue 本文に含め、`/anvil:create-issue` に連携する。

#### 判定 3 条件 [MANDATORY]

以下の **3 条件をすべて満たす場合のみ** Issue 化に分類する。

| # | 条件               | 内容                                                                                                               |
| - | ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 1 | 該当規定なし       | P1 で参照する SSOT のいずれにも該当規定が存在しない                                                                |
| 2 | 再発性または客観性 | 同種の指摘が複数箇所に観察される（再発性）、または客観的事実で説明可能（AI 主観の単発判断ではない）                |
| 3 | 明文化可能粒度     | ルールとして明文化可能な具体粒度を持ち、Issue として書き起こせる（「主観的にシンプルでない」等の評価語のみは不可） |

いずれかが不成立の場合は skip とし、理由を記載する。

### FNC-1307: デフォルト挙動の明示

`/forge:review <種別>`（フラグなし）は `--diff --interactive` と等価。明示形と省略形は常に等価とし、両方をサポートする。AI・利用者が「デフォルト時の挙動」を取り違えないため、デフォルト相当のフラグを明示形としても提供する。

廃止する軸:

- **scope 軸（diff / file / crossref）**: `--diff` / `--branch` / `--files` / `--dirs` で表現する
- **depth 軸**: 観点は P1〜P3 で固定。固有 perspective を持たないため段階的に観点を増減させる必要が無い

### FNC-1309: criteria の固定 3 セクション構造

`review_criteria_*.md` は以下の 3 セクション固定構造を持つ。3 セクション以外を追加してはならない。

1. **SSOT参照** — P1 で照合すべき principles / format / rules / 仕様書の文書一覧
2. **チェック順** — 「principles のどの節から先に読むか」の順序ガイド。規範本体は再掲しない
3. **判定ルール** — fix / Issue化 / skip / 要確認 の切替条件（運用フロー）

廃止セクション: `## Perspective:` 形式の固有観点ブロック / 重大度判定 / グレーゾーン判定 / 品質特性をレビュー独自観点として記述する箇所。

単一の真実源として `review_priorities_spec.md` を配布物に置き、各 criteria はこれを MANDATORY 参照する。

### FNC-1310: AI が誤判定しにくい CLI 構造

```
/forge:review <種別> [--diff | --branch | --files a.md,b.md,... | --dirs d1/,d2/,...] [--interactive | --auto] [--focus "<重点観点>"] [--scope "<到達目標>"] [--project-rules a.md,...] [--project-specs c.md,...] [--backend <name>]
```

- 位置引数は **種別 1 個のみ**。ファイル指定は `--files`、ディレクトリ指定は `--dirs` に統一する
- 各フラグは独立。値を取るのは `--files` / `--dirs` / `--focus` / `--scope` / `--project-rules` / `--project-specs` / `--backend` のみで、他はすべて値なし
- 最頻ユースケース（差分のみ × 段階的提示）は **引数なしで動く**
- 不正な組み合わせ（対象軸の二重指定・介入軸の二重指定）は early validation で拒否する
- プリセット（例: `--audit`）は導入しない

### FNC-1311: principles 拡充（重大度カタログ化 + グレーゾーン許容範囲明示化）

criteria から判断を除去するための前提として、principles 側を拡充する。

**重大度カタログ化**: 各 principles 文書の規範ごとに、違反時の重大度（🔴 致命的 / 🟡 品質問題 / 🟢 改善提案）を明示する。対象は `spec_priorities_spec.md` / `spec_design_boundary_spec.md` / `design_principles_spec.md` / `adr_principles_spec.md` / `plan_principles_spec.md`。

**グレーゾーン許容範囲の明示化**: 判定が割れやすい論点について「どの解釈を許容し、どれを許容しないか」を断定で明示する。レビュー時の false positive 警告を criteria 側に持たせず、principles で執筆者にも見える形にする。
