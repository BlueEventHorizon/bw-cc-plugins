# REQ-024 実装計画書 要件定義書

## 1. 概要

実装計画書は、設計書から抽出したタスクを保持し、実装を進める順序と進行状態を管理する成果物である。`/forge:start-plan` が作成し、`/forge:start-implement` が消費する。

本要件は計画書が保持すべき情報を定める。ファイル形式の選定は本要件の対象ではない（§2）。

### 1.1 対象システムの性質

forge プラグイン内部の文書運用であり、外部公開・本番運用・個人情報の保持を伴わない開発支援ツール相当のスコープである（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

## 2. 前提条件

- 計画書のファイル形式は JSON である（[REQ-001 オーケストレータパターン要件](REQ-001_orchestrator_pattern.md) FNC-005 が文書フォーマットの選定基準として定める）

## 3. 機能要件

### FNC-001: タスクの識別と順序付け

計画書は、実装すべき作業をタスクの集合として保持すること。各タスクは次を持つこと。

- 計画書内で一意な識別子
- 着手すべき順序を表す優先度
- 先に完了している必要がある他タスクの識別子

### FNC-002: 実行可能タスクの一意な決定

計画書の内容から、次に着手できるタスクが一意に決まること。判断に人間の解釈を要さないこと。

- 各タスクは未着手・実行中・完了のいずれかの進行状態を持つこと
- 未着手であり、かつ先行タスクがすべて完了しているタスクが実行可能であること
- 実行可能なタスクが複数ある場合は優先度で順序が決まること

理由: 次に何をするかの決定が解釈に依存すると、同じ計画書から異なる実行順序が生まれ、依存関係の前提が崩れる。

### FNC-003: トレーサビリティの保持

計画書は、要件・設計・タスクの対応関係を保持すること。

- どの要件がどの設計に対応し、その設計からどのタスクが生まれたかを辿れること
- 要件・設計それぞれについて、対応するタスクが計画書に存在しないことを検出できること

理由: 対応タスクの欠落は、実装が完了したように見えたまま要件が満たされない状態を生む。欠落を検出できなければ、計画書の全タスク完了が要件の充足を意味しなくなる。

### FNC-004: タスクの粒度

1 つのタスクは、単一の実装主体が他のタスクの完了を待たずに実行し完結できる範囲とすること。

理由: 1 タスクの中で他タスクの完了を待つ必要が生じると、進行状態がタスク単位で表せなくなり、FNC-002 の一意な決定が成立しない。

### FNC-005: 実装に必要な文書の指定

各タスクは、その実装に必要な文書のパスを保持すること。実装主体はタスクの記述だけでなく、指定された文書を読んで実装すること。

### FNC-006: 計画書の一時性

計画書は実装完了後に破棄しうる作業ファイルであり、恒久保存を目的としないこと。破棄するか残すかは利用者が選択すること。

### FNC-007: 差分 feature の識別子を持たない

計画書は差分 feature の識別子を持たないこと。計画書が差分 feature に属するかは、トレーサビリティが参照する要件定義書の識別子を辿って判定すること（[REQ-025 差分開発の仕組み 要件定義書](REQ-025_additive_development_spec.md) FNC-001）。

理由: 同じ事実を 2 か所に持つと、一方だけが更新された状態が生まれる。辿れる関係が既にあるなら、辿る側に持たせない。

## 4. 未確定事項

該当なし。
