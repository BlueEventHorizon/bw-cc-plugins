# REQ-027 reviewer の依頼契約と観点判定 要件定義書

## 概要

本書には、通常は設計書に属する具体的な記述（JSON のフィールド名・型等）を含む。これは、既に決定済みで選択の余地が無い事項を要件定義書に具体的に書く原則（[spec_design_boundary_spec.md](../../../../plugins/forge/docs/spec_design_boundary_spec.md) §2）に基づく。

本書は reviewer への入力と出力の契約、および観点を選ぶ主体を定める。

対象は reviewer（[reviewer.md](../../../../plugins/forge/agents/reviewer.md)）・reviewer への依頼・依頼を組み立てる review 本体（[review/SKILL.md](../../../../plugins/forge/skills/review/SKILL.md)）。

**本書が定める受け渡しの方式（FNC-302〜304）は、evaluator との受け渡しにも及ぶ。** 同じ問題への答えを 2 つ持たないため、方式は本書が持ち、[REQ-026](../../evaluator-perspective/requirements/REQ-026_evaluator_perspective.md) FNC-207 がこれに従う。evaluator の観点と評価の構造は同書が定める。

## 前提条件

- reviewer が所見（finding）を返し、別の主体が独立に評価する既存の枠組み（`forge:REQ-013`）が有効であること

## 対象システムの性質

開発者が自分の端末で使う review 機構の一部であり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。性能・可用性・運用性の定量目標は持たない。

## 用語

| 用語       | 定義                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| finding    | reviewer が返す所見 1 件                                                   |
| finding_id | finding 1 件を指す一意な識別子                                             |
| 依頼       | reviewer への入力の全体                                                    |
| キー       | 1 つのレビューを一意に指す値。依頼と所見の置き場を script が決める手がかり |
| 観点       | 対象を照らして違反を検出するための規範の集まり                             |

## 要件一覧

reviewer の仕事は 3 段からなる。**入力を得る → レビューする → 所見を返す。**

### 0. reviewer の定義が持つもの

#### FNC-301: 扱いと呼び方は reviewer の定義が持つ [MANDATORY]

reviewer 自身の定義が次を持つ。依頼はこれを運ばない——依頼ごとに変わらないものを、往復のたびに運ぶ理由がない。

| 持つもの                             | 内容                                                     |
| ------------------------------------ | -------------------------------------------------------- |
| script の呼び方                      | 依頼を得る script・所見を渡す script を、どう呼ぶか      |
| 依頼の各項目の扱い                   | 項目が何であり、どう扱うか。値を持たないときにどう扱うか |
| 対象の読み方                         | `targets` の形ごとに異なる（FNC-306）                    |
| 種別の判定基準と、種別ごとに読む文書 | FNC-307・FNC-308                                         |
| 所見として何を述べるか               | 何を問題として挙げ、どこまで書くか                       |

**JSON の構造は持たない。** 封筒・入れ子・型は script が持つ（FNC-303）。reviewer は JSON を組み立てないため、知る必要がない。

**reviewer として動く実行主体は、この定義を読めること。** 定義を読めない実行主体は、script の呼び方も依頼の扱いも知る手段を持たない。

### 1. 入力

#### FNC-302: 依頼はキーで受け渡す [MANDATORY]

依頼は JSON として保持し（構成は DM-301）、reviewer には**キーだけを渡す**。reviewer はキーを script へ渡して依頼を得る。

**AI が運ぶ値はキー 1 つに限る。** JSON そのものを AI の手で受け渡すと、書き写しの誤りという経路が生まれる。置き場は script が決め、AI は組み立てない（[deterministic_generation_spec.md](../../../../plugins/forge/docs/deterministic_generation_spec.md) §5）。

| 性質         | 内容                                                        |
| ------------ | ----------------------------------------------------------- |
| 生成する主体 | 本体。reviewer を起動する前に、依頼を保持する時点で生成する |
| 一意性       | 他のレビューと衝突しない                                    |
| 寿命         | **1 レビューにつき 1 つ**。往復の全ラウンドで同じキーを使う |

依頼は対象の指定の仕方でも、対象の種別でも形を変えない。対象の指定の仕方による違いは `targets` の形（DM-301）が表し、種別による違いは reviewer が判定する（FNC-307）。

#### FNC-303: 依頼と所見は script が組み立てる [MANDATORY]

依頼も所見も、script が組み立てる。AI が組み立てない。渡された値をそのまま置き、生成・要約・改変しない。

したがって**形式の検証を置かない**。形が壊れるのはバグであり、実行時の検査で受け止める対象ではない（[deterministic_generation_spec.md](../../../../plugins/forge/docs/deterministic_generation_spec.md) §3・§4）。同文書 §6.1 が「AI の応答を受け取る側に検査を置く」とする例外は、**代わりに組み立てられる実行系が存在しない**ことを根拠としており、script が組み立てる本設計では成立しない。

#### FNC-304: 値は変形せずに受け渡される [MANDATORY]

依頼と所見が運ぶ値は、途中で欠落・変形・分断されないこと。

所見の本文・重点観点・到達目標には、**改行・引用符・バッククォート・非 ASCII** が含まれる。これらを含む値が、渡した内容と同一のまま相手に届くこと。

- 値の内容を理由に受け渡しを拒む制約を置かない。改行を含むから渡せない、という形にしない
- 受け渡しの過程で値が構文として解釈される経路を作らない

#### FNC-305: 依頼はラウンドによって形を変えない

毎ラウンド同じ構成を渡す。前ラウンドの対応は依頼が持つ 1 項目であり（DM-301）、形を変える理由にはならない。

### 2. 作業

本節が定めるのは、本書が変える部分である。ここに無い事柄は現行のまま有効である。

#### FNC-306: 対象を読む

対象の読み方は `targets` の形（DM-301）で決まる。

| `targets` の形 | 読み方                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| 列挙           | 挙げられたファイルを全文読む。ディレクトリが挙げられている場合は、配下のファイルを reviewer 自身が列挙して全文読む |
| ブランチの組   | 基点から分岐して以降の全変更を、reviewer 自身が差分から確定する。対象の一覧は渡されない                            |
| 範囲           | 未コミット変更のすべてを、reviewer 自身が差分から確定する。対象の一覧は渡されない                                  |

**差分から確定する場合、削除とリネームも変更の一部である。** 追加・変更だけを見ると、消えた規範・契約・テストと、残ったファイルから消えた対象への参照が見落とされる。

#### FNC-307: 対象ごとに種別を判定する

依頼は対象の種別を指定しない。reviewer が対象ごとに判定する。ファイルやディレクトリで指定された対象には、ソースコードと各種の文書が混在しうる。対象全体に単一の種別を課すと、混在した対象を正しく扱えない。

判定する種別は **code / requirement / design / plan / uxui** の 5 つとする。ADR は design として扱う。

判定の材料は 2 つあり、**先に設定を引き、それで決まらないものだけファイルを見る**。

| 材料                         | 何が決まるか                                             | 取得の仕方                                                                                                                                                                                                                                                        |
| ---------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.doc_structure.yaml` の宣言 | 文書の種別。プロジェクトがパスと種別の対応を宣言している | **script が解決する。** `plugins/forge/scripts/doc_structure/resolve_doc_structure.py` を改修し、パスを与えて種別を返す口を設ける（新設しない。同 script が既に `.doc_structure.yaml` の解決を担っており、別 script にすると同じ設定を解釈する箇所が 2 つになる） |
| ファイルそのもの             | ソースコードか否か。import 等から UI に関わるか          | reviewer が読む                                                                                                                                                                                                                                                   |

**設定にも実体にも当たらずに、名前だけで種別を当ててはならない。** 設定が宣言している対応を使うことは、これに当たらない。

`.doc_structure.yaml` を AI が読まない。設定ファイルの解釈は決定論であり script の仕事である（[deterministic_generation_spec.md](../../../../plugins/forge/docs/deterministic_generation_spec.md) §6）。

### 3. 出力

#### FNC-309: 所見は script を通して返す

reviewer は所見の値を script へ渡し、script がキーの下へ所見を保持する（構成は DM-302）。本体はキーを script へ渡して所見を得る。所見が無い場合は 1 件も渡さない。

- **reviewer は JSON を自ら組み立てない。** 値を渡すだけであり、形は script が持つ（FNC-303）
- finding_id は reviewer が 1 始まりの連番として付与する
- reviewer は交換可能な実行主体であり、実行主体ごとにこの契約を分岐させない

#### FNC-310: 書き出しは判断を確定させた後に行う [MANDATORY]

所見を 1 件ずつ渡してよい。ただし**すべての判断を確定させてから書き出す**。判断しながら逐次書き出してはならない。

**上書き・修正の操作を持たない。** 持たせれば「後から直せる」前提が生まれ、逐次の書き出しを誘発する。

逐次に書き出すと、後から前の所見を直したくなる。対象を読み進めて前の判断が変わること、同じ問題が複数箇所にあると後で気づくことは起こるためである。evaluator ではこれが構造的に起きる——複数の所見を 1 件の評価で束ねるには（[REQ-026](../../evaluator-perspective/requirements/REQ-026_evaluator_perspective.md) FNC-201）、全所見を見てから評価を確定する必要がある。

#### FNC-311: 終了の値で結果の成否を表す [MANDATORY]

reviewer は所見を書き出し終えたら、**終了の値を渡す**（構成は DM-303）。終了の値は結果の一部であり、別の記録機構を設けない。

| 終了の値               | 意味                     | 誰が書くか                       |
| ---------------------- | ------------------------ | -------------------------------- |
| `0`                    | 正常終了                 | reviewer                         |
| **結果の JSON が無い** | 書けない異常終了         | **誰も書かない**（書けなかった） |
| 定義されたエラー値     | 自覚したエラーによる終了 | reviewer                         |

**書けない異常終了は、結果の JSON が存在しないことで表される。** 異常時に何かを書かせる形では、書けない異常（落ちた・黙って終えた・起動に失敗した）を取りこぼす。正常時にだけ印が残る形なら、それらがすべて「結果が無い」に収束する。

**エラーの感知は script が行う。** script は結果を読んで状態を報告するだけであり、記録のための状態を自ら持たない。記録の有無を AI に確かめさせ、その結果で進退を決めさせない——判定材料は終了の値だけであり、AI の判断を要しない（[deterministic_generation_spec.md](../../../../plugins/forge/docs/deterministic_generation_spec.md) §5）。

エラー値は**閉じた集合**とする。定義に無い値は、書けない異常終了と同じ扱いとする（未知の値を正常として通さない）。

| エラー値              | 意味                                         | 由来    |
| --------------------- | -------------------------------------------- | ------- |
| `target_unreadable`   | 対象が読めない（存在しない・差分が取れない） | FNC-306 |
| `criteria_unreadable` | 種別に対応する文書が読めない                 | FNC-308 |

種別が判定できないことはエラーに含めない。FNC-307 が「判定できない旨を所見にする」と定めており、正常終了の範囲である。

- **エラー終了した場合、それまでに書かれた所見を後続の工程で使わない。** 結果が不完全であるため。利用者への報告に用いることは妨げない
- **正常に終えたのに終了の値を書き忘れた場合も、書けない異常終了として扱う。** 正しい結果が異常として扱われることはあるが、異常が正常として通るよりは安全である

### データモデル

#### DM-301: 依頼の構成

依頼は次の情報を持つ。キーの下に保持され、reviewer は script を通してこれを得る（FNC-301）。

| 情報         | 型             | 必須 | 内容                                                                                   |
| ------------ | -------------- | ---- | -------------------------------------------------------------------------------------- |
| project_root | 文字列         | 必須 | レビュー対象プロジェクトの絶対パス                                                     |
| targets      | 下表           | 必須 | レビュー対象の指定                                                                     |
| focus        | 文字列         | 任意 | 今回の依頼で特に注意を払う対象                                                         |
| scope        | 文字列         | 任意 | 今回の到達目標と、意図的に含めなかった項目                                             |
| references   | 参照文書の配列 | 任意 | プロジェクト固有のルール文書・仕様書。各要素は絶対パスと、それが何かを述べる説明を持つ |
| prior_round  | 下表           | 任意 | 前ラウンドの所見に対してどう対応したか。初回は持たない                                 |

**パスは絶対パスとする。** reviewer は別の実行主体であり、作業ディレクトリが一致する保証がない。

##### targets の形

次のいずれか 1 つの形を持つ。どの形であるかが判別できること。

| 形           | 内容                                                                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 列挙         | レビュー対象のファイル・ディレクトリの並び。**ファイルとディレクトリを区別できる形で持ち、ディレクトリを配下のファイルへ展開しない**（`forge:REQ-013` FNC-1312 の粒度保存） |
| ブランチの組 | 比較の基点となるブランチと、対象のブランチ                                                                                                                                  |
| 範囲         | 未コミット差分。対象を列挙しない                                                                                                                                            |

##### prior_round の構成

初回の依頼は持たない。2 ラウンド目以降が持つ。

| 項目       | 内容                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 対応の並び | 前ラウンドの所見ごとに、対応したか・対応しない場合はその理由を持つ。所見は finding_id で指す |

#### DM-302: finding の構成

reviewer が返す finding は次のフィールドを持つ。

| フィールド | 型     | 必須 | 内容                                                          |
| ---------- | ------ | ---- | ------------------------------------------------------------- |
| finding_id | 整数   | 必須 | reviewer が付与する一意な識別子（1 始まりの連番）             |
| severity   | enum   | 必須 | critical / major / minor                                      |
| location   | 文字列 | 必須 | `ファイルパス:行`。特定できない場合は `位置未確定` と明示する |
| body       | 文字列 | 必須 | 所見本文                                                      |

#### DM-303: 結果の構成

reviewer の結果は、所見の集合と終了の値を持つ 1 つの構造である。

| フィールド | 型             | 必須                     | 内容                                                                   |
| ---------- | -------------- | ------------------------ | ---------------------------------------------------------------------- |
| findings   | finding の配列 | 必須（0 件もある）       | 書き出された所見（DM-302）。順序は finding_id の昇順                   |
| exit       | enum           | 終了の値を渡したとき必須 | `0`、またはエラー値（FNC-311）。**この構造自体が無い状態が異常を表す** |

`exit` が無い結果は、書き出しの途中で終えたことを意味する。FNC-311 の「書けない異常終了」と同じ扱いとする。
