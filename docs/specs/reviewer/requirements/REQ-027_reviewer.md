# REQ-027 reviewer の依頼契約と観点判定 要件定義書

## 概要

本書には、通常は設計書に属する具体的な記述（JSON のフィールド名・型等）を含む。これは、既に決定済みで選択の余地が無い事項を要件定義書に具体的に書く原則（[spec_design_boundary_spec.md](../../../../plugins/forge/docs/spec_design_boundary_spec.md) §2）に基づく。

本書は reviewer への入力と出力の契約、および観点を選ぶ主体を定める。

対象は reviewer（[reviewer.md](../../../../plugins/forge/agents/reviewer.md)）・reviewer への依頼・依頼を組み立てる review 本体（[review/SKILL.md](../../../../plugins/forge/skills/review/SKILL.md)）。

evaluator の観点と評価の構造は [REQ-026](../../evaluator-perspective/requirements/REQ-026_evaluator_perspective.md) が定める。

## 前提条件

- reviewer が所見（finding）を返し、別の主体が独立に評価する既存の枠組み（`forge:REQ-013`）が有効であること

## 対象システムの性質

開発者が自分の端末で使う review 機構の一部であり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。性能・可用性・運用性の定量目標は持たない。

## 用語

| 用語       | 定義                                           |
| ---------- | ---------------------------------------------- |
| finding    | reviewer が返す所見 1 件                       |
| finding_id | finding 1 件を指す一意な識別子                 |
| 依頼       | reviewer へ渡す入力の全体                      |
| 観点       | 対象を照らして違反を検出するための規範の集まり |

## 要件一覧

### 依頼

#### FNC-301: 依頼は JSON で渡す

reviewer への依頼を JSON として渡す（構成は DM-301）。

依頼が運ぶものは 2 種類であり、両者を混ぜない。

| 種類                                                                             | 扱い                                 |
| -------------------------------------------------------------------------------- | ------------------------------------ |
| データ（対象・重点観点・到達目標・プロジェクト固有の参照文書・前ラウンドの対応） | 構造として持つ                       |
| 指示文（reviewer の振る舞いを定める散文・返信形式契約）                          | 文字列として持ち、**内容を変えない** |

- **指示文をフィールドへ畳まない**。指示文は禁止とその帰結・欄の意味を理由とともに述べており、レビューの質はこの記述で決まる。フィールドに畳むと理由が失われる
- **データを指示文へ埋め込まない**。値が本文の構造を壊す経路を作らないため、データは構造の側にだけ置く
- 任意の項目が**無いことの意味**（到達目標が無ければ最終形とみなす等）は、指示文が述べる。値の不在そのものに意味を持たせない
- **依頼の定義は 1 つとする。** 対象の指定の仕方でも、対象の種別でも分岐させない。対象の指定の仕方による違いは `targets` の形（DM-301）が表し、種別による違いは reviewer が判定する（FNC-305）ため、定義を分ける理由が残らない

#### FNC-302: 受け渡しは自己記述的である [MANDATORY]

**reviewer が、外部のフォーマット定義を参照せずに、依頼の各項目が何を意味しどう扱うか、および応答をどう作るかを知れること。** 依頼の読み方と応答の作り方の双方が対象である。

散文の依頼は、見出しが項目の名を示し、直後の記述がその意味と扱いを述べるため、読めばそのまま意味が立ち上がる。構造化すると、値と、それをどう扱うかの記述が離れる。離れたままでは、reviewer は値を見ても扱いを決められず、依頼を組み立てる側もどの項目に何を入れるかを決められない。**文字は読めるが用途が分からない状態になる。**

したがって次を満たすこと。

- **依頼のすべての項目について、それが何であり、どう扱うかが依頼の中に書かれている**。項目名だけで意味が伝わることを前提にしない
- **項目が値を持たないときの意味も書かれている**（FNC-301）
- **応答のすべてのフィールドについて、何を入れるかが依頼の中に書かれている**
- 項目・フィールドを追加・改名したとき、その意味の記述も同時に揃っていること

この性質を機械的に確かめられること。依頼の項目・応答のフィールドと、その意味の記述の対応が取れているかを、双方について検証できる形にする。

#### FNC-303: 依頼の作成は決定論的に行う

依頼は、レビューの実行系が組み立てる。AI が組み立てない。

- 指示文は、**依頼定義が持つ文言をそのまま**載せる。実行系が生成・要約・改変しない
- データは、渡された値をそのまま構造へ置く

依頼定義は指示文の文言を保持する。依頼定義が 1 つである以上（FNC-301）、指示文の定義点も 1 つである。

#### FNC-304: 依頼はラウンドによって形を変えない

毎ラウンド同じ構成を渡す。前ラウンドの対応は依頼が持つ 1 項目であり（DM-301）、形を変える理由にはならない。

### 観点の判定

#### FNC-305: reviewer が対象ごとに適用する観点を判定する

依頼は対象の種別を指定しない。reviewer が対象ごとに、どの観点を適用するかを自ら判定する。

- 判定の材料は、ファイルの形式と、プロジェクトの文書構成である
- ファイルやディレクトリで指定された対象には、ソースコード・要件定義書・設計書・計画書が混在しうる。対象全体に単一の種別を課すと、混在した対象を正しく扱えない
- 対象の中身を読まずに、パス名から種別を推定してはならない

判定する種別は次の 5 つとする。

| 種別        | 対象                 |
| ----------- | -------------------- |
| code        | ソースコード         |
| requirement | 要件定義書           |
| design      | 設計書・ADR          |
| plan        | 計画書               |
| uxui        | UI / UX に関わる文書 |

### 応答

#### FNC-307: reviewer は所見を JSON で応答する

reviewer は所見を JSON 配列として返す（構成は DM-302）。所見が無い場合は空配列とする。

- reviewer は交換可能な実行主体であり、実行主体ごとに依頼を分岐させない。JSON 化は全実行主体に共通の契約として行う
- finding_id は reviewer 自身が 1 始まりの連番として付与する
- 自由記述から正規表現で抽出する方式は採らない。抽出が誤動作した実績があるため（本文中の文字列を位置情報と誤抽出する等）

### データモデル

#### DM-301: 依頼の構成

依頼は次の情報を持つ。

| 情報         | 型             | 必須 | 内容                                                                                   |
| ------------ | -------------- | ---- | -------------------------------------------------------------------------------------- |
| project_root | 文字列         | 必須 | レビュー対象プロジェクトの絶対パス                                                     |
| targets      | 下表           | 必須 | レビュー対象の指定                                                                     |
| focus        | 文字列         | 任意 | 今回の依頼で特に注意を払う対象                                                         |
| scope        | 文字列         | 任意 | 今回の到達目標と、意図的に含めなかった項目                                             |
| references   | 参照文書の配列 | 任意 | プロジェクト固有のルール文書・仕様書。各要素は絶対パスと、それが何かを述べる説明を持つ |
| prior_round  | 下表           | 任意 | 前ラウンドの所見に対してどう対応したか。初回は持たない                                 |
| instructions | 指示文         | 必須 | reviewer が依頼を読み、レビューを行い、応答を返すために要る記述（下表）                |

**パスは絶対パスとする。** reviewer は別の実行主体であり、作業ディレクトリが一致する保証がない。

##### targets の形

次のいずれか 1 つの形を持つ。どの形であるかが判別できること。

| 形           | 内容                                                                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 列挙         | レビュー対象のファイル・ディレクトリの並び。**ファイルとディレクトリを区別できる形で持ち、ディレクトリを配下のファイルへ展開しない**（`forge:REQ-013` FNC-1312 の粒度保存） |
| ブランチの組 | 比較の基点となるブランチと、対象のブランチ                                                                                                                                  |
| 範囲         | 未コミット差分。対象を列挙しない                                                                                                                                            |

##### prior_round の構成

初回の依頼は持たない。2 ラウンド目以降が持つ。

| 項目       | 内容                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 対応の並び | 前ラウンドの所見ごとに、対応したか・対応しない場合はその理由を持つ。所見は finding_id で指す |

##### instructions の内容

reviewer が依頼を読み、レビューを行い、応答を返すために要る記述をすべて含む。これを欠くと、reviewer は値を受け取っても扱いを決められない（FNC-302）。

| 内容               | 何を述べるか                                                   |
| ------------------ | -------------------------------------------------------------- |
| 依頼の形式         | 依頼が持つ項目の名前・型・入れ子・必須か任意か                 |
| 各項目の意味と扱い | その項目が何であり、どう扱うか。値を持たないときにどう扱うか   |
| レビューの進め方   | `targets` の形ごとの対象の読み方、してはならないこととその帰結 |
| 応答の形式         | 応答が持つフィールドの名前・型・入れ子・必須か任意か           |
| 応答の作り方       | 各フィールドに何を入れるか                                     |

対象の読み方は `targets` の 3 形で異なる。列挙された対象は全文を読む。差分・ブランチの組では対象の一覧を渡さないため、追加・変更・削除・リネームのすべてを reviewer が差分から確定する。指示文は 3 形すべての読み方を述べ、形による分岐を持たない。

種別ごとに扱う文書（FNC-306）はここに書かない。reviewer 自身の定義が持つ。

#### DM-302: finding の構成

reviewer が返す finding は次のフィールドを持つ。

| フィールド | 型     | 必須 | 内容                                                          |
| ---------- | ------ | ---- | ------------------------------------------------------------- |
| finding_id | 整数   | 必須 | reviewer が付与する一意な識別子（1 始まりの連番）             |
| severity   | enum   | 必須 | critical / major / minor                                      |
| location   | 文字列 | 必須 | `ファイルパス:行`。特定できない場合は `位置未確定` と明示する |
| body       | 文字列 | 必須 | 所見本文                                                      |
