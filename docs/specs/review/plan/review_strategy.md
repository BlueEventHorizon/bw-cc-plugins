# review 実装戦略

## アプローチ

**選択**: ボトムアップ

**根拠**:

対象は `combine_findings_and_evaluations.py`（DES-066 §3.10a）という単一の新規スクリプトと、その呼び出し元である `SKILL.md` Step 7 手順1の記述更新の2点のみであり、依存方向は一方向（SKILL.md がスクリプトに依存する）。設計書 §3.10a・§6（テスト設計）が入出力契約・検証条件・失敗時挙動をすべて確定済みで、`parse_findings.py`／`parse_evaluation.py`／`split_by_location.py` という同一ディレクトリの確立済みパターン（標準ライブラリのみ、`argparse` + JSON 標準入出力、判断を持たない決定論的 CLI、`tests/forge/review/` にミラー配置するユニットテスト）がそのまま流用できる。未検証技術・外部連携・スキーマ変更は無く、フィーチャースライスやリスク駆動を要する不確実性が存在しない。したがって、まず十分にテストされた基盤（スクリプト）を積み上げ、その上に消費側（SKILL.md の文言）を接続するボトムアップが最も無駄がない。

## フェーズ

### フェーズ 1: `combine_findings_and_evaluations.py` の実装とユニットテスト

- **目標**: `parse_findings.py` が生成した所見配列と `parse_evaluation.py` が検証済みの評価配列（`index`/`disposition`/`severity`/`confidence`/`fix_confident`）を受け取り、①両配列の長さ一致、②evaluator 側 `index` 集合が `{0,...,len-1}` と完全一致、の2条件をいずれも満たす場合のみ `index` で1件ずつ結合した配列を返す。いずれか不成立ならエラー（`status: "error"` 相当）を返し、結合を行わない。CLI 単体で `python3 -m unittest` によりこの契約が機械的に確認できる状態
- **スコープ**: `plugins/forge/skills/review/scripts/combine_findings_and_evaluations.py`（DES-066 §3.1 モジュール一覧・§3.10a 検証/結合ロジック）、対応ユニットテスト `tests/forge/review/test_combine_findings_and_evaluations.py`（DES-066 §6 テスト設計行）
- **検証ポイント**:
  - `python3 -m unittest tests.forge.review.test_combine_findings_and_evaluations -v` が通ること
  - 正常系（長さ一致・index 過不足なし）で `index` 昇順に1件ずつ結合されること（`parse_evaluation.py` は既に `index` でソート済みだが、本スクリプトは受け取った配列の並びに依存せず `index` で対応付けること）
  - 異常系: 件数不一致、`index` の欠落、`index` の重複のそれぞれで結合を行わずエラーを返すこと
  - `dprint check` が通ること（新規ファイルなし＝Python のみのため実質影響なしだが、既存 CI ゲート2点を両方確認）

### フェーズ 2: `SKILL.md` Step 7 手順1 の記述をスクリプト呼び出しへ更新

- **目標**: `plugins/forge/skills/review/SKILL.md` Step 7 手順1（現状「`status: "ok"` の場合、`evaluations` の各要素…を、対応する所見に結び付けて以後の手順で使う」という記憶依存の暫定記述）を、フェーズ1で実装したスクリプトを呼び出す手順へ更新する。DES-066 §3.10a が求める「対応付けを記憶に頼らず機械的に検証する」動作が実際の手順として成立している状態
- **スコープ**: `plugins/forge/skills/review/SKILL.md` Step 7 手順1（`parse_evaluation.py` 呼び出し直後、手順2「位置による振り分け」に渡す直前の箇所）。DES-066本体の§3.10aの検証条件・結合仕様自体は変更しない。ただし「現状（未実装）」という状態記述（§3.10a・§7 TBD-002）は、実装完了後の事実に合わせて更新する（記述の古さの解消であり、設計判断の変更ではない）
- **検証ポイント**:
  - 追記するコマンド呼び出し（`combine_findings_and_evaluations.py`）の引数・出力形式が、フェーズ1で確定した実際のCLI仕様と一致していること（架空の引数名を書かない）
  - エラー時（結合不成立）の記述が、DES-066 §3.10a「結合せずエラーを返し、そのラウンドを `halted_with_open_findings` として終端処理へ回す」と一致していること（Step 7 手順1の既存の evaluator 契約違反時フローと同型の記述にする）
  - 「現状（未実装）」を前提にした記述（DES-066 §3.10a・TBD-002）が本実装後は事実と乖離するため、`docs/specs/forge/design/DES-066_review_body_design.md` §3.10a「現状（未実装）」節および §7 TBD-002 の該当記述を、実装完了後の状態に合わせて更新する
  - `python3 -m unittest discover -s tests -p 'test_*.py'` 全体が引き続き通ること（SKILL.md はテスト対象外のため直接のテストは無いが、既存テストの回帰が無いことを確認）
