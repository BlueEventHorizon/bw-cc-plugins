# REQ-026 evaluator の独立評価とメタ観点 要件定義書

## 概要

本書には、通常は設計書に属する具体的な記述（JSON のフィールド名・型等）を含む。これは、既に決定済みで選択の余地が無い事項を要件定義書に具体的に書く原則（[spec_design_boundary_spec.md](../../../../plugins/forge/docs/spec_design_boundary_spec.md) §2）に基づく。

`forge:REQ-013` FNC-1322 は、所見を返した主体（reviewer）とは別の主体（evaluator）による独立評価を課している。しかし現状の evaluator は reviewer と同じ観点文書を同じ向きで読むため、reviewer と同じ誤りを繰り返すことがある。

**本書は evaluator の振る舞いを定める。** 中心は、reviewer とは異なる層（指摘の奥にある本質・対象文書の情報）を見るメタ観点と、それを評価としてどう述べるかである。

**受け渡し・採番・書き出しと終了の値・本体の仕事・データの構造は本書が定めない。** それらは review 機構の共通契約であり、[REQ-028](REQ-028_review_exchange.md) が定める。evaluator はその契約に従う。本書は共通契約を繰り返さず、evaluator に固有のことだけを書く。

対象は本体が起動する evaluator（[evaluator.md](../../../../plugins/forge/agents/evaluator.md)）である。agenda・consult の表示・記録**機構そのものの再設計**は本書のスコープ外であり、別の差分 feature（agenda 全面刷新）で扱う。

## 対象システムの性質

開発者が自分の端末で使う review 機構の一部であり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。性能・可用性・運用性の定量目標は持たない。

## 用語

evaluator だけが使う用語を定める。finding・finding_id・evaluation・disposition・結果など、本体も認識する用語は [REQ-028](REQ-028_review_exchange.md) が定める。

| 用語     | 定義                                                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| メタ観点 | evaluator が `disposition` を判定する際の手がかり（FNC-201）。レビュー観点が対象を照らす規範であるのに対し、メタ観点は判定そのものを疑う |

**`disposition` の各値が何を意味するか**は本書が定める。値の集合そのものは共通契約が持つ（[REQ-028](REQ-028_review_exchange.md) DM-201）。

| disposition の値   | 意味                                                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid`          | 観点文書・対象の実態に照らして妥当でない指摘                                                                                                                  |
| `misunderstanding` | 対象・前提の理解に誤りがある指摘                                                                                                                              |
| `out_of_scope`     | 到達目標欄が宣言した意図的な未実装を欠陥として報告している指摘。ただし、範囲外を前提に設計書・仕様書の記述と現状の乖離を指摘している場合は `valid` として扱う |
| `valid`            | 上記のいずれにも該当しない指摘                                                                                                                                |
| `flawed_premise`   | 規範文書自体に欠陥がある場合（本書が追加、FNC-201）                                                                                                           |

## 要件一覧

evaluator の仕事は、所見を起点に読んで当否を判定し、評価を返すことである。入力の得方と評価の渡し方は共通契約が定めるため、本書は**何を手がかりに判定し、何を述べるか**を定める。

### 0. evaluator の定義が持つもの

#### FNC-208: evaluator の定義が持つ中身

実行主体の定義が何を持つかという形は共通契約が定める（[REQ-028](REQ-028_review_exchange.md) FNC-314）。本節は、そのうち evaluator に固有の中身を定める。

| 持つもの               | 中身                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| script の呼び方        | 入力のパスを得る script・評価を渡す script を、どう呼ぶか          |
| 入力の各項目の扱い     | 依頼の項目が何であり、どう扱うか。**所見をどう読むか**             |
| 対象の読み方           | **所見を起点に読む**。所見が指す箇所と、判断に要るだけの周辺を読む |
| メタ観点               | FNC-201 の 5 つ                                                    |
| 評価として何を述べるか | `disposition` をどう判定するか、`reason` に何を書くか              |

**対象の読み方が reviewer と異なる。** reviewer は対象を網羅して読み所見を作るが、evaluator は所見を読んでから、それが指す箇所へ入る。対象の全文読破は課さない——判定に要る範囲を所見ごとに evaluator が決める。ただし FNC-206 の新規指摘は所見が指していない箇所からも生じるため、対象を自ら見に行くことを禁じない。

**target 種別の判定と、種別ごとに読む文書は reviewer と同じものを用いる。** evaluator は所見が指す箇所の種別を判定し、その種別に対応する観点文書を読む。判定の基準と文書の対応は reviewer の要件定義書が定める。

### 1. 作業

#### FNC-201: evaluator は指摘の奥にある本質・対象情報を疑う

evaluator は `disposition` を判定する際、次の 5 つを**メタ観点**として考える。網羅を課すものではなく、態度として持つ。

- 指摘された問題は本当にそれが原因か。個々の指摘の奥に、もっと本質的な原因は無いか。複数の指摘が実は 1 つの原因から出ていないか
- 修正の元になった開発文書・ソースコードの情報自体が誤っていないか
- 既存の決定（ADR 等）は、外から正しい・間違っていると判定しない。判定できるのは形式・論理的整合性・書き換え禁止のような手続きの違反までである
- 所見や規範文書は、まず最も合理的な読み方（目的に照らした読み方）を試し、それでも成立しないときだけ欠陥を疑う
- この所見・この判定が間違っているとしたら、どこがどう間違っているか

**本質・原因が無いこともある。作り出さないこと**——成立しない共通原因を書いてはならない。無いと判断したなら、その判断と根拠を `reason` に述べる。強制的に「無いことを明示する 1 項目」を作る必要はない——書きたいことがあれば書き、無ければ書かない。

規範文書自体の欠陥（`flawed_premise`）は、上記を尽くしてもなお成立しないときの結果であり、独立して優先的に探すものではない。

evaluator は自身の判断を見た目だけ整えるために、成立しないと分かっている根拠を作り出してはならない。

#### FNC-206: evaluator は reviewer の見落としを新規に指摘できる

evaluator は、reviewer が返した finding のどれとも対応しない問題を発見した場合、その問題に finding_id を採番して、それを参照する evaluation として新規に指摘してよい。

- **採番は script が行う**（[REQ-028](REQ-028_review_exchange.md) FNC-313）。reviewer と evaluator は 1 つのレビューに 1 本の連番を分け合う。evaluator の新規指摘は、**そのラウンドで reviewer が採番した最大の finding_id の次**から始まる
- したがって **そのラウンドの `review_result.json` に現れる最大の finding_id を超える値は、evaluator が新規に指摘したものである**——出自を示す別の印は持たない
- **出自を件数で判定しない。** ラウンドが進むと finding_id は 1 から始まらないため、所見の件数と finding_id の値は一致しない。判定の境界は常に、そのラウンドで reviewer が採番した最大の finding_id である
- そのラウンドで reviewer が 1 件も返さなかった場合、境界はそのラウンドの採番基点の 1 つ手前となり、evaluator の新規指摘は基点から始まる
- この場合、参照先の finding が存在しないため `location`（DM-201）を自ら明示する

### 2. 出力

#### FNC-209: evaluator が評価として返すもの

evaluator は判定した評価を渡す。渡し方・書き出す時機・終了の値は共通契約が定める（[REQ-028](REQ-028_review_exchange.md) FNC-302・FNC-310・FNC-311）。本節は evaluator が何を返すかを定める。

**確定後に書き出す規則は evaluator でとくに重要である。** 複数の所見を 1 件の評価で束ねる（FNC-201）には全所見を見てから評価を確定する必要があり、判断しながら逐次書き出すと束ねる評価が書けない。

- 所見が 0 件なら評価も 0 件とする。評価すべき対象が無い。この場合も終了の値を渡す
- 評価が 0 件で終了の値が `"0"` であることが「評価すべき対象が無かった」を表す

### データモデル

#### DM-202: evaluator の入力

evaluator は依頼と、reviewer が返した所見を読む。専用の入力ファイルを持たない。

| 読むもの | 構成                                                             |
| -------- | ---------------------------------------------------------------- |
| 依頼     | 共通契約が定める（[REQ-028](REQ-028_review_exchange.md) DM-301） |
| 所見     | 同 DM-302。0 件のこともある                                      |

**2 つを 1 つに束ねた入力ファイルを作らない。** 写しを作れば、原本と同じ内容が 2 箇所に置かれる。依頼は公開後に書き換えられず、結果は上書きされないため、別々に読んでも組がずれない。

**レビューが正常に終わっていなければ、所見へ到達できない。** そこで止まり、評価に入れない（同 FNC-311）。

#### DM-201 の補足: 新規指摘が持つ位置

evaluation の構成は共通契約が定める（[REQ-028](REQ-028_review_exchange.md) DM-201）。本書が補うのは、**`location` を自ら持つのはどんなときか**である。

そのラウンドで reviewer が採番した最大の finding_id を超える値を引く評価は、参照先の所見が存在しないため位置を自ら示す（FNC-206）。reviewer 由来の finding_id だけを引く評価は、位置を参照先の所見が持つため持たない。
