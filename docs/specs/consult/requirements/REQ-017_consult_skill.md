# REQ-017 consult 対話進行スキル要件定義書

## 1. 概要

consult は、利用者との議論・相談・調査結果の検討を**進行する**スキルである。論点を立て、背景と本質を
述べ、質疑を経て、決着した内容を記録する。

対象は「人間の理解と判断を要する対話」全般であり、設計方針の相談、調査結果の報告と合意形成、
たたき台のレビュー、口頭のディスカッションを含む。**利用者が起動する**。

レビュー所見の評価・修正・完了判定は本スキルの対象ではなく、`/forge:review` が自ら行う（REQ-013）。
ただし、所見を 1 件ずつ提示して採否を得る**対話進行**は、`/forge:review` から本スキルへ**委譲**する。
review と consult は対等なサブシステムだが、実行時には review が consult を呼び出す
一方向の依存を持つ。両者は提示の規範
[consult_principles_spec.md](../../../../plugins/forge/docs/consult_principles_spec.md) を共有し、
対話進行の実装も本スキルへ一本化する（同じロジックを review 側に複製しない）。

本スキルが担うのは**提示・質疑・記録**までである。判断に基づく実行（修正・起票・commit 等）は
行わない。

### 1.1 対象システムの性質

本スキルは開発者が自分の端末で使う対話ツールであり、外部公開・本番運用・個人情報の保持を伴わない
（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の
「上記いずれにも該当しない」に該当する）。ただし提示対象に機密情報が含まれうるため、その扱いは
NFR-004 で定める。

### 1.2 3層構造と本スキルの位置づけ

複数の議題（論点・レビュー所見等）を扱う対話システムは、性質の異なる 3 つの責務に分かれる。

| 層           | 責務                                                           | 担当                                   |
| ------------ | -------------------------------------------------------------- | -------------------------------------- |
| 対話層       | 1 項目についての背景・本質・推奨のやり取り                     | 本スキル（consult）                    |
| データ保存層 | 複数項目の状態保持、次に扱うべき項目の算出、状態遷移の可否判定 | 記録・表示機構（agenda）               |
| 表示層       | 記録の内容を人間が読める形へ変換する                           | 記録・表示機構（agenda）が生成する提示 |

**対話は 1 項目に閉じる**。背景・本質・推奨を述べ、質疑に応じるやり取りは、常に 1 つの論点についてのものである。一方、**複数項目がある場合の管理**（全体の把握、次に何を扱うべきかの判断材料、状態の保持）は対話そのものとは別の関心事であり、本スキルは持たない。これは記録・表示機構（agenda。データ保存層）の責務である。

**表示層が独立して必要な理由は 3 つある**。

1. **大量の情報の整理**: 項目数が増えると、整理されずに並べただけでは理解できない
2. **番号指定でのジャンプの困難**: コンソールでは「項目08を見て」と言われても、遡ってスクロール・検索する必要があり実用的でない。生成される提示（HTML等）ならアンカーリンクで直接到達できる
3. **コンソールの作業ノイズからの分離**: コンソールにはツール呼び出し・中間の思考過程が混在し、どこが読むべき提示でどこが作業ログか区別しづらい。生成される提示はこのノイズから独立している

生成される提示（表示層）が完全な情報を持つなら、コンソールに同じ詳細を重ねて書く必要は無い。ただし**会話（決着に向けたやり取り自体）は表示層の生成とは別に必要**である。

## 2. スコープ

### 2.1 対象

- 議論対象の把握と論点の抽出
- 記録・表示機構（agenda。[agenda:REQ-019](../agenda/requirements/REQ-019_agenda_record.md)）への記録の受け渡しと、判断内容の入力
- 複数論点の進行管理と、進捗・結果の把握
- 項目ごとの提示（背景と本質・推奨・確信度）
- 理解のための質疑応答
- 判断の取得
- 判断を求めない議論（ディスカッション）の進行
- 中断・保留・対象外の扱い

### 2.2 対象外

- 議論対象そのものの生成（レビューの実行、設計案の立案）。ただし論点の確信度を上げるための検証は行う
- 判断に基づく実行（ファイル修正、Issue 起票、commit、外部送信）
- レビュー所見の仕分け（`/forge:review` の責務）
- 提示対象の正しさの保証（誤りの指摘は利用者の応答として扱い、本スキルは判定しない）
- **記録の保存・状態管理（形式・置き場・個数・寿命・状態遷移の可否判定・提示の生成）**。これらは記録・表示機構（agenda。[agenda:REQ-019](../agenda/requirements/REQ-019_agenda_record.md)）の責務であり、本スキルは記録の内容（論点・判断）を渡すだけで、保存の実装を持たない

## 3. 機能要件

### FNC-001: 論点の抽出と検証 [MANDATORY]

議論の対象から論点を立て、**提示する前に確信度を上げること**。

- 各論点は「識別子」「見出し」「本文」を持つこと
- **識別子は議論の途中で変えないこと**。利用者が論点を指し示す手段になるため、番号の振り直しをしない
- 確信度が低く検証が可能な論点は、提示する前に検証すること（実物を読む・実行する・調べる）。
  検証せずに推測のまま提示し、利用者に検証を促されることがないようにする
- 論点が 0 件の場合、提示を行わずその旨を述べて終えること（空の対話を開始しない）

### FNC-002: 複数論点の進行管理 [MANDATORY]

論点が複数ある場合、記録・表示機構（agenda）を通じて全体像と各論点の状態を把握できること。

- **重要度はレビュー所見と同じ語彙**を用いること。用途ごとに別の重要度体系を作らないこと
- 状態は少なくとも「未着手（背景・本質とも未記入）」「進行中（背景・本質は記入済みだが結論は未記入）」
  「決着」「棄却」を区別できること。「棄却」は、対象外（最初から範囲外と決めた）・取り下げ（論点として
  誤りだったため取り消した）等、採用しない理由を問わず、これ以上扱わない論点を指す（理由は決着内容の
  自由記述で示す）。「保留」（今回は扱わないが再度扱う可能性がある論点）は、記録の生存期間内では
  「未着手」または「進行中」と同じ扱いとする——生存期間を超えて保留状態だけを個別に保持する仕組みは
  持たない（agenda:REQ-019 NFR-003 の記録寿命導出と整合）
- **進行の主導権を本スキルが持つこと [MANDATORY]**。「次はどれを見ますか」と利用者に選ばせない。
  重要度の高い順に自ら進め、利用者がすることは止める・飛ばす・順序を変えることだけでよい状態を保つ
- 同種の判断が繰り返される項目は、一括の判定表で提示してよいこと。往復が判断の質を上げない場面では
  往復を増やすことのほうが害になる。ただし一括へ切り替える件数の閾値を AI が独自に定めないこと
  （TBD-003）

### FNC-003: 項目の提示 [MANDATORY]

各項目は、**利用者が原文に戻らずに判断できる**形で提示すること。提示は次の順序に従うこと。

1. **背景と本質** — 何が問題で、なぜ今それが論点になったのか。判断を左右しているのはどこか
2. **推奨と理由** — すでに判断がついているなら伏せずに述べる。推奨は 1 つだけとすること
3. **選択肢** — 上記を満たしてなお選択が必要な場合に限り提示すること

- 背景を述べずに選択肢から始めないこと
- 提示は要約であってよいが、**原文への到達手段（位置・出典）を必ず併記すること**
- 選択肢を出す場合、各選択肢が何であるかと、選ぶと何が変わるかを示すこと。数を絞ること

提示の具体的な作法は
[consult_principles_spec.md](../../../../plugins/forge/docs/consult_principles_spec.md) を規範とし、
本スキルはこれに従うこと。同文書と矛盾する提示構造を独自に定義しないこと。

### FNC-004: 確信度の明示 [MANDATORY]

判断を左右する主張には、確認済みか推論か未検証かを区別できる形で確信度を示すこと。

- 確認済み・推論・未検証の 3 段階を区別できること
- **未検証を既定（無印）とすること**。表示を欠いたときに確信度が高く見えない向きにすること
- 確信度が低く検証できる場合、検証してから提示すること（FNC-001）
- 確信度の表示を全ての記述に付けないこと（分量を損なうため。FNC-006）

### FNC-005: 文脈の再掲 [MANDATORY]

過去のやり取りを参照するとき、参照で済ませず要点を再掲すること。

- 「前述の通り」「先ほどの案」といった参照だけで済ませないこと
- 自ら付与した識別子（項目番号・案の名前・ID）を再び用いるとき、それが何を指すかを併記すること
- 参照リンクや位置の明示を、再掲の代替としないこと

理由: 流れたやり取りから該当箇所を探し出すには労力がかかりすぎる。探して読み直せることを前提にした
提示は、その場で完結しない。

### FNC-006: 媒体ごとの分量 [MANDATORY]

**コンソールに置く分量に上限を設け、記録・表示機構が生成する提示には上限を設けないこと。**

- コンソールは読み返しに向かないため、置く量を絞ること。上限値は AI が独自に定めないこと（TBD-006）
- 記録・表示機構が生成する提示は、**理解に必要な内容を削らないこと**
- **同じ内容を両方へ重ねて書かないこと**。書く場所を 1 つに決める
- ただしコンソールには、**その項目単体で判断できるだけの要点を必ず書くこと**。生成される提示の存在を
  理由に要点を省かないこと（FNC-011）
- 並列する項目は表にまとめ、散文で列挙しないこと
- 詳細は求められてから提示すること。先回りして網羅しないこと

### FNC-007: 質疑応答 [MANDATORY]

利用者が判断ではなく**理解**を求めた場合、判断を促さずに応答すること。

- 掘り下げの要求（「詳しく」「なぜそうなるのか」「他の選択肢は」）に対し、判断を求める問いを
  返さないこと
- 質疑の往復回数に上限を設けないこと
- 質疑の結果として提示内容の誤りが判明した場合、当該項目を決着として記録し「棄却」扱いにできること
  （決着内容に「取り下げ」等、誤りだった旨を記す）。ただし**取り下げた事実・理由・誰の指摘によるものか
  （利用者の指摘か AI の自己訂正か）を記録すること**。記録せずに項目を消すことを禁じる
- 取り下げの判断が分かれる場合（誤りとまでは言えない場合）は決着させず「未着手」または「進行中」の
  まま残し、利用者の指示を待つこと。**判断が付かないことを取り下げの理由にしないこと**

### FNC-008: 判断の取得 [MANDATORY]

各項目について利用者が下した判断を、記録・表示機構（agenda）へ入力すること。

- 判断は少なくとも「採用する」「採用しない」「保留する」を区別できること
- 「採用しない」「保留する」には理由を伴わせること。理由の入力を省略しないこと
- 利用者が明示的に判断を下していない項目を、既定値で埋めないこと（未判断は未判断として残すこと）
- **AI が判断した項目は、その旨を判別できる形で入力すること**。人間の判断と混在させないこと

### FNC-009: 中断・保留・対象外 [MANDATORY]

対話は利用者の都合で任意の時点で終えられること。扱わないと決めた項目も見える形で残すこと。

- 「残りは全部あとで」「ここで終える」に対応し、その時点までの判断を確定して記録すること
- 中断した場合、**何件が未判断のまま残ったか**を明示すること。未判断を「対応不要」へ畳み込まないこと
- **今回扱わないと決めた項目を、アジェンダからも記録からも削除しないこと**。決着として記録し
  「棄却」扱いにし（決着内容に「対象外」等、なぜ扱わないかを記す）、利用者が確認できる状態にすること
- 中断後の再開は記録・表示機構（agenda）を通じて行えること（NFR-001）

### FNC-010: ディスカッションモード [MANDATORY]

提示意図が「判断を得ること」ではなく「議論すること」である場合、判断を求める問いを発しないこと。

- たたき台の提示・論点の列挙までを行い、そこで止まること
- 列挙した論点を順に問い詰める形へ移行しないこと
- 議論を決定フローへ変換するのは利用者の明示指示があった場合に限ること
- **禁じるのは選択肢の提示に限らないこと**。「どれから見ますか」「これで進めてよいですか」も
  判断の投げ返しであり、同じく発しないこと

### FNC-011: 記録との連携 [MANDATORY]

論点と決着を、記録・表示機構（agenda）へ渡し、記録として保持させること。

- 記録の保存形式・置き場・個数・寿命・状態遷移の可否判定は記録・表示機構の責務であり、本スキルは持たないこと
- **1 件決着するごとに記録・表示機構へ入力すること**。まとめて後から渡さないこと
- 取り下げた論点も、削除せず決着（「棄却」扱い。決着内容に「取り下げ」等を記す）として記録・表示機構へ渡すこと（FNC-009）
- 各項目に**議論の途中で変わらない識別子**を与えること（FNC-001）。識別子は記録・表示機構が保持する項目のキーになる

> 永続的な記録を要する内容は ADR 等へ組み直す必要がある。

### BL-001: 実行を行わない [MANDATORY]

本スキルは、取得した判断に基づく実行を行わないこと。

- ファイルの修正、Issue の起票、commit、外部への送信を行わないこと
- 実行を担う別スキル・別 Agent を起動しないこと
- 判断を記録するところまでを終端とすること

理由: 提示と実行を同一スキルが担うと、議論の途中で実行が始まり、利用者が決めていない変更が
成果物へ入る。記録・表示機構への記録は本スキルの成果物であり、この禁止の対象外である。

### BL-002: 提示の忠実性 [MANDATORY]

提示にあたり、対象の意味を変えないこと。

- 要約によって判断の分岐点を落とさないこと
- 複数の項目を統合して提示する場合、統合したことと統合の理由を示すこと。統合によって個別項目が
  利用者から見えなくなる状態にしないこと
- 提示対象に含まれていない評価・推測を、対象の記述であるかのように混ぜないこと

## 4. 非機能要件

### NFR-001: 状態は記録・表示機構に一元化する [MANDATORY]

本スキルは討議の状態を自ら保持せず、記録・表示機構（agenda）に一元化すること。

- 本スキル固有の状態ファイル・作業ディレクトリ・DB を持たないこと
- 中断した対話の再開を、記録・表示機構が保持する記録を通じて行うこと
- 提示は記録・表示機構が記録から生成すること

理由: 状態の置き場が複数あると、どれが正かが失われる。記録の実体を 1 つに集約することで、
記録と提示の食い違いを構造的に防ぐ。

### NFR-002: 用途非依存 [MANDATORY]

本スキルは特定の用途に固有の語彙・体系を、提示構造に持ち込まないこと。

- レビュー固有の概念（往復ラウンド・承認判定）を必須要素にしないこと
- 用途ごとの差異は、利用者が述べる議論の目的で吸収すること
- 用途が増えるたびに本スキルの構造を拡張しないこと

> 重要度の語彙をレビューと共有すること（FNC-002）は本要件に反しない。同じ概念に別の語彙を作らない
> ための共有であり、レビュー固有の体系を持ち込むことではない。

### NFR-004: 機密情報の非提示 [MANDATORY]

提示対象に機密情報が含まれる場合、その値そのものを提示にも記録にも含めないこと。

- 提示するのは「どこに」「どの種類の」機密が含まれるかまでとすること
- 利用者が値の表示を求めた場合も、本スキルは表示せず、利用者自身が原本を確認する経路を示すこと

### NFR-005: 失敗の可視性

論点の把握に失敗した場合（対象が不明・議論の目的が不明）、既定値で補って対話を開始しないこと。
何が不足しているかを利用者へ述べて終えること。
