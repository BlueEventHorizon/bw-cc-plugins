## 1. 概要

consult は、AI がすでに保持している内容を**人間が判断・議論できる形へ整えて提示し、質疑応答を経て、
確定した判断を呼び出し元へ返す**スキルである。

対象は「複数の項目について人間の判断を仰ぐ」場面すべてであり、レビュー所見の仕分けはその適用先の
一つに過ぎない。設計方針の相談、調査結果の報告と合意形成、口頭でのディスカッションも同じ対話層で
扱う。呼び出し元スキルからも、利用者の直接起動からも使える。

本スキルが担うのは**提示・質疑・判断の取得**までである。判断に基づく実行（修正・起票・commit 等）は
呼び出し元の責務であり、本スキルは行わない。

### 1.1 対象システムの性質

本スキルは開発者が自分の端末で使う対話ツールであり、外部公開・本番運用・個人情報の保持を伴わない
（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の
「上記いずれにも該当しない」に該当する）。ただし提示対象に機密情報が含まれうるため、その扱いは
NFR-004 で定める。

## 2. スコープ

### 2.1 対象

- 提示対象（項目群と提示意図）の受理
- アジェンダ表による進行と、進捗・結果の再掲
- 項目ごとの提示（背景と本質・推奨・確信度）
- 理解のための質疑応答
- 判断の取得・記録と、呼び出し元への返却
- 判断を求めない議論（ディスカッション）の進行
- 中断・保留・対象外の扱い

### 2.2 対象外

- 提示対象そのものの生成（レビューの実行、調査、設計案の立案）
- 判断に基づく実行（ファイル修正、Issue 起票、commit、外部送信）
- 判断結果のファイルへの永続化
- 提示対象を得るための外部システムとの往復
- 提示対象の正しさの検証（誤りの指摘は利用者の応答として扱い、本スキルは判定しない）

## 3. 機能要件

### FNC-001: 提示対象の受理 [MANDATORY]

呼び出し元または利用者から、**項目群**と**提示意図**を受け取ること。

- 項目は「識別子」「見出し」「本文」を必須とし、それ以外の属性（重要度・位置・分類・推奨対応など）は
  **任意**として扱うこと
- 特定の用途に固有の属性を必須にしないこと。レビュー所見の重大度体系を前提とした受理契約に
  してはならない
- 提示意図は「利用者に何を決めてほしいのか」または「何を理解してほしいのか」を含むこと
- 項目が 0 件の場合、提示を行わずその旨を返すこと（空の対話を開始しない）

### FNC-002: アジェンダ表による進行 [MANDATORY]

項目が複数ある場合、個別の提示に入る前にアジェンダを**表**で示し、進行に応じて更新・再掲すること。

- 表は「項目 / 重要度 / 状態 / 結果・結論」を持つこと
- **重要度はレビュー所見と同じ語彙**（critical / major / minor）を用いること。用途ごとに別の
  重要度体系を作らないこと
- 状態は少なくとも「未着手 / 進行中 / 決着 / 保留 / 対象外」を区別できること
- **背景・本質を表に入れないこと**。詳細は各項目に入ってから述べる（FNC-003）
- **1 件決着するごとに表を再掲すること**。利用者が会話を遡らずに現在地・残件・決定済み内容を
  確認できる状態を保つこと
- 項目は 1 件ずつ進めることを既定とし、同種の判断が繰り返される項目に限りまとめて扱えること
- 一括提示へ切り替える件数の閾値を、AI が独自に定めないこと（TBD-003）

### FNC-003: 項目の提示 [MANDATORY]

各項目は、**利用者が原文に戻らずに判断できる**形で提示すること。提示は次の順序に従うこと。

1. **背景と本質** — 何が問題で、なぜ今それが論点になったのか。判断を左右しているのはどこか
2. **推奨と理由** — すでに判断がついているなら伏せずに述べる。推奨は 1 つだけとすること
3. **選択肢** — 上記を満たしてなお選択が必要な場合に限り提示すること

- 背景を述べずに選択肢から始めないこと
- 提示は要約であってよいが、**原文への到達手段（位置・出典）を必ず併記すること**
- 選択肢を出す場合、各選択肢が何であるかと、選ぶと何が変わるかを示すこと。数を絞ること

提示の具体的な作法は forge 内蔵の
[consult_principles_spec.md](../../../../plugins/forge/docs/consult_principles_spec.md) を規範とし、
本スキルはこれに従うこと。同文書と矛盾する提示構造を独自に定義しないこと。

### FNC-004: 確信度の明示 [MANDATORY]

判断を左右する主張には、確認済みか推論か未検証かを区別できる形で確信度を示すこと。

- 確認済み・推論・未検証の 3 段階を区別できること
- **未検証を既定（無印）とすること**。表示を欠いたときに確信度が高く見えない向きにすること
- 確信度が低く検証が可能な場合、検証してから提示することを優先すること
- 確信度の表示を全ての記述に付けないこと（分量を損なうため。FNC-006）

### FNC-005: 文脈の再掲 [MANDATORY]

過去のやり取りを参照するとき、参照で済ませず要点を再掲すること。

- 「前述の通り」「先ほどの案」といった参照だけで済ませないこと
- 自ら付与した識別子（項目番号・案の名前・ID）を再び用いるとき、それが何を指すかを併記すること
- 参照リンクや位置の明示を、再掲の代替としないこと

理由: 利用者は会話を遡れない。遡れることを前提にした提示は、その場で完結しない。

### FNC-006: 分量の抑制 [MANDATORY]

1 回の提示の分量に上限を設け、それを超えないこと。

- 背景・本質・推奨を合わせた分量の上限を定めること。具体的な値は AI が独自に定めないこと（TBD-006）
- 並列する項目は表にまとめ、散文で列挙しないこと
- 詳細は求められてから提示すること。先回りして網羅しないこと

### FNC-007: 質疑応答 [MANDATORY]

利用者が判断ではなく**理解**を求めた場合、判断を促さずに応答すること。

- 掘り下げの要求（「詳しく」「なぜそうなるのか」「他の選択肢は」）に対し、判断を求める問いを
  返さないこと
- 質疑の往復回数に上限を設けないこと
- 質疑の結果として提示内容の誤りが判明した場合、当該項目を「判断保留」として扱い、利用者の指示を
  待つこと（AI が独断で項目を取り下げないこと）

### FNC-008: 判断の取得と返却 [MANDATORY]

各項目について利用者が下した判断を記録し、呼び出し元へ返すこと。

- 判断は少なくとも「採用する」「採用しない」「保留する」を区別できること
- 「採用しない」「保留する」には理由を伴わせること。理由の記録を省略しないこと
- 利用者が明示的に判断を下していない項目を、既定値で埋めないこと（未判断は未判断として返すこと）
- **AI が判断した項目は、その旨を判別できる形で記録すること**。人間の判断と混在させないこと
- 返却内容は呼び出し元が実行に使える形とすること。呼び出し元が本スキルの内部表現を解釈し直す
  必要がない形であること

### FNC-009: 中断・保留・対象外 [MANDATORY]

対話は利用者の都合で任意の時点で終えられること。扱わないと決めた項目も見える形で残すこと。

- 「残りは全部あとで」「ここで終える」に対応し、その時点までの判断を確定して返すこと
- 中断した場合、**何件が未判断のまま残ったか**を明示して返すこと。未判断を「対応不要」へ
  畳み込まないこと
- **今回扱わないと決めた項目をアジェンダから削除しないこと**。「対象外」として残し、なぜ扱わないかを
  利用者が確認できる状態にすること
- 中断後の再開を本スキルが自前で担保しないこと（NFR-001 参照）。再開が必要な場合は、呼び出し元が
  未判断の項目を再度渡すこと

### FNC-010: ディスカッションモード

提示意図が「判断を得ること」ではなく「議論すること」である場合、判断を求める問いを発しないこと。

- たたき台の提示・論点の列挙までを行い、そこで止まること
- 列挙した論点を順に問い詰める形へ移行しないこと
- 議論を決定フローへ変換するのは利用者の明示指示があった場合に限ること

### BL-001: 実行を行わない [MANDATORY]

本スキルは、取得した判断に基づく実行を行わないこと。

- ファイルの修正、Issue の起票、commit、外部への送信を行わないこと
- 実行を担う別スキル・別 Agent を起動しないこと
- 判断結果を呼び出し元へ返すところまでを終端とすること

理由: 提示と実行を同一スキルが担うと、実行側の前提（状態ファイル・専用 Agent・セッション基盤）が
提示側の起動条件になり、提示だけを使いたい呼び出し元から利用できなくなる。

### BL-002: 提示の忠実性 [MANDATORY]

提示にあたり、対象の意味を変えないこと。

- 要約によって判断の分岐点を落とさないこと
- 複数の項目を統合して提示する場合、統合したことと統合の理由を示すこと。統合によって個別項目が
  利用者から見えなくなる状態にしないこと
- 提示対象に含まれていない評価・推測を、対象の記述であるかのように混ぜないこと

## 4. 非機能要件

### NFR-001: 状態を永続化しない [MANDATORY]

本スキルは判断状態をファイルに永続化せず、対話の開始から判断の返却までを呼び出しの内側で
完結させること。

- 専用の作業ディレクトリ・状態ファイルを持たないこと
- 中断した対話の再開を、本スキルが保持する状態に依存して行わないこと
- 呼び出し元が状態を持つ場合も、その形式に本スキルが依存しないこと

理由: 状態を持つと、状態を持たない呼び出し元から利用できなくなる。提示層が呼び出し元の実行基盤に
結合することは、本スキルの汎用性を失わせる最大の要因である。

### NFR-002: 呼び出し元非依存 [MANDATORY]

本スキルは特定の用途に固有の語彙・体系を、受理契約にも提示構造にも持ち込まないこと。

- レビュー固有の概念（往復ラウンド・承認判定）を必須要素にしないこと
- 用途ごとの差異は、呼び出し元が渡す提示意図と任意属性で吸収すること
- 用途が増えるたびに本スキルの受理契約を拡張する構造にしないこと

> 重要度の語彙をレビューと共有すること（FNC-002）は本要件に反しない。同じ概念に別の語彙を作らない
> ための共有であり、レビュー固有の体系を持ち込むことではない。

### NFR-003: 実装依存

本スキルに付随するスクリプトは標準ライブラリのみで実装し、単体テストを持つこと。

### NFR-004: 機密情報の非提示 [MANDATORY]

提示対象に機密情報が含まれる場合、その値そのものを提示に含めないこと。

- 提示するのは「どこに」「どの種類の」機密が含まれるかまでとすること
- 利用者が値の表示を求めた場合も、本スキルは表示せず、利用者自身が原本を確認する経路を示すこと

### NFR-005: 失敗の可視性

提示対象の受理に失敗した場合（必須要素の欠落・意図の不明）、既定値で補って対話を開始しないこと。
何が不足しているかを呼び出し元または利用者へ返して終えること。
