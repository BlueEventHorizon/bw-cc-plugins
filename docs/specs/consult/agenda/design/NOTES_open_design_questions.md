## `verification.referenced` の形式検証（TASK-006 実装レビューで発見）

**要件側の制約**（変更しない。agenda:REQ-019 FNC-011 `[MANDATORY]`）:

- 機構が課すのは記録の存在と、**位置情報を伴う形式**までである（「欄を埋めることを学習し、内容が検証由来かどうかは誰も検査しないまま通過する」失敗パターンを防ぐため）
- 許容する形式は2種類: 「ファイル:行」と「コマンドと出力」

**現状**: `agenda_schema.py` の `required_fields_for()` は `verification.referenced` を非空文字列チェックのみで検証しており、位置情報を伴わない一般論・所感でも通過する。FNC-011が防ごうとする失敗パターンを素通りさせている。

**設計で決定する内容**:

- 「位置情報を伴う形式」をどう機械的に判定するか（`ファイル:行`は`:数字`等の正規表現で判定可能だが、`コマンドと出力`は自然文であり同じ正規表現に合致しない。厳密な形式チェックは後者を誤って拒否するリスクがある）
- 判定をagenda機構内で行うか、呼び出し側（consult）が渡す時点で保証するかの責務分岐
- 正式な設計書（DES-075）を改訂する際に、この内容を読んで§5.1・§4へ反映すること
