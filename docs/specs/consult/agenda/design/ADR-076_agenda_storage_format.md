# ADR-076 agenda 機構の保存形式

## 1. コンテキスト

agenda:REQ-019 NFR-001 は、記録の保存形式が「値の境界を形式自身が持つこと」を要求する。候補は標準ライブラリのみで扱える形式に限られる（[implementation_guidelines.md](../../../../../docs/rules/implementation_guidelines.md)：Python スクリプトは標準ライブラリのみ使用し、例外として PyYAML のみ許容——ただし個別の利用承認が要る）。

Issue #21 本文は「YAML は条件からの導出であって前提ではない。必要条件を満たす形式のうち、本プロジェクトが許容する外部依存は PyYAML だけである」と述べており、YAML 採用を選択肢として残していた。一方、[NOTES_open_design_questions.md](NOTES_open_design_questions.md)（要件定義から設計へ引き継いだ論点メモ）は「PyYAML は不採用（プロジェクト方針として承認が出ていないため）」「JSON を軸に検討する」と記している。

## 2. 決定

保存形式に **JSON**（標準ライブラリ `json` のみ）を採用する。PyYAML は使用しない。

理由:

1. **agenda.json は人間が直接編集する対象ではない**。agenda:REQ-021 FNC-004 は「AI が人間向けの提示物を読む必要がない」ことを要求しており、対称的に記録側も人間が直接読み書きする運用を想定していない（表示は `agenda_render.py` が別途生成する）。YAML の強み（人間可読性・手編集のしやすさ）が活きる場面が無い
2. **今回の要件が解決したい破損（半角パイプ混入・太字による読み戻し切り落とし）は、境界を実装が発明したことに起因する**（NFR-001 の理由節）。JSON 標準ライブラリの `json.dump`/`json.load` は文字列の境界・エスケープを構文自身が保証し、この種の破損が構造的に起きない
3. **PyYAML を要る理由が「人間可読性」以外に無い**。保存専用データにその価値が乗らない以上、外部依存を増やす理由が無い
4. **TOML（`tomllib`）は書き込みができず**、記録の更新用途に使えない（[NOTES_open_design_questions.md](NOTES_open_design_questions.md) で確認済み）

## 3. 検討した代替案

| 案                                                      | 却下理由                                                                                                         |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| YAML（PyYAML 使用）                                     | 人間可読性は agenda.json の用途（AI 専用の中間データ、表示は別生成）で価値を持たない。外部依存を増やす理由が無い |
| TOML（`tomllib`）                                       | 標準ライブラリだが読み取り専用。記録の更新（`agenda_store.py update`）が要件（FNC-005）であり使えない            |
| 独自テキスト形式（旧 discussion_file_template.md 方式） | まさに本 ADR が解決しようとしている問題（自作パーサ・値の境界の発明）そのものであり、NFR-001 が明示的に禁じる    |

**この判断が依拠する前提**: agenda.json が人間の直接編集対象にならないこと。将来、記録を人間が手編集する運用が要件として追加された場合、この前提が崩れ本決定を再検討する必要がある。

## 4. 影響

**得るもの**: `json.dump`/`json.load` による構文レベルの境界保証（NFR-001 を満たす）。追加の外部依存が発生しない（PyYAML の個別承認手続きが不要になる）。

**失うもの**: `agenda.json` の人間可読性。YAML と比べ、緊急時に人間が直接ファイルを開いて内容を確認・修正する場面での可読性は劣る（ただし §2 のとおり、この運用は前提として想定していない）。

**新たに生じる制約**: 表示層（agenda:REQ-021）が別途 HTML 等の人間向け提示を生成する構成が前提になる。`agenda.json` 単体を人間への提示物として直接使う設計は採れない（[DES-075](DES-075_agenda_mechanism_design.md) §8 の表示層設計はこの制約の上に成り立つ）。
