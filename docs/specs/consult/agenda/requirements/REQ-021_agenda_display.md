# REQ-021 agenda 表示層 要件定義書

## 1. 概要

agenda 機構（データ保存層、[agenda:REQ-019](REQ-019_agenda_record.md)）が保持する記録から、人間が読める提示を生成する表示層を定める。

保存とレンダリングは責務が異なる。保存（記録の永続化・状態遷移の可否判定）と表示（記録の内容を人間可読な形式へ変換すること）を1つの成果物に兼ねさせると、値の境界を実装が発明することになり、保存する内容が人間の文章である以上、必ず衝突する（agenda:REQ-019 NFR-001）。この誤りを再発させないため、表示層を独立した要件として分離する。

### 1.1 対象システムの性質

本機構は開発者が自分の端末で使う作業記録であり、外部公開・本番運用・個人情報の保持を伴わない（[spec_priorities_spec.md](../../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

### 1.2 用語

本文書で使う語（議題項目・アジェンダ・記録・提示・呼び出し側）は [agenda:REQ-019](REQ-019_agenda_record.md) §2 の定義に従う。本文書で新たに追加する語は無い。

## 2. スコープ

### 2.1 対象

- 記録（[agenda:REQ-019](REQ-019_agenda_record.md)）から生成される、人間向けの提示
- 扱っている議題項目の全体・各項目の状態・残件の俯瞰
- 直前の更新で変わった箇所の可視化
- 提示の内容と記録の内容が食い違わないこと

### 2.2 対象外

- **記録の保存・状態管理**（形式・置き場・個数・寿命・状態遷移の可否判定）。これらは記録・表示機構のうちデータ保存層（[agenda:REQ-019](REQ-019_agenda_record.md)）の責務である
- **いつ提示するか・何を問うか**。提示の契機と問いの立て方は呼び出し側ごとに異なり、各 SKILL が持つ
- **提示の作法**（背景と本質を先に述べる、推奨は 1 つ、確信度を示す等）。[consult_principles_spec.md](../../../../../plugins/forge/docs/consult_principles_spec.md) が定める
- **議題項目の内容の正しさ**。所見が妥当か、論点が的を射ているかは本機構の関心事ではない

## 3. 機能要件

### FNC-001: 俯瞰可能性

扱っている議題項目の全体・各項目の状態・残件が、**1 つのアジェンダで一目で分かること**。

- 項目を数え上げたり、複数の提示を突き合わせたりしなければ全体が分からない形にしないこと
- 扱わないと決めた項目（取り下げ・対象外）も提示から消さないこと。なぜ扱わないかを利用者が確認できる状態を保つこと

### FNC-002: 変更箇所の可視化

**直前の更新で変わった箇所が、提示上で他と区別できること。**

理由: 項目数が増えると、提示を再掲しても「今回何が変わったのか」が読み取れなくなる。利用者に差分を探させないため。

### FNC-003: 提示と記録の一致

提示の内容と記録の内容が食い違わないこと。

- 提示は記録から生成すること
- 同じ内容を、記録と提示のそれぞれに独立して書き込む経路を持たないこと
- AI が提示を直接書く経路を持たないこと

### FNC-004: AI は人間向けの提示物を読まない

AI が状態を知るために、人間向けの提示物を読む必要がないこと。

理由: 提示物は人間が読むために整形されており、そこから状態を読み戻す実装は必ず書式の解釈を伴う。読み戻しの経路を持たないことで、書式と状態の乖離が原理的に生じなくなる。

### FNC-005: 識別子からの直接到達

利用者が項目の識別子（番号）を指定したとき、その項目まで直接到達できること。

理由: コンソールでは識別子を言われても、遡ってスクロール・検索する必要があり実用的でない。項目数が増えるほど、この負担は大きくなる。

## 4. 非機能要件

### NFR-001: 提示は生成物であると読み取れる

生成物であることが、提示自体から読み取れること。

提示を記録から生成することは FNC-003 が定める。本節が課すのは、読み手が「これは生成されたものである」と判別できることだけである。
