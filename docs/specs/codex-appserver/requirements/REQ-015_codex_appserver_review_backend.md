## 1. 背景

### 1.1 現状の問題

forge:ADR-060 / REQ-013 FNC-1318 がレビュー実行主体を `--backend` で交換可能にしたが、現時点で存在するバックエンドは msg-review のみである。msg-review は「人間が常駐させた Codex TUI セッション・Stop フックによる pull 型の新着検知・相手のターンを起こす起床手段」という前提の上に成り立つ。

この前提を満たせないプロジェクトでは、実行主体だけでなく**レビューフロー全体**が使えない。とくに起床手段は端末多重化ツール（cmux）に依存しており、これを使わない環境では往復が沈黙したまま停止する（msg-review:DES-045 に、約 7 時間の待機・往復 2 ラウンド目以降の停止・1 レビューで 4 回の手動起床という実測が記録されている）。

### 1.2 本バックエンドの位置づけ

Codex CLI は app-server サブコマンドを持ち、JSON-RPC でスレッドの開始・再開とターンの実行を制御できる。**バックエンド自身がスレッドを所有する**構成を採れば、相手は人間の TUI ではなくバックエンドが管理するスレッドになる。

この構成では起床という概念が存在しない。ターンを開始するのはバックエンド自身だからである。したがって端末多重化ツール・起動シム・Stop フック・メッセージ DB のいずれも不要になる。

単発起動（`codex exec`）との違いはスレッドを保持することであり、複数ラウンドにわたって文脈が継続する。

## 2. スコープ

### 2.1 対象とする範囲（v1）

- forge:REQ-013 FNC-1318 の入出力契約を満たすレビューバックエンドとして動作すること
- 自前のスレッドを保持し、同一レビュー内の複数ラウンドで文脈を継続すること
- Codex の構造化応答を、全バックエンド共通の所見書式へ変換すること
- 往復の内容を監査可能な形で記録すること
- 前提が成立しない場合に、依頼を送る前に検出して報告すること

### 2.2 v1 で明示的に除外する範囲

- **レビュー依頼の組み立てと所見の処理**: 対象解決・観点の名指し・粒度保存・所見の評価と修正・完了判定は `/forge:review` 本体の責務である（forge:REQ-013 FNC-1318）
- **人間の途中介入と進行の可視化**: レビューの進行を画面で見て途中で介入する用途は本バックエンドでは扱わない。この性質が必要な場合は msg-review バックエンドを選ぶ
- **msg-review / msg-sys への変更**: 本バックエンドは両者の要件・設計・実装のいずれも変更しない。起床・Stop フック・メッセージ DB を使わない
- **Codex 以外のレビュアー**: app-server は Codex 固有のプロトコルである。他のレビュアーを使う場合は別バックエンドとする

### 2.3 v1 の位置づけ（意図的な判断）

v1 は、バックエンド軸に 2 つ目の実装を接続することで **forge:ADR-060 が「1 実装しかない期間は契約が実際に非依存かどうか検証できない」と述べた点を実地に検証する**位置づけを兼ねる。契約に不足が見つかった場合は forge:REQ-013 側の改訂として扱い、本文書で回避策を持たない。

## 3. 機能要件

### FNC-001: バックエンド契約の充足 [MANDATORY]

forge:REQ-013 FNC-1318 が定める入出力契約（forge:ADR-065 による改訂後）を満たすこと。

- 入力として、ラウンド実行（`review_id`、ラウンド番号、依頼本文（テンプレート展開済み））と、終了通知（`review_id`）を受け取ること
- 出力として判定（`approved` / `findings` / `failure`）を返すこと。`findings` は所見配列（重大度・位置・本文）を、`failure` は利用者が読める失敗理由を伴う
- 所見の位置は「ファイルパス + 行番号」または「位置未確定の明示」のどちらかを必ず持つこと
- **バックエンド固有の事情を本体へ漏らさないこと**。app-server の接続方式・スレッド管理・プロトコルの詳細を本体の関心事にしない

かつて本要件の充足を阻んでいた契約の 3 不足（失敗・レビュー終了・位置未確定）は、forge:REQ-013 FNC-1318 の改訂（forge:ADR-065）で解消された（§5 TBD-005〜007）。契約外の暫定挙動は引き続き定めない。

### FNC-002: スレッドの所有と文脈継続 [MANDATORY]

本バックエンドがレビュー用のスレッドを所有し、同一 `review_id` の複数ラウンドで文脈を継続すること。

- 人間が起動した TUI セッションに接続しないこと。相乗りは利用者の起動経路への介入を要するため採らない
- ラウンド間でスレッドを保持し、前ラウンドの指摘と修正の経緯を Codex 側が参照できること
- **保持した資源（app-server プロセス・スレッド・記録）を最終的に必ず解放すること**

解放の契機は、本体が発行する終了通知とすること（forge:REQ-013 FNC-1318。レビューがどの経路で終わる場合も——承認・介入軸による打ち切り・失敗の確定・利用者の中断——本体が通知する義務を負う）。レビューの終了を推測しないこと（`approved` を返したことや時間経過を終了の代替信号にしない）。

時間経過による回収を代替手段としない理由は 2 点ある（棄却の経緯は forge:ADR-065）: 次回の起動が無ければ走査自体が行われず最後のレビューの資源が残り続けること、人間の介入で長時間中断しているレビューを経過時間だけを根拠に破棄しうることである。いずれも「最終的に必ず解放する」を満たさない。

**本要件の適用範囲**: 上記の「必ず解放する」は、終了通知が発行されることを前提とする。本体自身の異常終了により通知が発行されない場合は契約違反の状態であり、本要件が保証する範囲の外にある。この場合バックエンドは残存資源を推測で停止せず、利用者へ可視化して判断を委ねること（設計は DES-064 §3.4）。

### FNC-003: 共通書式への変換 [MANDATORY]

Codex から返る構造化された応答を、全バックエンド共通の所見書式（自由記述 markdown + 重大度マーカー + 所見ごとの位置情報 + 完了宣言行。forge:REQ-013 FNC-1318）へ変換すること。

forge:ADR-060 は書式契約を全バックエンド共通に固定し、**構造化された形式で応答するレビュアーを使う場合の変換はバックエンドの内部責務**と定めている。本バックエンドはこれに該当する。

- 変換の失敗（期待する重大度マーカーや完了宣言行を取り出せない）を、所見なし（`approved`）と誤って扱わないこと
- 依頼テンプレートをバックエンド固有に分岐させないこと

所見の位置は、共通書式から抽出できた場合は「ファイルパス + 行番号」、抽出できなかった場合は「位置未確定の明示」として返すこと（forge:REQ-013 FNC-1318。位置未確定は契約上の正当な表現であり、本体側の扱い——推測補完・黙殺の禁止——も契約が定める）。位置を推測で埋めない（存在しない指摘箇所を本体に信じさせる）・位置の無い所見を破棄しない（指摘そのものを消す）・位置未確定の明示なく位置を欠落させたまま返さない。

なお、レビュアーが `パス:行` を明記した所見でもパーサが位置を抽出できない事例は実測されており（本バックエンドの仕様策定時のレビューで 3 件）、位置未確定の表現はこの実測に基づく要件である。

### FNC-004: 前提条件の事前検査 [MANDATORY]

依頼を送る前に前提を検査し、不成立の場合は依頼を送らず利用者に不足を報告すること。少なくとも以下を検査する。

- Codex CLI が利用可能で、app-server を提供すること
- 本バックエンドが用いるプロトコルのメソッドが、その Codex に存在すること
- app-server を起動または再利用できること

### FNC-005: 失敗の確定と報告 [MANDATORY]

前提検査の通過後に失敗した場合、結果を保留せず、そのラウンドの失敗として確定して本体へ返すこと。

- 応答を得られないまま無期限に待ち続けないこと
- 失敗を所見なし（`approved`）へ畳み込まないこと
- 別バックエンドへ暗黙にフォールバックしないこと（forge:REQ-013 FNC-1318 の fail closed と同旨。利用者が意図しない実行主体でレビューが走ることを避ける）

失敗は契約の `failure`（利用者が読める失敗理由を伴う）として本体へ返すこと（forge:REQ-013 FNC-1318）。`approved`（所見なしとして完了し失敗が消える）・所見 0 件の `findings`（矛盾した状態を本体が正常な判定として扱う）・呼び出しエラー（非ゼロ終了。契約の戻り値に含まれない経路）による代替はいずれも採らない（棄却の経緯は forge:ADR-065）。

### FNC-006: 実行権限の限定 [MANDATORY]

レビューは対象を読んで所見を述べる作業であり、対象の変更を伴わない。本バックエンドが開始するターンには、レビューに必要な範囲を超える権限を与えないこと。

- 具体的な権限設定の値は設計で確定する（§5 TBD-002）

### BL-001: 往復の監査可能性

レビューの往復内容（各ラウンドの依頼本文と応答）を、後から参照できる形で記録すること。

msg-review はこれを msg-sys の履歴に委ねているが（msg-review:REQ-012 BL-001）、本バックエンドはメッセージ DB を使わないため自前で満たす必要がある。

- 記録は `review_id` 単位で辿れること
- 複数のレビューが時間的に離れて行われた場合でも、対象レビューの往復のみを扱い、他のレビューと混同しないこと

## 4. 非機能要件

### NFR-001: 標準ライブラリのみでの実装 [MANDATORY]

Python 実装は標準ライブラリのみを使用し、外部パッケージへの依存を持たない。Bash からの外部コマンド呼び出し（`codex` 等）は許容する。

app-server との通信に WebSocket が必要であるが、これも標準ライブラリの範囲で実装する（同梱の中継サブコマンドはハンドシェイクを代行せず、素の JSON-RPC も受け付けないことを実測で確認済み。msg-review:ADR-061 §1）。

### NFR-002: 外部ツール非依存 [MANDATORY]

エージェント間メッセージング基盤等の外部プラグイン・パッケージを実行時依存として導入しない。端末多重化ツールにも依存しない。

### NFR-003: 位置づけと適用範囲

本バックエンドは本番運用・外部公開を前提としない実験段階の内部ツールである。性能目標値は定めない。恒久化の要否は、バックエンド軸に 2 つ目の実装が接続された状態での運用結果を踏まえて判断する（§2.3）。
