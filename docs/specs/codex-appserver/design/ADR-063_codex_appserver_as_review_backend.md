# ADR-063 Codex app-server を独立したレビューバックエンドとする

## メタデータ

| 項目     | 値                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------- |
| ADR ID   | ADR-063                                                                                        |
| Status   | proposed                                                                                       |
| 決定日   | 2026-08-02                                                                                     |
| 関連設計 | forge:ADR-060（バックエンド軸）、DES-064（本決定の設計）、msg-review:ADR-061（棄却した先行案） |
| 関連要件 | REQ-015（本バックエンドの要件）、forge:REQ-013 FNC-1318（バックエンド軸の入出力契約）          |

> **本文書のスコープ**
>
> - **定めること**: Codex の app-server プロトコルを用いるレビュー実行主体を、どの単位で仕様化し、どこに責務を置くか
> - **定めないこと**: レビュー依頼の組み立て・所見の処理・対象解決・観点の名指し。これらは forge:REQ-013 FNC-1318 により `/forge:review` 本体の責務である
> - **他バックエンドとの関係**: 本決定は msg-review バックエンドを置き換えない。両者は `--backend` で選択される並列の手段である

## 1. コンテキスト

先行案 msg-review:ADR-061 は、cmux 非導入環境で push 型起床が働かず往復が停止する問題に対し、**msg-review バックエンド内に app-server という第 2 の起床経路を足す**ことを提案した。この案は採用しなかった（同 ADR は `rejected`）。

採用しなかった理由は、forge:ADR-060 が導入したバックエンド軸と照らしたときに、**分割の単位が違っていた**ことにある。

forge:ADR-060 は「利用できるレビュー実行主体はプロジェクトごとに異なる」ことを前提に、実行主体を `--backend` で交換可能にした。そのコンテキストには、現行の唯一の実行主体が「常駐 Codex セッション・Stop フック・cmux による起床」の上に成り立つこと、それを満たせないプロジェクトではレビューフロー全体が使えないことが明記されている。ADR-061 が解こうとした痛点と同一である。

ここで msg-review バックエンドの本質を見ると、それは**「人間が常駐させた TUI セッションを相手にする」という手段**である。相手のターンを起こす必要があるのも、起こすためにシムが要るのも、シムが無ければ cmux が要るのも、すべてこの前提から派生している。

一方、app-server は別の使い方ができる。**バックエンド自身がスレッドを保持する**構成（`thread/start` / `thread/resume` で文脈を継続し、`turn/start` で依頼し、`turn/completed` と `item/agentMessage/delta` で応答を受ける）を採れば、相手は人間の TUI ではなくバックエンドが所有するスレッドになる。この場合、**起床という概念自体が存在しない**。自分で起こすからである。

つまり app-server は「msg-review の中の別の起床手段」ではなく、**msg-review と並ぶ別の手段**である。手段が違うなら、バックエンド軸の単位で分けるのが筋であり、仕様も手段別に分離されているべきである。

なお、この構成は msg-review:REQ-012 §1.2 が `codex exec` の弱点として挙げる「呼び出しごとに使い捨てられ文脈を保持しない」も解消する。app-server はスレッドを保持するため、単発起動とは異なる。

## 2. 決定

**Codex app-server を用いるレビュー実行主体を、`codex-appserver` という独立したレビューバックエンドとして定義する。**

- forge:REQ-013 FNC-1318 のバックエンド軸に乗る。`--backend codex-appserver` で選択し、既定バックエンドの指定は forge:DES-061 の設定ファイル機構に従う
- **バックエンドがスレッドを所有する**。人間が常駐させた TUI セッションには接続しない。したがって起床・シム・cmux・Stop フック・msg-sys のいずれも使わない
- **仕様は手段別に分離する**。本バックエンドの要件・設計は専用の spec ディレクトリに置き、msg-review の仕様には手を入れない
- **共通書式への変換は本バックエンドの内部責務とする**。app-server は構造化イベントで応答するため、forge:ADR-060 が全バックエンド共通に固定した所見の書式契約（自由記述 markdown + 重大度マーカー + 完了宣言行）への変換を自分で行う
- **監査記録を自分で持つ**。msg-review が msg-sys の履歴に委ねていた往復の監査可能性を、本バックエンドは自前で満たす
- msg-review バックエンドは廃止しない。人間が進行を見て途中介入できるという性質は本バックエンドにはなく、両者は等価ではない

## 3. 検討した代替案

| 代替案                                                        | 棄却理由                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| app-server を msg-review 内の第 2 起床経路にする（ADR-061）   | 手段の単位を誤っている。app-server がスレッドを所有する構成では起床という概念自体が消えるため、「起床経路の 1 つ」として位置づけると、シムによる TUI 相乗りという不要な複雑さを抱え込む。またバックエンド軸という既存の分割単位を使わずに、msg-review 内部に第 2 の分岐を作ることになる            |
| 人間の TUI セッションに相乗りする構成を本バックエンドでも採る | TUI は起動時にしか app-server へ接続できないため、利用者の PATH またはシェル関数にシムを差し込む必要がある。バックエンドがスレッドを所有すればこの介入が丸ごと不要になる                                                                                                                           |
| MCP（`codex mcp-server`）を用いる                             | 棄却ではなく**将来の別バックエンド候補として保留する**。バックエンド軸がある以上、MCP は既存バックエンドを置き換えるものではなく並列に足せる。ADR-061 が挙げた懸念（レスポンスのトークン上限・長時間実行のタイムアウト）は「置き換える場合」に成立するものであり、並列に足すなら別途評価すればよい |
| msg-review バックエンドを廃止して本バックエンドへ一本化する   | msg-review は人間が進行を見て途中介入できる。本バックエンドにこの性質は無く、等価な置き換えにならない。forge:ADR-060 が実行主体を可変にした趣旨にも反する                                                                                                                                          |

## 4. 影響

### 得るもの

- cmux・シム・Stop フックの trust 登録・msg-sys の SQLite のいずれも不要になり、これらを満たせない環境でもレビューフローが使える
- 起床が不要になるため、msg-review:DES-045 に記録された失敗モード（約 7 時間の待機、往復 2 ラウンド目以降の停止、1 レビューで 4 回の手動起床、いずれも沈黙して止まる）が構造的に発生しない
- TUI を介さないため、**バックエンドの動作を人手を介さず自動検証できる**。ADR-061 が `proposed` に留まった原因（TUI の対話起動が必要で検証できない）が解消する

### 失うもの・新たに生じる制約

- 人間がレビューの進行を画面で見て途中介入することはできない。この性質が必要な場合は msg-review バックエンドを選ぶ
- msg-sys の履歴による監査（msg-review:REQ-012 BL-001）を使えないため、監査記録を自前で持つ必要がある（REQ-015 の要件として定義する）
- 承認ポリシーとサンドボックスを本バックエンドが決める必要がある
- app-server は `[experimental]` と明記されたインターフェースであり、破壊的変更が起きうる。追随コストを負う
- WebSocket クライアントの自前実装を保守対象として抱える（`proxy` は生バイト中継でハンドシェイクを代行せず、`unix://` も素の JSON-RPC を受け付けないことを実測で確認済み。msg-review:ADR-061 §1）

### msg-review 側への波及: FNC-007 の一部撤回

msg-review:REQ-012 FNC-007 は 2026-08-02 に追加した時点で「**単一の実行環境に固定しないこと**: 特定の端末多重化ツール等の導入を前提としないこと。環境に応じて複数の経路から選択できること」を [MANDATORY] として含んでいた。これは ADR-061 の複線化案を前提とした記述である。

本決定によりこの項目を撤回し、**msg-review バックエンドの起床手段は cmux 単一とする**。cmux を満たせない環境では、msg-review バックエンド自体が使えないものとして前提検査（FNC-003）で検出し、利用者に別バックエンドの選択を促す。これは forge:ADR-060 の「実行主体の前提を満たせないプロジェクトでは別の実行主体を選ぶ」という考え方と一致する。

同日中の追加と撤回であり、実装には至っていない。撤回の事実をここに記録する。
