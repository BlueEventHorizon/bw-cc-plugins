## 1. コンテキスト

forge は文書検索 backend として doc-db を使う。このとき次の 2 つを取り違えてはならない。

- **KEY / series が未整備**: 索引を作成してから検索する
- **KEY がゴミ箱状態**: 索引を作成してはならず、復活操作を案内する

前者を後者と誤れば案内が出ず、後者を前者と誤ればゴミ箱状態の KEY へ同期を試みる。したがって両者を判別する手段が要る。

doc-db 0.3.2 に対する実測では、KEY 不在は JSON-RPC error ではなく `tools/call` result の `isError: true` + `content[].text` の日本語文言として返り、構造化された識別子を持たなかった。この時点の DES-057 は「実測して得た error の識別可能な要素を判別根拠として確定する」としており、実質的に**メッセージ文言への依拠**を前提にしていた。ゴミ箱状態は `trash_index` が既存 KEY を壊すため未実測のまま残っていた。

doc-db 側へ照会した結果（doc-db-mcp-server Issue #7）、次が判明した。

- 当該文言は公開契約として規定されていなかった。要件・設計のいずれにも error code の設計は無く、実装は平文の `fmt.Errorf` だった
- doc-db 側で識別子が新設され、0.3.3 でリリースされた。`*jsonrpc.Error` を返す形に変わり、KEY 不在とゴミ箱状態は **JSON-RPC error** として届く
- 識別子は `error.data.code`（正本）と `message` 先頭の両方に載る。**値は公開契約として固定**され、数値 code は補助と位置づけられた
- doc-db 側から「文言には依拠しないこと」が明示された

つまり「文言を実測して判別根拠に固定する」という当初方針は、契約でないものへ依拠する設計だった。文言が変われば forge は例外を出さずに静かに誤判定する。

## 2. 決定

1. **判別は `error.data.code` の識別子にのみ依拠する。** 対象は `KEY_NOT_FOUND`（索引を作成してよい）と `KEY_TRASHED`（作成せず復活を案内する）の 2 値。メッセージ文言・数値 code では分岐しない
2. **doc-db は 0.3.3 以上を要求する。** 0.3.2 以下に向けた文言一致のフォールバック経路を持たない
3. **識別子を読み取れない error は、従来どおり障害として扱う。** 未整備側へ倒して索引作成を試みることはしない

決め手は、識別子だけが doc-db 側の公開契約であり、それ以外はいつ変わっても forge に通知されない値だという点である。契約でない値に依拠した分岐は、壊れたことが検出できない形で壊れる。

## 3. 検討した代替案

| 代替案                                            | 棄却理由                                                                                                                                                  |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| メッセージ文言の一致で分岐する（当初方針）        | 文言は公開契約ではないと doc-db 側が明言した。変更時に静かに誤判定し、テストも実運用も異常を検出できない                                                  |
| `message` 先頭の識別子トークンで 0.3.2 以下も支援 | 接頭辞が付くのは 0.3.3 以降であり、0.3.2 以下では結局日本語文言との一致になる。後方互換を名目に、棄却したはずの文言依拠が残る                             |
| 数値 code（-31001 / -31002）で分岐する            | doc-db 側が「判別の正本は `data.code`、数値は補助」と位置づけている。補助側に依拠すると、正本だけが保たれた変更で壊れる                                   |
| ゴミ箱状態を実測して文言を確定してから決める      | 実測には `trash_index` の実行（破壊的操作）が要るうえ、得られるのは契約でない文言という脆い根拠。識別子契約の確定により、実測しても判断が変わらなくなった |

## 4. 影響

**得られるもの**

- 判別根拠が公開契約になり、doc-db 側の文言変更で静かに壊れなくなる
- ゴミ箱状態を判別するための破壊的な実測が不要になった
- KEY 不在と障害の区別が実装可能になり、未整備時の索引自動作成という要件を安全に満たせる

**失うもの・新たに生じる制約**

- doc-db 0.3.2 以下では両者を判別できず、いずれも障害として扱われる。索引の自動作成は行われず、利用者には失敗として報告される（誤って同期を試みることはないが、復旧は手動になる）
- 前提条件として要求する外部依存の版が 2 つになった（doc-advisor と doc-db）。どちらかが古い環境では該当機能が縮退する
- 識別子の網羅範囲は上記 2 種のみであり、それ以外の error は引き続き判別できない。判別対象を増やす場合は doc-db 側への依頼が要る
