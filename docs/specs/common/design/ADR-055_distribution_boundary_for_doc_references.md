# ADR-055 配布物から開発文書への参照を禁止する

## メタデータ

| 項目     | 値                               |
| -------- | -------------------------------- |
| ADR ID   | ADR-055                          |
| Status   | accepted                         |
| 決定日   | 2026-07-25                       |
| 関連設計 | COMMON-DES-001_skill_base_design |

## 1. コンテキスト

本リポジトリは 2 種類の文書を持つ。

| 種類       | 所在                                                    | 配布                     |
| ---------- | ------------------------------------------------------- | ------------------------ |
| 配布物     | `plugins/` 配下（SKILL.md / agent / scripts / docs 等） | 利用者環境へコピーされる |
| 開発用文書 | リポジトリルート `docs/` 配下（specs / rules / readme） | 配布されない             |

マーケットプレイス経由でインストールすると、利用者環境のキャッシュへコピーされるのはプラグインディレクトリ配下のみである。実測（インストール済みキャッシュを `find`）で、`plugins/<plugin>/docs/` は配布される一方、リポジトリルートの `docs/specs/` に相当する実体は存在せず、`DES-*.md` / `REQ-*.md` は 1 件も見つからない。

にもかかわらず、配布物 63 ファイル・約 290 箇所に開発文書への参照が蓄積していた。参照形式は 2 種類ある。

1. パス直書き（`docs/specs/forge/design/DES-029...` を参照）
2. spec ID による出典表記（`複数文書間の優先順位は DES-028 §3.4.1 に従う`、`本スクリプトは REQ-012 FNC-004 の実装である`）

蓄積を許した直接の原因は、既存のアンチパターン記述が「プロジェクト spec のパスを SKILL.md に直書きしない」というパス参照のみを対象としており、ID 参照を対象外にしていたことである。ID 参照は無害な出典表記に見えるため、規範として明示されない限り増え続けた。

もう 1 つの原因は**開発環境と利用者環境の非対称性**である。開発リポジトリでは `docs/` が存在するため同じ参照が解決でき、違反が開発中に一切表面化しない。利用者が実行した時点で初めて欠損になる。

SKILL.md や `review_criteria_*.md` はランタイムで AI（および Codex 等の外部レビューエンジン）が読む指示書であり、解決できない参照は指示の欠損に直結する。

## 2. 決定

**配布物から開発文書へのあらゆる参照を禁止する。** パス直書きに加え、spec ID による出典表記も禁止対象に含める。

決め手は次の 2 点であり、いずれも単独で禁止を正当化する。

- **参照が解決不能**: 利用者環境に参照先の実体が存在しない。参照先を探しに行った AI は必ず失敗する
- **根拠を検証できない**: 配布されない情報を規範の根拠として提示することになる。リポジトリが公開されていても、プラグイン利用者から見れば同梱されていないファイルであり、規範の妥当性を確認する手段がない

規範を示す必要がある場合は、参照ではなく**規範本文を配布物側へ持たせる**（置き場は 2.2）。逆方向（開発文書が配布物の実装を参照する）は禁止しない。開発文書は配布されないため、参照先が失われる問題が発生しない。

### 2.1 禁止対象は「実在文書への参照」に限る

**ID 体系・書式の抽象例は禁止対象に含めない。** プレースホルダ番号（`DES-001` / `REQ-001` / `TASK-001` 等）や、対象プロジェクト側の構造を示すプレースホルダパス（`docs/specs/<feature>/design/*.md`、`docs/specs/**/design/`）は、本リポジトリの実在文書を指していない。

この区別は必須である。配布物には `plan.yaml` の書式定義・`.doc_structure.yaml` の設定例・ID 記法の説明が含まれ、これらは抽象例なしには成立しない。実測で、配布物内の `docs/specs` 出現のうち約 70 行がこの正当な用途だった。禁止対象を「文字列パターンの一致」で定義すると、これらを巻き込んで文書を破壊する。

なお、抽象例のつもりで**実在する ID を書いてしまう**ケースは禁止対象である（例: 記法の説明に `DES-014 の設計を実装する` と実在 spec を挙げる）。これは `document_style_guide.md`「抽象例の命名」— 例文に特定プロジェクトを連想させる固有名を使わない — にも反する。

### 2.2 規範の置き場は 2 通りとし、執筆者が選ぶ

初版は「参照元へ fold する」のみを示していたが、これは分量の大きい規範に対して機能しない。SKILL.md は起動ごとにコンテキストへ注入されるため、根拠をすべて本文へ取り込むと肥大化し、追従精度が落ちる（REQ-001 §1 の God-Skill 問題と同根）。したがって次の 2 方式を対等な選択肢とする。

| 方式                                    | 内容                                                                         | 向いているケース                                                         |
| --------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **A. 参照元に本文を持たせる**           | 規範本文を参照元（SKILL.md / agent / 内蔵 docs）に直接書く                   | 分量が小さい。1 箇所でしか使わない                                       |
| **B. 配布物内に別文書を作って参照する** | 規範本文を `plugins/<plugin>/docs/` 配下の新規文書に書き、参照元から参照する | 分量が大きい。複数の SKILL / agent から使う。SKILL.md を肥大させたくない |

方式 B が本 ADR に反しない理由: 参照先が**同一配布単位に同梱される**ため、2 つの決め手（参照が解決不能／根拠を検証できない）がいずれも成立しない。利用者環境で参照先の実体が存在し、規範の妥当性も確認できる。配布物内リンクの許容は ADR-056 §2.4 と整合する。

方式 B の運用上の条件:

- 参照記法は参照元の位置で決まる（forge の `document_style_guide.md` §5.1）
- 新規文書を追加したら当該配布物の ToC を再生成する。しないと `query-forge-rules` から発見できず、置き場を分けた意味が失われる

## 3. 検討した代替案

| 代替案                                                          | 棄却理由                                                                                                                      |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 開発文書も配布物に同梱する                                      | 配布サイズと関心事が膨張する。利用者に不要な設計判断記録・要件定義書を配ることになり、プラグインの責務境界が崩れる            |
| ID 参照は出典表記なので許容し、パス参照のみ禁止する（現状維持） | ランタイムで AI が ID から参照先を探す挙動を止められない。今回 290 箇所まで蓄積した実績そのものが、この線引きが機能しない証拠 |
| 配布物内に開発文書へのリンク切れ注記を添える                    | 参照が解決できない事実は変わらず、利用者側で確認できない根拠を提示する問題も解消しない                                        |
| 規約化せずレビューで都度指摘する                                | 開発環境では違反が表面化しないため、レビューでも検知しにくい。機械的検出が可能な規約として明文化するほうが確実                |

## 4. 影響

得られるもの:

- 配布物が自己完結する。利用者環境で解決できない参照が構造的に発生しなくなる
- 規範本文が配布物側に集まるため、ランタイムで AI が読む指示書として完全になる
- `plugins/` 配下に spec ID パターンが出現しないという形で、機械的に検出できる状態になる

失うもの・新たに生じる制約:

- 配布物に設計判断の出典を書けない。「なぜこの規範なのか」を配布物内で辿れなくなる（開発文書側に残るが、利用者からは参照できない）
- 既存の約 290 箇所を解消する作業が必要になる。うち一部は出典表記を落とすだけでは済まず、§2.2 のいずれかの方式で規範本文を配布物側へ移す作業を伴う
- 開発文書側にしか存在しない議論（代替案の棄却理由など）は、配布物の読み手には見えない前提で書く必要がある

再発防止は、明文化した規約と機械的検出の 2 段で行う。規約のみでは今回と同じ経路で再発する。
