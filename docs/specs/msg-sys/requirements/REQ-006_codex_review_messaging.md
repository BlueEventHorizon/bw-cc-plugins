# REQ-006 Codex 継続対話メッセージング要件

## 1. 背景

### 1.1 現状の問題

Claude セッションと、別プロセスとして常駐する Codex セッションの間には、人間が仲介せずにメッセージを往復させる手段がない。両者を連携させる応用（最初の応用は継続対話レビュー。msg-review:REQ-012）を成立させるには、以下を満たす通信基盤が必要である。

- 各セッションがターン境界で新着メッセージを検知し、次ターンの入力として受け取れること
- 往復が人間の確認なしに無制限に継続しないこと
- 受信側 AI が事前知識なしに返信操作を実行できること

とくに最後の点について、継続対話が成立しても、Stop フックが差し戻す配信メッセージには「どう返信するか」という操作手順が含まれていなかった。SKILL はトリガー句のマッチングに依存するため必ず読まれる保証がなく、受信側 AI がプロトコルを認識できないまま対話が止まってしまう課題があった（§3 FNC-003 で解決する）。

### 1.2 検討の経緯（この文書に残す理由）

要件確定までに以下の代替案を検討し、却下した。将来同じ議論を繰り返さないよう経緯を残す。

| 検討した案                                                                 | 却下理由                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **agmsg**（外部 OSS、SQLite 経由のエージェント間メッセージング基盤）の導入 | 技術的には要件に適合するが、外部ツールの導入によるセキュリティ監査コストが見合わないと判断                                                                                                                                                                                                                                                                                   |
| **DSS**（REQ-007 で開発中の Doc Session System）の流用                     | DSS は「1 workflow = 1 session、1 往復（request→response）」を前提とした単一オーケストレータ内の成果物受け渡し機構であり、`turn` フィールドは常に `1` 固定・`resume`/`continue` コマンドは実装されていない（REQ-007 §10 で多ターン session は明示的にスコープ外）。独立して起動・常駐する外部プロセス（Codex）との継続的な往復を想定した設計ではなく、目的が異なるため不採用 |
| **push型通知の実装**                                                       | 実際に agmsg の実装を調査した結果、Codex 向けの `turn` delivery モード（デフォルト）自体が Stop フック起点のポーリングであり、push 通知は Claude Code 向け `monitor`（5秒間隔ポーリング）ですら実体はポーリングだった。1秒〜数秒間隔のポーリングで要件を満たせるため、push 型通知の実装コストは不要と判断                                                                    |

### 1.3 検証済みの技術的前提

要件確定前に、本リポジトリのローカル環境で以下を実機検証済み（`meta/msg-sys-experiment/` 参照。git 管理外の実験コードのため本要件には同梱しない）。

- Codex CLI（`codex-cli 0.142.5`）は `.codex/hooks.json` に `Stop` フックを持ち、Claude Code の hooks とほぼ同一の JSON スキーマ（`hooks.Stop[].hooks[].type/command/timeout`）で動作する。実プロジェクト（Homebrew）での実運用例で確認済み
- Codex CLI は `resume` / `fork` / `archive` サブコマンドを持ち、以前のセッションを文脈ごと再開できる
- sqlite3 標準ライブラリ（WAL モード + `busy_timeout`）による送受信の最小実装（`send`/`inbox`/`history`）を作成し、往復・既読化・履歴監査が正しく動作することを確認済み
- **Claude Code 側の `Stop` フックが `{"decision": "block", "reason": "<text>"}` を出力した場合、`reason` の内容が人間の操作なしに次ターンの入力として自動的に差し戻されることを本リポジトリで実機検証済み（2026-07-11）**。これにより INT-003（Claude 側の新着検知）が Codex 側（INT-002）と同一の仕組みで成立することが確認された
- **返信ヒント付きの `decision:block` を受け取った Codex が、人間の仲介なしに自律的にターンを終え、Stop フックが自動発火して次の往復が成立することを実機検証済み（2026-07-18）**。返信ヒントの手順（一時ファイル書き込み → `send.py` 実行 → 削除）をそのまま実行するだけで返信チェーンが形成されることが確認された

## 2. スコープ

### 2.1 対象とする範囲（v1）

- Claude セッションと、人間が手動起動して常駐させる Codex セッションとの間で、メッセージを非同期（ポーリング）に往復できること
- メッセージの送受信履歴が失われず、監査可能な形で残ること
- 受信側セッションの対話文脈の永続性は各ランタイム自身の機能（Codex の `resume` 等）に委ね、本機構では扱わない
- Stop フックが差し戻す配信メッセージには、受信側 AI が追加のドキュメント参照や事前知識なしに返信操作を実行できる自己完結的な返信ヒントを含めること。Claude→Codex、Codex→Claude いずれの方向にも同様に適用すること

### 2.2 v1 で明示的に除外する範囲

- **本基盤上で行う応用の手順・完了判定**: メッセージで何を依頼し、返信をどう処理し、いつ対話を完了とするかは応用側の要件（レビュー応用は msg-review:REQ-012）が定める。本文書は通信路（送受信・検知・返信ヒント・停止条件・整合性）のみを定める
- push 型通知の実装
- agmsg 本体・DSS の流用

### 2.3 v1 の位置づけ（意図的な判断）

v1 は本番運用・外部公開を前提としない実験段階の内部ツールとして位置づける（NFR-003）。基盤としての恒久化・拡張の要否は、最初の応用である継続対話レビュー（msg-review:REQ-012 §2.3 の比較評価）の運用結果を踏まえて判断する。

## 3. 機能要件

### INT-001: メッセージ送受信 [MANDATORY]

Claude と Codex（エージェント名で識別する任意の宛先）の間で、以下を満たすメッセージ送受信ができること。

- 送信: 送信者・宛先・本文を指定してメッセージを1件記録できる
- 受信: 宛先ごとに未読メッセージを取得できる。既読化は「取得」そのものとは分離すること（取得しただけでは既読化しない）。既読化操作の完了が配信成功の確定点である（INT-004 参照）
- 履歴: 2エージェント間の全メッセージ履歴を送信順に取得でき、既読状態に関わらず参照できる（監査用）
- メッセージは削除されず、追記のみで蓄積される

### INT-002: Codex 側の新着検知 [MANDATORY]

Codex 側は、ターン終了時（Stop フック相当のタイミング）に自動的に inbox を確認し、未読メッセージがあればそれを次のターンの入力として受け取れること。未読が無い場合はそのまま終了できること。**ただし FNC-002 の停止条件に該当する場合（往復上限到達時）は、未読があっても次ターンへの差し戻しを行わず、人間への通知に降格すること**（詳細は FNC-002 参照）。

### INT-003: Claude 側の新着検知 [MANDATORY]

Claude 側も同様に、ターン終了時に inbox を確認し、未読メッセージがあれば次のターンで処理できること。INT-002 と同様に、FNC-002 の停止条件に該当する場合は次ターンへの差し戻しを行わない。

### FNC-002: 継続対話の停止条件 [MANDATORY]

INT-002 と INT-003 は対称に「未読があればターンを止めて差し戻す」動作を定義するため、Claude と Codex が交互に応答を送り合い続けると、人間の確認なしに往復が無制限に継続し得る。これを防ぐため、継続対話には停止条件を設ける。

- 同一の対話（人間が新規メッセージを送ってから続く一連の返信チェーン）における往復回数が一定の上限に達した場合、それ以上は自動継続せず、人間に状況を報告して判断を仰ぐこと
- 上限回数の具体値は本文書の未確定事項とする（§5 TBD-004）

### FNC-003: 返信ヒントの自己完結性 [MANDATORY]

配信されるメッセージには、受信側が追加情報なしに返信操作を実行するために必要な情報（実行可能な形式の案内・対象 message id・宛先）が含まれていること。曖昧な自然文の指示のみでは満たさない。

### FNC-004: 返信ヒントの双方向適用 [MANDATORY]

Claude→Codex、Codex→Claude いずれの方向の配信メッセージにも FNC-003 が同様に適用されること。

### BL-001: 返信ヒントの内容一貫性

返信ヒントは配信メッセージごとに動的生成され、実際にそのメッセージへの返信として機能する値（正しい message id 等）を反映していること。固定文言の使い回しでは満たさない。

### INT-004: メッセージ配信の整合性 [MANDATORY]

送信されたメッセージは、受信側に配信されたことが確認できるまで、失われてはならない。具体的には以下を満たすこと。

- 受信側が「取得」しただけ（既読化前）の段階では、その内容を実際に処理（次ターンの入力として提示する等）できなかった場合に備え、当該メッセージは未読のまま残るか、再取得可能な状態に戻ること（「取得」のみで即座に既読化する設計は避ける。既読化は別操作として分離する）
- **「配信成功」の定義の範囲限定**: 受信側システム（Stop フック）は一方向出力のみ行い、送信先ランタイム（Claude Code / Codex）が実際にその内容を次ターンの入力として処理したかどうかを技術的に確認する手段がない。加えて、既読化操作とメッセージ出力操作を単一のアトミックな処理として扱うことはできない（実装上の制約）。したがって本要件における「配信成功」は、**受信側システムが当該メッセージの既読化操作を完了したこと**（既読化の完了そのものを配信成功の確定点とする。既読化操作それ自体が「配信成功の確認」を兼ねる。具体的な確認方法・操作順序は設計に委ねる）までを指し、送信先ランタイムが実際に処理したかどうかまでの保証は求めない

## 4. 非機能要件

### NFR-001: 標準ライブラリのみでの実装 [MANDATORY]

`docs/rules/implementation_guidelines.md` に従い、Python 実装は標準ライブラリのみを使用する（sqlite3 等）。外部パッケージへの依存を持たない。Bash からの外部コマンド呼び出し（`codex` 等）は許容する。

### NFR-002: 外部ツール非依存 [MANDATORY]

agmsg 等の外部プラグイン・パッケージを本機構の実行時依存として導入しない（§1.2 の検討経緯を参照）。

### NFR-003: 性能・可用性・セキュリティ・運用性の適用範囲

本機構は本番運用・外部公開を前提としない実験段階の内部ツールである（§2.3 参照）。カテゴリごとの扱いを以下に定める。

- **性能**: 独自のポーリング間隔設定は持たない。Stop フック起点のイベント駆動（INT-002/INT-003）であり、具体的なレイテンシ目標値は当事者が運用しながら体感で判断するため、本文書では確定しない（未確定値を要件として捏造しない）
- **可用性・復旧**: DB ロック時の再試行・既読化失敗時の再取得は INT-004 で扱う。それ以上の高可用性要求（冗長化・フェイルオーバ等）は設けない（内部ツールのため対象外）
- **セキュリティ・データ保護**: メッセージ本文はレビュー所見等の開発内部情報のみを想定し、個人情報・機密情報の送受信は想定しない。DB ファイルはプロジェクトローカルに保存し、アクセス制御はファイルシステム権限に委ねる（追加の暗号化・認可機構は設けない）
- **運用性**: 履歴は追記専用で無期限保持する（INT-001）。ログローテーション・アーカイブは本 v1 のスコープ外。人間への通知は OS 通知を用い、対応は手動 ack で行う（FNC-002 参照）
