# ADR-082 トリアージを「Issue の正誤検証 + TASK 化可否による 2 ルート判定」へ転換し、impl-issue の直接起動と自前調査を復活させる

## 1. コンテキスト

anvil の Issue 起点開発フローは、REQ-007 / DES-038（トリアージ工程の差分 feature 文書。後に REQ-005 / DES-025 へ統合）に基づき次の形で運用されていた。

- トリアージは「変更の検証・追跡に必要な開発文書の種別」を判定軸とし、ワンショット実装 / SDD（`start-requirements` または `start-design`）/ plan モード提案の 3 ルートへ振り分ける
- 実装工程（`impl-issue`）の入口はトリアージ経由の一本に限り（`user-invocable: false`）、トリアージの調査結果（仕様書・ルール・類似 PR・既存コード）を Issue コメントの機械可読マーカー経由で引き継いで再調査を省く
- 調査手順は Phase 別の references ファイルに分割して両スキルが参照する

運用で次の問題が顕在化した。

- **Issue の内容そのものの誤りが検証されない**。トリアージは「進め方」を判定する工程として設計され、Issue に書かれた症状・原因・提案が実体と食い違っていても、それを正す責務を持たなかった。誤った記述は Issue に残り、後続の工程や将来この Issue を読む AI が旧文言を引用して正しい記述を改変する事故を起こした
- **plan モードルートは文書の調査結果に依存し、判定が安定しない**。「対話でしか決着しない決め事が残るか」という判定は調査の深さで結論が変わり、同じ Issue でも実行ごとに結果が揺れた
- **`start-design` エントリは要件定義書の実在を前提とし、SDD の連続フロー（要件 → 設計 → 計画）の途中から入る判定が機能しなかった**。計画は要件定義書・設計書を必要とするため、実務上は要件定義から入る以外の選択肢が成立しなかった
- **調査の引き継ぎがスキルの独立性を壊した**。`impl-issue` はマーカー付きコメントが無いと停止する設計になり、直接起動できず、セッションを跨いだ再開の経路も複雑化した。一方でマーカーゲートは実行時に強制されない（`user-invocable: false` は起動経路を隠すだけ）
- **類似 PR 調査はトリアージの責務ではなかった**。類似 PR は「どう解決するか」の情報であり、「Issue は正しいか」には寄与しない
- **references 分割による重複**。「特定した文書は**すべて** Read する」等の同一規律が複数ファイルに散在し、片方だけ更新される乖離が生じた

## 2. 決定

### 2.1 トリアージの責務を「Issue の正誤検証と是正」に置く

`triage-issue` は既存仕様書・実装ルール・既存コードの実体で Issue の事実主張を裏取りし、誤り・不足・過剰があれば Issue を正しい内容に書き直す。是正の範囲は全面改訂（本文の書き起こしと既存コメントの全削除）を含む。誤った記述を残す選択肢（参考として残す・打ち消し線で残す）は採らない。書き直しはユーザーの承認を得てから実行する。

類似 PR 調査はトリアージの調査から外す。

### 2.2 ルートを 2 択にし、判定軸を「TASK 化できるか」にする

ルートは「ワンショット実装（`impl-issue`）」と「要件定義から開始（`/forge:start-requirements`）」の 2 つに限る。plan モード提案と `start-design` エントリは廃止する。

判定軸は、やるべきことを「対象・変更内容・完了の確認方法」が埋まる TASK として列挙できるかどうかである。影響範囲が不明なら深掘りを必須とし、その結果 TASK が増えても列挙できるならワンショット実装とする。列挙できない項目（要件が定まらない・妥当な解が複数あり選択基準が要件に依存する・影響範囲が閉じない）が残るなら要件定義から開始する。変更量・修正規模は判定に使わない（この点は旧設計と同じ）。

forge の差分開発規範による feature 要否判定はトリアージから外し、`start-requirements` 以降の工程に委ねる。

### 2.3 impl-issue を直接起動可能にし、修正のための調査を自ら行う

`impl-issue` は `user-invocable: true` とし、トリアージからの起動と直接起動の両方を受け付ける。仕様書・実装ルール・類似 PR・既存コードの調査は「修正のための調査」として自ら行い、トリアージの調査結果を根拠に省かない。マーカー付きコメントによる引き継ぎと起動ゲートは廃止する。トリアージの結果は監査記録としての平文コメントに留める。

同一 Issue に対してトリアージと実装工程の調査が重なることは、調査の目的（正誤検証 / 修正）が異なるため許容する。

### 2.4 Figma ベースの UI フローを impl-ui に分離する

UI Issue の Figma 依存部分（デザイン仕様書作成・視覚比較レビュー・実装設計書・UI 実装・三点突合レビュー）を `anvil:impl-ui` に切り出し、`impl-issue` は `--stage design` / `--stage implement` の 2 回の Skill 起動で委譲する。`impl-issue` は Figma 固有の手順を持たない。将来別のデザインソースに対応する場合は、同じ段階契約を持つ別スキルを用意して委譲先を差し替える。

### 2.5 統合時に、実装されなかった設計を要件・設計から外す

統合前の REQ-005 / DES-025 が持っていた次の要件・設計は、一度も実装されずに運用が成立していたため、統合時に要件・設計から外した: Issue 本文への成果物リンク・進捗ステータスの書き戻し（`update-issue`）、外部 API 呼び出しの監査ログ、前提条件検査・push 検証の共通スクリプト、工程失敗からの `--resume` 再開経路、公開チャネルへの機密マスク、レート制限の再試行方針。

Issue から成果物への追跡は、実装工程が Issue 本文へ追記する実装計画、トリアージの監査コメント、PR の `Closes #N` で成立している。

## 3. 検討した代替案

| 代替案                                                                       | 棄却理由                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3 ルート（plan モード提案を含む）を維持する                                  | plan モードの判定は「対話でしか決着しない決め事が残るか」を調査結果から推定するもので、調査の深さに結論が依存し安定しない。前提: トリアージの調査は有限の時間で打ち切られる。決め事が残るなら、それは要件定義で合意すべき論点として `start-requirements` に渡せば足りる |
| `start-design` エントリを残す                                                | 設計から入るには有効な要件定義書の実在が前提だが、実務上その前提が満たされる Issue はほぼ無く、判定の分岐が空振りしていた。前提: forge の SDD は要件 → 設計 → 計画の連続フローで、途中から入る自動繰り上がりを持たない。前提が変われば再検討してよい                    |
| 調査結果の引き継ぎ（重複調査の排除）を維持する                               | 引き継ぎのために `impl-issue` を直接起動できなくし、マーカー解析・セッション跨ぎ復元の機構を持つ代償が、省ける調査コストより大きかった。目的の異なる調査（正誤検証 / 修正）は重なっても無駄ではない。前提: 調査コストはトークンと時間であり、スキルの独立性より軽い     |
| 入口一本化のためのマーカーゲートを維持する                                   | ゲートは実行時に強制されず（frontmatter は起動経路を隠すだけ）、経路違反を止める機構として機能していなかった。機能しないゲートは複雑さだけを残す                                                                                                                        |
| 実装されなかった設計（進捗の書き戻し・監査ログ・再開経路等）を要件として残す | 実装が無いまま長期間運用が成立しており、追跡は実装計画・監査コメント・`Closes #N` で足りている。前提: Issue を索引として使うのは人間と AI であり、本文末尾の実装計画と PR 参照で成果物へ辿れる。書き戻しを機械化する必要が生じれば、その時点で要件として再定義する      |
| Issue の旧本文を `<details>` 等で残したまま新本文を追記する                  | 旧本文が残ると、後続の AI が旧文言を引用して新本文を改変する事故が再発する。前提: Issue を読むのは人間だけではなく AI であり、AI は折りたたみを無視して全文を読む                                                                                                       |
| 類似 PR 調査をトリアージに残す                                               | 類似 PR は解決手法の情報であり、Issue の正誤判定に寄与しない。トリアージの調査コストを増やすだけになる                                                                                                                                                                  |

## 4. 影響

**得られるもの**

- Issue の誤りが実装前に是正され、誤った前提のまま実装・要件定義に進む事故が減る
- ルート判定の基準が「TASK として列挙できたか」という検証可能な形になり、判定の妥当性を事後に確認しやすい
- `impl-issue` が単独で動き、トリアージ・実装のどちらのスキルも他方の内部状態に依存しない
- Figma 依存部分が `impl-ui` に閉じ、デザインソースの差し替えが `impl-issue` を変えずに行える

**失うもの・新たに生じる制約**

- 同一 Issue に対する調査がトリアージと実装工程で重なる（目的が異なるため許容する）
- Issue の全面改訂はコメントの削除を伴う不可逆操作であり、承認前のプレビュー提示を省いてはならない
- 「対話でしか決着しない決め事」は要件定義工程で扱うことになり、`start-requirements` の入力に TASK 化できなかった論点を添える運用が必要になる
- ADR-039 の決定（判定 A / B を前提とした Phase 順序）は前提を失い失効する
