# REQ-005 Issue 起点開発フロー 要件定義

## 1. 背景

GitHub Issue を開発の入口とし、起票 → 内容の検証と進め方の判定 → 実装 → PR 作成までを一連の流れで辿れるようにする。変更には、開発文書（要件定義書・設計書）を起こさなければ検証できないものと、やるべきことが明確で直接実装できるものがある。両者を判定基準に基づいて振り分け、前者は forge の SDD（要件定義から）へ、後者は実装工程へ進める。

---

## 2. 目的

1. 問題・要望を、後続工程が参照するに足る情報量で Issue に記録できる
2. Issue の内容が実体（既存仕様書・実装ルール・既存コード）に照らして正しいことを実装前に確認し、誤りがあれば Issue を正しい内容に書き直せる
3. やるべきことを TASK として列挙できる Issue は直接実装し、列挙できない Issue は要件定義から始める
4. 実装は調査・計画・実装・レビュー・PR 作成まで一貫して進み、Issue から PR へ辿れる
5. UI を伴う Issue は Figma を情報源とした設計・実装・レビューを経る

---

## 3. スコープ

### 3.1 含める

- Issue の起票（Issue 種別の選択と、種別ごとの必須セクションの記録）
- トリアージ（Issue の正誤検証・是正、TASK 化可否による進め方の判定）
- 実装工程（修正のための調査、実装計画の Issue 記載、実装、レビュー、commit・PR 作成）
- UI Issue の設計・実装・レビュー（Figma を情報源とする）
- 上記工程間の連携と、各工程の入口

### 3.2 含めない

| 非対象                                                  | 理由                                                                    |
| ------------------------------------------------------- | ----------------------------------------------------------------------- |
| forge の SDD 機能（要件定義・設計・計画・実装）の改修   | 本フローは SDD を呼び出す側である                                       |
| commit / PR 作成機能の改修                              | 本フローは既存機能を呼び出す側である                                    |
| GitHub Issue 以外（Jira / Linear 等）を起点とするフロー | スコープを GitHub Issue に限定する                                      |
| 1 Issue で複数画面を扱う UI Issue                       | 1 Issue は単一画面を対象とする。複数画面は Issue を分割する             |
| Figma 以外のデザインソースへの対応                      | 差し替え可能な契約（FNC-04）だけを定め、対応そのものは別 feature で扱う |

## 4. 用語定義

| 用語             | 定義                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| Issue            | GitHub Issue。Issue 番号 `#N` で識別する                                                                 |
| Issue 種別       | 起票時のコンテンツ分類。Bug Report / Feature Request の 2 種                                             |
| UI Issue         | 実装対象に画面・レイアウト・視覚表現を含み、Figma 由来情報を参照する Issue                               |
| 非 UI Issue      | Figma 由来情報を参照しない Issue                                                                         |
| トリアージ       | Issue の内容を実体で検証・是正し、進め方を判定する工程                                                   |
| 事実主張         | Issue に書かれた症状・現状の記述。実体で確認するまで事実として扱わない                                   |
| 解決提案         | Issue に書かれた修正方針・実装案・スコープ。判定の入力であって要件ではない                               |
| TASK             | 対象（実在をパスで確認済み）・変更内容・完了の確認方法の 3 項目が埋まる作業単位                          |
| ワンショット実装 | 開発文書を新たに起こさず、実装工程へ直接進む経路                                                         |
| 要件定義から開始 | forge の要件定義（`start-requirements`）から SDD を始める経路                                            |
| 監査コメント     | トリアージの判定結果と根拠を Issue に残すコメント                                                        |
| 実装計画         | 実装工程が Issue 本文末尾に追記する解決内容（実装スコープ・スコープ外・TODO）                            |
| Figma URL        | Figma で描いたデザインソースへのリンク URL。画面設計書に記載され、設計段階の入力として UI 工程へ渡す     |
| Figma 由来情報   | Figma から取得する情報（対象フレームの識別子と URL、デザイン詳細、デザイントークン、スクリーンショット） |
| デザイン仕様書   | Figma 由来情報から作成する、画面の構造・値・アクションを定めた文書（What）                               |
| 実装設計書       | デザイン仕様書と既存コードを照合して作成する、使用コンポーネント・トークン・状態管理を定めた文書（How）  |
| 三点突合         | Figma のスクリーンショット・実装画面のキャプチャ・コード（設計書）を突き合わせる実装レビュー             |
| forge 既存 skill | forge が提供する検索（仕様書・ルール・内蔵規範）、レビュー、要件定義の各 skill                           |

## 5. 要件一覧

### 5.1 FNC-01: Issue 起票

**目的**: 問題または要望を、後続工程が参照するに足る情報量で GitHub Issue として記録する。

**ユーザー視点の振る舞い**:

- 利用者が Issue 種別（Bug Report / Feature Request）を選び、種別ごとの必須セクションを順に入力すると、タイトルと本文が整った Issue が GitHub に登録される
- タイトルは改行を含まない 1 文で、種別が読み取れる接頭辞（`[Bug]` / `[Feature]`）を持ち、256 文字以内である
- Issue にはラベル（Bug Report: `bug`、Feature Request: `enhancement`）が付く
- 作成後、利用者は「ブラウザで開く」「トリアージへ進む」「終了」を選べる

**Bug Report の必須セクション**:

| セクション          | 内容                                                              |
| ------------------- | ----------------------------------------------------------------- |
| 背景 / コンテキスト | 何をしようとしていたか、いつ気付いたか                            |
| 現象（実際の動作）  | 実際に起きたこと。エラーメッセージがあれば原文を含める            |
| 期待動作            | 本来どう動作すべきだったか                                        |
| 再現手順            | 既知の初期状態を明記した上での、番号付きの操作列                  |
| 環境情報            | 少なくとも OS / バージョン / 使用ツールやランタイムのバージョン   |
| 重大度              | `業務継続不能` / `機能に支障あり` / `軽微` のいずれか             |
| 証跡                | スクリーンショット / ログ / 動画への参照。存在しない場合は `なし` |
| 原因                | 判明している場合のみ記載。不明な場合は `調査中`                   |

**Feature Request の必須セクション**:

| セクション          | 内容                                                                           |
| ------------------- | ------------------------------------------------------------------------------ |
| 背景 / コンテキスト | なぜこの要望が生まれたか、現状の課題は何か                                     |
| ユーザーストーリー  | 役割・やりたいこと・得たい価値の 3 要素を明示する                              |
| 受け入れ基準        | 満たされたと判断できる客観的な条件。各条件は単独で真偽判定できる粒度で記述する |
| 代替案 / 補足       | 検討した代替案または補足情報。存在しない場合は `なし`                          |

**不変条件**:

- 情報が得られない項目は、空欄ではなく閉じた集合の不在表現（`不明` / `なし` / `調査中` / `該当なし`）のいずれかで埋める。別表記は許容しない
- 必須セクションの見出し名は上表の正規名で固定する
- 中核セクション（Bug Report: 「現象（実際の動作）」「再現手順」、Feature Request: 「ユーザーストーリー」「受け入れ基準」）が不在表現のみで埋まる場合、Issue を起票せず再入力を求める
- UI に関わる Feature Request は、Figma 参照情報（Figma URL / 画面名 / 対象フレームの識別子のいずれか 1 つ以上）を本文に含める。得られない場合は起票しない
- 利用者記述の範囲は本文中のマーカー対で区切り、後続工程はこの範囲を上書きしない
- 種別の自動判定は行わない。起票時に利用者が選ぶ
- 解決内容（対策・実装計画）は起票時に記録しない。実装工程が追記する（FNC-03）

---

### 5.2 FNC-02: トリアージ

**目的**: Issue の内容が正しいことを実体で確認し、誤りがあれば是正したうえで、ワンショット実装と要件定義から開始のどちらへ進むかを判定する。

**ユーザー視点の振る舞い**:

- 利用者が Issue 番号（または URL）を指定すると、Issue 本文・コメントが読み取られ、**事実主張と解決提案が分離**して提示される
- 事実主張は、関連する既存仕様書・実装ルール・既存コード（発生箇所と参照元・呼び出し元）で裏取りされる。見つからなかった調査は「該当なし」と明記される
- 各主張・提案は「正しい / 誤り / 不足 / 過剰 / 判定不能」に分類され、根拠（仕様書・ルール・コードの位置）とともに提示される。判定不能は利用者への質問 1 回で結論を得る
- 誤り・不足・過剰が 1 件以上あれば、Issue は正しい内容に**書き直される**。書き直しは本文の全面改訂と既存コメントの全削除を含んでよく、新本文と削除対象コメントの一覧を提示して利用者の承認を得てから実行される。承認されなければ書き直さず、以降の工程へも進まない。誤り等が無ければ Issue に触れない
- 是正後、影響範囲が確定するまで再調査され、やるべきことが TASK として列挙される。列挙できない項目は理由（要件が定まらない / 妥当な解が複数あり選択基準が要件に依存する / 影響範囲が閉じない）とともに示される
- 全 TASK が列挙できれば**ワンショット実装**、列挙できない項目が残れば**要件定義から開始**と判定され、一文の根拠が添えられる
- 判定結果・是正の要旨・調査で特定した参照先・TASK 一覧が会話で報告され、同内容が Issue に監査コメントとして残る
- 判定後、利用者に 1 回だけ確認し、承認されればワンショット実装は実装工程（FNC-03）へ、要件定義から開始は forge の要件定義（`start-requirements`）へ進む。要件定義へ進む場合、TASK 化できなかった論点が合意対象として引き渡される

**不変条件**:

- 事実主張は実体で確認するまで事実として扱わない
- 「Issue に書かれていない」「未調査」だけを理由に判定不能としない。調べれば分かることは調べ、利用者に聞けば決まることは聞く
- TASK 化の判定は内容の明確さで行う。TASK の数・変更量・修正規模は判定に使わない
- 要件定義から開始と判定するときは、TASK 化できなかった項目とその理由を根拠として具体的に示す
- Issue の書き直しは利用者の承認を得るまで実行しない。誤った記述を「参考として残す」「打ち消し線で残す」形は採らない
- 是正後の本文は FNC-01 の構造（マーカー対と必須セクション）に揃える
- 監査コメントには判定結果と根拠・是正の要旨・参照先・TASK 一覧を書き、実装方法（クラス名等）は書かない
- 認証・権限不足・参照先の消失で調査を完了できない場合は、判定せず調査ブロッカーとして終了し、何が確認できず何があれば再開できるかを報告する

---

### 5.3 FNC-03: 実装工程

**目的**: Issue の実装を、修正のための調査から PR 作成まで一貫して行う。

**ユーザー視点の振る舞い**:

- 実装工程は、トリアージ（FNC-02）からの起動と、利用者による直接起動の両方を受け付ける。どちらの経路でも同じ手順を踏む
- Issue 番号（または URL）を指定すると、次が順に進行する:
  1. Issue 本文・コメントが読み取られる。監査コメントがあれば参考にするが、それを根拠に調査を省かない
  2. 現在のブランチに Issue 番号が含まれ、commit が進み、Issue 本文に実装計画が既にあれば「PR 作成のみ未達」と推定され、利用者の確認のうえ PR 作成から再開できる
  3. 作業ブランチが確認・作成される。ブランチ名の接頭辞は Issue のラベルから決まり（`fix/` / `feature/` / `refactor/` / `docs/` / `chore/`）、判定できなければ利用者が選ぶ。タイトル・本文から推測しない
  4. UI Issue か否かが判定される。判断が割れる場合は利用者に確認する
  5. 修正のための調査が行われる: 関連仕様書・実装ルール（すべて本文を読む）、同じスコープのマージ済み PR（3 件以上）、再利用できる既存資産と影響範囲。見つからなかった調査は「該当なし」と明記される
  6. UI Issue の場合、設計段階（FNC-04）を経る
  7. 実装計画（実装スコープ・実装順序・スコープ外・参考 PR）が策定され、Issue 本文の末尾に追記される
  8. 利用者が実装開始を確認する
  9. 実装される。UI Issue は実装段階（FNC-04）へ委ね、非 UI Issue は実装計画の TODO に沿って実装し、レビュー（forge のコードレビュー）を受ける
  10. commit と PR 作成が行われる。PR 本文には Issue を自動クローズする参照（`Closes #N`）と受け入れ条件のチェックリストが含まれる

**不変条件**:

- 実装計画は既存本文の末尾に追記し、FNC-01 の利用者記述と FNC-02 の是正内容を上書きしない
- Issue に記載する参照は GitHub / Figma で開けるものに限る。ローカルにしか無いファイルは載せない
- 既存資産を探してから作る。既存があれば改修を優先し、兄弟機能が確立したパターンを壊さない
- 仕様書・設計書に無い値を推測で実装しない
- 実装レビューをサイレントにスキップしない
- PR 作成に失敗した場合、PR 作成機能を直接再実行せず、実装工程を再実行して再開判定を経る

---

### 5.4 FNC-04: UI Issue の設計・実装・レビュー

**目的**: UI Issue について、Figma を情報源としてデザイン仕様書・実装設計書を作り、それに従って実装し、三点突合でレビューする。

**ユーザー視点の振る舞い**:

UI 工程は実装工程（FNC-03）から 2 段階で呼ばれる。

- **設計段階**（実装計画の前）:
  1. Figma への到達性（PAT）と依存ツールの有無が確認される。依存ツールが不足していれば、AI がインストールする / 利用者が手動で入れる / プレビュー生成をスキップする / 中断する、から利用者が選ぶ。AI は勝手にインストールしない
  2. Figma 由来情報（FNC-05）からデザイン仕様書が作成され、Figma のスクリーンショットと AI 理解プレビューの視覚比較が提示される
  3. 利用者が視覚比較を確認し、承認 / 修正要求 / 中断を選ぶ。承認されるまで次へ進まない
  4. デザイン仕様書と既存コード調査結果から実装設計書が作成される。実装設計書には全テキストノードの Typography 対応表と、アクション一覧の実装方針を必ず含む
- **実装段階**（実装開始の確認後）:
  1. デザイン仕様書を構造の正、Figma をビジュアル詳細の正として実装される。設計書に無い値は Figma から取得し、推測で埋めない
  2. 2 画面以上から参照される共用コンポーネントは 1 画面の都合で書き換えない。不一致なら画面専用コンポーネントを作る
  3. 実装後、Figma のスクリーンショット・実装画面の実機キャプチャ・コード（設計書）の三点突合でレビューされる。実機キャプチャを取得できない場合は、利用者に取得を依頼する / 未実施を明示して進める / 中断する、から選ぶ
  4. 実装したファイル一覧とレビュー結果（差異件数・対応有無・実機キャプチャ有無）が実装工程へ返され、commit・PR 本文に反映される

**不変条件**:

- 設計段階と実装段階の入出力契約は、デザインソースに依存しない形で定める（設計段階: Issue 番号・画面情報・Figma URL・既存コード調査結果 → デザイン仕様書と実装設計書の所在・承認結果。実装段階: 両文書の所在 → 実装ファイル一覧とレビュー結果）
- 実装工程は Figma 固有の手順を持たない。別のデザインソースは同じ契約を持つ別の UI 工程で差し替える
- ブランチ操作・Issue 更新・commit・PR 作成は UI 工程では行わない（実装工程の責務）
- Figma 情報の取得に失敗した場合、推測で設計・実装・レビューを進めない

---

### 5.5 FNC-05: Figma 由来情報

**目的**: UI Issue で参照する Figma 由来情報を、正しい対象フレームから取得する。

**ユーザー視点の振る舞い**:

- Issue または画面設計書に記載された Figma URL / 画面名 / フレーム識別子を入力に、対象フレームの識別子と永続 URL、デザイン詳細（レイアウト・要素構成・スタイル）、デザイントークン（色・余白・書体）、スクリーンショットが取得される
- 識別子が複数一致した場合は候補一覧が提示され、利用者が選ぶ

**不変条件**:

- 記載された識別子を信頼せず、Figma 側で対象フレームを確認して確定する。記載と Figma 側が矛盾する場合は Figma 側を採用し、利用者に通知する
- Figma ファイルの識別子（fileKey）に既定値を持たない。引数または URL から解決できなければ中断する
- 1 Issue につき単一の対象フレームのみを扱う

---

### 5.6 NFR-01: 依存方向

- 本フローの全 skill は anvil プラグイン配下に置く
- forge の既存 skill を呼び出してよいが、forge の実装には手を入れない（anvil → forge の一方向依存）
- forge の改修が必要と判明した場合は、本フロー内で改修せず、別 Issue として要件定義から扱う

### 5.7 NFR-02: Issue 索引性

- Issue に書くのは、利用者記述・是正内容・実装計画・監査コメント・PR への参照である
- デザイン仕様書・実装設計書・実装コードの本文を Issue に複製しない。参照は GitHub / Figma で開ける URL で記載する

### 5.8 NFR-03: 判定の監査可能性

- トリアージの判定結果（ルート）とその根拠、是正の要旨は Issue コメントとして残し、事後に「この判定は妥当だったか」を検証できるようにする

### 5.9 ERR-01: 前提条件未充足時の振る舞い

以下が未充足の場合、静かに失敗せず、明示的に停止して充足方法を案内する:

| 前提条件                                               | 対象                                                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| gh CLI がインストールされ認証されていること            | 起票・PR 作成工程で明示的に検査する。トリアージ・実装工程は検査を持たず、gh コマンドの失敗で停止する |
| カレントディレクトリが git リポジトリ内であること      | 起票・実装工程                                                                                       |
| リモートリポジトリが設定されていること                 | 起票・実装工程                                                                                       |
| 指定された Issue が現在のリポジトリに属すること        | URL 指定時。不一致のとき、トリアージ・実装工程とも警告して中断し、対象リポジトリでの再実行を案内する |
| `FIGMA_PAT` で Figma に到達できること                  | UI 工程                                                                                              |
| デザイン仕様書のプレビュー生成に必要なツールがあること | UI 工程の設計段階（不足時は FNC-04 の選択肢）                                                        |

## 6. 主要シナリオ

**S1. 起票**

1. 利用者が種別を選び、必須セクションを入力する
2. プレビューを承認すると Issue が作成される
3. 「トリアージへ進む」を選ぶと、トリアージの起動方法が案内される

**S2. トリアージ → ワンショット実装**

1. 利用者が Issue 番号を指定してトリアージを開始する
2. 事実主張が仕様書・ルール・コードで裏取りされ、誤りが是正される（承認のうえ）
3. 影響範囲が確定し、全 TASK が列挙される
4. ワンショット実装と判定され、監査コメントが Issue に残る
5. 利用者が確認し、実装工程が起動する
6. 実装工程が修正のための調査 → 実装計画の追記 → 実装 → レビュー → commit → PR 作成を行う

**S3. トリアージ → 要件定義から開始**

1. S2 の 1〜2 と同じ
2. TASK 化できない項目（要件が定まらない等）が残る
3. 要件定義から開始と判定され、監査コメントが Issue に残る
4. 利用者が確認し、forge の要件定義（`start-requirements`）が起動する。合意すべき論点はそこで扱われる

**S4. UI Issue の実装**

1. 実装工程が UI Issue と判定し、修正のための調査を行う
2. 設計段階: Figma 到達性・依存ツール確認 → デザイン仕様書 → 利用者の視覚比較承認 → 実装設計書
3. 実装計画が Issue に追記され、利用者が実装開始を確認する
4. 実装段階: 仕様書に従う実装 → 三点突合レビュー
5. commit → PR 作成

**S5. PR 作成失敗からの再開**

1. 利用者が実装工程を再実行する
2. ブランチと Issue 本文から「PR 作成のみ未達」と推定され、利用者が確認する
3. commit 差分の確認と PR 作成から再開される

## 7. 横断不変条件

| ID   | 内容                                                                                 |
| ---- | ------------------------------------------------------------------------------------ |
| I-01 | forge の既存 skill は改変されない（NFR-01）                                          |
| I-02 | 成果物本文を Issue に複製しない（NFR-02）                                            |
| I-03 | 起票時の利用者記述と是正内容は、実装計画の追記で上書きされない（FNC-01 / FNC-03）    |
| I-04 | 事実主張は実体で確認するまで事実として扱わない（FNC-02）                             |
| I-05 | Issue の書き直しは利用者の承認を得るまで実行しない（FNC-02）                         |
| I-06 | ルート判定に変更量・修正規模を使わない（FNC-02）                                     |
| I-07 | 実装工程は起動経路によらず同じ調査手順を踏む（FNC-03）                               |
| I-08 | 実装工程は Figma 固有の手順を持たず、UI 工程は差し替え可能な契約で呼ばれる（FNC-04） |
| I-09 | 前提条件未充足は静かに失敗させず、明示的に停止する（ERR-01）                         |
