## 1. 解決する問題

現行の msg-review（DES-045 実装済み）は、`--interactive` / `--auto-critical` / `--auto` を **CLI 引数として受理はするが、意味を持たせず警告付きで無視する**（REQ-012 FNC-006「非対応軸の警告付き続行」）。受信モードでは Codex が返す所見をすべて Claude が直接評価し、必要と判断すれば全件修正する。重大度による自動修正範囲の区別が無い。

一方 `/forge:review` は、この3値で自動修正の範囲を明確に区別する:

| 値                      | 挙動                                          |
| ----------------------- | --------------------------------------------- |
| `--interactive`（既定） | 所見を1件ずつ提示し、都度ユーザーに確認       |
| `--auto-critical`       | 🔴 critical のみ自動修正。🟡🟢 は対象外       |
| `--auto`                | 🔴🟡（critical+major）を自動修正。🟢 は対象外 |

`/forge:start-implement` Phase 5 等の既存呼び出し元は `--auto` を明示して `/forge:review` を起動している。msg-review がこの軸を無視したまま `/forge:review` の代替として使われると、**「critical のみ直すつもりが、Claude の裁量で全部直ってしまう」**といった、呼び出し元の意図と異なる挙動になる。本設計はこのギャップを埋める。

**`--interactive` の本来の実装（所見を 1 件ずつ提示して人間の判断を仰ぐ段階的提示）はスコープ外とする**（理由は §2 参照）。

**暫定運用（ユーザー指示・ユーザー責任 [2026-07-19]）**: `--interactive` 本来の実装は次回以降に持ち越すが、それまでの間、この介入軸の仕組み（DES-046 §3.1〜§3.3）を早期に多くのプロジェクトで実運用し問題を洗い出すため、`--interactive` 指定時・介入軸未指定時（既定）は、**内部的に `--auto` と同じ振り分け（🔴🟡自動修正・🟢対象外）を適用する**。これは「Claude が全件を直接評価・修正する」という旧来の既定動作からの意図的な変更であり、`/forge:review` の `--interactive`（本来は段階的提示）とは異なる暫定挙動である。ユーザーが明示的に指示し、責任を負うことを確認済み。`--interactive` 本来の実装（§2「やらないこと」）に着手する際は、この暫定エイリアスを解除する。

## 2. 本設計のスコープ

### やること

- 受信モード（DES-045 §4 UC-2）で、Codex の所見ごとに重大度（🔴/🟡/🟢）を抽出する
- `--auto-critical` / `--auto` が指定された場合、および `--interactive`・介入軸未指定時（暫定的に `--auto` へエイリアス。上記「暫定運用」参照）に、所見ごとに「自動修正する / 対象外として報告する」を振り分ける
- 振り分けロジックを decision 単位でテスト可能な形（純粋関数）に切り出す

### やらないこと（明示的に対象外）

- **`--interactive` 本来の実装（所見を 1 件ずつ提示して人間の判断を仰ぐ段階的提示）**: 本設計では対応しない（上記「暫定運用」により `--auto` へのエイリアスで代替する）。検討時点では旧 review パイプラインの `/forge:present-findings` へ委譲する案があったが、同スキルはセッション基盤（session_dir・findings_state.yaml・`forge:fixer` Agent 起動）に強く結合しており、実際の修正を Claude が直接行う本方式（REQ-012 FNC-004）とは接続できなかった。その後 `present-findings` はパイプラインごと削除されたため、委譲先自体が存在しない。実装する際は**本スキル内で完結させる**（受信本文から `parse_findings.py` で得た所見配列をそのまま AskUserQuestion で提示する）
- **evaluator/fixer Agent の分離**: `/forge:review` の allowlist・単一 finding 起動等の安全境界は導入しない。修正の実施主体は引き続き Claude 自身（REQ-012 FNC-004・v1 の意図的な判断）
- **エンジン軸（`--codex`/`--claude`）への対応**: msg-review は引き続き常駐 Codex 固定
- **`/forge:review` を置き換える／切り替える判断（TBD-001）そのもの**: 本設計はその判断とは独立に、msg-review 単体の機能ギャップを埋めるものである。TBD-001 の結論（置き換えるか・共存するか）を左右しない
- **常駐 Codex + cmux 依存の解消**: DES-045 §3.8 の既知の限界（環境依存のpush起床）はそのまま

## 3. 設計

### 3.1 所見の重大度パース（新規スクリプト `parse_findings.py`）

Codex の返信本文は自由記述markdown（DES-045 §3.4 の契約: 重大度マーカー + `ファイルパス:行` を含む自由記述、厳密なJSON構造ではない）。実際の返信例（本セッションでの実測）:

```
1. 🔴 critical `path/to/file.py:59-60` — 説明...
   （複数行に渡る場合あり）

2. 🟡 major `path/to/other.sh:32-37` — 説明...

REVIEW_RESULT: findings
```

`parse_findings.py` は以下を行う:

1. 本文を行単位に走査し、**行頭**（箇条書き記号 `-`/`*` または番号付け `1.` を除いた直後）に severity マーカー（🔴/🟡/🟢）がある行を「新しい finding の開始」とみなす。行の途中・引用・説明文中に偶然出現するマーカー（例: 「概要: 🟡 major の基準を参照しました。」）は finding の開始として扱わない（実 Codex レビューで発見。誤検出の具体例が実際に指摘された）
2. **コードブロック内は finding 開始として扱わない**: 返信形式の例や既存所見の引用をコードブロックで示す際、その中の severity マーカーを実在しない finding として誤抽出しないため（実 Codex レビューで発見）。fenced code block（\`\`\` または ~~~ で囲まれた範囲）はフェンス行を追跡してスキップし、インデントコードブロック（行頭4スペースまたはタブ、Markdown のもう一つの標準的なコードブロック記法）は `.lstrip()` する前の生の行を見て判定する（`.lstrip()` 後に判定するとインデントが失われ誤検出する。実 Codex レビューで発見）。いずれも finding 開始判定をスキップするのみで、既存 finding の本文継続としては保持する
3. 次の finding 開始行（または完了宣言行）までを、その finding の本文として束ねる
4. 各 finding を `{"severity": "critical"|"major"|"minor", "text": "..."}` の dict として抽出する

```
python3 parse_findings.py --body-file <path>
```

出力（標準出力に単一 JSON）:

```json
{
  "findings": [
    {
      "severity": "critical",
      "text": "🔴 critical `path/to/file.py:59-60` — 説明..."
    },
    {
      "severity": "major",
      "text": "🟡 major `path/to/other.sh:32-37` — 説明..."
    }
  ]
}
```

**フォーマット逸脱への fail-closed 対応**: 完了宣言行が `REVIEW_RESULT: findings`（指摘ありの宣言）であるにもかかわらず finding 開始行が一つも見つからない場合、本文全体を `severity: "unclassified"` の単一 finding として返す（`findings: []` を返して所見を黙って落とさない。実 Codex レビューで発見: 空リストを返すと、受信モードはこの所見の存在にすら気づけず、対象外として報告することさえできなかった）。`REVIEW_RESULT: approved`（指摘なしの宣言）の場合はこの fallback を適用しない（承認宣言と矛盾するため、本文中のマーカー無し説明文を偽の finding として抽出することを避ける）。`gate_findings.py` の決定表は `critical`/`major` のみを自動修正対象とするため、`unclassified` は両モードで常に `excluded` に振り分けられ、受信モードは「対応しない（理由: 重大度を判定できませんでした。人間の確認が必要です）」として報告する。

### 3.2 振り分けロジック（新規スクリプト `gate_findings.py`）

```
python3 gate_findings.py --findings-json '<parse_findings.py の出力>' --mode <auto-critical|auto>
```

決定表:

| mode            | critical | major              | minor              |
| --------------- | -------- | ------------------ | ------------------ |
| `auto-critical` | 自動修正 | 対象外（報告のみ） | 対象外（報告のみ） |
| `auto`          | 自動修正 | 自動修正           | 対象外（報告のみ） |

`--interactive`（既定）指定時・介入軸未指定時も、暫定運用（§1）により `--mode auto` で本スクリプトを呼ぶ（ユーザー指示・ユーザー責任 [2026-07-19]。「Claude が全件を直接評価・修正する」という旧来の既定動作は、本来の段階的提示を実装するまでの間、暫定的に停止する）。

出力（標準出力に単一 JSON）:

```json
{
  "auto_fix": [/* finding dict の配列 */],
  "excluded": [/* finding dict の配列（対象外として報告のみ）*/]
}
```

この関数は純粋（決定表のみ、I/O なし）であり、`docs/rules/implementation_guidelines.md`「決定論的な処理はスクリプト化する」に従い単体テストで全パターン（2 mode × 3 severity）を検証する。

### 3.3 SKILL.md 受信モードへの統合（DES-045 §4 UC-2 の変更）

現行の受信モード Step 2a に以下を追加する。`--auto-critical`/`--auto` 指定時に加え、`--interactive`・未指定時も暫定運用（§1）により `--auto` としてこの振り分けを実行する（ユーザー指示・ユーザー責任。次回以降、本来の段階的提示に置き換え予定）:

1. `parse_findings.py` で所見を重大度ごとに分解する
2. `gate_findings.py` で `auto_fix`（severity に基づく自動修正**候補**） / `excluded`（severity によるモード範囲外・`unclassified`）に振り分ける
3. **`auto_fix` は候補であり確定ではない [MANDATORY]（ユーザー指示による明確化 [2026-07-19]）**: `auto_fix` の各所見について、DES-045 §3.4 の所見評価（review_criteria に基づく妥当性判断）を必ず適用する。severity による自動修正対象範囲に含まれることは、Codex の指摘を無条件に採用してよい理由にはならない。評価の結果、以下の3群に分ける:
   - **`confirmed_fix`**: 妥当と判断し、影響範囲・代替案・よりよい方法を検討したうえで実施内容を決めた所見
   - **評価でドロップした所見**（不要な指摘・Codex の勘違い）: severity に関わらず修正しない。勘違いの場合は次ラウンドで Codex に確認・再考を求めてもよい
   - `excluded`（`gate_findings.py` の出力そのまま）
4. **終了判定 [MANDATORY]**: `confirmed_fix` が空の場合、修正・再レビュー依頼を行わず**新設の Step 2c（未対応所見を残した完了（承認以外））**へ進む。**この分岐が無いと無限往復ループに陥る**（実 Codex レビューで発見）: 対応しなかった所見を残したまま再レビューを依頼すると、Codex が同じ所見を毎回指摘し続け、`REVIEW_RESULT: findings` から抜け出せず往復上限に達するまで往復し続ける。`confirmed_fix` の空判定はこちら（Claude/msg-review）側の決定論的な判断であり、Codex がこちらの意図を汲むかどうかに依存しない、自己完結した停止条件である。**Step 2c は Step 2b（`REVIEW_RESULT: approved` による承認完了）とは明確に区別する**（実 Codex レビューで発見: Codex はこの時点でなお `REVIEW_RESULT: findings` と判定しており、承認と同一視して報告すると、対応していない所見が残っている事実を人間が見落とす。REQ-012 FNC-005 に完了条件の第3項として明記済み）。Step 2c の要約報告は Step 2b の内容に加え、Codex がなお指摘ありと判定していること・対象外所見の一覧と理由・対応するにはモード変更が必要である旨を明記する
5. `confirmed_fix` が空でない場合のみ、`confirmed_fix` の所見について Claude が直接修正を実施する（既存 FNC-004 のまま）。修正しなかった所見は、severity 除外（`excluded`）は「対応しない（理由: 重大度が現在のモード `<mode>` の自動修正範囲外）」（`severity` が既知の場合）または「対応しない（理由: 重大度を判定できませんでした。人間の確認が必要です）」（`unclassified` の場合）、評価でドロップした所見は「対応しない（理由: 検証の結果、該当しないと判断）」または具体的な確認事項として、修正報告に明記する
6. 修正しなかった所見が残る場合、再レビュー依頼の本文に「対応しなかった所見は今回のモードでは意図的に対象外としています。今回対応した所見が正しく解消されているかのみご確認ください」を明記する（Codex への協力依頼であり、これ自体は停止条件の根拠ではない。実際の停止条件は §3.3-4 の終了判定）
7. 修正報告メッセージ・再レビュー依頼の送信手順は既存の手順（DES-045 §3.4）のまま

### 3.4 依頼モードの変更点

- **既定値の暫定変更 [ユーザー指示・ユーザー責任]**: 介入軸未指定時（既定）は、暫定運用（§1）に従い `--auto` と同じ振り分けを適用する。`--interactive` を明示指定した場合も同様に `--auto` へエイリアスする
- 「引数解釈結果」定型表の「無視したフラグ」欄からは介入軸を全て除外する（`--interactive`/`--auto-critical`/`--auto` のいずれも、暫定運用により実際に意味を持つため）。エンジン軸 `--codex`/`--claude` のみ引き続き「無視したフラグ」欄の対象
- Codex への依頼本文（`build_review_request.py`）は変更しない。介入軸は受信側（Claude）の判断にのみ影響し、Codex に伝える必要はない

## 4. 要件定義書への影響

- REQ-012 FNC-006 の「非対応軸の警告付き続行」から介入軸（`--interactive`/`--auto-critical`/`--auto`）を全て除外する改訂が必要（エンジン軸 `--codex`/`--claude` のみ「無視して続行」の対象として残る）。あわせて、`--interactive`・未指定時の既定動作が暫定的に `--auto` へエイリアスされている旨（ユーザー指示・ユーザー責任、次回以降に本来の段階的提示へ置き換え予定）を明記する
