# ADR-068 可用性検査を決定論的判定に限り、画面推測による生存確認を廃止する

| 項目     | 値                                                                   |

| ADR ID   | ADR-068                                                              |
| Status   | accepted                                                             |
| 決定日   | 2026-08-04                                                           |
| 関連設計 | REQ-012 FNC-003 / FNC-007 / FNC-008、DES-045、ADR-061、forge:ADR-067 |

## 1. コンテキスト

forge:ADR-067 が全レビューバックエンドに可用性検査を義務づけた。バックエンドは自身が利用可能かと、不足している前提を返す。本バックエンドはその実装が未了である。

本サブシステムには、これとは別に「Codex が生きているかを cmux ペインの画面表示から推測する」設計（旧 DES-048、未実装）が存在していた。相手が応答できない状態のまま待機予算いっぱい（最大 1620 秒）ブロックすることを避け、待機を短縮する目的だった。

両者は同じ場面を扱いながら**逆の動作**を指示していた。前者は「使えないと判定したら依頼を送らない」、後者は「判定だけで応答機会を奪わず、必ず送信してから短縮待機で確認する」。後者がこの立場を採ったのは、実 Codex レビューで「cmux の不在は Codex の不在を意味しない」と指摘され、当初案（cmux が無ければ送信ごとスキップ）を撤回した経緯による。

**しかし相手セッションの常駐は、既に決定論的に判定できていた。** `find_codex_pane.py` が `found` を返す条件は、ペインの存在ではなく、**surface にアタッチされた実プロセス名が Codex 実行バイナリに一致すること**である（`cmux top --processes` による一次情報）。この判定は推測を含まない。

したがって、画面表示からの推測が判定材料を追加する余地はない。旧 DES-048 が定めていた 2 つの判定規則——素のシェルプロンプトの検出、Claude Code の UI の検出——はいずれも、Codex プロセスが稼働している surface では成立しない。残る到達経路は cmux の読み取り自体が失敗した場合のみであり、それは cmux 側の一時障害であって相手の応答可能性を示す信号ではない。

## 2. 決定

### 2.1 判定を確実性で 3 軸に分け、可用性検査には決定論的判定のみを含める

前提の判定を次の 3 軸に分離する。**軸ごとに独立したスクリプトで判定し、1 つのスクリプトに畳まない。**

| 軸                              | 判定の性質                                  | 扱い                                                     |
| ------------------------------- | ------------------------------------------- | -------------------------------------------------------- |
| A. 起床手段（cmux）の可用性     | 決定論（コマンドの実在）                    | 可用性検査に含める                                       |
| B. 相手セッションの常駐         | 決定論（稼働中の Codex プロセスの直接確認） | 可用性検査に含める                                       |
| C. 相手が実際に応答できる状態か | 推測（画面表示からの間接的な判断）          | **前提の判定に使わない**（§2.2。起床の安全ゲートは別件） |

**分離する理由は将来の可用性の組み合わせが変わることである。** 現時点では A と B の両方が必要だが（起床手段が無ければ、相手が常駐していてもターンを起こす契機が生まれず往復が成立しない）、将来 A を必要としない起床経路が成立すれば B のみで足りるようになる。判定が 1 つのスクリプトに畳まれていると、この変化に対して判定ロジックの解体が必要になる。

**不足している前提は個別に返す**（forge:ADR-067 §2.1）。A と B のどちらが欠けているかを区別して返し、「使えません」に畳み込まない。

**可用性検査は相手に作用しない**。依頼を送らず、相手のターンも起こさない。本体は複数の候補バックエンドを順に検査するため、検査自体が**相手の状態**を変えてはならない。

> **禁止範囲の訂正（2026-08-04）[MANDATORY]**: 本項は当初「読み取りのみで行い」と書かれていた。この過大な禁止が実害を生んだ——バックエンド自身の初期化（`ensure_codex_hook.py` が用意する Codex 側フック登録と非追跡 symlink）を検査より前に置けないと解釈され、可用性検査が**未初期化の状態**を判定した結果、新規クローン・新規 worktree で初期化に到達できず `/forge:review` が恒久的に fail closed した。禁止すべきは相手（レビュアー）への作用であり、**自分の初期化は検査の前提**である。順序は常に初期化 → 検査 → 送信とする（DES-045 §3.5.2「初期化を済ませてから検査する」/ REQ-012 FNC-003）。初期化は冪等で、相手にも他候補のバックエンドにも作用せず、人間由来のファイルを上書きしない（競合は報告のみ）。

### 2.2 軸 C の判定を持たず、旧 DES-048 を廃止する

相手の応答可能性を画面表示から推測して**前提の判定に使う**仕組みを設けない。旧 DES-048（未実装）は文書ごと廃止する。

**既存の画面読み取りは対象外である**。push 型起床は起床テキストを注入する直前に対象ペインの画面を読み、実行中を示す表示を検出したら注入を見送っている（DES-045 §3.8）。これは「相手が使えるか」を判定するためではなく、**注入によって相手の作業を壊さないための安全ゲート**であり、本決定はこれを変更しない。廃止するのは、前提の判定という別の目的で画面表示を根拠にすることである。

決め手は §1 のとおり、**軸 B が実プロセスを直接確認しており、その先の画面推測が判定材料を追加しない**ことである。旧設計の判定規則は Codex プロセスが稼働している surface では成立せず、到達しない分岐と、それを検証する到達しないテストを抱えることになる。

**待機短縮の効果も実際には生じない**。旧設計は「常駐は確認できないが応答も得られない」状態を短縮の対象としていたが、常駐が決定論的に確認できる以上、この状態は可用性検査の段階で利用不可として分離される。可用性検査を通過したラウンドで待機が長引くのは、相手が別の作業でターンを実行中の場合であり、これは push 起床側が画面上の実行中表示を見て見送りとして扱っている（DES-045 §3.8）。

旧 DES-048 が代替として設計していた**ローカルレビュー経路**（応答が得られないとき Claude 自身がその場で対象を点検する）も廃止する。この経路は同文書が自ら「独立した別モデルによるチェックを経ない」「二重チェックの効果を持たない」と認めていた。レビューを求める利用者が得たいのは独立した第二の視点であり、同一の Claude による自己点検はそれを満たさない。完了報告で「独立レビューを経ていない」と明示する設計だったが、明示は代替にならない——利用者は依頼した独立レビューを得られないまま完了報告を受け取る。

前提を満たすバックエンドが 1 つも無い環境での成立は、本体側のバックエンド解決に委ねる。外部依存を持たない実行主体を独立したバックエンドとして候補に加えれば、隔離コンテキストで動くため独立性を保てる（forge:ADR-067 §2.2）。

この廃止に伴い、ローカルレビュー経路の存在を前提とした付帯機構——遅延返信の取り違えを防ぐための claim/lease 記録——も不要になる。返信を受け取る主体が受信モードだけになり、二重処理の起点が存在しない。

## 3. 検討した代替案

| 代替案                                                                         | 棄却理由                                                                                                                                            |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 軸 A・B・C をまとめて 1 つの可用性検査スクリプトで判定する                     | 確実性の異なる判定が混ざり、推測を根拠に依頼を止めることになる。将来 A が不要になったときに判定ロジックの解体が必要になる                           |
| 軸 C を可用性検査に含め、応答不可と推測したら依頼を送らない                    | 推測の偽陽性で、応答できる相手の機会を奪う。旧 DES-048 が実 Codex レビューを経て撤回した誤りの再導入にあたる                                        |
| 軸 C を可用性検査の外に置いたまま、待機短縮のために残す                        | 軸 B が実プロセスを確認するため、旧設計の判定規則はいずれも到達しない。到達しない分岐とテストを保守対象として抱えるだけで、待機短縮の効果も生じない |
| 軸 C の判定規則を作り直して残す（画面の無変化の継続等を新たな判定材料にする）  | 稼働中の Codex が別の作業でターンを実行中であることは push 起床側が既に検出して見送っている。同じ状態を二重に判定する仕組みを新設する理由がない     |
| 可用性検査を設けず、ラウンド実行の失敗だけで済ませる                           | forge:ADR-067 が契約の要求として定めた検査を実装しないことになる。かつ決定論的に判明する不成立（cmux 不在・相手の不在）でも待機予算を消費する       |
| ローカルレビュー経路を残し、外部依存を持たないバックエンドと併存させる         | 同じ「代替手段」が 2 系統になる。一方は独立性を持たず、利用者はどちらで走ったかによって承認の意味が変わることを追う必要が生じる                     |
| ローカルレビュー経路を残したまま、独立性の欠如を完了報告での明示のみで担保する | 明示は独立レビューの代替にならない。利用者は依頼したものを得られないまま完了を受け取る                                                              |

## 4. 影響

**得られるもの**

- 決定論的に判明する不成立が、待機予算を消費せず送信前に確定する
- 起床手段と相手の常駐が独立に判定されるため、起床経路が将来変わっても判定の解体が不要になる
- 推測に基づく判定を持たないため、到達しない分岐・到達しないテストを抱えない
- Codex が使えない環境での代替が、独立コンテキストによるレビューとして成立する（自己点検に落ちない）
- 不足している前提が個別に返るため、利用者が何を用意すればよいか判断できる

**失うもの・新たに生じる制約**

- 軸 A・B のいずれかが欠ける環境では、本バックエンドは依頼を送らずに不可を返す
- 判定スクリプトが軸ごとに分かれるため、可用性検査はそれらを集約する層を持つ
- 外部依存を持たないバックエンドが実装されるまでの間、前提を満たさない環境ではレビューが成立しない（本体の fail closed による）。縮退手段を持たない
- 軸 B の判定はプロジェクトルートの作業ディレクトリに紐づく surface の発見に依存する。相手セッションが発見条件から外れた構成で常駐している場合、常駐していても不可と判定されうる
- 可用性検査の通過後に相手が応答できなくなった場合（検査からラウンド実行までの間に終了した等）は、従来どおり待機予算を消費してから失敗が確定する。この経路の短縮手段は持たない
