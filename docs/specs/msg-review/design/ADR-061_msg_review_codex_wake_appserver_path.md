# ADR-061 Codex 起床経路の複線化（app-server 経路の追加）

> **本文書のスコープ**
>
> - **定めること**: 常駐 Codex セッションのターンを起こす手段（push 型起床）を、どの方式で提供するかの選択
> - **定めないこと**: メッセージの送受信・新着検知・返信ヒント・停止条件・配信整合性。これらは通信基盤の責務であり [REQ-006](../../msg-sys/requirements/REQ-006_codex_review_messaging.md) が定める
> - **msg-sys との関係**: 本決定は msg-sys の要件・設計・実装を変更しない。[REQ-006](../../msg-sys/requirements/REQ-006_codex_review_messaging.md) §2.2 は push を明示的にスコープ外としており、起床は通信基盤ではなく**往復の即時性を必要とする応用側の責務**である。本文書は msg-sys の要件を参照するが、改訂は行わない

## 1. コンテキスト

msg-sys の新着検知は pull 型である。Codex 側・Claude 側いずれの Stop フックも、**相手自身のターンが終わったとき**にしか発火しない（[REQ-006](../../msg-sys/requirements/REQ-006_codex_review_messaging.md) INT-002 / INT-003）。

往復のために常駐させた専用 Codex セッションでは、人間が操作しない限りターンが終了する契機が発生しない。この状態では依頼が配信されないまま滞留する。FNC-004 が求める「所見の受領・修正・再依頼の往復」は、依頼を送るたびに相手がターンを終えることで初めて成立するため、この滞留は往復そのものを止める。

[DES-045](DES-045_msg_review_skill_design.md) に記録された実測値がこの帰結を示している。待機が約 7 時間に達した事例、往復 2 ラウンド目以降の恒常的な停止、1 レビューで 4 回の手動起床を要した事例である。いずれもエラーにならず静かに止まるため、人間が気づくまで検知されない。

[DES-045](DES-045_msg_review_skill_design.md) はこの限界に対し push 型起床を導入した。当時 agmsg の app-server ブリッジ方式を認識したうえで、「実運用環境（cmux 端末多重化ツール）が既に提供する同等の機能で軽量に実現する」として cmux を選んでいる。当時の判断としては妥当である。

**問題は、その経路が 1 つしか無いことにある。** cmux が無い環境では起床が `skipped` となり、push 起床という手段が丸ごと失われる。cmux は端末多重化ツールという特殊な前提であり、これを満たさない環境では往復が上記の停止状態に戻る。

### 1.1 実測で確認した事実（2026-08-02、codex-cli 0.146.0）

- Codex CLI 自身が app-server サブコマンドを持ち、`--listen`（`stdio://` 既定 / `unix://` / `ws://IP:PORT` / `off`）で JSON-RPC の口を開ける。これは OpenAI 公式 CLI の機能であり、第三者ツールの発明ではない
- プロトコル定義を CLI 自身から生成できる（`generate-json-schema`）。クライアントが送れる 127 メソッドに `thread/loaded/list`・`turn/start`・`turn/steer`・`thread/inject_items`・`process/spawn` が含まれる
- TUI は `--remote <ADDR>` で既存の app-server に接続する。**起動後に接続する経路は無い**
- `app-server daemon` は公式インストーラ版の standalone install を要求し、Homebrew 版では起動できない
- `app-server proxy` は生バイト中継であり、WebSocket アダプタではない（終了コード 0・出力なしを実測）
- `unix://` トランスポートは素の改行区切り JSON-RPC を拒否する（接続クローズを実測）。実体は WebSocket-over-UDS である
- 以上より、クライアント側に RFC 6455 の実装が必要になる。ただし Python 標準ライブラリで完結し、Node・サードパーティ依存は生じない

## 2. 決定 ⚠️失効（ADR-063 が独立バックエンド化を採用）

> **本案は採用されなかった。** 以下は提案として記録したものであり、一度も有効な決定になっていない。失効マーカーは代わりに ADR-063 が採られたことを示すものであって、本案が一時期有効だったことを意味しない。

**push 型起床を、単一実装から複数経路を選択できる構造に改め、Codex 向けに app-server 経路を追加する。cmux 経路は削除せず維持する。**

これは DES-045 の撤回ではなく、その上への追加である。

- 起床の入口を経路の選択点とする。既存の契約——best-effort であること、構造化された結果を返すこと、起床の失敗が待機の正しさを壊さないこと——は一切変更しない。新経路はこの契約をそのまま満たす
- 選択順序は「app-server が利用可能なら優先、次に cmux、いずれも不可なら従来どおり見送り」とする。app-server を優先する理由は、端末の入力欄を書き換えないため下書き破壊・作業割り込みのリスクが無く、cmux send を nudge 用途に限定していた理由がそのまま解消されるためである
- app-server 経路は Codex 専用とする。エージェント非依存の汎用性は cmux 経路が引き続き担う
- TUI を app-server に接続させるため、Codex 起動をラップするシムを導入する
- WebSocket クライアントは Python 標準ライブラリで自前実装する
- `app-server daemon` には依存しない
- **設定不備と「無効化」を同じ挙動にしない**。シムやブリッジが壊れている場合は警告を出し、沈黙して素通りさせない
- **msg-sys の要件・設計・実装を変更しない**。起床は msg-sys のスコープ外であり、本決定は応用側で完結する

## 3. 検討した代替案

| 代替案                                           | 棄却理由                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起床を msg-sys の要件として持たせる              | [REQ-006](../../msg-sys/requirements/REQ-006_codex_review_messaging.md) §2.2 が「push 型通知の実装」を v1 のスコープ外として明示し、§1.2 に棄却理由も記録している。msg-sys は「相手がターンを終えたら配信する」ところまでを引き受け、相手にターンを終えさせることは引き受けない。往復の即時性を必要とする応用側が持つのが正しい |
| cmux 経路を app-server 経路で置き換える          | cmux 経路は端末入力欄への注入であり、相手のエージェント種別を問わない。Codex 以外が相手のときの唯一の push 手段であるため、Codex 専用の app-server で置き換えると汎用性を失う                                                                                                                                                   |
| agmsg を外部依存として採用する                   | msg-sys:REQ-006 NFR-002「外部ツール非依存」[MANDATORY] が agmsg 等の外部プラグインを実行時依存として導入することを禁じている。本 SKILL は msg-sys 上に成り立つため同じ制約を受ける。加えて下流ユーザーに agmsg 本体と Node.js の導入を要求することになり、配布方針とも衝突する                                                  |
| MCP（`codex mcp-server`）へ寄せる                | 常駐セッションが不要になり起床問題自体は消えるが、レスポンスのトークン上限と、バックグラウンド化できないことによる長時間レビューのタイムアウトという未検証リスクを抱える。また Claude Code 側の MCP サーバはツール群を公開するのみでモデルの推論を呼べず、双方向性が非対称になる                                                |
| `app-server daemon` を利用する                   | 公式インストーラ版の standalone install を要求し、Homebrew 等の他のインストール方法を排除する。配布物が利用者のインストール手段を縛ることになる                                                                                                                                                                                 |
| `app-server proxy` に WebSocket を肩代わりさせる | proxy は生バイトを中継するのみでハンドシェイクを行わないことを実測で確認した                                                                                                                                                                                                                                                    |

## 4. 影響

### 4.1 得るもの

- cmux 非導入環境でも push 起床が成立し、待機予算いっぱいのタイムアウトと手動起床が不要になる
- 入力欄を書き換えないため、下書き破壊・作業割り込みのリスクが消える。cmux 経路が必要としていた作業中判定などの安全ゲートは、app-server 経路では不要になる
- プロトコル定義を Codex 自身から生成できるため、インターフェース変更の検出を画面パースなどの推測に頼らずに済む

### 4.2 失うもの・新たに生じる制約

- Codex の起動をシム経由にする必要があり、利用者の PATH またはシェル関数への介入を伴う
- app-server は `[experimental]` と明記されたインターフェースであり、破壊的変更が起きうる。その追随コストを継続的に負う
- WebSocket クライアントの自前実装を保守対象として抱える
- app-server 経路は Codex 専用であり、他のエージェントには適用できない。Gemini 等を将来輪に加える場合は別途手当が要る（Gemini には現状 push の口が存在しない）
- TUI に後から接続する経路が無いため、シムを経由せずに起動された Codex には app-server 経路が効かない。その場合は cmux 経路、または従来どおりの待機へ縮退する

### 4.3 未検証の前提

本案が採用に至らなかった一因でもある。以下は未検証のまま残った。

- TUI が `--remote` で app-server に接続し、`thread/loaded/list` に現れること
- 0.146 の `--remote` が `unix://` を受けるか、`ws://` 限定か

いずれも **TUI の対話起動を人手で行わないと確認できない**項目である。[ADR-063](../../codex-appserver/design/ADR-063_codex_appserver_as_review_backend.md) が採る構成ではバックエンド自身がスレッドを持ち TUI を介さないため、この 2 点は前提ごと不要になる（検証も自動化できる）。

### 4.4 DES-061 との同番号を解消しない

本 ADR の番号 061 は `docs/specs/forge/design/DES-061` と同番号である。`spec_format.md`「新規採番では発生させない」に反するが、**改番による波及リスクを避けるため個別の例外として現状維持とする（利用者判断）**。同文書の「既存の同居の扱い」による過去事例の容認とは別の判断である。
