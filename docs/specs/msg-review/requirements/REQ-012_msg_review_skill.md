# REQ-012 msg-review レビューバックエンド要件定義書

## 1. 概要

msg-review は、常駐 Codex セッションとレビュー 1 ラウンドを同期的に往復する `/forge:review`
バックエンドである。前提を検査し、依頼を送信して同一ターン内で返信を待ち、共通書式を解釈した
`approved` / `findings` / `failure` と所見配列を本体へ返す。

対象解決、依頼本文の組み立て、所見の評価、修正、再レビューの判断、完了判定、要約報告は
`/forge:review` 本体の責務であり、msg-review は行わない。

## 2. スコープ

### 2.1 対象

- ラウンド実行前の可用性検査
- msg-sys を介した依頼の送信、相手ターンの起床、返信待機
- msg-review ワイヤヘッダの付加と任意再掲時の検証
- 共通 parser による応答の 3 値判定と所見配列化
- 本体からの終了通知の受理
- 利用者が明示的に求めた場合の履歴復元

### 2.2 対象外

- レビュー対象とレビュー種別の解決
- 共通依頼本文の組み立て
- 所見の妥当性評価、修正対象の選別、修正の実施
- ラウンド継続とレビュー完了の判定
- 未解決所見や修正内容の要約報告
- Codex セッションの起動と管理
- タイムアウト後の遅延返信を契機とする自動再開

## 3. 機能要件

### FNC-001: 可用性検査 [MANDATORY]

本体からの可用性検査要求に対し、本バックエンドが利用可能かと不足している前提を返すこと。

- バックエンド自身の初期化を済ませてから検査すること
- 依頼を送信せず、相手のターンを起こさないこと
- 起床手段、相手セッションの常駐、設定の健全性を独立した軸として判定すること
- 不足を「利用不可」の 1 件へ畳み込まず、軸ごとに理由と対処を返すこと
- 判定できた構造化結果を終了コードだけで判定不能へ畳み込まないこと
- 不成立時にバックエンド内部で別の実行主体へ切り替えないこと

### FNC-002: 同期ラウンド実行 [MANDATORY]

本体から `review_id`、ラウンド番号、レビュー種別、共通依頼本文を受け取り、1 ラウンドを
同一ターン内で完結させること。

1. 送信前の設定検査を行い、不成立なら依頼を送らず `failure` を返す
2. 共通依頼本文へワイヤヘッダを付加する
3. 依頼を送信し、相手ターンを起床して返信を待機する
4. 返信を取得した場合は共通 parser で解釈して結果を返す

返信を期待する送信は、ヘッダ付加、送信、起床、待機を単一の実行経路にまとめること。送信だけ、
起床だけ、待機だけを個別に実行する経路をラウンド実行に持たないこと。

### FNC-003: ラウンド結果 [MANDATORY]

ラウンド結果は次の 3 値とする。

| 判定       | 意味                           |
| ---------- | ------------------------------ |
| `approved` | 有効な承認応答を受信した       |
| `findings` | 有効な所見応答を受信した       |
| `failure`  | ラウンドを成立させられなかった |

`failure` は利用者が読める理由を伴うこと。前提不成立、送信失敗、待機タイムアウト、ワイヤヘッダ不正、
共通書式不正を `approved` や所見 0 件の `findings` へ畳み込まないこと。

各所見は重大度と、「ファイルパス + 行番号」または「位置未確定の明示」を持つこと。重大度や位置を
推測で補完せず、欠落時は共通 parser の契約違反として `failure` を返すこと。

完了宣言行は応答の最終有効行に厳密に 1 行だけ存在すること。複数宣言、宣言後の本文、
`findings` 宣言に対する重大度マーカー付き所見の欠落は `failure` とすること。

### FNC-004: ワイヤプロトコルとスレッド連鎖 [MANDATORY]

msg-review は、送信直前に共通依頼本文の先頭へ次のワイヤヘッダを付加すること。

```text
[msg-review] <種別> review_id=<review_id> round=<n>
```

- 本体から受け取る共通本文はワイヤヘッダを含まないこと
- 既に正規ヘッダを含む本文への二重付加を拒否すること
- 初回依頼以外の送信は、直前に受信したメッセージ ID を `in_reply_to` に設定すること
- スレッド判定は `in_reply_to` の連鎖を主とし、ヘッダは連鎖の起点特定に使うこと
- レビュアーは返信へヘッダを再掲しなくてよいこと
- 返信にヘッダが再掲された場合は、種別、`review_id`、ラウンド番号の一致を検証してから除去すること
- 不正なヘッダや現在のラウンドと一致しないヘッダは `failure` とすること

ワイヤ識別子 `[msg-review]` は msg-sys の DB に永続化された履歴を復元するため、変更しないこと。

### FNC-005: タイムアウト [MANDATORY]

待機予算内に返信が得られなかった場合は、確定した `failure` として返すこと。

- 非同期往復へ切り替えたように見せて本体を先へ進めないこと
- タイムアウト後の遅延返信を Stop フックで自動処理しないこと
- 遅延返信を契機に msg-review を自動再開しないこと
- 経過時間、`review_id`、最後に観測した依頼の既読状態、起床失敗があればその理由を診断情報として返すこと

遅延返信は msg-sys の DB に残る。利用者が明示的に履歴復元を求めた場合に限り確認可能とする。

### FNC-006: 終了通知

本体から `review_id` を伴う終了通知を受理すること。本バックエンドはレビューをまたいで解放を要する
資源を持たないため、同一 `review_id` に対する重複通知も冪等に受理すること。

### FNC-007: 履歴復元の任意拡張

利用者または本体が `review_id` を明示して履歴復元を求めた場合、msg-sys の永続記録から当該レビューの
往復履歴と解決状態を返すこと。

- 履歴復元はラウンド実行、可用性検査、終了通知の成立条件にしないこと
- 履歴復元をラウンドの自動再開として扱わないこと
- 対象スレッドはワイヤヘッダで起点を特定し、`in_reply_to` の連鎖で抽出すること
- 既存 DB 履歴を変更せず、独自の永続記録を追加しないこと
- 履歴が存在する場合は `status: "ok"` と履歴を返すこと
- 対象が存在しない場合は `status: "not_found"` と理由を返し、空履歴へ畳み込まないこと

### FNC-008: 相手ターンの起床

返信を期待する送信ごとに、常駐 Codex セッションのターンを起こすこと。

- 起床手段は cmux とすること
- 起床結果を `sent` / `skipped` / `failed` で区別すること
- 起床は best-effort とし、起床結果だけで待機を中止しないこと
- セッションの新規起動や管理を行わないこと

### BL-001: 監査可能性

レビューの往復内容は msg-sys の既存 DB 履歴で監査できること。msg-review はこれと重複する独自の
永続記録を持たず、既存履歴、ワイヤヘッダ、`in_reply_to` の連鎖を維持すること。

## 4. 非機能要件

### NFR-001: 通信基盤との境界 [MANDATORY]

msg-review は msg-sys の公開 CLI と共通モジュールを利用し、DB パス導出、送受信、既読化、
スレッド抽出の規則を独自に再実装しないこと。

### NFR-002: 実装依存

msg-review に付随する Python スクリプトは標準ライブラリのみで実装し、単体テストを持つこと。

### NFR-003: 失敗の可視性

前提不成立、送信失敗、タイムアウト、応答契約違反をフォールバックで隠さず、本体が利用者へ報告できる
構造化結果として返すこと。
