## 1. 背景

### 1.1 現状の問題

msg-sys（msg-sys:REQ-006 / msg-sys:DES-034）は、Claude と Codex がターン終了時の Stop フック起点でメッセージを非同期に往復する通信基盤を提供し、返信ヒント付き配信により人間の仲介なしに往復チェーンが成立することを実機検証済みである。

しかし msg-sys が提供するのは通信路のみであり、この上で**レビューを行うための入口と手順**は未定義である。現状、Codex にレビューを依頼するには人間（または Claude が都度アドホックに）以下を手作業で行う必要がある。

- レビュー対象（ファイル・差分）の特定と依頼文の組み立て
- `send.py` による送信と、往復の各ターンでの所見の解釈・修正・再依頼
- 「どこまで往復したら終わりか」の判断

この手順が定型化されていないため、依頼のたびに内容がぶれ、レビュー品質・完了判定が再現しない。

### 1.2 既存 `/forge:review` との関係

Codex を `codex exec` の **stdin を閉じた単発・非対話モード**で毎回起動する方式では、Codex は呼び出しごとに使い捨てられ、前回のレビューで何を指摘し、Claude がどう修正したかという文脈を保持しない。この結果、「レビュー→修正→再レビュー」を繰り返す運用は毎回ゼロから文脈を再構築するコストを払う。

msg-review はこれの**代替経路**として、常駐 Codex セッションとの継続対話でレビューを行う SKILL である。

- v1 では `/forge:review` パイプライン（session_dir / refs.yaml / findings JSON / evaluator / fixer）とは接続しない独立 SKILL とする
- `/forge:review` のバックエンドの 1 つとして統合する（REQ-013 FNC-1318 / ADR-060）。本サブシステムはレビュアーとの往復・前提検査・セッション復旧・ワイヤプロトコルを担い、依頼の組み立てと所見の処理は `/forge:review` 本体に置く

## 2. スコープ

### 2.1 対象とする範囲（v1）

- レビュー対象（未 commit 差分・現ブランチの全変更・指定ファイル群のいずれか）を指定して Codex へのレビュー依頼を定型手順で開始できること
- Codex から返る所見の受領・評価・修正・再レビュー依頼の往復を、msg-sys の返信チェーン上で完結できること
- **所見の評価（妥当性判断）・要修正判断・修正の実施を、Claude（オーケストレーター自身）が直接行うこと（FNC-004）**。これが本 SKILL の中核スコープである
- レビューの完了（承認または往復上限到達）を判定し、人間に結果を要約報告すること

### 2.2 v1 で明示的に除外する範囲

- **`/forge:review` パイプラインとの統合**: session_dir / refs.yaml / findings JSON / evaluator / fixer のいずれとも接続しない
- **evaluator / fixer の Agent 起動**: 所見の評価・修正のために専用の evaluator/fixer Agent を起動しない（評価・修正そのものは §2.1 のとおりオーケストレーターが直接行う）
- **fixer の機械的な安全境界**: 既存 `/forge:review` が fixer Agent に課している安全境界（1 起動 1 所見の限定・修正可能ファイルの allowlist・所見と無関係なリファクタリングの禁止・修正後の構文検証）を設けない。これらは隔離コンテキストで動く別 Agent への安全装置であり、修正がメイン会話上で利用者の目に見える v1 の構成では前提が異なる（比較実験としての理由は §2.3）
- **Codex セッションの自動起動・管理**: Codex セッションは人間が手動起動して常駐させる（msg-sys の前提と同一）
- **msg-sys 既存実装の変更**: 本 SKILL は msg-sys の CLI を利用者として呼び出すのみで、既存ファイル・既存テストを変更しない。ただし msg-sys 側に責務が属する機能（例: セットアップ自己診断）が必要になった場合は、msg-review 側で msg-sys の内部規則を再実装せず、相当の理由を示しユーザー承認を得たうえで msg-sys 側の改訂（新規 CLI 追加等）として実施する

### 2.3 v1 の位置づけ（意図的な判断）

v1 は「ガードレールなしの最小構成で1つのお題を最後まで走らせ、既存の evaluator/fixer ありのパイプラインと比較して逸脱がどの程度生じるかを評価する」ための実験実装として位置づける。evaluator/fixer 相当の安全境界を後から追加するかどうかは、この比較評価の結果を踏まえて別途判断する（§5 TBD-004）。

evaluator/fixer が担っていた**機能**（所見の妥当性評価・要修正判断・修正の実施）が無くなるわけではなく、オーケストレーターがこれらを直接担う（FNC-004）。v1 で省くのは機能ではなく、隔離コンテキストと機械的制約（§2.2）による**強制**である。

## 3. 機能要件

### FNC-001: レビュー依頼の定型起動 [MANDATORY]

利用者は SKILL `/forge:review` を起動することで、レビュー対象を指定して Codex へのレビュー依頼を開始できること。

- 対象指定: 以下のいずれかを選べること
  - 現ブランチの未 commit 差分
  - 現ブランチの全変更（base ブランチから分岐して以降の差分全体。commit 済みを含む）
  - 明示指定したファイル群
- 依頼の開始にあたり、利用者がメッセージ本文を手で組み立てる必要がないこと

### FNC-006: `/forge:review` とのコマンド互換性 [MANDATORY]

`/forge:review` の代替（rename による差し替え、またはバックエンドとしての統合。§1.2）を妨げないよう、コマンド構文を `/forge:review` と互換にすること。

- レビュー種別は `/forge:review` と同じ位置引数（`code` / `design` / `requirement` / `plan` / `uxui` / `generic`）で受け取る
- 対象軸は `--diff`（既定）/ `--files` を同じ意味で受理する。現ブランチの全変更（FNC-001）は追加フラグとして提供する（フラグ名は設計で確定）
- 介入軸 `--auto-critical` / `--auto` は所見の重大度（🔴/🟡/🟢）に応じた自動修正範囲を実際に区別する（DES-046）。`--interactive`（既定）本来の段階的提示（所見を 1 件ずつ提示して人間の判断を仰ぐ）は実装しない（当時存在した `/forge:present-findings` への委譲を検討したが、session_dir 前提のレビューパイプラインに強く結合しており、v1 スコープ外の evaluator/fixer 統合を伴わずには再利用できなかった。同スキルはその後パイプラインごと削除済み。DES-046 §2）。**暫定運用（ユーザー指示・ユーザー責任 [2026-07-19]）**: 本来の段階的提示の実装を次回以降に持ち越す間、この仕組みを早期に多くのプロジェクトで実運用し問題を洗い出すため、`--interactive`・介入軸未指定時は内部的に `--auto` と同じ振り分けを暫定的に適用する（DES-046 §1）。本来の段階的提示に着手する際はこの暫定エイリアスを解除する
- v1 が対応しない軸（エンジン軸 `--codex` / `--claude`）のフラグが与えられた場合は、**警告を表示したうえで当該フラグを無視し、既定動作で続行する**（黙殺はしない）。エラー終了にすると、`/forge:review` を発行する既存の呼び出し元（他 SKILL のレビュー工程等）が差し替え後に動作しなくなるため
- **呼び出し元から見た完了挙動の互換性**: `/forge:review` を発行する既存の呼び出し元（`/forge:start-implement` Phase 5 等）は、レビュー結果を受け取ってから次工程に進む前提で書かれている。本 SKILL を rename で差し替えても同じ前提が崩れないよう、依頼を送信したターンの中で Codex の返信を待ち、結果（承認 or 所見）を得てから完了報告する（設計は DES-045 §3.7 に委ねる）。待機してもなお完了しない場合は、`/forge:review` のレビューエンジン呼び出しが失敗・ハングした場合と同じ扱いとし、**そのターン内で明確にタイムアウト（失敗）として報告し、呼び出し元に確定した結果を返す**。結果を保留したまま非同期往復に委ねて次工程へ進めることはしない

### FNC-002: レビュー依頼内容の自己完結性 [MANDATORY]

Codex へ送るレビュー依頼には、Codex が追加の指示を人間に求めることなくレビューを開始・返信できるだけの情報が含まれていること。少なくとも以下を含む。

- レビュー対象の特定情報（対象ファイルの所在、または差分の取得方法）
- 依頼するレビューの観点・粒度
- レビューで参照すべきルール・基準文書への到達手段（Codex の実行環境で実際に解決できるファイルパス）。設計文書と異なり forge 内蔵のルール文書は受信側からの自力発見が困難なため、依頼側が明示的にパスを渡す。forge は plugin として配布されるため、渡すパスの実体（リポジトリ内原本か plugin キャッシュ配下か）の選定を含めて設計で確定する（§5 TBD-002）
- 所見の返信に期待する形式（重大度区分を含む）

返信操作そのものの案内（返信ヒント）は msg-sys の配信機構（msg-sys:REQ-006 FNC-003/FNC-004）が担うため、本要件では扱わない。

### FNC-003: 前提条件の事前検査 [MANDATORY]

レビュー依頼の送信前に、往復が成立するための前提を検査し、不成立の場合は依頼を送信せず利用者に不足を報告すること。少なくとも以下を検査する。

- メッセージ DB への到達性（msg-sys の DB パス解決が成立すること）
- 受信側（Codex）の新着検知が機能する状態にあるか、確認できる範囲での検査（検査可能な範囲は設計に委ねる）

### FNC-004: 所見の受領・修正・再依頼の往復 [MANDATORY]

Codex から返る所見に対して、以下の往復を人間の仲介なしに継続できること。

- 所見の評価（妥当性判断）・要修正判断・修正の実施・再レビュー依頼を、いずれも Claude（オーケストレーター）が直接行う。専用の evaluator/fixer Agent は起動しない（v1 限定。§2.3）
- 修正結果を、同一の返信チェーン上の返信として Codex に報告し、再レビューを依頼する
- 採用しない所見については、その理由を返信に含める

### FNC-005: レビュー完了の判定と報告 [MANDATORY]

以下のいずれかでレビューを完了とし、人間に結果を要約報告すること。

- Codex が指摘なし（承認）を表明した場合
- 往復回数が msg-sys の継続対話停止条件（msg-sys:REQ-006 FNC-002）に到達した場合（この場合は未解決の所見を明示して人間の判断を仰ぐ）
- 介入軸（`--auto-critical`/`--auto`、DES-046）指定時、**または `--interactive`・介入軸未指定時（DES-046 §1「暫定運用」により内部的に `--auto` へエイリアスされる。ユーザー指示・ユーザー責任 [2026-07-19]）**、Codex が指摘あり（`findings`）と判定し続けているが、現在のモードの自動修正範囲に該当する所見がもう残っていない場合（対象外所見のみが残っている場合）。この完了は Codex の承認とは異なる状態であり、要約報告では**承認された場合と混同しない形**で、Codex がなお指摘ありと判定していること・対象外とした所見の一覧と理由を明記し、人間の判断を仰ぐこと

要約報告には、指摘の件数・対応した修正の概要・不採用とした所見とその理由を含めること。

### BL-001: 往復の監査可能性

レビューの往復内容は msg-sys の履歴（msg-sys:REQ-006 INT-001）でそのまま監査できること。本 SKILL はこれと重複する独自の永続記録を持たないこと。

複数のレビューが時間的に離れて行われた場合でも、往復履歴・要約報告・再開時の未解決所見集計（FNC-005）が対象レビューの往復のみを扱い、他のレビューの往復と混同しないこと（設計は DES-045 §3.4 に委ねる）。

## 4. 非機能要件

### NFR-001: msg-sys 既存実装の不変更と改訂経路 [MANDATORY]

本 SKILL の導入によって msg-sys の既存実装・既存テストに変更が生じないこと。msg-sys の CLI（`send.py` / `inbox.py` 等）を公開インターフェースとして利用する。

msg-sys 側への機能追加が必要な場合（msg-sys 自身の責務に属する機能を本 feature が必要とする場合）は、本 feature 側で msg-sys の内部規則（DB パス導出等）を再実装せず、相当の理由とユーザー承認のもと msg-sys 側仕様（msg-sys:REQ-006 / msg-sys:DES-034）の改訂として行うこと。

### NFR-002: 標準ライブラリのみでの実装 [MANDATORY]

`docs/rules/implementation_guidelines.md` に従い、本 SKILL に付随する Python スクリプトは標準ライブラリのみを使用する。

### NFR-003: 性能・可用性・セキュリティ・運用性の適用範囲

msg-sys:REQ-006 NFR-003 と同一の位置づけ（本番運用・外部公開を前提としない実験段階の内部ツール）を引き継ぐ。通信路のレイテンシ・可用性・データ保護は msg-sys 側の定めに従い、本 SKILL 独自の追加要求は設けない。
