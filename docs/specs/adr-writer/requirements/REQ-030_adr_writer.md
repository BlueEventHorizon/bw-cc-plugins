# REQ-030 ADR ライター 要件定義書

## 1. 概要

ADR（アーキテクチャ決定記録）を、設計の途中経過から切り離して判断し、記載する主体（ADR ライター）の振る舞いを定める。

ADR を正しく書くには、作るかどうかの判定、仕様・ルールの本文を写さないこと、棄却理由が依拠する前提の明記など、設計とは別の視点の判断を一度に多数下す必要がある。設計を進めている AI はこれらを正しく判断できず、ADR の規範・書式・採番手順が設計の context を占有する。ADR ライターは、渡された内容を吟味し、ADR に値しなければ棄却し、値するが形が不十分なら直して記載する。

対象は、ADR を作る・更新する必要が生じた開発者（人・AI）である。

### 1.1 対象システムの性質

forge プラグイン内部の文書運用であり、外部公開・本番運用・個人情報の保持を伴わない開発支援ツール相当のスコープである（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

## 2. 前提条件

- ADR が何であり、どんなときに作るかは、規範文書が定める（[adr_principles_spec.md](../../../../plugins/forge/docs/adr_principles_spec.md)）
- 文書の配置は `.doc_structure.yaml` が宣言する（[REQ-028 文書体系 要件定義書](../../forge/requirements/REQ-028_document_system.md)）
- 新規の文書 ID は採番スキルで決める。手動で決めない（同 FNC-003）

## 3. 用語

| 用語         | 定義                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| ADR ライター | ADR の吟味と記載を、呼び出し元の context から切り離して担う主体                                              |
| ADR ファイル | 1 つの feature の ADR を、すべて書くファイル。feature ごとに 1 つだけ存在する                                |
| 決定の節     | ADR ファイルの中で、1 つの決定を書く節。節番号で指す                                                         |
| 依頼         | ADR にしたい内容を ADR ライターへ渡すこと                                                                    |
| 類型         | 依頼の種別。承認記録・判断記録・更新の 3 つ                                                                  |
| 承認記録     | 要件定義書に無い設計を、利用者の承認のもとで採った場合の、承認の記録。規範が ADR への記録を義務づける        |
| 判断記録     | 呼び出し元の判断で渡す、義務の無い決定。優れた方式がありそうなのに採らなかった決定の、採らなかった理由を残す |
| 更新         | 既存の決定の、撤回・転換・訂正。決定が否決されたことを含む                                                   |
| 判定         | 依頼に対する結果。作成・棄却・不足の 3 値                                                                    |

## 4. 機能要件

### FNC-001: 依頼の受付

ADR ライターは、類型を持つ依頼を受け付けること。依頼には ADR にしたい内容（決定・文脈・検討した代替案と棄却理由・関連する文書）を含めること。

- 承認記録には、要件へ戻せない理由と、利用者の承認の引用（発言そのまま）を含めること
- 更新には、対象の決定の節と、変更の内容と理由を含めること

理由: 類型により、検査の観点が異なる。承認の事実は仕様にもコードにも現れないため、逐語の引用が無ければ、記録が成立したかを検査できない。

### FNC-002: 吟味と棄却

判断記録について、次のいずれかに当たる場合、ADR ライターは ADR に書かず棄却し、理由を返すこと。

- 決定に至っていない（提案・未承認・未確認）
- 選んだ方式が誰が見ても正しい。棄却した代替案が、説明されなくても明白に劣り、優れた方式がありそうに見えない
- コード・ルール・仕様を見れば理由が分かる、選択肢が無かった、一般論で答えられる、一度きりの事故である
- 作業の経緯や文書整理の記録である
- ADR に書くほどでない小さな理由である。この場合は、理由を参照元の文書へ書くよう返す

理由: ADR を足すことは、「検討済みか」を引く読み手の負担を増やす。誰が見ても正しい方式の理由は、読み手の得が無く、読む context を消費するだけである。

### FNC-003: 修正して記載

吟味を通った内容が、ADR として形が不十分な場合、ADR ライターは直して記載すること。直す内容は次のとおり。

- 経緯・実装状況・後続作業・日付入りの訂正を、本文から除く
- 仕様・ルールの本文を写さず、決定の要旨・理由・参照に絞る
- 棄却理由を、「なぜ優れていそうに見える案を採らなかったか」に絞り、将来の別案が使う語彙で書く。実装の語彙を除く
- 1 つの決定の節で完結させ、他の決定の節を前提にしない

理由: 渡す側は ADR の書き方の規範を持たない前提で、書き手が形を保証する。

### FNC-004: 情報が足りないときの扱い

棄却理由が依拠する前提など、ADR に書くべき情報が渡された内容から分からない場合、ADR ライターは補って書かず、何が足りないかを返すこと。呼び出し元は、足りない情報を補って再び依頼できること。

理由: ADR ライターは決定者ではない。理由や前提を補うと、作り話になる。

### FNC-005: 承認記録の扱い

承認記録は、ADR ライターが棄却しないこと。「ADR に値するか」ではなく、「義務の記録が成立しているか」で検査する。要件へ戻せない理由、または利用者の承認の引用が欠けている場合は、不足として返すこと。

理由: 記録の無い承認は、承認として扱われない。棄却すると、設計を進められない。

### FNC-006: 既存の決定の更新

ADR ライターは、既存の決定の更新を扱うこと。決定が否決された（撤回・転換・訂正された）ときは、同じ決定の節を書き直し、否決された内容を、新しい決定の中へ取り込む。

- 「決定」を、新しい決定に書き直す
- 旧い案は、同じ節の「検討した代替案」へ移し、否決の理由を添える。理由が誤りだった場合は、誤りだった旨と正しい理由を書く。前提が変わっただけの場合は、当時は妥当だったことと、変わった前提を書く
- 旧い決定の本文と、誤っていた理由は残さない
- 別の ADR を作らない。ADR ファイルを分けない。「失効」の印を付けない
- 決定の節の番号は変えない

更新が成立したときの判定は「作成」である。

理由: 否決された決定は、論理や理由に誤りがあったことが多い。誤りを残しても、読み手は間違った理由を読むだけである。ADR を可変にしてあるのは、書き損じを書き直して正すためである。旧い案が将来また提案されうる場合は、正しい理由とともに代替案へ残すことで、その提案への答えになる。

### FNC-007: 判定の返却

ADR ライターは、判定（作成・棄却・不足）を、呼び出し元へ返すこと。

- 「作成」には、何も添えない。ADR ライターは独立した書き手であり、できたことで足りる。記載先は、feature の ADR ファイルであり、呼び出し元が出力先から知っている
- 「棄却」と「不足」には、理由を添えること
- 呼び出し元は、判定の値で分岐でき、文章の読み違いに依存しないこと
- 棄却と不足は、依頼された操作が完了した結果であり、エラーではない
- ADR ライターが最後まで終えられなかった場合は、判定を返さず、呼び出し元がそれを異常として知ること

理由: 返す情報があるのは、呼び出し元が次の手を取るために理由を要する、棄却と不足だけである。判定を読み違えると、承認記録が無いまま設計が進む。

### FNC-008: 出力先と ADR ファイル

ADR は、feature ごとの `adr/` ディレクトリに置くこと。同じ feature の ADR は、すべて 1 つの ADR ファイルに書き、決定ごとにファイルを分けないこと。

- `.doc_structure.yaml` が、文書種別 `adr`（`docs/specs/**/adr/`）を宣言する
- ファイル名は `ADR-{NNN}_{feature}.md` とする。ファイルを最初に作るときに、採番スキルで番号を 1 回だけ決め、以後は変えない
- 新しい ADR ファイルを作るのは、その feature に ADR ファイルがまだ無いときだけである。ある場合は、そのファイルへ書く
- ファイルの中の各決定は、節番号で指せる。節番号は変えない
- 複数のコンポーネントに跨る決定は、feature に `common` を指定して置く
- どの経路から依頼されても、出力先は一意に決まる
- 文書種別の宣言が無いプロジェクトでは、置き場を導出・発明せず、宣言を促す

理由: 同じ feature の決定を 1 つのファイルに集めれば、読み手が「検討済みか」を引くとき、開くファイルが 1 つで済む。ファイル名に番号があれば、ファイル名で指定でき、検索もできる。

### FNC-009: 書き込みの範囲

ADR ライターが書き込めるのは、ADR ファイルだけとすること。他の文書・コードを書き換えないこと。

理由: 吟味のために仕様・ルール・コードを読むため、書き込みの権限が広いと、読んだ場で直してしまう。

### FNC-010: 起動経路

利用者が直接起動できる入口を 1 つ持つこと。他の SKILL（`start-design` など）も、同じ入口を通すこと。入口は、依頼の組み立てと、完了処理（索引の更新・レビュー・commit の確認）を担う。呼び出し元が完了処理を担う場合は、入口は完了処理を行わない。

ADR ライター自身は、利用者に質問しないこと。情報が足りないときは、不足として返し、質問と再依頼は呼び出し元が行う。

理由: 呼び出し元が複数あっても、依頼の形と完了処理を 1 か所に保つ。隔離した context では、利用者との対話が成り立たない。

### FNC-011: 設計フローが ADR の規範を抱えない

`start-design` は、ADR の書式・規範文書を読み込まず、ADR の採番・作成の手順を持たないこと。要件定義書に無い設計を承認のもとで採ったときは、承認記録を依頼すること。

理由: 作らない場合が大半の ADR の規範・書式・採番手順が、設計の context を常に占有する。

### FNC-012: 規範の一元化

ADR の定義の核・吟味の基準・書式・配置は、規範文書に 1 か所で定め、ADR に言及する他の文書は、そこを指すこと。読み手向けの義務（ADR を根拠に判断するときの、前提の確認と、ADR の番号（ファイル番号と節番号）の併記）は、書き手向けの規範とは別の文書に定めること。

理由: 規範の本文が 2 か所にあると、片方だけが古くなる。書き手向けの規範を、ADR を書かない作業が読む必要はない。

## 5. 非機能要件

### NFR-001: 隔離

ADR の判断は、呼び出し元の設計の途中経過から隔離した context で行うこと。呼び出し元の context に、ADR の規範・書式・採番手順が常駐しないこと。

### NFR-002: 失敗の可視化

ADR ライターが最後まで終えられなかった場合に、成功として扱われないこと。
